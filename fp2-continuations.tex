Since the early 1960s, continuations have appeared in the literature multiple times in various forms and diverse applications~\cite{reynolds1993discoveries, landin1997histories}, until in the 1970s Wadsworth coined a general term and a unified concept --- \vocab{continuation}\footnote{\url{https://en.wikipedia.org/wiki/Continuation}} --- ``the meaning of the rest of the program''.

The initial impetus for these reflections was the Algol 60 language, which had a non-trivial mechanism of labels and jumps.
The problem was both the implementation of the semantics and its denotational description together with translation into lambda calculus.
Indeed, how does one mathematically describe \texttt{goto}?
In which domain should one seek the semantics of such programs?
How does one write a definitional interpreter mapping a program into this domain?
The solution turned out to be the ability to refer to the semantics of the remainder of the program, the continuation, at a given point (for example, at a label).

The language designer must always think about continuations, since the evaluator at each point of a program needs to know what to execute next.
And as we have already understood, every programmer is the author of many languages that bring them closer to solving their problem.
Moreover, many everyday language constructs explicitly or implicitly directly manipulate continuations.

\subsection{The concept of continuations}

Let us consider the semantics of an expression from the operational point of view, as a sequence of rewriting steps (see\ \ref{subsubsec:semantics}).
If we carefully examine each step, we discover that it consists of two stages: finding a subexpression (redex) in which an elementary computation step can be performed, executing that step, and so on\footnote{In fact, computing with continuations is taught in elementary school, when students learn to evaluate expressions ``step by step.''}.
During the search for a redex, the expression is split into two parts (see~\ref{fig:basic-continuation}):
\begin{itemize}
    \item The focus --- the subexpression in which we search for a redex;
    \item The continuation --- the remainder of the expression with a ``hole,'' indicating the place where the result of the computation step should be plugged in.
\end{itemize}

\begin{figure}
    \centering
    \includegraphics[width=0.35\textwidth]{figs/cont-expr}
    \caption{The expression is split into a focus (red) and a continuation (blue); when a step is performed in the focus, they are combined into a new expression, and the process repeats.}
    \label{fig:basic-continuation}
\end{figure}

As a rule, continuations exist outside user code as the state of the interpreter, which at each successive moment in time needs to remember what code to execute next and in what state.
However, languages provide users with many constructs that allow controlling continuations (see\ \ref{fig:exit-exceptions}):
\begin{itemize}
    \item The function \mintinline{kotlin}|exit| discards the entire program continuation;
    \item The construct \mintinline{kotlin}|try-catch| allows discarding part of the continuation up to the exception handler and executing the remainder;
    \item The construct \mintinline{kotlin}|return| allows resuming execution at the point where the function was called;
    \item The constructs \mintinline{kotlin}|break| and \mintinline{kotlin}|continue| restore the continuation after and before the loop, respectively\ldots
\end{itemize}

\subsubsection{Reduction semantics}

The style of specifying operational semantics through the description of searching for primitive (``\vocab{head}'') redexes and their reductions is called \vocab{reduction semantics (reduction context semantics)}\footnote{\url{https://en.wikipedia.org/wiki/Operational_semantics}}.
As usual, following Hutton's Razor, let us consider the interpretation of a small simple language with subtraction (an asymmetric operation for testing the implementation):
\begin{minted}{haskell}
    data Expr = Const Int | Diff Expr Expr
\end{minted}

First, we need to define the syntax of continuations, ``expressions with a hole.''
That is, from a technical standpoint, a continuation is a data structure containing all the information necessary to continue execution (here --- only the remainder of the expression):
\begin{minted}{haskell}
    data K
      = Hole         -- hole ?$\boxempty$?
      | LDiff K Expr -- focus went into the left subexpression, remembered the right
      | RDiff Int K  -- computed the left, focus went right
\end{minted}

Let us define the operation of splitting an expression into a focus and a continuation:
\begin{minted}{haskell}
    split :: Expr -> (Expr, K)
    split e = case e of
      Const _ -> (e, Hole)
      Diff (Const _) (Const _) -> (e, Hole) -- primitive redex
      Diff (Const l) r ->                   -- left subexpression already computed
        let (focus, k) = split r in         -- search for redex in the right
        (focus, RDiff l k)
      Diff l r ->                           -- nothing computed yet
        let (focus, k) = split l in         -- start by searching for redex on the left
        (focus, LDiff k r)

    ghci> split (Diff (Diff (Const 1) (Const 2)) (Const 3)) -- (1 - 2) - 3
    (Diff (Const 1) (Const 2), LDiff Hole (Const 3)) -- (1 - 2, ?$\boxempty$? - 3)
\end{minted}

The primitive reduction step only knows how to subtract numbers:
\begin{minted}{haskell}
    headReduction :: Expr -> Expr
    headReduction = \case
      Diff (Const l) (Const r) -> Const (l - r)
      e -> e
\end{minted}

After a primitive reduction step, we need to plug the result back into the continuation, so that from an ``expression with a hole'' we obtain a full expression that can be further reduced:
\begin{minted}{haskell}
    plugIn :: Expr -> K -> Expr
    plugIn e k = case k of
      Hole -> e
      LDiff k' r -> Diff (e `plugIn` k') r
      RDiff l k' -> Diff (Const l) (e `plugIn` k')
\end{minted}
As a rule, plugging a term $t$ into a continuation $E$ is denoted as $E[t]$.

Now we can define a full step:
\begin{minted}{haskell}
    transition :: Expr -> Expr
    transition e =
      let (focus, k) = split e in    -- split into focus and context
      headReduction focus `plugIn` k -- perform computation in the focus and plug in
\end{minted}

Then the operational semantics is the unfolding of the list of intermediate expressions:
\begin{minted}{haskell}
    eval :: Expr -> [Expr]
    eval = List.unfoldr \prev ->
      let next = transition prev in
      if prev == next then Nothing else Just (next, next)
\end{minted}

One can notice that \texttt{split} and \texttt{plugIn} are uniquely determined by the syntax of continuations and the form of head reductions, while \texttt{transition} and \texttt{eval} are the same for any language.
Therefore, reduction semantics is usually specified as the syntax of continuations, a list of head reductions, and a single inference rule --- a step in context:\footnote{$\ominus$ here denotes syntactic minus (a node in the tree).}
%! suppress = EscapeAmpersand
\[
    \begin{array}{lrl}
        \text{Values}             & v & \Coloneqq \mathbb{Z}                                       \\
        \text{Terms}              & t & \Coloneqq v ~|~ t \ominus t                                \\
        \text{Evaluation context} & E & \Coloneqq \square ~|~ E \ominus t ~|~ \mathbb{Z} \ominus E \\
        \text{(diff)}             &   & v_1 \ominus v_2 \longrightarrow v_1 - v_2                  \\
        \text{step}               &   & \infer{E[t] \longrightarrow E[t']}{t \longrightarrow t'}
    \end{array}
\]

There exists a standard tool PLT Redex\footnote{\url{https://redex.racket-lang.org/}} for describing and testing semantics in the reduction context style.

\subsubsection{Continuation semantics} \label{subsubsec:continuation-semantics}

Let us write the denotational semantics of our language:
\begin{minted}{haskell}
    evalDirect :: Expr -> Int
    evalDirect = \case
      Const n -> n
      Diff l r -> evalDirect l - evalDirect r
\end{minted}

Let us rewrite the denotational semantics in a style with explicit continuations.
But first, let us work with the type \mintinline{haskell}{K} and simplify handling it:
\begin{minted}{haskell}
    data K = Hole | LDiff K Expr | RDiff Int K
    -- ?$K = 1 + (K \times Expr) + (Int \times K) = 1 + (Expr + Int) \times K$?
    data Frame = LDiff Expr | RDiff Int
    type K = [Frame]
\end{minted}
We have obtained a representation of the continuation as a stack of frames.

We will write the denotational semantics for the domain \mintinline{haskell}{K -> Int}.
Such a variant of denotational semantics with an explicit representation of the meaning of the rest of the program (in the form of \mintinline{haskell}{K}) is sometimes called \vocab{continuation semantics}.
And the corresponding programming style with passing continuations is called \vocab{continuation passing style (CPS)}.

In our case, the continuation semantics will look like a pair of mutually recursive functions:
\begin{minted}{haskell}
    evalK :: Expr -> K -> Int
    evalK e k = case e of
      Const n -> k `appK` n             -- execute the rest of the program
      Diff l r -> evalK l (LDiff r : k) -- remember to compute the right next

    appK :: K -> Int -> Int
    appK k result = case k of
      [] -> result                                -- nothing more to do
      LDiff r : k' -> evalK r (RDiff result : k') -- go compute the right
      RDiff l' : k' -> k' `appK` (l' - result)    -- continue on the result
\end{minted}
Here we again descend through the expression searching for a primitive redex (here --- a constant), while remembering what needs to be done afterwards.

The first recursive implementation \texttt{evalDirect} did not worry about continuations.
However, continuations are an integral part of the computation process: the evaluator needs to know what to do next at every moment.
In fact, \texttt{evalDirect} merely delegates the management of the object language's continuations to the meta-language, but how?
Notice that the resulting implementation \texttt{evalK} is tail-recursive, meaning it can be compiled into a loop that does not consume the call stack, while \mintinline{haskell}{K} is the stack.
Thus, in the first case we made recursive calls and the continuation was allocated on the (hardware) stack of the meta-language, while in the second case we manually allocate the stack on the heap.

In the case where the meta-language's stack is implemented on top of the hardware stack, there is a risk of a stack overflow error.
To avoid this, the \vocab{trampolining} technique is used, which consists precisely in manually allocating the continuation on the heap~\cite{ganz1999trampolined, bjarnarson2012stackless}.

Just as the type of a zipper's context can be computed as the derivative of the algebraic representation of the corresponding type~\cite{huet1997zipper, mcbride2001derivative, abbott2003derivatives}, one can compute the type of a fold's continuation~\cite{mcbride2008clowns}.

\subsubsection{First-class continuations} \label{subsubsec:first-class-cont}

In the examples above, language constructs manage continuations implicitly (see\ Fig.\ \ref{fig:exit-exceptions}).
However, sometimes operators are introduced that allow explicitly manipulating continuations.
With their help one can implement both control flow manipulation capabilities such as generators and coroutines\footnote{\url{https://en.wikibooks.org/wiki/Haskell/Continuation_passing_style\#Example:_coroutines}}\footnote{\url{https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.coroutines/suspend-coroutine.html}}, as well as all other effects such as state (see~\ref{sec:effects}).

\vocab{First-class continuations} are continuations that can be represented as values in the program.
Given that a continuation has a vacant slot for a not-yet-computed subexpression, first-class continuations are represented as first-class functions.

To obtain a first-class continuation in code, one needs to either write the code in CPS, or use a built-in language operator, of which a great many have been invented~\cite[appendix A]{hillerstrom2022foundations}.
For example, $J$, \texttt{escape}~\cite{reynolds1972definitional}, \texttt{call/cc}\ldots

As an example, let us implement in our language an operation \texttt{Cont} that allows capturing the current continuation.
It will take a user function and pass to it the current continuation from itself to the end of the program:
\[
    E[cont\ap f] \longrightarrow f\ap (\lambda x\ldotp E[x])
\]

First, let us extend the language with lambda calculus:
\begin{minted}{haskell}
    data Expr
      = Const Int | Diff Expr Expr
      | Var String | Lam String Expr | App Expr Expr

    data Frame
      = LDiff Expr | RDiff Value
      | LApp Expr | RApp Value
      | SetEnv Env -- after executing a closure, restore the current environment
\end{minted}

The interpreter implementation is fairly straightforward.
The only thing is that the remainder of the program is now represented as a linear list that is effectively traversed sequentially in a loop.
We must not forget to restore the original environment after executing a closure body for the continuation to proceed:\footnote{For convenience, we will pass the environment as an implicit parameter.}
\begin{minted}[escapeinside=##]{haskell}
    evalK :: (?env :: Env) => Expr -> K -> Value
    evalK e k = case e of
      Const n -> k `appK` Number n
      Diff l r -> evalK l (LDiff r : k)
      Var name -> k `appK` (?env ! name)
      Lam name body -> k `appK` Closure name ?env body
      App f arg -> evalK f (LApp arg : k)

    appK :: (?env :: Env) => K -> Value -> Value
    appK k result = case k of
      [] -> result
      LDiff r : k' -> evalK r (RDiff result : k')
      RDiff l' : k' -> k' `appK` Number (unwrapNumber l' - unwrapNumber result)
      LApp arg : k' -> evalK arg (RApp result : k')
      RApp f : k' -> case f of
        Closure name env body ->
          let currEnv = ?env in
          let ?env = Map.insert name result env in
          evalK body (SetEnv currEnv : k')
        K env k'' ->
          let currEnv = ?env in
          let ?env = env in
          (k'' ++ SetEnv currEnv : k') `appK` result
        other -> error $ "Expected callable, got " <> show other
      SetEnv env : k' -> let ?env = env in k' `appK` result
      where
        unwrapNumber = \case
          Number n -> n
          other -> error $ "Expected number, got " <> show other
\end{minted}

Finally, let us implement the \texttt{cont} operator:
\begin{minted}[escapeinside=##]{haskell}
    data Expr = ... | Cont Expr
    data Frame = ... | ContFrame

    evalK e k = case e of
       ...
       Cont f -> evalK f (ContFrame : k)

    appK k result = case k of
       ...
       ContFrame : k' -> [RApp result] `appK` K ?env k' -- reuse the RApp branch
\end{minted}

Let us consider several examples (denoting \mintinline{haskell}{contLam name body = Cont (Lam name body)}, \mintinline{haskell}{(-.) = Diff}, \mintinline{haskell}{c = Const}, \mintinline{haskell}{v = Var} and \mintinline{haskell}{(@) = App}):
\begin{itemize}
    \item \mintinline{haskell}{c 10 -. contLam "k" (c 1)} --- discard the continuation and return 1 ($k = 10 - \boxempty$);
    \item \mintinline{haskell}{c 10 -. contLam "k" (v "k" @ c 1)} --- $\step k\ap 1 \step 10 - 1 \step 9$;
    \item \mintinline{haskell}{c 10 -. contLam "k" (v "k" @ c 1 -. c 2)} --- $\step k \ap 1 - 2 \step 9 - 2 \step 7$;
    \item \mintinline{haskell}{c 10 -. contLam "k" (v "k" @ c 1 -. v "k" @ c 2)} --- $\step k \ap 1 - k \ap 2 \step 9 - 8 \step 1$.
\end{itemize}

Thus, we have obtained a language that allows the user to obtain the current continuation as a function at any point in the program.

The ability to obtain first-class continuations is almost never provided by industrial languages, as it is a rather dangerous tool.
Indeed, if the user does not invoke the continuation, resources may not be released.
If they invoke it multiple times, there may again be incorrect resource handling or corruption of mutable memory (continuations that can be safely invoked multiple times are called \vocab{multi-shot}).
Such behaviors can be excluded by special handling of these situations~\cite{muhcu2025multiple}, compile-time checks (e.g., using linear types) or runtime checks.
Currently, with active research on integrating effect handlers (see~\ref{sec:effects}), first-class continuations may get a new chance.

\subsection{Continuations by hand} \label{subsec:functional-cps}

Let us consider what CPS looks like in ordinary code, rather than in the context of deep embedding.
For this, we will first switch to shallow embedding and directly construct elements of the target domain.
Second, we will refunctionalize the continuations \mintinline{haskell}{K} and generalize: instead of \mintinline{haskell}{K -> Int} we will use \mintinline{haskell}{forall r . (a -> r) -> r}, where \texttt{a -> r} is the functional representation of the continuation.

Such CPS exploits the following isomorphism:
\begin{minted}{haskell}
    to :: a -> (forall r . (a -> r) -> r)
    to x k = k x

    from :: (forall r . (a -> r) -> r) -> a
    from comp = comp id
\end{minted}
In other words, instead of providing a value of type \texttt{a}, one can ask the caller how they intend to use this value \texttt{a -> r}, do it oneself, and return \texttt{r} to the caller.

Practitioners know this isomorphism through the technique of using callbacks.
Theoreticians know that it is a special case of the Yoneda lemma~\cite{hinze2010reason}.
Compare CPS with the instance of this lemma in preorder theory (above we took \texttt{a = Unit; b = a}):
\begin{gather*}
    a\to b \iso \forall r\ldotp (b\to r)\to (a\to r) \\
    a \le b \iff \forall r\ldotp (b \le r) \Rightarrow (a \le r)
\end{gather*}

For example, we can rewrite factorial in CPS.
Note that the code has access to a first-class continuation (however, it does not yet use it in any non-trivial way), and is again tail-recursive.
\begin{minted}{haskell}
    facCps :: Int -> (forall r . (Int -> r) -> r)
    facCps n k
      | n <= 1 = k 1
      | otherwise = facCps (n - 1) \res -> k (n * res)

    facCps 3 id ?$\step$? facCps 2 \res -> id (3 * res)
    ?$\step$? facCps 1 \res -> id (3 * (2 * res)) ?$\step$? id (3 * (2 * 1)) ?$\step$? 6
\end{minted}

\subsubsection{Defunctionalization and accumulators} \label{subsubsec:defunctionalization-cont}

Let us defunctionalize the continuations in \texttt{facCps}.
We use two higher-order functions, \texttt{id} and \mintinline{haskell}{\res -> k (n * res)}, which give us two constructors:
\begin{minted}{haskell}
    data K = Id | Times Int K
    -- ?$\iso$?
    type K = [Int]

    runK :: K -> Int
    runK = product

    facCps :: Int -> K -> Int
    facCps n k
      | n <= 1 = runK k
      | otherwise = facCps (n - 1) (snoc k n)

    facCps 3 [] ?$\step$? facCps 2 [3] ?$\step$? facCps 1 [3, 2] ?$\step$? runK [3, 2] ?$\step$? 3 * (2 * 1)
\end{minted}

We have again obtained the representation of the continuation as a stack of frames.
This means that the interpreter \texttt{evalK} we obtained earlier (\ref{subsubsec:continuation-semantics}) is a CPS version of a regular interpreter, but with defunctionalized continuations (which are convenient for debugging --- they can be printed, unlike Haskell functions).
If we extend our earlier language and write factorial in it, then perform fusion or refunctionalization (\ref{subsubsec:deforestation-fusion}) of the program tree and the continuation tree, we obtain the current factorial implementation.
And in general, correspondences can be established between various styles of semantics implementations (see\ Fig.\ \ref{fig:semantics-diagram}).

We obtain the familiar factorial implementation with an accumulator:
\begin{minted}{haskell}
    facAcc :: Int -> Int -> Int
    facAcc n acc
      | n <= 1 = acc
      | otherwise = facAcc (n - 1) (acc * n)

    facAcc 3 1 ?$\step$? facAcc 2 (1 * 3) ?$\step$? facAcc 1 ((1 * 3) * 2) ?$\step$? (1 * 3) * 2 ?$\step$? 6
\end{minted}

\subsubsection{\mintinline{haskell}{Monad Cont}} \label{subsubsec:monad-cont}

Due to CPS, the code has lost its familiar structure where functions directly return their results (i.e.\ \vocab{direct style}).
With a large number of calls to transformed functions, the code becomes hard to read (a problem known as \vocab{callback hell}):
\begin{minted}{haskell}
    fibCps :: Int -> (forall r . (Int -> r) -> r)
    fibCps n k = if n <= 2 then k 1 else
      fibCps (n - 1) \res1 ->
      fibCps (n - 2) \res2 ->
      k (res1 + res2)
\end{minted}

The domain \mintinline{haskell}{(a -> r) -> r} can be made into a monad, restoring direct-style code inside \mintinline{haskell}{do}-notation.
Let us introduce a \mintinline{haskell}|newtype| wrapper for declaring instances:
\begin{minted}{haskell}
    newtype Cont r a = Cont { runCont :: (a -> r) -> r }
\end{minted}

The functor adds post-processing to the result before passing it to the continuation:
\begin{minted}{haskell}
    instance Functor (Cont r) where
      -- fmap :: (a -> b) -> ((a -> r) -> r) -> ((b -> r) -> r)
      fmap f (Cont comp) = Cont \k -> comp (k . f)
\end{minted}

The applicative simply passes the value to the continuation:
\begin{minted}{haskell}
    instance Applicative (Cont r) where
      pure x = Cont \k -> k x
      (<*>) = ap
\end{minted}

One can notice that monadic bind also takes a continuation as its second argument, but a ``small'' one, up to the end of the \mintinline{haskell}|do|-block.
Thus, the meaning of the monadic bind implementation for \mintinline{haskell}{Cont} is composing the ``small'' continuation with the ``large'' continuation passed from outside:
\begin{minted}{haskell}
    instance Monad (Cont r) where
      (>>=) :: Cont r a -> (a -> Cont r b) -> Cont r b
      Cont comp >>= k = Cont \k' -> comp \x -> runCont (k x) k'
\end{minted}

\begin{minted}{haskell}
    fibCont :: Int -> Cont r Int
    fibCont n = if n <= 2 then pure 1 else do
      res1 <- fibCont (n - 1)
      res2 <- fibCont (n - 2)
      pure (res1 + res2)
\end{minted}

Practitioners know this technique of writing CPS code via monads through the concepts of \mintinline{kotlin}{Future}/\mintinline{kotlin}{Promise}\footnote{\url{https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise}}\footnote{\url{https://github.com/promises-aplus/promises-spec/issues/94}}. % todo cite Barbara Liskov and Liuba Shrira. 1988. \subsubsection{\texttt{call/cc}}

The most well-known classical operator used in Scheme for obtaining first-class continuations is \vocab{\texttt{call/cc} (call with current continuation)}\footnote{\url{https://en.wikipedia.org/wiki/Call-with-current-continuation}}\footnote{\url{https://en.wikibooks.org/wiki/Haskell/Continuation_passing_style\#callCC}}.
The provided continuation is \vocab{undelimited (abortive)}, since it contains ``the end of the program'' --- no code will execute after its invocation.
Undelimited continuations are, de facto, not quite functions, since they do not return a result (it is already ``beyond the grave''); consequently, they also do not compose (just as it would be strange to compose \texttt{abort} with \texttt{exit})\footnote{\url{https://okmij.org/ftp/continuations/undelimited.html}}\footnote{\url{https://okmij.org/ftp/continuations/against-callcc.html}}.
They are more like co-values: while a part of the program is executing, they await its result~\cite{curien2000duality}.

Let us emulate \texttt{call/cc} in the \mintinline{haskell}{Cont} monad.
We cannot capture the entire program continuation, since it is only assembled within \mintinline{haskell}{Cont}, but we can ignore the continuation of the call to the captured continuation:
\begin{minted}{haskell}
    callCC :: ((a -> Cont r b) -> Cont r a) -> Cont r a
    callCC f = Cont \k -> runCont (f \x -> Cont \_ -> k x) k

    foo :: Int -> Cont r String
    foo x = callCC \k -> do
      let y = x ^ 2 + 3
      when (y > 20) $ k "over twenty" -- throws next line away
      pure (show $ y - 4)
\end{minted}

\subsection{Delimited continuations} \label{subsec:delimited-cont}

In modern practice, continuations are typically used not up to the end of the program, but only up to a certain point.
They are called \vocab{delimited} or \vocab{composable continuations}, \vocab{subcontinuations}\footnote{\url{https://www.cl.cam.ac.uk/teaching/2324/R277/handout-delimited-continuations.pdf}}\footnote{\href{https://youtu.be/TE48LsgVlIU?si=cBdUCzYwYWpwPkkh}{(youtube)  Keynote: Delimited Continuations, Demystified by Alexis King | Lambda Days 2023}.}.

Constructs for working with such continuations come in pairs: an operator is introduced that delimits the current continuation (possibly with a label); as well as an operator for capturing a fragment of the current continuation (possibly up to a specific delimiter with a given label).
Many such operators have been invented~\cite[appendix A]{hillerstrom2022foundations}, but they are more or less all reducible to each other.

For example, working with exceptions involves two constructs: the continuation is delimited by \mintinline{kotlin}|try-catch|, and \mintinline{kotlin}|throw| discards the corresponding partial continuation without capturing it (see\ Fig.\ \ref{fig:exit-exceptions}):
\[
    E_1[try\{E_2[throw(v)]\}catch(x) \{t\}] \to E_1[\subst{t}{x}{v}]
\]

We will consider the universal operators from~\cite{dyvbig2007monadic}.
The paper introduces the following set of syntactic constructs (Fig.~\ref{fig:prompt-syntax}) for working with delimited continuations, in addition to pure call-by-value lambda calculus:
\begin{itemize}
    \item $newPrompt$\footnote{Historically in Lisps, undelimited continuations were delimited only by the REPL, hence the name for delimiters --- ``prompt.''} --- creates a fresh identifier (label) for a delimiter;
    \item $pushPrompt \ap p \ap e$ --- installs a delimiter with label $p$ and executes expression $e$;
    \item $withSubCont\ap p\ap f$ --- captures the partial continuation up to the delimiter with label $p$ and passes it to function $f$, returns the result of $f$ (Fig.~\ref{fig:push-prompt});
    \item $pushSubCont\ap k \ap v$ --- executes the composition of the current continuation and $k$ on value $v$.
\end{itemize}

Delimited continuation operators can be easily understood as \vocab{resumable exceptions}, i.e.\ exceptions that can be caught and the program resumed from the point where the exception was thrown (with some value).
What is unusual is that the classical delimited continuation operators accept code that works with the partial continuation at the ``throw site,'' rather than at the ``catch site.''
That is, the handling block is written not with \mintinline{kotlin}|catch|, but with \mintinline{kotlin}|throw|:

\begin{gather*}

    \\
    E_1[try\{E_2[throw \ap v]\} catch(x, k) \{t\}] \to E_1[\subst{\subst{t}{k}{\lambda y\ldotp E_2[y]}}{x}{v}]
\end{gather*}

\subsubsection{Implementing the operators}

Let us extend the language from\ \ref{subsubsec:first-class-cont} with the operators for working with delimited continuations discussed above.
For simplicity, instead of fresh prompt labels we will use names, and instead of \texttt{pushSubCont} ordinary application:
\begin{minted}{haskell}
    data Expr = ...| PushPrompt String Expr | WithSubCont String Expr
    data Frame = ... | PushPromptFrame String | WithSubContFrame String
\end{minted}

The redex search is extended in the obvious way:
\begin{minted}[escapeinside=##]{haskell}
    evalK :: (?env :: Env) => Expr -> K -> Value
    evalK e k = case e of
      -- ...
      PushPrompt promptName body -> evalK body (PushPromptFrame promptName : k)
      WithSubCont promptName f -> evalK f (WithSubContFrame promptName : k)
\end{minted}

The entire job of \texttt{PushPrompt} is to get stuck in the continuation as \texttt{PushPromptFrame}, but when execution reaches it, it is simply ignored:
\begin{minted}[escapeinside=##]{haskell}
    appK :: (?env :: Env) => K -> Value -> Value
    appK k result = case k of
      -- ...
      PushPromptFrame _ : k' -> k' `appK` result
\end{minted}

To capture a fragment of the continuation, we need an operation that finds the first prompt with the matching name in the continuation and returns the \vocab{subcontinuation} --- up to that prompt, and the \vocab{metacontinuation} --- after it:
\begin{minted}[escapeinside=##]{haskell}
    splitByPrompt :: K -> String -> (K, K)
    splitByPrompt k targetPromptName = go [] k
      where
        go _ [] =  error $ "Prompt " ++ targetPromptName ++ " not found"
        go subcont (PushPromptFrame promptName : metacont)
          | promptName == targetPromptName = (subcont, metacont)
        go subcont (frame : metacont) = go (subcont ++ [frame]) metacont
\end{minted}

Now \texttt{WithSubCont} must simply apply the user function to the subcontinuation, while not forgetting to execute the metacontinuation afterwards:
\begin{minted}[escapeinside=##]{haskell}
    appK :: (?env :: Env) => K -> Value -> Value
    appK k result = case k of
      -- ...
      WithSubContFrame promptName : k' ->
        let (subcont, metacont) = k' `splitByPrompt` promptName in
        (RApp result : metacont) `appK` K ?env subcont
\end{minted}

\subsection{Applications of continuations} \label{subsec:cont-applications}

Continuations are useful for understanding the meaning of programs we write every day (see\ \ref{foot:the-lost-art-of-denotations}).
Furthermore, as we will see in this chapter, first-class continuations can be used as a means of building powerful embedded languages.

\subsubsection{Everything through continuations} \label{subsubsec:god-cont}

Let us implement a number of useful embedded languages using first-class continuations.
To gain access to continuations, we will use the shallow embedded language \mintinline{haskell}{Cont}\footnote{\url{https://blog.poisson.chat/posts/2019-10-26-reasonable-continuations.html}}.
Thus, we will work with the tower of languages Haskell, \mintinline{haskell}{Cont}, X, where X is the embedded language under consideration.

Let us start with a trivial embedded imperative language:
\begin{minted}{haskell}
    runIdentityC :: (forall r . Cont r a) -> a
    runIdentityC comp = runCont comp id

    exampleIdentity :: Int
    exampleIdentity = runIdentityC do
      x <- pure 4
      y <- pure 5
      pure (x + y)
\end{minted}

Let us implement a language with exceptions.
For this we modify the first type parameter of \mintinline{haskell}{Cont}, the \vocab{answer (response) type}\footnote{\url{https://wiki.haskell.org/Cont_computations_as_question-answering_boxes}}.
The function \texttt{abort} ignores the program continuation up to \texttt{runExn}, which concludes the continuation by wrapping the successful result in \mintinline{haskell}{Just}:
\begin{minted}{haskell}
    abort :: Cont (Maybe r) a
    abort = Cont $ const Nothing

    runExn :: (forall r . Cont (Maybe r) a) -> Maybe a
    runExn comp = runCont comp Just

    exampleExn :: Int -> Maybe Int
    exampleExn n = runExn do
      when (n < 0) abort
      pure (n + 1)
\end{minted}
Notice that the semantics of the abort operation is entirely concentrated in the function \texttt{abort}, whereas in \mintinline{haskell}{Monad Maybe} the corresponding function would only be responsible for constructing a domain element, while monadic bind would handle the continuations.
Having access to first-class continuations, we no longer need to implement monadic bind manually.
It is said that for arbitrary \texttt{m}, \mintinline{haskell}{Cont (m r) a} is a ``free'' implementation of a monad\footnote{\url{https://hackage.haskell.org/package/kan-extensions-5.2/docs/Control-Monad-Codensity.html}}.

Error handling through returning a special result (\mintinline{haskell}{Either} in Haskell, \mintinline{rust}{Result} in Rust, \mintinline{go}{nil} in Go\ldots) has monadic semantics (conditional branches at each point discard only part of the continuation), while a full-fledged exception mechanism has access to the entire delimited continuation up to the corresponding \mintinline{kotlin}{try-catch} block, which resembles our current implementation.
From the perspective of syntactic noise at the source code level, the exception variant is clearly preferable, and we will consider the question of typing exceptions later (see\ \ref{sec:effect-systems}).
From a performance perspective, things are less obvious\footnote{\url{https://www.serpentine.com/2011/02/25/cps-is-great-cps-is-terrible/}}\footnote{\url{https://stackoverflow.com/questions/13835817/are-exceptions-in-c-really-slow}}, though stack unwinding by the runtime seemingly has more room for optimization.

Now let us try invoking the continuation multiple times.
We obtain a language with nondeterminism (or backtracking).
Here, \texttt{choice} continues the rest of the program twice and accumulates all obtained results in a list:
\begin{minted}{haskell}
    choice :: Cont [r] Bool
    choice = Cont \k -> k True ++ k False

    runNondet :: (forall r . Cont [r] a) -> [a]
    runNondet comp = runCont comp (:[])

    exampleNondet :: Int -> [Int]
    exampleNondet n = runNondet do
      b <- choice
      if b then pure n else pure (n - 1)
\end{minted}

Remarkably, having only first-class continuations one can even implement a language with a mutable memory cell:
\begin{minted}{haskell}
    -- s -> (s, a) ~ ((s, a) -> r) -> (s -> r)
    -- ~ (a -> s -> r) -> (s -> r) ~ Cont (s -> r) a

    get :: Cont (s -> r) s -- (s -> s -> r) -> (s -> r)
    get = Cont \k s -> k s s

    put :: s -> Cont (s -> r) ()
    put s' = Cont \k _s -> k () s'

    runStateC :: (forall r . Cont (s -> r) a) -> s -> (a, s)
    runStateC comp = runCont comp (,)

    exampleState :: Int -> ((), Int)
    exampleState = runStateC do
      s <- get
      put (s + 1)
\end{minted}
The idea is quite simple: capturing the continuation leaves behind a function into which the previous continuation call supplies the current state.
And indeed, mutable state is simply a fragment of the continuation (e.g., the hardware stack) to which we have direct read and write access.
Here we have placed an application at the beginning of the continuation, to which, by capturing the continuation, we jump to obtain the argument and update it to a new one.

Intuitively, the power of continuations can be explained as follows: maintaining the continuation is the primary responsibility of the language's runtime system; when continuations are handed to the user, their code becomes involved in the runtime's activity and effectively becomes part of it.

\subsubsection{The mother of all monads} \label{subsubsec:monadic-reflection}

In the previous section (\ref{subsubsec:god-cont}) we implemented the capabilities of classical monads in a language with continuations.
Does this work for an arbitrary monad?
It turns out that yes\footnote{\url{http://www.schoolofhaskell.com/school/to-infinity-and-beyond/pick-of-the-week/the-mother-of-all-monads}}\footnote{\url{https://blog.poisson.chat/posts/2019-10-26-reasonable-continuations.html}}~\cite{filinski1994representing}.

Recall that a monad is a type constructor \texttt{m} with which we represent the denotation of a computation.
The operations \texttt{pure} and \texttt{bind} allow creating and composing denotations.
Thus, we have computations represented as first-class data.

If our language provides first-class continuations (let us take \mintinline{haskell}{Cont (m r)} as such a language for example), we can define two operations: \texttt{reflect} --- execute a monadic computation in the language with continuations and obtain the result \texttt{a}; \texttt{reify} --- obtain a denotation from a computation in the language with continuations\footnote{For a strict language, \texttt{reify} should accept a thunk \texttt{(() -> a) -> m a}.}.
In Haskell, this can be expressed as overloading this pair of functions for various monads:
\begin{minted}{haskell}
    class MonadicReflection m where
      -- m a -> (a -> m r) -> m r
      reflect :: m a -> forall r . Cont (m r) a
      -- (forall r . (a -> m r) -> m r) -> m a
      reify :: (forall r . Cont (m r) a) -> m a
\end{minted}

For example, for the \mintinline{haskell}{State} domain the implementation looks as follows:
\begin{minted}{haskell}
    newtype State s a = State { runState :: s -> (a, s) }

    instance MonadicReflection (State s) where
      reflect :: State s a -> (forall r . Cont (State s r) a)
      reflect comp = Cont \k -> State \s ->
        let (a, s') = runState comp s in
        runState (k a) s'

      reify :: (forall r . Cont (State s r) a) -> State s a
      reify comp = State $ runState (runCont comp (\x -> State (x,)))

    exampleStateReflection :: Int -> (Int, Int)
    exampleStateReflection = runState $ reify do
      x <- reflect get
      reflect $ put (x + 1)
      pure x
\end{minted}

Intuitively, this can be understood as follows: the bind implementation does not actually care whether it is given a ``small'' continuation (assembled via desugaring of \mintinline{haskell}{do}-notation) or a ``large'' continuation assembled by the meta-language or the \mintinline{haskell}{Cont} monad.
And in principle, monads can be defined through their embedding into the \mintinline{haskell}{Cont} monad\footnote{\url{https://blog.poisson.chat/posts/2019-10-27-continuation-submonads.html}}.

Thus, if the language supports first-class continuations, one can implement the functionality of an arbitrary monad in direct style\footnote{\url{https://www.unison-lang.org/docs/fundamentals/abilities/for-monadically-inclined/}}, without \mintinline{haskell}{do}-notation, applicative chains, and other syntactic noise\footnote{\url{http://www.valuedlessons.com/2008/01/monads-in-python-with-nice-syntax.html}}\footnote{\url{https://github.com/lampepfl/monadic-reflection/blob/main/TUTORIAL.md}}.
Later we will see that this approach, unlike monads, natively supports composition (\ref{sec:effects}), and also does not impose restrictions on typing (\ref{sec:effect-systems}).
This raises the question: do we still need monads in programming?

\subsubsection{Generators and coroutines} \label{subsubsec:generators-coroutines}

Generators and coroutines are usually defined as computations that can be suspended and resumed in the same state~\cite{moura2009revisiting}.
Coroutines generalize generators and are typically used as a primitive for asynchronous programming in the form of \texttt{async/await} or other language constructs~\cite{elizarov2021kotlin}.
The difference between synchronous and asynchronous programming can be understood as follows: in the former case, continuations are managed exclusively by the operating system, while in the latter --- by the language facilities.

As an example, let us implement generators.
As the result of a generator we will use a lazy list, an iterator encoded as an unfold (see\ \ref{subsec:all-unfolds}):
\begin{minted}{haskell}
    data Box f = forall s . Box s (s -> f s)
    data ListF a rec = Nil | Cons a rec
    type Iterator a = Box (ListF a)

    box2list :: Iterator a -> [a]
    box2list (Box s next) = case next s of
      Nil -> []
      Cons x s' -> x : box2list (Box s' next)
\end{minted}

The hidden state of the iterator will be the not-yet-executed continuation.
We will obtain access to the continuation via the \mintinline{haskell}{Cont} monad, where we take \mintinline{haskell}{GenState} as the response type.
Thus, the \texttt{yield} operation suspends the computation and saves the continuation in the \mintinline{haskell}{Yield} constructor, while \texttt{makeGen} finishes the given generator by producing the \mintinline{haskell}{Stop} constructor:
\begin{minted}{haskell}
    data GenState a = Stop | Yield a (() -> GenState a)

    makeGen :: Cont (GenState a) () -> Iterator a
    makeGen comp = Box
      (\() -> runCont comp (\() -> Stop))
      (\k -> case k () of
          Stop -> Nil
          Yield x k' -> Cons x k'
      )

    yield :: a -> Cont (GenState a) ()
    yield x = cont \k -> Yield x k
\end{minted}

Now we can write code that sequentially produces multiple results:
\begin{minted}{haskell}
    exampleGen :: [Int]
    exampleGen = it2list $ makeGen do
      yield 1
      yield 2
      yield 3
\end{minted}

\subsection{Efficient work with continuations} \label{subsec:efficient-cps}

In practice, implementing generators and coroutines requires suspending and resuming programs, in other words, capturing continuations.
This needs to be done as efficiently as possible.

\subsubsection{Contiguous stack}

The continuation is represented as a hardware stack.
As soon as a continuation needs to be captured, the stack is copied to the heap (possibly lazily)\footnote{\href{https://youtu.be/kwS3OeoVCno?si=c4MkSkmLHNeywPrZ}{(youtube) Ivan Uglyansky - Java Project Loom.}}. % todo cite
That is, this approach relies entirely on support from the language runtime.

\subsubsection{Segmented stack} % todo cite

The call stack is represented as a linked list of heap-allocated segments, each corresponding to a delimiting operation.
Thus, no copying is required; it suffices to swap pointers.
However, in this case the stack is non-local, which is not great for cache performance.

\subsubsection{Finite state machine (FSM)}

This implementation involves automatic CPS transformation of user code by the compiler.
To avoid allocating a large number of closures, continuations are defunctionalized and within each function are represented by a single mutable object.
Thus, the function's entire state is allocated on the heap once, and resuming the function body at a particular point is implemented as a state machine --- using labels and jumps\footnote{\url{https://github.com/Kotlin/KEEP/blob/master/proposals/coroutines.md\#state-machines} \label{note:kotlin-state}}.

This is how, for example, coroutines are implemented in Kotlin\footref{note:kotlin-state}, generators in C\#\footnote{\url{https://csharpindepth.com/Articles/IteratorBlockImplementation}}\ldots

Even in this form, CPS remains a heavyweight transformation that can slow down code execution by orders of magnitude.
The issue is, in particular, that variables in this approach are difficult to place in registers (functions have many entry and exit points\footref{note:kotlin-state}), and they constantly have to be written to RAM --- performing \vocab{spilling}\footnote{\url{https://en.wikipedia.org/wiki/Register_allocation}}.
