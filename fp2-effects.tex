Earlier we recognized managing complexity as the programmer's main task, and constructing embedded languages as the primary tool for solving it (\ref{subsec:interpreters-rules}).
In this chapter we consider the notion of an effect.
It is closely related to embedded languages and will give us a better understanding of when to construct them, what this gives us, and what one needs to be careful about.

For implementing embedded languages we preferred shallow embedding in the form of tagless final (\ref{subsec:tagless-final}), which maximally reuses the capabilities of the meta-language and allows giving different interpretations to the same program.
Next we studied the computation process and extracted the notion of a continuation (\ref{sec:continuations}).
It turned out that the tagless final languages we were building around monads can be expressed through continuations more conveniently and simply (\ref{subsubsec:god-cont},\ \ref{subsubsec:monadic-reflection}).
In this chapter we will understand how this will help us solve the expression problem (\ref{subsec:expression-problem}) completely.

From a historical-philosophical perspective, the theory of effects is a solid bridge between the functional and imperative programming paradigms.
The two originated separately --- as the Turing machine and Church's $\lambda$-calculus --- and remained largely isolated schools of thought for decades.
Only in the last 30 years has this begun to change, and we have come to understand how the two worlds complement each other.
The theory of effects remains an extremely hot topic to this day\footnote{\href{https://youtu.be/m821Vz8N_bo?si=HQTDfs52vYKaBcqJ}{(youtube) The Evolution of Effects --- Nickolas Wu.}}\footnote{\url{https://github.com/yallop/effects-bibliography}}.

\subsection{The notion of an effect} \label{subsec:about-effects}

Let us begin the discussion from the opposite end, with the property of purity.
A \vocab{pure function} possesses the following properties:
\begin{itemize}
    \item Its result is always the same given the same set of arguments (it does not depend on anything else in any more non-trivial way);
    \item Its only observable result is its return value.
\end{itemize}

% todo obsidian What is a purely functional language?

In general, the programming style using pure functions is encouraged, as it possesses many good properties.
One can conveniently reason about them using equational reasoning; everything needed to understand the code is explicitly written in that code; classical type systems work well, providing abstraction completeness, quality documentation, and partial specification\ldots
It is also known that everything can be expressed using pure computations, even working with IO~\cite{jones2001tackling}.

However, using only pure functions, everything must be done manually.
In the case of IO (and similarly with state) --- passing the resulting world as an argument again and again:
\begin{minted}{haskell}
    getList :: Int -> World -> (World, [Int])
    getList n w | n == 0 = (w, [])
                | otherwise =
      let (w', x) = getInt w in
      let (w'', xs) = getList (n - 1) w' in
      (w'', x : xs)
\end{minted}

Thus, code made of pure functions is filled with inessential ceremony, behind which the business logic and essence are hidden.
To focus on the important details, one needs to delegate all this bookkeeping to external code, sweep the uninteresting details under the rug.
Then the code above can be rewritten, for example, as follows:
\begin{minted}{haskell}
    getList :: Int -> IO [Int]
    getList n | n == 0 = pure []
              | otherwise = do
      x <- getInt
      xs <- getList (n - 1)
      return (x : xs)
\end{minted}

The abstract entity to which we will delegate details inessential to the given fragment of business logic we will call the \vocab{execution context}\footnote{\url{https://okmij.org/ftp/Computation/having-effect.html} \label{lab:having-effect}}.
And an \vocab{effect} is the interaction of a function with the execution context, which occurs through calls to \vocab{effect operations} (for example, \texttt{getInt} from the example above)\footnote{Sometimes the term ``effect'' also refers to the transfer function in dataflow analysis~\cite{moller2012static}. In essence, it describes the change of context.}. % todo Effect systems revisited—control-flow algebra and semantics % todo Data-flow analyses as effects and graded monads
Thus, one can view the execution context as a server to which the client function sends requests and receives responses (see\ Fig.\ \ref{fig:effect-server}).
In this model, such a function can violate both properties of pure functions.

\begin{figure}
    \centering
    \includegraphics[width=0.5\textwidth]{figs/effects}
    \caption{Effects as client-server interaction.}
    \label{fig:effect-server}
\end{figure}

In practice, this context is the interpreter of an (embedded) language, and the effect operations are its constructs.
If the language is embedded, one speaks of \vocab{user-defined effects}.
Thus we again return to the task of building modular interpreters (\ref{subsec:expression-problem}).
Moreover, the implementation of a computational context can also delegate the implementation of certain functionality to another execution context, and so on.
We obtain the already familiar tower of interpreters (\ref{subsubsec:interpreters-tower}).

Let us consider some examples of computational contexts and operations:
\begin{itemize}
    \item Context --- memory management subsystem, \texttt{modify} --- effect operation: the context maintains the state of memory cells for us;
    \item Context --- exception handler, \texttt{throw MyException} --- effect operation: the context determines how the error will be handled for us (note that here control does not return to the term);
    \item Context --- dependency injection settings, requesting functionality --- effect operation: the context determines the implementation of the functionality we use\footnote{There exists the term \vocab{contextual polymorphism} --- code in different contexts can have different behavior.}.
    As we will see later, this and similar simple effects can be implemented simply and efficiently (see\ \ref{subsubsec:evidence-passing}).
\end{itemize}

\end{task}

When we talk about a standalone language in which we program (for example, Haskell), any action of ours in the program is executed by it.
That is, for instance, is addition an effect operation?
In that case it is reasonable to identify a subset of language constructs that are ``interesting'' enough to be considered as producing an effect.

Which language constructs should be considered ``interesting''?
Notice that on the one hand it is good that effects hide some complexity from us, allowing us to focus on other things.
On the other hand, this is also bad, because we cease to observe this complexity, yet it permeates our code and maintains implicit dependencies between its parts.
Thus, effects require additional care from the programmer\footnote{\href{https://youtu.be/_nG09Z_tdUU?si=lo9It6299rsB1vAr}{(youtube) Kris Jenkins --- Side-Effects Are The Complexity Iceberg.}}.
Accordingly, it is precisely such non-trivial constructs that should be considered ``interesting.''
At the very least, constructs whose use takes a function out of the pure category should definitely be considered ``interesting.''
Also, these can be operations that make complex non-local modifications to the control flow (maintained by the interpreter in the form of a continuation).

Ultimately, the choice of ``interesting'' constructs depends on the task and the developer's perspective\footref{lab:having-effect}.
Thus, constructs affecting arbitrary observable properties of code, such as termination or computational complexity, can motivate considering recursive calls or long-running operations as effects.

Later we will learn to track and control the use of effects at the type level using effect systems (see\ later\ \ref{sec:effect-systems}).

\subsection{Effect handlers} \label{subsec:effect-handlers}

Effect handlers are a modern universal method for building modular interpreters of embedded languages, directly implementing the client-server metaphor.
As is often the case, handlers were invented multiple times.
In this chapter we will look at the main implementations that will best help us understand the concept.

The main idea of effect handlers is fairly simple.
A language construct \texttt{handle} is introduced that allows defining a computational context for a given scope, providing implementations of effect operations.
A construct \texttt{perform} is also introduced that allows invoking an effect operation (sending a request to the context).
Each operation has a set of parameters, as well as a ``return address,'' the continuation of the call site, to which it will return the result.
For example, in the experimental language Koka\footnote{\url{https://koka-lang.github.io/koka/doc/index.html}} a context providing some constant can be implemented as follows (\texttt{resume} is the name of the call-site continuation, \texttt{perform} is inserted implicitly):
\begin{minted}{cpp}
    with handler
      ctl ask() resume(21)
    ask() + ask()
\end{minted}

If the nearest context cannot handle the required request, the request is delegated to an outer context, and so on until a suitable context is found.
The modularity of interpreters defined by handlers is based on this idea.

\subsubsection{Handlers via delimited continuations}

As we have already seen, various effects can be implemented using access to the current continuation (\ref{subsubsec:god-cont}, \ \ref{subsubsec:monadic-reflection}).
Effect handlers extend this idea by using delimited continuations to transfer control to various interpreters (handlers).

It is known that the classical operators for manipulating delimited continuations, monadic reflection, and effect handlers are expressible in terms of each other~\cite{forster2017expressive}.

\subsubsection{Efficient implementation of handlers} \label{subsubsec:evidence-passing}

In general, the speed of \texttt{perform} is determined by the speed of capturing and restoring delimited continuations.
However, there exists a class of operations that can be implemented much more efficiently.

If we look at the implementation of the \texttt{ask} operation, we see that its last action is calling the continuation, returning control to the calling code.
Such operations are called \vocab{tail-resumptive}; they strongly resemble ordinary functions, except that their implementations are determined by the context (handler).
Thus, tail-resumptive operations can be implemented as implicit passing of a dictionary of functions from the handler to \texttt{perform}, thereby avoiding expensive continuation manipulations~\cite{xie2020effect}\footnote{Handlers of tail-resumptive operations resemble co-pattern matching and, correspondingly, objects (see\ \ref{subsubsec:data-codata}).}.

\subsubsection{Embedded handlers as explicit client-server communication} \label{subsubsec:extensible-effects}

To better understand the semantics of handlers, let us implement a language with handlers embedded in Haskell.
We start with the variant proposed by Oleg Kiselyov, which most straightforwardly encodes the idea of client-server communication between the term and the context~\cite{kiselyov2013extensible}.

Let us begin with the \texttt{ask} effect, which requests numbers from the context.
We define the data type of messages to the context: it is either the final result of the computation, or a request \mintinline{haskell}{Ask} containing a ``return address'' --- the current continuation:
\begin{minted}{haskell}
    data Message res = Val res | Ask (Int -> Message res)
\end{minted}

We will assemble continuations into a specialized \mintinline{haskell}{Monad Cont} with a suitable response type (see~\ref{subsubsec:monad-cont}, \ \ref{subsubsec:god-cont}):
\begin{minted}{haskell}
    newtype Eff res = Eff
      { runEff :: forall res' . (res -> Message res') -> Message res' }
\end{minted}

Then the \texttt{ask} effect is implemented simply as ``sending'' an \mintinline{haskell}{Ask} request with the current continuation:\footnote{Earlier we similarly implemented generators, see\ \ref{subsubsec:generators-coroutines}.}
\begin{minted}{haskell}
    ask :: Eff Int
    ask = Eff \k -> Ask k
\end{minted}

We implement the handler as a ``server'' that processes requests in a loop until the computation sends the final result:
\begin{minted}{haskell}
    run :: Eff res -> Message res
    run comp = runEff comp Val

    runReader :: Eff res -> Int -> res
    runReader comp env = loop (run comp)
      where
        loop = \case
          Val res -> res
          Ask k -> loop (k env)
\end{minted}

Finally, we can write effectful code:
\begin{minted}{haskell}
    exampleReader :: Int -> Int
    exampleReader = runReader do
      x <- ask
      y <- ask
      pure (x + y)
\end{minted}
The \mintinline{haskell}{Eff} monad will turn it into a lazy list of messages:
\begin{minted}{haskell}
    exampleReader :: Int -> Int
    exampleReader = loop $
      Ask \x ->
      Ask \y ->
      Val (x + y)
\end{minted}

\subsubsection{Extensible messages and forwarding} \label{subsubsec:extensible-messages}

Let us abstract the message type over the ``shape'' of requests that can participate in them (see\ \ref{subsubsec:functor-fixpoint}):
\begin{minted}{haskell}
    data Message effs res = Val res | Request (effs (Message effs res))
\end{minted}

The previous message type is obtained by passing the following shape functor:
\begin{minted}{haskell}
    newtype Reader env msg = Ask (env -> msg)
\end{minted}

\begin{task}
    Verify that \mintinline{haskell}{Message (Reader Int) res} is equivalent to the previous message type.
\end{task}

The coproduct of shape functors is a shape functor (see\ \ref{subsubsec:functor-coprod}):
\begin{minted}{haskell}
    data (eff |> effs) a = L (eff a) | R (effs a)
\end{minted}

Now the \texttt{ask} operation admits the existence of other request types \texttt{effs}:
\begin{minted}{haskell}
    ask :: Eff (Reader env |> effs) env
    ask = Eff \k -> Msg $ L $ Ask k
\end{minted}

The new handler processes only a portion of the requests, forwarding the rest to the handler above (composing the continuations in the correct way):
\begin{minted}{haskell}
runReader
  :: forall effs env res . Functor effs
  => Eff (Reader env |> effs) res
  -> env -> Eff effs res
runReader comp env = loop (run comp)
  where
    loop :: Request (Reader env |> effs) res -> Eff effs res
    loop = \case
      Val res -> pure res
      Msg (L (Ask k)) -> loop (k env)
      Msg (R unknownReq) -> do
        response <- Eff \k -> Msg (fmap k unknownReq)
        loop response
\end{minted}

Notice that uninterpreted effects remain in the resulting domain.
The final domain is obtained by applying all the necessary interpreters.
This is how the stable denotations problem (\ref{subsec:expression-problem}) is solved.

\subsubsection{Free monads} \label{subsubsec:free-monads}

To obtain a full-fledged solution in a simpler and more minimalistic way, let us turn to the most classical implementation of handlers via free monads.
First, let us discuss free monads themselves.

Consider some algebraic structure, for example, a monoid (a neutral element and an associative binary operation).
From an arbitrary set $X$ one can construct a certain monoid $M(X)$ in the most ``economical'' way --- the \vocab{free monoid}.
This is done as follows: to the set $X$ one adds expression trees with the monoid operations:
\begin{minted}{haskell}
    data M x = Element x | Mempty | Mappend (M x) (M x)
    instance Monoid (M x) where
      mempty = Mempty
      mappend l r = Mappend l r
\end{minted}
One only needs to organize the new set so that there are no trees that are identical from the algebra's perspective (for example, \mintinline{haskell}{Mappend Mempty Mempty} and \mintinline{haskell}{Mempty}).
In the case of a monoid, one can choose the list type:
\begin{minted}{haskell}
    type M x = [x]
    instance Monoid (M x) where
      mempty = []
      mappend = (++)
\end{minted}

Free monads are constructed analogously to free monoids.
We use the definition of a monad as a functor with operations \texttt{pure} and \texttt{join}.
Then from an arbitrary functor $F$ one can obtain a monad $Free(F)$ (we show this using the equivalent monad definition from Haskell):
\begin{minted}{haskell}
    data Free f a = Pure a | Join (f (Free f a))
    instance Functor f => Monad (Free f) where
      return = Pure
      Pure x >>= k = k x
      Join f >>= k = Join (fmap (>>= k) f)
\end{minted}

Let us rename the constructors:
\begin{minted}{haskell}
    data Term sig var = Var var | Op (sig (Term sig var))
    (>>=) :: Term sig var -> (var -> Term sig var') -> Term sig var'
    data MonoidSig subtree = Mempty | MAppend subtree subtree -- (Bool -> subtree)
\end{minted}
This is nothing other than an encoding of algebraic terms over the signature \texttt{sig} with variables from the set \texttt{var}.
And monadic bind is substitution.

\subsubsection{Handlers via free monads} \label{subsubsec:free-monad-handlers}

Notice that the following types are isomorphic: \mintinline{haskell}{Message} $\iso$ \mintinline{haskell}{Free} $\iso$ \mintinline{haskell}{Term}.
Handlers in the classical form arose precisely in the process of studying how to describe effects as algebraic structures~\cite{bauer2018algebraic}\footnote{\href{https://www.youtube.com/watch?v=vPVMXLJVylU&list=PLt7hcIEdZLAkebYy70DdBDm2qLrw7ptfp}{(youtube) What is algebraic about algebraic effects and handlers --- Andrej Bauer.}}.

Instead of variables we store the pure result of the computation, and signatures are written in the form $P\times (A \to K)$, where $P$ is the operation parameter and $A$ is the operation result, by which the handler selects the needed continuation subtree for resuming the computation:
\begin{minted}{haskell}
    data Comp effs res = Res res | Op (effs (Comp effs res))
    data Reader env comp = Ask () (env -> comp)
    data State s comp = Get () (s -> comp) | Put s (() -> comp)
\end{minted}

The \mintinline{haskell}{Monad Comp} implementation will compose continuations for us in \mintinline{haskell}{do}-notation:
\begin{minted}{haskell}
    ask = Op (Ask () (\e -> Val e)
    example = do
      x <- ask
      y <- ask
      pure (x + y)
    -- $\alpha\beta$-equivalent to
    example =
      Op (Ask () (\x ->
      Op (Ask () (\y ->
      Res (x + y)))))
\end{minted}

The handler also simply folds the list of operations.
Operations it cannot handle are left in the tree.
To skip an unknown operation and interpret the subtree (continuation), \texttt{fmap} is used:
\begin{minted}{haskell}
    runReader
      :: Functor effs => Comp (Reader env |> effs) res -> env -> Comp effs res
    runReader comp env = case comp of
      Res res -> Res res
      Op (L (Ask () k)) -> runReader (k env) env
      Op (R other) -> Op (fmap (`runReader` env) other)
\end{minted}

\begin{task}
    Build an example computation using \mintinline{haskell}{Reader} and \mintinline{haskell}{State}.
    What tree results after interpreting one of the effects?
\end{task}

As usual, the fold can be generalized as a catamorphism:
\begin{minted}{haskell}
    handle
      :: Functor effs => (res -> d) -> (effs d -> d) -> Comp effs res -> d
    handle val alg = \case
      Pure res -> val res
      Op eff -> alg $ fmap (handle val alg) eff
\end{minted}
Now in the implementation the continuation (subtree) is already interpreted into the desired domain:
\begin{minted}{haskell}
    runReader
      :: Functor effs => Eff (Reader env |> effs) res -> env -> Eff effs res
    runReader = handle (\res _env -> pure res) \case
      L (Ask k) -> \env -> k env env
      R other -> \env -> Op (fmap ($ env) other)
\end{minted}

When handlers are implemented as a built-in language feature, a design decision must be made: in the provided continuation, is the current effect already interpreted or not?
The first variant is called \vocab{deep handlers}, the second --- \vocab{shallow handlers}; they are expressible in terms of each other~\cite{hillerstrom2018shallow}.

Unfortunately, since the various effect variants are ordered both at the term level and at the type level, we need an operation that turns a computation with fewer effects into a computation with more:
\begin{minted}{haskell}
    liftF :: Functor effs => Comp effs res -> Comp (eff |> effs) res
    liftF = \case
      Pure x -> Pure x
      Op effs -> Op $ R $ liftF <$> effs

    example :: Comp (Reader Int |> State Int) ()
    example = do
      env <- ask
      liftF (put env)
\end{minted}
The ordering can be eliminated using type classes~\cite{swierstra2008data} (\ref{subsubsec:open-structs}).

One can notice that besides a large number of allocations, using \mintinline{haskell}{Monad Free} can lead to quadratic complexity of code due to linear passes in each bind.
Various alternative encoding schemes exist~\cite{ploeg2014reflection, kiselyov2015freer}.

Free monads find other, albeit analogous, applications: trampolining~\cite{bjarnarson2012stackless} and pipelines~\cite{kiselyov2012iteratees}~\cite[chapter 14]{bragilevsky-haskell}.

\subsubsection{Applications of handlers} \label{subsubsec:handler-applications}

Let us consider handlers of tail-resumptive operations, which treat continuations in a trivial way.
They are needed for propagating values and functionality down the stack.
As we discussed earlier~\ref{subsubsec:evidence-passing}, such handlers are analogous to having dynamic free variables or implicit function arguments~\ref{subsubsec:ad-hoc-implicits}, and, along with them, records or anonymous classes~\ref{subsubsec:data-codata}.

Among non-trivial use cases for continuations, we highlight the following:
\begin{itemize}
    \item The continuation can be left uninvoked; thus, an exception mechanism can be implemented.
    However, in practice continuations may contain resource finalization logic.
    In that case, some special handling is still needed\footnote{\url{https://koka-lang.github.io/koka/doc/book.html\#sec-resource}}.
    \item It can be invoked multiple times to emulate nondeterminism.
    This limits the use of efficient mutable continuations~\ref{subsec:efficient-cps}~\cite{leijen2018algebraic}\footnote{\url{https://koka-lang.github.io/koka/doc/book.html\#sec-multi-resume}}, and also requires non-trivial handling when working with resources.
    \item It can be invoked not immediately.
    This is needed for implementing mutable state, generators, and coroutines.
    For mutable state this is too expensive.
    Generators are a good application, but a built-in generator implementation can be more efficient by saving on continuation allocations (an \mintinline{kotlin}{Iterator} is created directly)\footnote{\url{https://csharpindepth.com/Articles/IteratorBlockImplementation}}.
    Implementing coroutines on top of handlers gives users the ability to write their own schedulers, which is the most valued application of handlers at the present time~\cite{sivaramakrishnan2021retrofitting, phipps2023continuing}. % todo
\end{itemize}

\subsubsection{Monad transformers} \label{subsubsec:monad-transformers}

In the classical implementation of handlers via free monads~\ref{subsubsec:free-monad-handlers}, each handler produces an intermediate tree of uninterpreted operations.
The desire to deforest~\ref{subsubsec:deforestation-fusion} these intermediate trees arises naturally.
One can go all the way and completely eliminate free monads and signature functors~\cite{wu2015fusion}.
In doing so, we effectively obtain the tagless final shallow embedding~\ref{subsec:tagless-final}, another popular solution to the expression (stable denotations) problem --- \vocab{monad transformers}~\cite{liang1995monad,jones1995functional}\footnote{\url{https://hackage.haskell.org/package/mtl}}.
In general, these approaches are equivalent in expressiveness, but may in practice have different characteristics when embedded in a language~\cite{schrijvers2019monad}.
However, unlike transformers, handlers can be made a convenient built-in language feature.

\subsubsection{Algebraicity and higher-order effects} \label{subsubsec:algebraicity-higher-order}

In the early 2000s, the idea emerged of describing effect operations not with monads directly, but algebraically, using signatures and equations~\cite{plotkin2002notions, bauer2018algebraic}.
Effects in this formalism are composable by construction, just as the signatures of algebraic theories are composable (concatenation of signatures is a signature~\ref{subsubsec:extensible-messages}); thus we have extensible syntax.
However, a restriction is imposed on operations in the form of the \vocab{algebraicity property} --- an operation commutes with the continuation and ``bubbles up'' to the top:
\[
    E[op(v, k)] \equiv op(v, \lambda x\ldotp E[k(x)])
\]
The corresponding effects are called \vocab{algebraic}.

In our implementation (\ref{subsubsec:free-monad-handlers}), the algebraicity restriction can be seen as follows.
Our operation signatures are functors in their continuations.
This is used by both monadic bind for accumulating continuations and handlers for interpreting the continuations of unknown operations.

Many useful effects are algebraic, but not all.
For example, catching exceptions \texttt{catch} is not an algebraic operation, since its signature would be written as follows:
\begin{minted}{haskell}
    data Catch e comp = Catch { try :: comp, onExn :: (e -> comp), next :: comp }
\end{minted}
In this case the only reasonable functor implementation would also work with nested continuations, and the entire program, as a result of bind, would end up inside the \texttt{try} block.

In other words, \point{algebraic effects cannot accept other effectful computations as arguments}.
It was precisely to model \texttt{catch} that handlers were originally proposed~\cite{plotkin2013handling}\footnote{Despite the fact that algebraic effects are simply a class of ``well-behaved'' operations, often when they are mentioned, effect handlers are implied.}.
Thus, handlers have two tasks: delimiting the scope of certain functionality and interpreting effects.
However, as we know, the order of handlers determines the resulting domain and, accordingly, the semantics.
At the same time, the task of scope delimitation fixes the handler's position, which limits expressiveness and makes some domains inaccessible.

Operations that do not satisfy the algebraicity property correspond to \vocab{higher-order effects}, which can accept other effectful computations as arguments.
Embeddings of handlers for such effects exist along with an extensive body of research on the topic~\cite{wu2014effect}\footnote{\url{https://github.com/fused-effects/fused-effects}}\footnote{\href{https://youtu.be/vfDazZfxlNs?si=3o1zkoL8GsmezMtU}{(youtube) Building Haskell Programs with Fused Effects --- Patrick Thomson}}~\cite{yang2022structured}.

The key to higher-order effects lies in the ability to execute the effects of argument computations in the context of those handlers that are available at the call site of the higher-order effect~\cite{van2022handling}.
This is related to another idea, bidirectional effects, which allows the operation's implementation to produce effects at its call site (for example, throw exceptions there), an extremely necessary practical capability~\cite{zhang2020handling}\footnote{\url{https://effekt-lang.org/docs/concepts/bidirectional}}.
