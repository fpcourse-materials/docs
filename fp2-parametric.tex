No non-trivial property of programs can be checked algorithmically\footnote{\url{https://en.wikipedia.org/wiki/Rice\%27s_theorem}}.
To remain decidable (in terms of type checking and/or inference), many type systems sacrifice completeness and, besides incorrect programs, reject many correct ones.
At the same time, type systems also try to provide various capabilities that make it possible to type as many correct programs as possible.
One of these is parametric polymorphism.

By \vocab{parametric polymorphism} we mean the ability of code to work uniformly with arbitrary data types~\cite{strachey2000fundamental, cardelli1985understanding}, which in many cases allows avoiding code duplication.

In this chapter we will look at how polymorphism is described in its simplest form --- in typed $\lambda$-calculus.
We will study different forms of parametric polymorphism and the associated safe programming techniques.
We will analyze possible ways to implement parametric polymorphism efficiently.
And finally, we will consider runtime representation polymorphism, "polymorphism over polymorphism."

\subsection{Parametric polymorphism in the language} \label{subsec:lang-parametric-polumorphism}

$\lambda$-abstraction allows generalizing expressions over values; each abstraction adds an arrow to the type of the expression, while application removes an arrow:
\[
    \begin{array}{cc}
        \infer[Lam]{\Gamma\vdash \lambda x : \tau\ldotp M : \tau\to\sigma}{x : \tau, \Gamma\vdash M : \sigma}
        &
        \infer[App]{\Gamma\vdash M\ap N : \sigma}{\Gamma\vdash M : \tau\to\sigma & \Gamma\vdash N : \tau}
    \end{array}
\]
At the same time, $\Lambda$-abstraction allows generalizing expressions over types by adding a quantifier to the type (a $\Pi$-abstraction), and term application to a type (\vocab{universal application}) allows choosing which concrete type this term is intended to use~\cite[chapter 23]{pierce2002types}:
\[
    \begin{array}{cc}
        \infer[TLam]{\Gamma\vdash\Lambda\alpha\ldotp M : \forall\alpha\ldotp\tau}{\Gamma\vdash M : \tau}
        &
        \infer[TApp]{\Gamma\vdash M\ap\sigma : [\alpha\to\sigma]\ap\tau}{\Gamma\vdash M : \forall\alpha\ldotp\tau}
    \end{array}
\]

Thus, for example, the function $id$ actually takes \point{two arguments: a type and a value}:
\[
    \begin{array}{ll}
        id : \forall\alpha\ldotp\alpha\to\alpha            \\
        id = \Lambda\alpha\ldotp\lambda x : \alpha\ldotp x \\
        id \ap nat : nat \to nat                           \\
        id\ap nat \ap 42 : nat
    \end{array}
\]

In Haskell, type abstractions and applications are attached implicitly by type inference.
However, there are language extensions that allow writing them explicitly: \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/type_abstractions.html}{TypeAbstractions}, \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/type_applications.html}{TypeApplications}.
This can help, for example, when the term does not provide enough information to infer the type.
Thus, you can explicitly specialize \texttt{id} to the desired type:
\begin{minted}{haskell}
    id :: forall a . a -> a
    ghci> :t id @Int
    id @Int :: Int -> Int
\end{minted}

Quantifiers are also implicitly attached at the beginning of a type, following a naming convention: concrete types start with an uppercase letter, while polymorphic ones start with a lowercase letter.
Similarly, the user may explicitly write \mintinline{haskell}|forall|s using the \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/explicit_forall.html\#extension-ExplicitForAll}{ExplicitForAll} extension.
This may be useful either to manually fix the order of type abstractions, or to refer to the abstracted type inside the body of a function (the \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/scoped_type_variables.html#extension-ScopedTypeVariables}{ScopedTypeVariables} extension).

Polymorphic data types are expressed by another construct.
If previously we controlled the type at the term level by universal application, now we want to control it at the type level.
For this we introduce $\lambda$ abstraction in types, type application, and, accordingly, $\beta$-reduction.
The kind system (for now) is just the simplest "type system for types" and ensures well-formedness of types and strong normalization\footnote{\vocab{Strong normalization} means any order of reductions leads to a normal form.}.
For example, we can write the type of a pair, abstracted over the concrete types of its components, so that the user can pick the desired instantiation:
\begin{align*}
    &Pair : * \rightarrow * \rightarrow * \\
    &Pair = \lambda \tau^*~\sigma^*\ldotp\forall \gamma\ldotp(\tau\rightarrow\sigma\rightarrow\gamma)\to\gamma \\
    &pair : \forall \alpha~\beta\ldotp\alpha \rightarrow \beta \rightarrow Pair~\alpha~\beta \\
    &pair = \Lambda \alpha^*~\beta^*\ldotp\lambda x^\alpha~y^\beta\ldotp(\Lambda \gamma^*\ldotp\lambda f^{\alpha\rightarrow\beta\rightarrow\gamma}\ldotp f~x~y) \\
    &fst : \forall \alpha~\beta\ldotp Pair~\alpha~\beta\rightarrow \alpha \\
    &fst = \Lambda \alpha^*~\beta^*\ldotp\lambda p^{Pair~\alpha~\beta}\ldotp p~\alpha~(\mathbf{K}\ap\alpha\ap\beta)
\end{align*}

In Haskell, the computational semantics of polymorphic types can be traced in type synonyms:
\begin{minted}{haskell}
    type Pair a b = forall c . (a -> b -> c) -> c
    intPair :: Pair Int Int -- forall c . (Int -> Int -> c) -> c
\end{minted}
Regular type constructors are nominal.
For example, \mintinline{haskell}{(Int, Int)} or \mintinline{haskell}{Maybe Int} do not further compute.

Haskell does not allow writing functions at the type level in place using an explicit type lambda\footnote{\url{https://stackoverflow.com/questions/4069840/lambda-for-type-expressions-in-haskell}} due to the difficulty of this construct for type inference.
However, named functions at the type level do exist, and we will examine them later~\ref{subsec:families}.
Scala has a non-trivial trick\footnote{\href{https://stackoverflow.com/questions/8736164/what-are-type-lambdas-in-scala-and-what-are-their-benefits}{(stackoverflow) Scala type lambdas.}}\footnote{\url{https://stackoverflow.com/questions/9443004/what-does-the-operator-mean-in-scala}}, which makes this possible.
Scala 3, however, has added this capability directly to the language\footnote{\url{https://docs.scala-lang.org/scala3/reference/new-types/type-lambdas.html}}.

\subsubsection{Emulating type abstractions and applications (\mintinline{haskell}{Proxy})} \label{subsubsec:proxy}

In Haskell, extensions that allow manually writing type applications and abstractions appeared relatively recently\footnote{\href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/type_applications.html\#extension-TypeApplications}{TypeApplications}, \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/type_abstractions.html\#extension-TypeAbstractions}{TypeAbstractions}.}.
Before that, the following technique was used.

The standard library defines the type \mintinline{haskell}|Proxy| with one parameter.
This is a \vocab{phantom type parameter}~--- values of the corresponding type are not stored in the data structure, it only allows placing additional information at the type level\footnote{\url{https://wiki.haskell.org/Phantom_type}}.
Consequently, the uninformative constant \mintinline{haskell}|Proxy| can be annotated with the desired type and passed to a function to specialize the type parameter to the required type.
Or you can accept a \mintinline{haskell}|Proxy| and use \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/scoped_type_variables.html\#pattern-type-signatures}{ScopedTypeVariables} for type signatures in patterns\footnote{The type parameter actually has polymorphic kinds: \mintinline{haskell}{data Proxy (a :: k) = Proxy}, so that this technique works with types of arbitrary kinds (see also \ref{subsubsec:promotion}).}.
\begin{minted}{haskell}
    data Proxy a = Proxy

    id :: Proxy a -> a -> a
    ghci> :t id (Proxy :: Proxy Int)
    id (Proxy :: Proxy Int) :: Int -> Int

    id (Proxy :: Proxy ?\framebox{a}?) x = (x :: ?\framebox{a}?)
\end{minted}

Sometimes the proxy type is left polymorphic so as not to depend on \mintinline{haskell}{Data.Proxy}.
Instead of a concrete value, one may pass a specialized value \texttt{undefined}, and the receiver, not knowing the type, cannot force it (however, any occurrence of \texttt{undefined} in a term is too suspicious, so this is not a very good practice).
\begin{minted}{haskell}
    id :: proxy a -> a -> a
    id (_ :: proxy a) x = (x :: a)

    ghci> :t id (undefined :: Proxy Int)
    id (undefined :: Proxy Int) :: Int -> Int
\end{minted}

\subsubsection{First-class polymorphism} \label{subsubsec:first-class-polymorphism}

There is the possibility to write functions that accept other polymorphic functions as arguments.
The types of such functions are called \vocab{higher-rank types}, they can be used with the extension \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/rank_polymorphism.html}{RankNTypes}.
Thus, the type parameter of function \texttt{g} is determined by the function \texttt{f}, not by the caller of \texttt{f}:
\begin{minted}{haskell}
    f :: (forall a . a -> a) -> (Int, Char)
    f g = (g @Int 42, g @Char 'a') -- universal application for clarity
    ghci> f (\x -> x)
\end{minted}

The problem with higher-rank types is that their inference is undecidable, meaning Haskell's global type inference does not work in this case.
But if higher-rank types are annotated manually, the rest of the inference works as before.
For example, Church numerals have higher rank\footnote{\url{https://okmij.org/ftp/tagless-final/course/Boehm-Berarducci.html}}\footnote{Anyone interested in programming languages is invited to spend more than a month of their life on Oleg Kiselyov's site: \url{https://okmij.org/ftp/README.html}.}:
\begin{minted}{haskell}
    suc :: (forall a . (a -> a) -> a -> a) -> (a -> a) -> a -> a
    suc n s z = s (n s z)
\end{minted}

%! suppress = LineBreak
\begin{task}
    What rank does the type \mintinline{haskell}|Int -> (forall a . a -> a)| have?
\end{task}

Many problems associated with higher-rank types can be avoided by wrapping them.
For example, for Church numerals we can define a wrapper \mintinline{haskell}{newtype Church}.
Now code that works with the wrapper can be typed with first-rank types; only the constructor has a higher-rank type:
\begin{minted}{haskell}
    newtype Church = Church (forall a . (a -> a) -> a -> a)
    (+) :: Church -> Church -> Church -- rank 1
\end{minted}

Code like that can also be written in Java (Kotlin):
\begin{minted}{kotlin}
    interface Church { fun <a> fold(s: (a) -> a, z: a): a }
    fun plus(n: Church, m: Church): Church = object : Church {
        override fun <a> fold(s: (a) -> a, z: a): a = n.fold(s, m.fold(s, z))
    }
\end{minted}

By default, type parameters can only be instantiated to concrete types.
The extension \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/impredicative_types.html}{ImpredicativeTypes} allows specializing type parameters to polymorphic types (including \mintinline{haskell}|forall|s inside them) --- \vocab{impredicative application}.
\begin{minted}{haskell}
    runST :: (forall s. ST s a) -> a
    ($) :: forall a b . (a -> b) -> a -> b
    foo = runST $ ... -- only typechecks with ImpredicativeTypes
\end{minted}

Higher-rank types can be used as type-based escape analysis, that is, to prevent the user from passing some value outside a certain scope.
For example, Haskell provides the efficient \mintinline{haskell}{ST} monad, which within a restricted scope allows working with mutable memory cells~\cite{launchbury1995state}\cite[7.2, ST trick]{maguire-types}:
\begin{minted}{haskell}
    newtype ST s a = ST (IO a)
    runST :: (forall s. ST s a) -> a

    sumTo :: Int -> Int
    sumTo n = runST do
      ref <- newSTRef 0
      forM [0..n] \i -> modifySTRef ref (+ i)
      readSTRef ref
\end{minted}
Notice that if you try to return a reference to a mutable cell from \texttt{runST}, the resulting type will not pass the well-formedness check because it would contain the phantom parameter \texttt{s} that is not bound anywhere:
\begin{minted}{haskell}
    newSTRef :: a -> ST s (Ref s a)
    ghci> runST (newSTRef 0) :: Ref s Int -- error
\end{minted}
In practice, to distinguish such locally bound type variables, one uses the concept of levels\footnote{\url{https://okmij.org/ftp/ML/generalization.html}}~\cite{peytonjones2019typeinference}.

Higher-rank types together with impredicative application form \vocab{first-class polymorphism}, when polymorphic types can be used almost as freely as any other.
The classical Hindley-Milner global inference algorithm cannot handle this (and in general the problem is undecidable), so there is a variety of solutions that make different tradeoffs.
You can make inference local, relying only on nearby AST nodes and auxiliary type annotations~\cite{pierce2000local, christiansen2013bidirectional, dunfield2019sound}.
Or you can try to help global inference with additional preprocessing (Quick Look\footnote{\href{https://youtu.be/ZuNMo136QqI?si=qp8PAEeeF-bioCB_}{(youtube) A Quick Look at Impredicativity (Simon Peyton Jones)}}~\cite{serrano2020quick}, recently implemented in Haskell) or with additional controlling constructs (FreezeML~\cite{emrich2020freezeml}).

\subsubsection{Higher-order/kinded polymorphism}

Haskell also allows abstraction over types of arbitrary kinds, not only \mintinline{haskell}{Type}, both in \mintinline{haskell}{data} declarations (\vocab{higher-order/kinded types (HKT)}\footnote{\url{https://serokell.io/blog/kinds-and-hkts-in-haskell}}) and in polymorphic functions.
We will encounter many examples later.
For example, \mintinline{haskell}{Fix} has kind \mintinline{haskell}{(Type -> Type) -> Type}, and the catamorphism is abstracted over the arrow kind:
\begin{minted}{haskell}
    newtype Fix f = Fix (f (Fix f))
    cata :: forall (f :: Type -> Type) a . Functor f => (f a -> a) -> Fix f -> a
\end{minted}

Later we will study a technique that allows encoding higher-order kinds in a language that does not support them (see~\ref{subsubsec:simulating-hkt}).

\subsubsection{Generalized algebraic data types (GADTs)} \label{subsubsec:gadts}

Generalized algebraic data types (GADTs) allow attaching more information to data at the type level.
As a model example, consider the syntax of a tiny programming language.
Our goal is to prevent the construction of ill-typed syntax trees in Haskell.
\begin{minted}{haskell}
    data Expr = Const Int | IsZero Expr | If Expr Expr Expr
\end{minted}

As we know, data constructors in Haskell are ordinary functions, except that their implementation is generated by the compiler (allocation, field layout, ...).
Functions have types.
For example, \mintinline{haskell}{IsZero :: Expr -> Expr}.

Haskell has syntax for defining \mintinline{haskell}{data} by explicitly listing constructor types\footnote{\url{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/gadt_syntax.html\#gadt-style}}.
It is completely analogous to the form we saw earlier, only much more convenient for complex data structures.
The previously considered term type \mintinline{haskell}{Expr} looks like this:
\begin{minted}{haskell}
    data Expr where
      Const :: Int -> Expr
      IsZero :: Expr -> Expr
      If :: Expr -> Expr -> Expr -> Expr
\end{minted}

For polymorphic data structures, the list example uses the following syntax.
The name \texttt{elem} is needed only for documentation and cannot be used otherwise; it only marks the presence of a type parameter and allows giving it a kind manually\footnote{The kind may be omitted. Alternatively, you can omit parameter names and simply write \mintinline{haskell}{data List :: Type -> Type where ...}.}.
\begin{minted}{haskell}
    data List (elem :: Type) where
      Nil :: List a
      Cons :: a -> List a -> List a
\end{minted}

Let us add a phantom type parameter \texttt{ty} to \mintinline{haskell}{Expr}, indicating the Haskell type into which the expression should be interpreted, and use a GADT to assign concrete \texttt{ty} values to constructor result types.
Thus we state that a program built with \mintinline{haskell}{Const} evaluates to an integer, \mintinline{haskell}{IsZero} evaluates to a boolean, and a conditional evaluates to the type of its branches.
\begin{minted}{haskell}
    data Expr ty where
      Const :: Int -> Expr Int
      IsZero :: Expr Int -> Expr Bool
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty

    eval :: Expr ty -> ty
\end{minted}

Now we can write a safe typed interpreter.
Note that when pattern matching on constructors, the information about the type parameter is refined:\footnote{This uses the convenient \href{https://downloads.haskell.org/~ghc/9.0.1/docs/html/users_guide/exts/lambda_case.html}{LambdaCase} extension, which avoids introducing extra names.}
\begin{minted}{haskell}
    eval :: Expr ty -> ty
    eval = \case
      Const x  -> x           -- ty ?$\\sim$? Int
      IsZero t -> eval t == 0 -- ty ?$\\sim$? Bool
      If c t e -> if eval c then eval t else eval e
\end{minted}

Next we will examine how GADTs in Haskell are expressed through more basic language mechanisms~\ref{subsubsec:system-fc}.

\subsubsection{Type-level structures, data promotion} \label{subsubsec:promotion}

To gain greater control over program correctness, let us learn to encode arbitrary data structures at the type level.
As a model task, we will define a vector with length information.

First, define Peano-style natural numbers at the type level:
\begin{minted}{haskell}
    data Zero
    data Suc n
\end{minted}

\begin{task}
    How many inhabitants does the type \mintinline{haskell}|Suc (Suc Zero)| have?
\end{task}

Now we can define a vector type that carries length information:
\begin{minted}{haskell}
    data Vec (size :: Type) (elem :: Type) where
      VNil :: Vec Zero a
      VCons :: a -> Vec n a -> Vec (Suc n) a

    example :: Vec (Suc (Suc Zero)) Int
    example = VCons 1 (VCons 2 VNil)
\end{minted}

For such a type, for example, one can write a safe \mintinline{haskell}|vzip| function that only works on vectors of the same length:
\begin{minted}{haskell}
    vzip :: Vec n a -> Vec n b -> Vec n (a, b)
    vzip VNil VNil = VNil                                      -- n ?$\\sim$? Zero
    vzip (VCons x xs) (VCons y ys) = VCons (x, y) (vzip xs ys) -- n ?$\\sim$? Suc n'
\end{minted}

Note that in the other branches of \mintinline{haskell}|vzip|, equalities must arise that begin with different constructors, for example \mintinline{haskell}|Zero ?$\\sim$? Suc n|.
Since it is impossible to construct such function arguments, Haskell allows the corresponding branches to be omitted.

\begin{task}
    Write a function that appends an element to the end of a vector.
    Proceed step by step, filling in type holes and tracking the equalities that arise.
\end{task}

Currently the kind language that should control types is too poor.
Indeed, the kind \mintinline{haskell}|Suc| is \mintinline{haskell}|Suc :: Type -> Type|, so nothing prevents writing, for example, \mintinline{haskell}|Suc (Maybe Int)|.
At the same time it is too restrictive because it does not support polymorphism, which led to a lot of duplication like \mintinline{haskell}|Typeable (ty :: Type)|, \mintinline{haskell}|Typeable1 (ty :: Type -> Type)|, ...

Modern Haskell has the \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/type_data.html#extension-TypeData}{TypeData} extension, which allows declaring new types and kinds similarly to how \mintinline{haskell}{data} allows declaring new types.
\begin{minted}{haskell}
    type data Nat = Zero | Suc Nat
\end{minted}

Now the vector can be given a more precise kind:
\begin{minted}{haskell}
    data Vec (size :: Nat) (elem :: Type) where
      VNil :: Vec Zero a
      VCons :: a -> Vec n a -> Vec (Suc n) a
\end{minted}

\begin{task}
    What does \mintinline{haskell}|ghci> :k Vec| print?
\end{task}

Another way to achieve the same result is using \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/data_kinds.html#extension-DataKinds}{DataKinds}~\cite{yorgey2012giving}.
This extension automatically promotes all \mintinline{haskell}|data| declarations one level higher.
Specifically: any type constructor also becomes a kind, and any data constructor becomes a type constructor.
Thus, in the example with natural numbers, we can declare them normally and use them at the type level:
\begin{minted}{haskell}
    data Nat = Zero | Suc Nat
    ghci> :k Suc :: Nat -> Nat -- here it is clear that Suc is used as a type
\end{minted}

Because types and terms live in different namespaces in Haskell, one can name type constructors and data constructors identically.
However, if such a data type is promoted, ambiguity arises: do we mean the type or the promoted constructor?
Haskell allows explicitly indicating that we mean the promoted constructor with a leading apostrophe.
\begin{minted}{haskell}
    data T = T Nat
    ghci> :k T
    T :: Type      -- about the type constructor
    ghci> :k 'T
    'T :: Nat -> T -- about the promoted data constructor
\end{minted}

Not every \mintinline{haskell}|data| declaration is suitable for promotion, while \mintinline{haskell}|type data| declarations allow explicitly requesting a type-level structure and getting sensible errors if the declaration is written incorrectly.

In the case of promoting a polymorphic type, we obtain polymorphic kinds (\href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/poly_kinds.html}{PolyKinds}):
\begin{minted}{haskell}
    data [a] = [] | (:) a [a]
    ghci> :k '(:)
    '(:) :: forall k . k -> [k] -> [k]
\end{minted}

Data structures can also be kind-polymorphic.
Consider the type \href{https://hackage.haskell.org/package/tagged-0.8.8/docs/Data-Tagged.html#t:Tagged}{\mintinline{haskell}|Tagged|}, which allows attaching an additional type tag to the value type.
The kind of the tag may be arbitrary, so for example we can use type-level constants from \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/type_literals.html}{TypeLits} (another example of polykind usage we saw earlier in \ref{subsubsec:proxy}):
\begin{minted}{haskell}
    newtype Tagged (tag :: k) (a :: Type) = Tagged a
    ghci> :t Tagged
    Tagged :: forall k (tag :: k) a. a -> Tagged tag a

    example :: Tagged ("dbId" :: Symbol) Int
    example = Tagged 42
\end{minted}

Modern Haskell has ultimately arrived at the point where the type system does not distinguish between types and kinds (Fig.~\ref{fig:types-eq-kinds}).
In particular, \mintinline{haskell}|Type :: Type|.
This is required to extend Haskell in the direction of dependent-type programming by adding non-syntactic equivalences for kinds (\href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/poly_kinds.html#extension-TypeInType}{TypeInType}).

\subsection{Implementation of parametric polymorphism}

A \vocab{calling convention}\footnote{\url{https://en.wikipedia.org/wiki/Calling_convention}} is a set of agreements between how a function is compiled and how it must be called.
For example, a function takes two word-sized arguments and returns one word-sized result.
Then the generated low-level code may, for example, expect both arguments to be passed through a specific pair of registers and place the result in a third register.
In that case, the caller must provide the arguments in the correct registers and expect the result in a predetermined register.

In general, the calling convention of a function depends on the types of its arguments and result.
You need to know at least their size to decide whether to place them in registers or on the stack.
You need to know whether it is a pointer (\vocab{reference type}) or a value itself (\vocab{value type}) to understand how to handle it.
For data structures, you need to know field offsets.

Thus, implementing parametric polymorphism in a language is not a trivial task.
Different languages use different approaches, each with its own strengths and weaknesses.

\subsubsection{Monomorphization} \label{subsubsec:monomorphization}

\vocab{Monomorphization} is the most straightforward approach: compile polymorphic functions and structures for each set of type arguments.
Thus, if there are 100 different sets of type arguments with which a function is called, then its code will be compiled 100 times and occupy 100 times more space in the binary.
This is what C++ and Rust do, for example.

In fact it is even worse.
If the project is multi-module and consists of many compilation units (pieces that are compiled separately), the same specialization of the function for type arguments will be compiled again in every compilation unit where it is needed.
Then the linker will remove duplicates, which is also not the fastest or most efficient process.

\begin{itemize}
    \item[\positive] Generated code is maximally efficient for each type;
    \item[\positive] \texttt{is}-style runtime type checks are easy to implement at compile time (in other approaches this is difficult);
    \item[\negative] Compilation time becomes very large;
    \item[\negative] The resulting binary size increases significantly, which may be critical for some applications;
    \item[\negative] It may work inefficiently due to instruction cache pollution;
    \item[\negative] Polymorphic methods cannot exist in interfaces, because at the call site we do not know which concrete implementation should be specialized (similarly, higher-rank polymorphism does not work);
    \item[\negative] Polymorphic functions cannot be dynamically linked in general (they have no code before specialization);
    \item[\negative] In general, variance cannot be supported because the code is compiled for a concrete type and cannot in general work for an arbitrary subtype or supertype (if reference and value types may live in the same subtyping hierarchy).
\end{itemize}

Some languages (for example, C++ and Zig) do not treat instantiation as a hidden implementation detail of the language, but provide it as a tool for users.
This provides the following possibilities:
\begin{itemize}
    \item If values are allowed in types, instantiation can be used as a compile-time computation mechanism.
    \item If error checking is deferred to instantiation time, we get a kind of static duck typing.
    This allows not describing complex signatures of polymorphic functions.
    However, then functions for testing must be manually instantiated against all possible types, otherwise it is impossible to determine statically whether they compile for those types.
\end{itemize}

\subsubsection{Type erasure} \label{subsubsec:type-erasure}

One can do the opposite: unify the values that arrive at polymorphic functions and are stored in polymorphic data structures, instead of compiling code for each type.

Suppose each value is allocated on the heap and passed by pointer.
Then we can reuse the same code for different type arguments --- it will simply expect pointers.

\begin{itemize}
    \item[\positive] Each function is compiled exactly once --- fast;
    \item[\positive] It is possible to dynamically load new polymorphic functions and types and use them together;
    \item[\positive] Flexibility --- variance, polymorphic methods in interfaces, higher-rank types, etc. just work;
    \item[\negative] Heap allocation and pointer dereferencing can significantly slow down code;
    \item[\negative] Since type information is erased, one cannot do anything with a type argument without having its inhabitants (for example, query reflection information or perform an \texttt{is} check).
\end{itemize}

This approach is followed by the JVM, Haskell, and generally other functional languages due to its flexibility and compile-time speed.

The special problem is working with primitives and other value types, because each value has to be boxed first and then used in a polymorphic context.
Therefore languages fight this problem as best they can.
Some languages reduce the range of primitive values to reserve a bit that indicates whether it is a pointer or a value.
Code consults this bit to operate (similar to~\ref{subsubsec:swift-generics}).
This is done, for example, by OCaml and \href{https://koka-lang.github.io/koka/doc/book.html#sec-value-types}{Koka}.
Aggressive inlining together with other optimizations also helps~\cite{blanchet1999escape}.
Java, for example, is also trying to move carefully toward the possibility of monomorphization\footnote{\href{https://youtu.be/JI09cs2yUgY?si=MLkRs31mN1koXIu1}{Type Specialization of Java Generics - What If Casts Have Teeth?}}\footnote{\url{https://cr.openjdk.org/~jrose/values/parametric-vm.html}}.

\subsubsection{Hybrid approach} \label{subsubsec:hybrid}

C\# implements a hybrid approach\footnote{\href{https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/generics/generics-in-the-run-time}{Generics in the runtime (C\# programming guide).}}.
It distinguishes values stored on the heap --- reference types --- from values stored on the stack --- value types.
For the former it generates one specialization that works with pointers.
For each set of value types it lazily generates specializations at runtime.

Thus, traces of generics exist both in the CIL intermediate representation and in the runtime.

\begin{itemize}
    \item[\positive] Value types are stored and passed as-is without boxing;
    \item[\positive] Reflection over generics is available;
    \item[\positive] Compilation time is small;
    \item[\negative] Runtime instantiation slows execution;
    \item[\negative] Variance works only for reference types (which is odd --- there is ``correct'' subtyping and ``incorrect'' subtyping).
\end{itemize}

\subsection{Representation polymorphism} \label{subsec:representation-polymorphism}

As we already discussed above~\ref{subsubsec:type-erasure}, parametric polymorphism in Haskell is implemented as follows: all values are stored on the heap and passed to polymorphic functions by pointer.
However, if performance is important for computational code, that approach is not suitable because of the heavy load on the memory management subsystem and many indirections.
Therefore Haskell also allows writing code using unboxed values.
And if the calling convention is not essential, one can abstract over it and write one code path for both boxed and unboxed values~\cite{eisenberg2017levity}.

\subsubsection{Varieties of runtime representations in Haskell}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{figs/haskell-value-kinds}
    \caption{Kinds of values in Haskell with examples~\cite{eisenberg2017levity}.}
    \label{fig:haskell-value-kinds}
\end{figure}

Figure~\ref{fig:haskell-value-kinds} shows the classification of values in Haskell with examples of types.
\vocab{Unboxed types} are held and passed by value.
\vocab{Boxed types}, conversely, are passed by pointer and stored on the heap.
The ordinary \mintinline{haskell}|Int| is just a declaration of the following form, where \mintinline{haskell}|I#| is an ordinary constructor with an unusual name that contains an unboxed value.
\begin{minted}{haskell}
    data Int = I# Int#
\end{minted}

\vocab{Lifted types} may contain $\bot$ as a value.
In other words, they may represent suspended computations (the compiler and runtime provide this specially).
\vocab{Unlifted types}, in contrast, cannot be suspended.
Operations producing values of unlifted types are always strict.
The property lifted/unlifted is called \vocab{levity}.
To extend the exposition to eager languages, one can replace levity with boxity and everything remains valid.

A hash sign in type and function names is a convention that indicates that unlifted values are involved nearby\footnote{You need to enable the \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/magic_hash.html}{MagicHash} extension to use \# in identifiers.}.

Haskell also has unboxed tuples, which do not exist as runtime objects.
For example, the following function appears to return a pair of values, but in fact the compiler may place them, for example, in a pair of registers.
Accordingly, pattern matching on such tuples simply allows referring to each of those values.
\begin{minted}{haskell}
    divMod# :: Int -> Int -> (# Int, Int #)
    case divMod# n k of (# quot, rem #) -> ...
\end{minted}
Consequently, there is no distinction between differently nested unboxed tuples:
\begin{minted}{haskell}
    (# A, (# B, C #) #) ?$\equiv$? (# (# A, B #), C #) ?$\equiv$? (# A, B, C #)
\end{minted}

\subsubsection{Classification of values by runtime representation}

Values of different types may be arranged differently at runtime.
That is, we need some system for classifying types.
But such a system already exists in Haskell --- kinds.
We describe the domain as data structures and then promote it to the required level using DataKinds~\ref{subsubsec:promotion}.

The standard Haskell library \href{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/representation_polymorphism.html}{provides} the following data types:
\begin{minted}{haskell}
    TYPE :: RuntimeRep -> Type

    data Levity = Lifted | Unlifted

    data RuntimeRep = BoxedRep Levity
                    | IntRep | DoubleRep
                    | TupleRep [RuntimeRep]
                    | SumRep [RuntimeRep]
                    | ...

    type LiftedRep = BoxedRep Lifted

    type Type = TYPE LiftedRep
\end{minted}

\mintinline{haskell}|TYPE| is a magic type defined in the compiler.
It is parameterized by the runtime representation of values.
Now the familiar \mintinline{haskell}|Type| is simply a special case with boxed lifted values.

%! suppress = Quote
\begin{itemize}
    \item \mintinline{haskell}|Int :: TYPE (BoxedRep Lifted)| or \mintinline{haskell}|:: Type|
    \item \mintinline{haskell}|IntRep| and \mintinline{haskell}|DoubleRep| correspond to the runtime representation of numeric constants (depending on the processor architecture, integers and floating-point numbers may need to be placed in different special registers)\\ \mintinline{haskell}|Int# :: TYPE IntRep|
    \item \mintinline{haskell}|Maybe Int :: Type|
    \item \mintinline{haskell}|Maybe :: Type -> Type|
    \item \mintinline{haskell}|TupleRep| and \mintinline{haskell}|SumRep| are unboxed algebraic representations, parameterized by the representations of their stored values\\
    \mintinline{haskell}|(# Int, Bool #) :: TYPE (TupleRep '[LiftedRep, LiftedRep])|
    \item For simplicity, nested tuple types are not unified
    \begin{minted}{haskell}
        (# Int#, (# Int, Double# #) #)
          :: TYPE (TupleRep '[IntRep, TupleRep '[LiftedRep, DoubleRep]])
    \end{minted}
\end{itemize}

\subsubsection{Representation polymorphism}

Having exposed the runtime representation in the kind structure, we can now parameterize over it.
For example, the kind of the function arrow looks as follows\footnote{Disable simplifications: \mintinline{haskell}|ghci> :set -fprint-explicit-foralls -fprint-explicit-runtime-reps|}:
\begin{minted}{haskell}
    ghci> :k (->)
    (->) :: forall {q :: RuntimeRep} {r :: RuntimeRep}. TYPE q -> TYPE r -> Type
\end{minted}

\begin{task}
    Think about why the function has a boxed type.
    Can it be different?
    Could that be useful?
\end{task}

Unfortunately, Haskell imposes a rather strict restriction: binders cannot have a type that is polymorphic over runtime representation.
One can easily guess why --- it is impossible to generate code for a function that works with a parameter of an arbitrary runtime representation.
This can only be solved by monomorphization~\ref{subsubsec:monomorphization}, but Haskell avoids that approach\footnote{\url{https://gitlab.haskell.org/ghc/ghc/-/issues/14917}}.
The community is also trying to find other solutions\footnote{\url{https://mail.haskell.org/pipermail/haskell-cafe/2023-January/135770.html}} (something like~\ref{subsubsec:swift-generics}).

For example, initially the application operator was generalized only over the result type.
This does not cause problems, because the caller can infer the representation and generate the appropriate code:
\begin{minted}{haskell}
    ($) :: forall r a (b :: TYPE r). (a -> b) -> a -> b
    f $ ?\framebox{x}? = f x
\end{minted}
However, it was noticed that for the application operator one can obtain another implementation that does not use a levity-polymorphic binder\footnote{\url{https://gitlab.haskell.org/ghc/ghc/-/merge_requests/10131}}:
\begin{minted}{haskell}
    ($) :: forall ra rb (a :: TYPE ra) (b :: TYPE rb). (a -> b) -> a -> b
    ($) f = f
\end{minted}

Thus, in Haskell representation polymorphism is somewhat degenerate and helps only in a small number of cases, but not unimportant ones.
If one allows monomorphization over \mintinline{haskell}{RuntimeRep} parameters, one gets a system similar to the hybrid implementation of parametric polymorphism~\ref{subsubsec:hybrid}, only with greater programmer control over monomorphization.
