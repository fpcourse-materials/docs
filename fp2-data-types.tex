This chapter collects some general knowledge about types.
We will also obtain various equivalent representations of recursive data types (in other words, collections).
Many concepts are special cases of this variety.

Sections~\ref{subsec:variance}, ~\ref{subsec:isomorphism} mostly follow~\cite[chapter 1]{maguire-types}.

\subsection{Variance} \label{subsec:variance}

In this section we will consider the topic from the programming perspective~\cite[chapter 3]{maguire-types}, without doing justice to category theory.
The gap can be filled with the help of a wonderful article written in the style of a play~\cite{hinze2012functional}.

A \vocab{covariant functor} is a pair of some type constructor \texttt{F} and an operation on functions \texttt{fmap :: (a -> b) -> (F a -> F b)}.
Plus laws stating that \texttt{fmap} respects \texttt{id} and composition.

\begin{minted}{haskell}
    class Functor f where
      fmap :: (a -> b) -> (f a -> f b)
\end{minted}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.3\textwidth]{figs/functor}
\end{figure}

A \vocab{contravariant functor} is a pair of a type constructor and an operation on functions that reverses the arrow.
Plus corresponding laws.

\begin{minted}{haskell}
    class Contravariant f where
      contramap :: (a -> b) -> (f b -> f a)
\end{minted}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.3\textwidth]{figs/contra-functor}
\end{figure}

A type constructor can be declared a covariant or contravariant functor (or neither) with respect to a given type parameter depending on the form of the declarations of the corresponding data constructors.
Namely, on the sign of the positions in which that type parameter appears in the type.

Let us develop an intuitive understanding of position signs.
Type \mintinline{haskell}{A} appears in a positive position in \mintinline{haskell}{B} if its value can be extracted from \mintinline{haskell}{B}.
Conversely, type \mintinline{haskell}{A} appears in a negative position if its value must, on the contrary, be provided.
Let us consider position signs of types in basic type constructors:
\begin{center}
    \begin{tabular}[h]{|c|c|c|}
        \hline
        Type                             & sign of position \mintinline{haskell}{A} & sign of position \mintinline{haskell}{B} \\
        \hline
        \mintinline{haskell}{Either A B} & $+$                                  & $+$                                  \\
        \mintinline{haskell}{(A, B)}     & $+$                                  & $+$                                  \\
        \mintinline{haskell}{A -> B}     & $-$                                  & $+$                                  \\
        \hline
    \end{tabular}
\end{center}

Indeed, from a sum and a product one can extract components via pattern matching, and from an arrow one can obtain the right type by applying it to an argument.
At the same time, a value of the type on the left of the arrow must be provided.

Plus and minus obey intuitive algebraic rules when considering more complex types.
Let us consider the example \mintinline{haskell}{f :: ((A, B) -> C) -> (D, E)}.
\begin{itemize}
    \item Plus times plus gives plus.
    Indeed, one simply needs to apply two eliminations instead of one to obtain the desired type.
    In our example, to obtain \mintinline{haskell}{D}, one first applies the function, then destructs the pair.
    \item Plus times minus (and vice versa) gives minus.
    Indeed, \mintinline{haskell}{C} must be provided by us: \mintinline{haskell}{f (\ab -> provideC)}.
    \item Minus times minus gives plus.
    The pair \mintinline{haskell}{(A, B)} is provided to us: \mintinline{haskell}{f (\ab -> ...)}.
\end{itemize}

\begin{task}
    Verify that plus times minus gives minus.
\end{task}

Returning to functors, if a type parameter appears in the declaration only in positive positions, the type constructor can be declared a covariant functor with respect to that parameter.
If only in negative positions --- a contravariant functor.
If in both, then it cannot be declared any functor.
Accordingly, we call type parameters covariant, contravariant, and invariant.

\begin{task}
    Declare \mintinline{haskell}{instance Contravariant F} for \mintinline{haskell}{data F a = L (a -> ()) | R Int}.
\end{task}

Thus, a covariant functor can be understood as a computation whose result can be post-processed, and a contravariant functor as a computation whose arguments can be pre-processed.

A type with two positive parameters can be declared a \vocab{bifunctor}:
\begin{minted}{haskell}
    class Bifunctor f where
      bimap :: (a -> c) -> (b -> d) -> f a b -> f c d
\end{minted}

A type with two parameters, one positive and one negative, is a \vocab{profunctor}:
\begin{minted}{haskell}
    class Profunctor p where
      dimap :: (c -> a) -> (b -> d) -> p a b -> p c d
\end{minted}

Profunctors are certain generalizations of the function arrow.
For example, if we have an SQL query that takes data and returns a result, it can be declared a profunctor with the semantics of adding pre-processing of input data and post-processing of output data:
\begin{minted}{haskell}
    dimap serialize deserialize (query :: Sql Text Text) :: Sql Age [User]
\end{minted}

The concept of variance is also frequently encountered in object-oriented languages (and in subtyping theory in general) to denote the possibility of extending the subtyping relation to polymorphic types.

Indeed, the \vocab{subtyping relation} \texttt{B <: A} says that a value of type \texttt{B} can safely be used in a position where a value of type \texttt{A} is expected.
In other words, there exists a function \texttt{upcast :: B -> A}.
If the type constructor \texttt{F a} is covariant with respect to parameter \texttt{a}, then from \texttt{upcast} one can obtain \texttt{upcast' :: F B -> F A}.
That is, the subtyping relation also automatically includes \texttt{F B <: F A}.
The contravariant case is analogous.

    Verify in your favorite language with subtyping and variance support that minus times minus gives plus.
\end{task}

\subsection{Isomorphism} \label{subsec:isomorphism}

Suppose we need to design a function or a data model.
We start with a type declaration --- how should we choose it and from which alternatives?
First, let us understand when two types are interchangeable; for this, we consider the notion of isomorphism.

Two types \texttt{A} and \texttt{B} are called \vocab{isomorphic} (denoted \texttt{A $\iso$ B}) if and only if there exists a pair of functions \texttt{to :: A -> B} and \texttt{from :: B -> A} such that\footnote{Equality of terms can mean different things, for example $\alpha\beta\gamma$-equivalence. We will use \vocab{extensional equality} for functions --- two functions are equal when their results are equal on all inputs. \url{https://ncatlab.org/nlab/show/function+extensionality}}
\begin{minted}{c}
    to . from = id
    from . to = id
\end{minted}

In other words, one can establish a bijection between the inhabitants of such types.
It is easy to see that from a semantic point of view it does not matter which of the isomorphic types is used --- they can be substituted for each other by adding calls to the conversion functions.
Two such types contain the same ``amount of information.''
For example, the types \mintinline{haskell}|Bool| and \mintinline{haskell}|Maybe ()| are in this sense completely interchangeable.
Let us demonstrate this by exhibiting a pair of mutually inverse functions\footnote{One must not forget to show that the functions are mutually inverse, but this is done trivially by enumeration of inputs (possibly with induction) and reduction.}:
\begin{minted}{haskell}
    to :: Bool -> Maybe ()
    to b = if b then Just () else Nothing

    from :: Maybe () -> Bool
    from m = case m of Nothing -> False; Just () -> True
\end{minted}

Despite semantic interchangeability, to encode information about whether the user passed a particular flag to the program, we would most likely use the type \mintinline{haskell}|Bool| due to non-functional considerations of code readability.
Analogously, one can consider efficiency considerations.

A categorical perspective on the matter can be found in~\cite{hinze2010reason}.
We, however, adhere to the set-theoretic interpretation of types.

\subsubsection{Cardinality: sums, products, exponentials} \label{subsubsec:cardinality}

Types can be thought of as syntax for writing sets, and the terms inhabiting them as syntactic representations of elements of those sets.
Thus the term \mintinline{haskell}|(True, False)| is a representation of an element of the set of pairs, written in type syntax as \mintinline{haskell}|(Bool, Bool)| (instead of the mathematical $\mathbb{B}\times\mathbb{B}$).
Or the term \mintinline{haskell}|\x -> x + 1| is a representation of the function adding one from the set of functions over integers, written as \mintinline{haskell}|Integer -> Integer| (instead of the mathematical $\mathbb{Z}\to\mathbb{Z}$).

Note that two types are isomorphic if the corresponding sets have the same number of elements.
Moreover, there are $n!$ such isomorphisms in the case of finite sets.
Let us learn to determine the number of such elements.
Using $|\cdot|$ we will denote the \vocab{cardinality} of a type --- the number of elements in the corresponding set.

\begin{center}
    \begin{tabular}{|l|c|}
        \hline
        Type and its declaration                                                                                                                                                                            & cardinality \\
        \hline
        \mintinline{haskell}{data Void}                                                                                                                                                                 & $0$            \\
        \mintinline{haskell}{data Unit = Unit}\footnote{\mintinline{haskell}|Unit| is written in Haskell using special syntax \mintinline{haskell}|()|, meaning something like an empty tuple.} & $1$ \\
        \mintinline{haskell}{data Bool = False | True}                                                                                                                                                  & $2$            \\
        \hline
    \end{tabular}
\end{center}

The idea of algebraic data types is that complex types can be built from simple ones using the operation $+$ (``or'') and the operation $\times$ (``and'')\footnote{\url{https://stanford-cs242.github.io/f18/lectures/02-2-algebraic-data-types.html}}:
\begin{center}
    \begin{tabular}{|l|c|}
        \hline
        Type                                                      & cardinality   \\
        \hline
        \mintinline{haskell}{data Either a b = Left a | Right b} & $|a| + |b|$      \\
        \mintinline{haskell}{data Pair a b = Pair a b}           & $|a| \times |b|$ \\
        \hline
    \end{tabular}
\end{center}

Let us count the number of inhabitants of various types (you can verify the conclusion by enumerating all terms manually):
\begin{itemize}
    \item \mintinline{haskell}{|Either Unit (Either Bool Bool)| = |Unit| + (|Bool| + |Bool|) = 5}.
    \item \mintinline{haskell}{|Pair (Either Bool Unit) (Pair Unit Void)| = 0} --- the type \mintinline{haskell}|Void| is uninhabited, as is a tuple containing it.
    \item If \mintinline{haskell}{data Example = FirstAlternative Bool | AnotherOne Unit Bool Bool}, then \\\mintinline{haskell}{|Example| = |Bool| + |Unit| * |Bool| * |Bool| = 2 + 1 * 2 * 2 = 6}.
\end{itemize}

The function arrow is called the exponential type.
Indeed, combinatorially the number of inhabitants of \mintinline{haskell}|A -> B| is computed as \[|A \to B| = |B|^{|A|}\]

So how should one design types?
There are several considerations:
\begin{itemize}
    \item The type should have no fewer elements than the domain, so that all necessary objects are representable.
    \item The type should have as few elements as possible that are not in the domain, so that the error space is minimal.
    \item Then among isomorphic types, the optimal one is chosen based on non-functional requirements.
\end{itemize}

Per the second rule, before manipulating a domain object one should first convert the data describing it into the most structured representation possible --- the one that provides the strongest guarantees\footnote{\url{https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/}}.

\subsubsection{Algebraic representation of a type} \label{subsubsec:type-algebra}

As we saw above, to show the existence of an isomorphism between two types one can either exhibit a pair of mutually inverse functions, or show that the cardinalities of the two types coincide.
In this section we will learn to associate an algebraic expression with a type, reflecting its structure and cardinality.
Thus, we will be able to obtain equivalent expressions via syntactic transformations of formulas, from which we will recover types that are guaranteed to be isomorphic to the given one\footnote{\url{https://codewords.recurse.com/issues/three/algebra-and-calculus-of-algebraic-data-types}}.

The algebraic representation is based on computing cardinalities of types.
In effect, we forget information inessential for isomorphism about the names of data constructors and type constructors, i.e.\ we transition to structural typing.
\begin{center}
    \begin{tabular}{|p{0.5\textwidth}|c|}
        \hline
        Type                                                      & algebraic formula      \\
        \hline
        \mintinline{haskell}{data Void}                          & $0$                         \\
        \mintinline{haskell}{data Unit = Unit}                   & $1$                         \\
        \mintinline{haskell}{data Bool = False | True}           & $1 + 1$ (denote as $2$) \\
        \mintinline{haskell}{data Maybe a = Nothing | Just a}    & $1 + a$                     \\
        \mintinline{haskell}{data Either a b = Left a | Right b} & $a + b$                     \\
        \mintinline{haskell}{data Pair a b = Pair a b}           & $a \times b$                \\
        \mintinline{haskell}{a -> b}                             & $b^a$                       \\
        \hline
    \end{tabular}
\end{center}

\begin{task}
    Write the following type in algebraic form:
    \begin{minted}{haskell}
        data T a b = Undefined | Defined a (a -> b)
    \end{minted}
\end{task}

As the equivalence relation, we use isomorphism of the corresponding types.
Under this interpretation, the classical properties of algebraic operations are preserved (Fig.~\ref{fig:school-alg}).
Indeed, for example:
\begin{minted}{haskell}
    -- ?$(c^b)^a \iso c^{a\times b}$?
    to :: (a -> b -> c) -> (a, b) -> c
    to = uncurry
    from :: ((a, b) -> c) -> a -> b -> c
    from = curry
\end{minted}

    \includegraphics[width=0.4\textwidth]{figs/school-alg}
    \caption{Laws of school algebra for nostalgia's sake~\cite{hinze2010reason}.}
    \label{fig:school-alg}
\end{figure}

\begin{task}
    Show that $(a + b) + c \iso a + (b + c)$.
\end{task}

\begin{task}

\end{task}

An interesting observation is that functions can be used as data structures, in accordance with the isomorphism $c^{a + b} \iso c^a\times c^b$.
Indeed, in that case the function argument serves as an index (its cardinality must coincide with the size of the collection).
\begin{minted}{haskell}
    -- ?$a \times a \iso a^2$?
    get :: (a, a) -> (Bool -> a)
    get (x, y) idx = if idx then x else y
    tabulate :: (Bool -> a) -> (a, a)
    tabulate f = (f True, f False)
\end{minted}

The \vocab{canonical representation of a type} is a sum of products of types:
\[
    \sum_{i}\prod_{j} t_{ij}
\]
The canonical representation is a kind of normal form in which algebraic types can be written (any algebraic type can be reduced to it using the rules).
It is easy to recognize in it the form of \mintinline{haskell}{data} declarations in Haskell.

Remarkably, even the derivative of an algebraic type has a perfectly understandable semantics.
It is the context of a zipper, a data structure similar to an iterator that allows navigating through a data structure of arbitrary shape~\cite{huet1997zipper, mcbride2001derivative, abbott2003derivatives}.

\subsection{Recursive types} \label{subsec:recursive-types}

Recursive types, similarly to recursive terms, can include themselves in their definitions.
In other words, a recursive type is isomorphic to some other type in which it itself appears as a subtype.
\begin{minted}{haskell}
    fac n = if n <= 1 then 1 else n * ?\framebox{fac}? (n - 1)
    data Nat = Zero | Suc ?\framebox{Nat}?
\end{minted}

We will mostly look at recursive types from a practical perspective.
However, their formal type-theoretic description, category-theoretic and set-theoretic interpretations are of independent interest~\cite[part 4]{pierce2002types}.

\subsubsection{Just a list}

Consider the classical functional list.
A list is either a collection of zero elements, or one, or two\ldots
Algebraically this can be written as follows:
\[
    L = 1 + a + a^2 + a^3 + \ldots
\]
In effect we obtained a type with an infinite expression.
Let us work with it as a formal series.
Factor out $a$:
\[
    L = 1 + a \times (1 + a + a^2 + \ldots)
\]
Notice that the expression in parentheses represents a list, yielding the following recursive equation\footnote{Alternatively, one can obtain the same result by noticing that we are dealing with a Taylor series \url{https://codewords.recurse.com/issues/three/algebra-and-calculus-of-algebraic-data-types}.}:
\[
    L = 1 + a \times L
\]
It is easy to see that this is in fact the familiar list definition from Haskell:
\begin{minted}{haskell}
    data List a = Nil | Cons a (List a)
\end{minted}

Let us obtain a finite non-recursive representation of the type $L$.
In effect, we need to obtain a type isomorphic to a type that includes the original:
\[
    L \iso 1 + a \times L
\]
Let us extend the type language with abstraction (polymorphism) and solve the resulting recursive equation in the style of $\lambda$-calculus, using a fixpoint combinator:
\[
    L = FIX\ap\lambda r\ldotp 1 + a \times r
\]

Let us encode this in Haskell.
As the recursion combinator we take \mintinline{haskell}{data FixList a}:
\begin{minted}{haskell}
    type Shape a r = Either () (a, r) -- ?$\lambda a r\ldotp 1 + a\times r$?
    data FixList a = In (Shape a (FixList a))
    -- FixList a ?$\iso$? Shape a (FixList a) ?$\iso$? Shape a (Shape a (FixList a)) ?$\iso$? ...

    example :: FixList Int -- [1, 2, 3]
    example = In (Right (1, In (Right (2, In (Right (3, In (Left ())))))))
\end{minted}

% todo step-by-step pictures showing fold and unfold in action

Thus, we have separated the list definition into two parts: one is responsible for the shape of the type, and the other for recursion\footnote{The technique of abstracting over the ``recursive self-reference'' is called \vocab{open recursion}. This gives the user more control. For example, at the term level, the recursion combinator can count the number of recursive calls and abort the computation when some limit is exceeded.}.
The shape can be reused in the definition of a fold:
\begin{minted}{haskell}
    foldr :: (Either () (a, r) -> r) -> FixList a -> r
    foldr phi (In shape) = case shape of
      Left () -> phi (Left ())
      Right (x, xs) -> phi (Right (x, foldr phi xs))
    -- compare with the classical definition
    foldr :: r -> (a -> r -> r) -> [a] -> r
    foldr ini f list = case list of
      [] -> ini
      x:xs -> f x (foldr ini f xs)
\end{minted}

Indeed, a fold in the general sense allows replacing each data constructor in the tree with some function.
The result is a computation that has access to the entire contents of the data structure and returns an aggregated result:
\begin{center}
    \includegraphics[width=0.5\textwidth]{figs/foldr}
\end{center}

That is, the number and types of arguments to the fold depend on the ``shape'' of the type being folded.
In the case of a list, a nullary function is needed in place of \mintinline{haskell}{Nil} and a binary one in place of \mintinline{haskell}{Cons}.
We represent these two functions as one using the shape type.
Compare:
\begin{minted}{haskell}
    foldr                   0 (      \e  r  -> e + r)
    foldr (\case Left () -> 0; Right (e, r) -> e + r)
\end{minted}

\subsubsection{Fixpoint of a functor} \label{subsubsec:functor-fixpoint}

Let us abstract \mintinline{haskell}{FixList} over the shape type:
\begin{minted}{haskell}
    newtype Fix :: (Type -> Type) -> Type
    newtype Fix f = In { out :: f (Fix f) }

    data ListF a r = Nil | Cons a r
    type List a = Fix (ListF a)
\end{minted}

\begin{task}
    What will the types of \mintinline{haskell}|In| and \mintinline{haskell}|out| be?
\end{task}

One can show that \mintinline{haskell}{[a] ?$\iso$? List a}:
\begin{minted}{haskell}
    to :: [a] -> List a
    to = \case
      [] -> In Nil
      x:xs -> In $ Cons x (to xs)

    from :: List a -> [a]
    from (In shape) = case shape of
      Nil -> []
      Cons x xs -> x : from xs
\end{minted}

The shape type can be made a functor in its last parameter.
This will allow us to subsequently replace occurrences of subtrees with something useful.
\begin{minted}{haskell}
    instance Functor (ListF a) where
      fmap :: (rec -> other) -> ListF a rec -> ListF a other
      fmap f = \case
        Nil -> Nil
        Cons x xs -> Cons x (f xs)
\end{minted}

\subsubsection{Recursion schemes} \label{subsubsec:recursion-schemas}

Just as structured imperative programming, compared to undisciplined use of \texttt{goto}, helps in reasoning about programs, so \vocab{recursion schemes} allow one to algebraically describe properties of recursive functions, as opposed to ``unstructured'' recursion\footnote{\url{https://reasonablypolymorphic.com/blog/recursion-schemes/index.html}}~\cite{meijer1991functional, meijer1995bananas}.

The overarching idea was to formulate required properties and compute the needed programs similarly to how mathematicians find solutions to differential equations.
However, this idea did not gain the necessary development and adoption (though mastering the algebraic approach is generally useful~\cite{maguire-algebra}).
Nevertheless, this knowledge, on the one hand, gives a deeper understanding of recursion, and on the other hand, will serve us when examining and solving the main problem of this course --- the expression problem.

The universal fold is called a \vocab{catamorphism}.
A catamorphism first recursively folds the subtrees, reaching them via \mintinline{haskell}|fmap|, and leaves fold results of type \texttt{a} in place of the former occurrences of subtrees.
The result is a value of type \texttt{f a}, where \texttt{f} is some shape functor.
Then a function of type \texttt{f a -> a} is applied, which determines how to fold one layer of the recursive structure when the subtrees have already been folded.
\begin{minted}{haskell}
    cata :: Functor f => (f a -> a) -> Fix f -> a
    cata phi = phi . fmap (cata phi) . out
\end{minted}

In other words, \mintinline{haskell}{cata} replaces all \mintinline{haskell}{In} constructors with the function \texttt{phi}, which contains information about how to react to different constructor variants in the tree:
\begin{minted}{haskell}
    example           = In  (Cons 1 (In  (Cons 2 (In  (Cons 3  (In  Nil))))))
    cata phi example ?$\eqbeta$? phi (Cons 1 (phi (Cons 2 (phi (Cons 3 (phi Nil))))))
\end{minted}

For example, summing a list looks as follows (Fig.~\ref{fig:cata-step}):
\begin{minted}{haskell}
    sum :: List Int -> Int
    sum = cata \case
      Nil -> 0
      Cons x result -> x + result
\end{minted}

\begin{figure}
    \centering
    \includegraphics[width=0.8\textwidth]{figs/cataStep.excalidraw}
    \caption{A catamorphism reuses occurrences of recursive subtrees to store the fold results of the corresponding subtrees.}
    \label{fig:cata-step}
\end{figure}

The function \texttt{f a -> a} is called an \vocab{f-algebra}.
Indeed, if we take the signature of an algebra as the functor \texttt{f} and the carrier as \texttt{a}, then the f-algebra defines some interpretation of the signature:
\begin{minted}{haskell}
    data MonoidSig carrier = Mempty | Mappend carrier carrier

    interpretSig :: MonoidSig Int -> Int
    interpretSig = \case Mempty -> 0; Mappend l r -> l + r
\end{minted}

In contrast to the universal fold, one can construct an \vocab{anamorphism} --- a universal unfold (analogous to \texttt{unfold} for a list).
Here the f-coalgebra (the arrow in the opposite direction) shows how to obtain one layer of a data structure from some seed value, where in place of recursive references there will be seeds from which subtrees will subsequently grow.
The anamorphism first unfolds one layer, and then recursively unfolds all the subtrees:
\begin{minted}{haskell}
    ana :: Functor f => (s -> f s) -> s -> Fix f
    ana psi = In . fmap (ana psi) . psi
    -- compare with the classical definition of list unfold
    unfoldr :: (s -> Maybe (a, s)) -> s -> [a]
\end{minted}

\begin{task}
    Implement an anamorphism that builds a list from $0$ to a given $n$.
\end{task}

One also introduces the \vocab{hylomorphism}, which allows describing an arbitrary recursive computation.
A hylomorphism is defined as a composition of an anamorphism and a catamorphism.
First, the anamorphism builds an explicit tree representing the call tree of some recursive procedure, then the catamorphism folds it into the result.
\begin{minted}{haskell}
    hylo :: Functor f => (a -> f a) -> (f b -> b) -> a -> b
    hylo psi phi = cata phi . ana psi
\end{minted}

For example, computing factorial can be implemented as follows:
\begin{minted}{haskell}
    fac n = hylo
      (\n -> if n > 0 then Cons n (n - 1) else Nil)
      (\case Nil -> 1; Cons n acc -> n * acc)
\end{minted}

One can introduce many more different recursion schemes\footnote{\url{https://wiki.haskell.org/Zygohistomorphic_prepromorphisms}} and describe their properties.
However, we will stop here for now.

An interesting fact: a catamorphism represents the set-theoretic principle of induction, and an anamorphism represents coinduction, if one takes the function as the set embedding~\cite[chapter 21]{pierce2002types}.

\subsection{Everything through folds} \label{subsec:all-folds}

It turns out that using a catamorphism one can obtain an isomorphism between data structures and their folds:
\mintinline{haskell}|Fix f ?$\iso$? forall a . (f a -> a) -> a|.
\begin{minted}{haskell}
    to :: Functor f => Fix f -> (forall a . (f a -> a) -> a)
    to = flip cata

    from :: (forall a . (f a -> a) -> a) -> Fix f
    from g = g In
\end{minted}

For example, the following two lists are equivalent (all \mintinline{haskell}{In} constructors are replaced with the given algebra):
\begin{minted}{haskell}
    data ListF elem rec = Nil | Cons elem rec

    xs1 :: Fix (ListF Int)
    xs1 = In (Cons 1 (In (Cons 2 (In (Cons 3 (In Nil))))))

    xs2 :: (ListF Int a -> a) -> a
    xs2 = \alg -> alg (Cons 1 (alg (Cons 2 (alg (Cons 3 (alg Nil))))))

    ghci> xs2 @Int \case Nil -> 0; Cons x acc -> x + acc
    6
\end{minted}

Now let us get rid of the shape functor.
It is a non-recursive type that can be presented in canonical form (see~\ref{subsubsec:type-algebra}):
\[
    f\ap a \iso \sum_{i}\prod_{j} (t_{ij}\ap a)
\]
Then the algebra can be written as follows:
\[
    f\ap a\to a\iso a^{\sum_{i}\prod_{j} (t_{ij}\ap a)} \iso \prod_{i}a^{\prod_{j} (t_{ij}\ap a)}
\]
Products remain, which can be eliminated using currying, yielding \vocab{Church encoded} data structures.
For example, for a list we have:
\begin{align*}
    \text{\texttt{(ListF elem a -> a) -> a}}
    \iso a^{\displaystyle a^{\displaystyle 1 + elem\times a}}
    \iso a^{\displaystyle a\times a^{\displaystyle elem\times a}}
    \iso \left( a^{\displaystyle a} \right)^{\displaystyle \left(\left( a^{\displaystyle a}\right)^{\displaystyle elem}\right)} \\
    \iso \text{\texttt{a -> (elem -> a -> a) -> a}}
\end{align*}

We have obtained nothing other than a Church list\footnote{\url{https://en.wikipedia.org/wiki/Church_encoding}}\footnote{\url{https://okmij.org/ftp/tagless-final/course/Boehm-Berarducci.html}}.
A data structure without a single constructor!\footnote{In fact this is not at all surprising, if one recalls that first-class functions are represented as closures that contain data. We have obtained the same singly linked list, but using closures.}
Let us rewrite the list we already know once more:
\begin{minted}{haskell}
    xs3 :: a -> (Int -> a -> a) -> a
    xs3 = \ini f -> f 1 (f 2 (f 3 ini))
\end{minted}

\begin{task}
    Which familiar standard list function on a \mintinline{haskell}{data} list returns a Church list?
\end{task}

Let us try to intuitively understand what all this means.
Notice that a Church list accepts functions corresponding to pattern-matching branches or arguments of the folding function.
Instead of constructors, the corresponding functions are called directly.
That is, instead of creating a data structure and delivering it to the site of deconstruction (pattern matching), we \point{deliver the deconstruction site to the construction site}, and it turns out that there is nothing to construct after all.

We have already worked with the reverse process, defunctionalization, when first-class functions were turned into constructor calls, and their bodies into pattern-matching branches~\ref{subsubsec:defunctionalization}.
One can notice that here we are dealing with the reverse process, \vocab{refunctionalization}, when instead of constructor calls the corresponding interpreting code is called directly~\cite{DANVY2009534}.

From a technical perspective, we have understood that conditional branching (if, pattern matching, switch constructs) and virtual calls (closure calls, method calls on interfaces) are interchangeable.

It is also worth noting that the isomorphism \mintinline{haskell}|Fix f ?$\simeq$? forall d . (f d -> d) -> d| is a generalization of the isomorphism \mintinline{haskell}{a ?$\sim$? forall r . (a -> r) -> r} (with \mintinline{haskell}{f = Const a}), which is the foundation of the CPS transformation that we consider later in the chapter~\ref{sec:continuations}.

\subsubsection{Deforestation \& list fusion} \label{subsubsec:deforestation-fusion}

In functional programming we build new functions by composing existing, simpler functions.
This approach allows reusing implemented functionality, reducing code complexity and the probability of errors.
However, it can lead to unnecessary overhead from allocation and deconstruction of intermediate data structures.

For example, compare the following two implementations.
The first is preferable from a code quality standpoint, but it creates an intermediate list during execution:
\begin{minted}{haskell}
    all p xs = and (map p xs)
    -- or the fused version
    all p [] = True
    all p (x:xs) = p x && all p xs
\end{minted}

Obviously, this is the job of an optimizing compiler to turn good code with abstractions into fast code.
The optimization that eliminates (intermediate) data structures (trees) from programs is called \vocab{deforestation}.
As a result, two functions are said to ``fuse.''

The term and the first deforestation algorithm were proposed by Philip Wadler~\cite{wadler1988deforestation}; it is based on several simple rewriting rules aimed at obtaining the situation \mintinline{haskell}{case K args of ...}, and aggressive inlining (see examples of operation in Fig.~\ref{fig:deforestation-examples}).
However, this algorithm can lead to exponential code blowup and may not terminate in the presence of recursive calls\footnote{Deforestation is a special case of supercompilation~\cite{supercomp}, which in turn is a generalization of a large number of compiler optimizations.}.
For the algorithm to terminate, programs must be written in a certain strict form called treeless.

\begin{figure}
    \centering
    \includegraphics[width=0.6\textwidth]{figs/deforestation-examples}
    \caption{Examples of the deforestation algorithm in action~\cite{wadler1988deforestation}.}
    \label{fig:deforestation-examples}
\end{figure}

Let us focus on lists and consider more practical solutions\footnote{\url{https://markkarpov.com/tutorial/ghc-optimization-and-fusion.html}}.
The first obvious solution would be to add a special rewrite rule for each pair of list functions (see~\ref{subsubsec:rules}), deforesting using algebraic properties of list transformations.
However, there would be exponentially many such rules.
\begin{minted}{haskell}
    {-# RULES
    "map/map" forall f g xs. map f (map g xs) = map (f . g) xs
      #-}
\end{minted}

The modern deforestation technique in Haskell --- fold/build list fusion~\cite{gill1993short} --- instead of using many algebraic rules, defines a universal way of constructing and deconstructing a list.
We deconstruct a list using \mintinline{haskell}|foldr|.
We construct using the function \mintinline{haskell}|build|:
\begin{minted}{haskell}
    build :: (forall b . (a -> b -> b) -> b -> b) -> [a]
    build g = g (:) []
\end{minted}
For example, the list \mintinline{haskell}{[1, 2, 3]} and the function \mintinline{haskell}{map} are now written as follows\footnote{In the Haskell standard library, list functions are written normally, but alongside them are \texttt{RULES} rules (see~\ref{subsubsec:rules}) that substitute their implementation with fold/build versions.}:
\begin{minted}{haskell}
    list123 :: [Int]
    list123 = build \s z -> s 1 (s 2 (s 3 z))

    map :: (a -> b) -> [a] -> [b]
    map f xs = build \s z -> foldr (\x acc -> s (f x) acc) z xs
\end{minted}
One can notice that the input to \texttt{build} is a Church list, hence the unsurprising law:
\begin{minted}{haskell}
    foldr f ini (build g) ?$\equiv$? g f ini
\end{minted}

Thus, we eliminated list construction by replacing constructor calls with calls to folding functions.

Deforestation can also be performed manually (see~\ref{fig:cpp-deforestation}).

\subsubsection{Visitor pattern} \label{subsubsec:visitor}

Consider some tree and its fold:
\begin{minted}{haskell}
    data Tree a = Leaf | Node a [Tree a]
    foldTree :: Tree a -> r -> (a -> [r] -> r) -> r
\end{minted}

Let us rewrite and rename:
\begin{minted}{haskell}
    data Visitor a r = Visitor { onLeaf :: r, onNode :: a -> [r] -> r }
    visitTree :: Tree a -> Visitor a r -> r
\end{minted}

To make this look even more like OOP style, the tree itself should be given by a fold (as an interface with a \texttt{visit} function), and different nodes by concrete implementations (descendant objects):
\begin{minted}{haskell}
    data Tree a = Tree { visit :: forall r . Visitor a r -> r }

    leaf :: Tree a
    leaf = Tree { visit = \Visitor{onLeaf} -> onLeaf }

    node :: a -> [Tree a] -> Tree a
    node x ts = Tree { visit = \v@Visitor{onNode} -> onNode x (map (`visit` v) ts) }
\end{minted}

For clarity, let us show this code in Kotlin as well:
\begin{minted}{kotlin}
    interface Visitor<a, r> {
        fun onLeaf(): r
        fun onNode(x: a, subtrees: List<r>): r
    }

    interface Tree<a> {
        fun <r> visit(visitor: Visitor<a, r>): r
    }
    class Leaf : Tree<Nothing> {
        override fun <r> visit(visitor: Visitor<Nothing, r>): r = visitor.onLeaf()
    }
    class Node<a>(val value: a, val subtrees: List<Tree<a>>) : Tree<a> {
        override fun <r> visit(visitor: Visitor<a, r>): r =
            visitor.onNode(value, subtrees.map { it -> it.visit(visitor) })
    }
\end{minted}

\subsection{Everything through unfolds} \label{subsec:all-unfolds}

Recall that there exists a universal unfold --- the anamorphism, which from a generating procedure produces an entire data structure (see~\ref{subsubsec:recursion-schemas}).
\begin{minted}{haskell}
    ana :: Functor f => forall s . (s -> f s) -> s -> Fix f
    ana psi = In . fmap (ana psi) . psi
\end{minted}

Let us bring the function \texttt{ana} to a type of the form \mintinline{haskell}{A -> B}, so that it is then easier to study the arrow \mintinline{haskell}{B -> A}.
To do this, we uncurry and move the quantifier to the left of the arrow (it changes to the opposite):
\begin{minted}{haskell}
    ana :: Functor f => (exists s . (s, s -> f s)) -> Fix f
\end{minted}
Let us encode the existential quantifier using a new type (see~\ref{subsubsec:existentials}) and rewrite the anamorphism to work with it:
\begin{minted}{haskell}
    data Box f where
      --     exists s. (s,    s -> f s)
      Box :: forall s . s -> (s -> f s) -> Box f

    ana' :: Functor f => Box f -> Fix f
    ana' (Box currSeed psi) =
      In $ (\nextSeed -> ana' (Box nextSeed psi)) <$> psi currSeed
\end{minted}
Now let us build an isomorphism between data structures and their trivial unfolds, which each time return the next layer of the given structure, \mintinline{haskell}|Fix f ?$\simeq$? Box f|:
\begin{minted}{haskell}
    to :: Fix f -> Box f
    to x = Box x out

    from :: Functor f => Box f -> Fix f
    from = ana'
\end{minted}
Thus, we have obtained evidence that any recursive data structure can be, at least trivially, represented as \mintinline{haskell}{Box f}.
Such a representation is sometimes called \vocab{co-Church encoding}~\cite{gibbons2008unfolding}.

For example, an infinite lazy list of natural numbers can be defined as follows.
Note that here we \point{do not rely on Haskell's laziness}, which means we can use this technique in eager languages as well.
\begin{minted}{haskell}
    nats :: Box (ListF Int)
    nats = Box 0 \curr -> Cons curr (curr + 1)
\end{minted}

\begin{task}
    Implement a lazy function \\ \mintinline{haskell}{take :: Int -> Box (ListF Int) -> Box (ListF Int)}.
\end{task}

In other words, infinite data structures can be represented as procedures that lazily generate one layer of a recursive structure at a time on demand.

\subsubsection{Abstract data types} \label{subsubsec:abstract-data-types}

Consider the case when the shape functor is a product:
\[
    \text{\texttt{s -> f s}} \iso \left( \prod_{i}(t_i\ap s) \right)^{\displaystyle s} \iso \prod_i(s\to t_i\ap s)
\]
That is, the coalgebra is equivalent to a tuple of functions.
Thus, \mintinline{haskell}{Box} is nothing other than an \point{abstract data type (ADT)}: it contains hidden state of unknown nature and a set of operations for working with it~\cite{gibbons2008unfolding}.
In fact, we have already encountered such a construction earlier, when we discussed existential types~\ref{subsubsec:existentials} (there we used type class instances as tuples of functions).

OOP objects can also be viewed through coalgebras.
More about the relationship between objects and abstract data types can be found in~\cite{cook2009understanding}.

\subsubsection{Stream fusion} \label{subsubsec:stream-fusion}

Earlier we considered the foldr/build list fusion optimization that eliminates intermediate lists (see~\ref{subsubsec:deforestation-fusion}).
However, this technique does not work for many popular functions, such as \texttt{zip} (one needs to coroutine between two algebras) or \texttt{take} (one needs to abort the fold at a certain point).

Later, a technique using the co-structure of a list --- an unfold or \mintinline{haskell}{Stream} --- was proposed\footnote{\url{https://markkarpov.com/tutorial/ghc-optimization-and-fusion.html}}~\cite{coutts2007stream}:
\begin{minted}{haskell}
    data ListF a r = Nil | Cons a r
    type MyStream a = Box (ListF a) -- ?$\exists$?s . (s -> ListF a s, s)
    -- ?$\iso$?
    data Step a s = Done | Yield a s
    data Stream a where
      Stream :: forall s . (s -> Step a s) -> s -> Stream a

    stream :: [a] -> Stream a
    stream xs = Stream (\case [] -> Done; x:xs -> Yield x xs) xs

    unstream :: Stream a -> [a]
    unstream (Stream next s) = case next s of
      Done -> []
      Yield a s' -> a : unstream (Stream next s')
\end{minted}

The idea is that now \point{stream processing functions are non-recursive} and easily undergo basic compiler deforesting transformations in the style of~\cite{wadler1988deforestation}.
Indeed, instead of a recursive call we remember the state for the next iteration.
\begin{minted}{haskell}
    mapS :: (a -> b) -> Stream a -> Stream b
    mapS f (Stream next s) = Stream next' s
      where
        next' s = case next s of
          Done -> Done
          Yield x s' -> Yield (f x) s'
\end{minted}

The overall pipeline looks as follows:
\begin{enumerate}
    \item We write all list functions through streams:
    \begin{minted}{haskell}
        map :: (a -> b) -> [a] -> [b]
        map f = unstream . mapS f . stream
    \end{minted}
    \item Using RULES (see~\ref{subsubsec:rules}) we define a rewrite rule for stream/unstream, dual to foldr/build: \texttt{stream . unstream = id}.
    \item Standard compiler optimizations take care of the rest.\footnote{Full deforestation can be guaranteed using staging (see later~\ref{sec:datatype-generic})~\cite{kiselyov2017stream}.}
\end{enumerate}

To support a non-recursive filter function, a separate kind of step is usually added:
\begin{minted}{haskell}
    data Step a s = Done | Skip s | Yield a s

    filterS :: (a -> Bool) -> Stream a -> Stream a
    filterS p (Stream next s) = Stream next' s
      where
        next' s = case next s of
          Done -> Done
          Skip s' -> Skip s'
          Yield a s' -> if p a then Yield a s' else Skip s'
\end{minted}

The Haskell standard library still uses foldr/build fusion, but there exist many industrial stream libraries~\cite[chapter 14]{bragilevsky-haskell}.

More about streams can be found at Oleg Kiselyov's page\footnote{\url{https://okmij.org/ftp/Streams.html}}.

\subsection{Ubiquitous duality} \label{subsec:data-duality}

We have considered three forms of recursive data:
\begin{itemize}
    \item \mintinline{haskell}{Fix f} --- ordinary recursive data types, finite in eager languages;
    \item \mintinline{haskell}{?$\forall$?a . (f a -> a) -> a} --- Church encoding, finite structures defined by folds;
    \item \mintinline{haskell}{?$\exists$?s . (s -> f s, s)} --- co-Church encoding, potentially infinite data structures, data abstractions (working through an interface over a hidden representation).
\end{itemize}

In this section we consider some practical examples in which the solution space is defined by dual representations of collections.

\subsubsection{Push vs pull streaming} \label{subsubsec:push-pull}

Let us consider various representations of lists or, as they are sometimes called, event streams.
A more detailed comparison can be found here~\cite[section 3]{kiselyov2017stream}.

Church encoding for lists gives a \vocab{push stream}, or \vocab{internal iteration}, or \vocab{Observer pattern}\footnote{\url{https://learn.microsoft.com/en-us/dotnet/api/system.iobserver-1?view=net-9.0}} (in a sense a special case of the Visitor pattern~\ref{subsubsec:visitor}), where we register an event handler and the collection calls (pushes) methods on it.
Examples of push streams include the Java Stream API\footnote{\url{https://docs.oracle.com/javase/8/docs/api/java/util/stream/Stream.html}}, Clojure Transducers\footnote{\url{https://clojure.org/reference/transducers}}.
\begin{minted}{kotlin}
    events.observe(object : Observer<Event> {
        override fun onComplete() { .. }
        override fun onNext(elem: Event) { .. }
    })
\end{minted}

co-Church encoding for lists gives a \vocab{pull stream}, or \vocab{external iteration}, or \vocab{Iterator pattern}.
To get the next element, the consuming code must explicitly request (pull) it.
This representation is often much more convenient from a usage perspective (see~\ref{subsubsec:stream-fusion})\footnote{\url{https://github.com/pulldown-cmark/pulldown-cmark/?tab=readme-ov-file\#why-a-pull-parser}}, but is more complex on the implementation side, because one needs to identify and maintain the existential state in the coalgebra.
Generators are designed to automate the identification of this state, since one can notice that it is the continuation of the computation (see later~\ref{subsubsec:generators-coroutines}).

\subsubsection{Data vs codata} \label{subsubsec:data-codata}

Recall the shape functor for lists:
\begin{minted}{haskell}
    data ListF a r = Nil | Cons a r
\end{minted}

Using the \mintinline{haskell}{data} keyword we define a new algebraic data type through the ways to construct it.
Then, using pattern matching we can deconstruct values of an algebraic data type and use the information stored in it.
\begin{minted}{haskell}
    data List a where
      List :: ListF a (List a) -> List a

    fold :: (ListF a r -> r) -> List a -> r
    fold alg xs = case xs of
      List Nil -> alg Nil
      List (Cons y ys) -> alg (Cons y (fold alg ys))
\end{minted}

However, one can also define a data type through the ways to deconstruct it using the \mintinline{haskell}{codata} keyword (in an imaginary language).
Thus, from a co-list one can request the next layer of the structure.
Such a data type can be constructed using co-pattern matching, describing how the deconstructing function should behave on a constructing term (\texttt{unfold coalg s})\footnote{\href{https://youtu.be/ZCdYIEwcna0?si=XEQSBFhnehQFZPxy}{(youtube) CS410 2017 Lecture 15 Coinduction and Coalgebras}}.
\begin{minted}{haskell}
    codata CoList a where
      force :: CoList a -> ListF a (CoList a)

    unfold :: (s -> ListF a s) -> s -> CoList a
    force (unfold coalg s) = case coalg s of
      Nil -> Nil
      Cons x s' -> Cons x (unfold coalg s')
\end{minted}

Essentially, \mintinline{haskell}{codata} represents a dictionary of functions that capture some state necessary for generating subsequent layers of the structure.
Thus, \mintinline{haskell}{codata} can be compared to OOP interfaces, and co-pattern matching to an anonymous interface implementation.
The two preceding examples can be written, for example, in Kotlin as follows (the list shape is encoded as \mintinline[escapeinside=**]{kotlin}|Pair<a, r>?|, verify for yourself that this type is isomorphic to \mintinline{haskell}{ListF}).
\begin{minted}[escapeinside=**]{kotlin}
    class List<a>(val layer: Pair<a, List<a>>?)

    fun <a, r> fold(alg: (Pair<a, r>?) -> r, xs: List<a>): r =
        if (xs.layer == null) alg(null)
        else alg(Pair(xs.layer.first, fold(alg, xs.layer.second)))

    interface CoList<a> { fun force(): Pair<a, CoList<a>>? }

    fun <a, s> unfold(coalg: (s) -> Pair<a, s>?, ini: s): CoList<a> =
        object : CoList<a> {
            override fun force(): Pair<a, CoList<a>>? {
                val layer = coalg(ini)
                return if (layer == null) null else
                    Pair(layer.first, unfold(coalg, layer.second))
            }
        }
\end{minted}

The functional style of programming primarily operates on directly observable data \mintinline{haskell}{data}, while OOP hides data behind interfaces \mintinline{haskell}{codata}.
However, both constructs have their clear areas of application and should not be neglected regardless of preferred style~\cite{downen2019codata}\footnote{\url{https://reasonablypolymorphic.com/blog/review-codata/}}.

In languages with totality checking, inductive and coinductive definitions are distinguished.
For them, pattern matching and co-pattern matching, the induction principle (catamorphism) and the coinduction principle (anamorphism) are used.
Inductive definitions specify finite data structures; totality checking verifies that recursive calls are made on structurally smaller subterms.
Coinductive definitions specify potentially infinite data structures; for them, productivity is checked --- the generating function always produces a new constructor after a recursive call\footnote{\url{https://rocq-prover.org/doc/V8.18.0/refman/language/core/coinductive.html}}.

\subsection{Appendix: category of algebras} \label{subsec:cats}

This is an optional section that is not necessary for understanding the rest of the course.
However, it is useful for understanding frequently used terminology.

A \vocab{category} is a collection of objects and a collection of arrows.
For each object $X$ there exists an identity arrow, and for each pair of arrows there exists a way to obtain their composition: $f : Y \to Z, g : X \to Y \Rightarrow f \circ g : X \to Z$.

One defines a category corresponding to Haskell --- $Hask$.
In reality this is a poor category from the theoretical standpoint, but it will suffice for our informal reasoning\footnote{\url{https://math.andrej.com/2016/08/06/hask-is-not-a-category/}}.
Objects in Hask are types of the Haskell language, and morphisms are terms defining functions between the corresponding types.
The identity morphism is \mintinline{haskell}|id|, and composition is defined as \mintinline{haskell}|f . g = \x -> f (g x)|.

\begin{task}
    How does one represent constants in such a category?
\end{task}

A \vocab{functor} is a mapping between categories that maps objects of one category to objects of another, and arrows of one to arrows of the other.
In Haskell, type constructors define the mapping between objects, and \mintinline{haskell}|fmap| defines the mapping between arrows.
A functor must preserve the identity morphism and composition.
\begin{figure}[h!]
    \centering
    \includegraphics[width=0.25\textwidth]{figs/functor}
\end{figure}

An \vocab{algebra} in a category $C$ is a pair of an object of the category $X \in Obj(C)$ and a morphism $\phi : F\ap X \to X$, where $F$ is a functor.
The morphism $F\ap X \to X$ itself is called an \vocab{f-algebra}.
Algebras in the categorical sense can describe algebras.
Thus, as the object $X$ we take the carrier of the algebra.
As the functor $F$ --- the signature of the algebra in the form of a shape type.
Then the morphism is the interpretation of the signature.

An \vocab{algebra morphism} is a morphism between carriers $h : X \to Y$ such that the following diagram commutes.
A \vocab{diagram commutes} if all possible paths along the arrows in it are equal.
\begin{figure}[h!]
    \centering
    \includegraphics[width=0.3\textwidth]{figs/alg-homomorphism}
\end{figure}

In an algebra morphism one can recognize familiar features of homomorphisms, that is, operations between carriers that ``respect'' the operations of the algebraic theory's signature.

Algebras over a category $C$ form a \vocab{category of algebras}, in which the objects are algebras and the morphisms are algebra morphisms.

An \vocab{initial object} of a category is an object from which there exists a unique arrow to every other object.
A \vocab{terminal (final) object} of a category is an object into which there exists a unique arrow from every other object.

Initial and terminal objects of a category do not necessarily exist in a single instance.
But all initial objects are isomorphic to each other, as are all terminal objects.

\begin{task}
    Give the initial and terminal objects of the category $Hask$.
\end{task}

A recursive type is a type, which means it corresponds to an object in the category Hask.
$X$ is a recursive type with shape $F$ if the following isomorphism holds:
\[X \simeq F\ap X\]

One can notice that the isomorphism witness from right to left resembles an f-algebra, and from left to right an f-coalgebra (everything is the same, but with all arrows reversed).
And indeed, the appropriate object $X$ must be either the initial object of the category of algebras, or the terminal object of the category of coalgebras (with the corresponding morphisms).
The first variant corresponds to finite data structures, and the second to potentially infinite ones.
