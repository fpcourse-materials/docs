Рекурсивные структуры данных можно описывать через способы их конструирования, потребления или порождения.
Например, список можно представить цепочкой конструкторов, процедурой свёртки с заданными обработчиками или состоянием и функцией, выдающей очередной элемент.
Выбор представления влияет на интерфейс: кто управляет обходом, какие операции удобно выразить и как организовать вычисление без промежуточных структур.

Чтобы разобраться в этих представлениях, начнём с вариантности и алгебры типов: научимся переносить функции через типовые конструкторы и находить изоморфизмы между типами.
Затем отделим форму рекурсивной структуры от самой рекурсии и получим универсальные свёртки и развёртки.
Они позволят связать привычные типы данных с кодировками Чёрча, паттернами Visitor и Iterator, а также с потоками, в которых данные могут порождаться по запросу.

На примере оптимизаций fusion мы увидим, как смена представления помогает устранить промежуточные структуры, сохранив композиционный стиль программирования.
Сопоставляя эти подходы, будем обращать внимание на способы наблюдения данных, возможность работать с бесконечными структурами и роль ленивости.
Эти связи пригодятся при проектировании API и при изучении интерпретаторов в следующей главе.

\subsubsection{Функторы}

% TODO смешались слова про позиции в типах и декларации

Пусть у нас есть функция \mintinline{haskell}|h :: a -> b| и типовой конструктор \mintinline{haskell}|F|.
Можно ли с помощью \mintinline{haskell}|h| преобразовать \mintinline{haskell}|F a| в \mintinline{haskell}|F b|?
Для списка ответ знаком: достаточно применить \mintinline{haskell}|map h|.
Но для других типовых конструкторов направление преобразования может оказаться обратным.
\vocab{Вариантность} описывает, как преобразование параметра связано с преобразованием всего типа.

\vocab{Ковариантный функтор} --- пара из некоторого типового конструктора \texttt{F} и операции на функциях \texttt{fmap :: (a -> b) -> (F a -> F b)}.
Эта операция сохраняет направление стрелки и должна уважать тождественную функцию и композицию:

\begin{minted}{haskell}
    class Functor f where
      fmap :: (a -> b) -> (f a -> f b)

    -- Законы:
    fmap id == id
    fmap (g . h) == fmap g . fmap h
\end{minted}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.3\textwidth]{figs/functor}
\end{figure}

Рассмотрим теперь предикат: \mintinline{haskell}|type Predicate a = a -> Bool|.
Имея предикат на \mintinline{haskell}|b| и функцию \mintinline{haskell}|a -> b|, мы можем проверять значения типа \mintinline{haskell}|a|: сначала преобразуем аргумент, затем применим предикат.
Так, из проверки числа получается проверка длины строки:
\begin{minted}{haskell}
    type Predicate a = a -> Bool

    contramapP :: (a -> b) -> Predicate b -> Predicate a
    contramapP h predicate = predicate . h

    longEnough :: Predicate Int
    longEnough n = n >= 8

    longText :: Predicate String
    longText = contramapP length longEnough
    -- longText "hello" == False
\end{minted}
Функция \mintinline{haskell}|length :: String -> Int| превращает предикат на числах в предикат на строках: направление преобразования предикатов противоположно направлению \mintinline{haskell}|length|.

\vocab{Контравариантный функтор} --- пара из типового конструктора и операции на функциях, разворачивающей стрелку.
При переносе композиции порядок операций также меняется:

\begin{minted}{haskell}
    class Contravariant f where
      contramap :: (a -> b) -> (f b -> f a)

    -- Законы:
    contramap id == id
    contramap (g . h) == contramap h . contramap g
\end{minted}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.3\textwidth]{figs/contra-functor}
\end{figure}

Типовой конструктор можно объявить ковариантным или контравариантным функтором (или никаким из них) относительно некоторого типового параметра в зависимости от вида декларации соответствующих конструкторов данных.
А именно, от знака позиций, в которых входит этот типовой параметр в тип.

\subsubsection{Знаки позиций в типе}

Разовьём интуитивное понимание знаков позиций.
Тип \mintinline{haskell}{A} входит в положительной позиции в \mintinline{haskell}{B} если его значение можно извлечь из \mintinline{haskell}{B}.
И наоборот, тип \mintinline{haskell}{A} входит в отрицательной позиции, если его значение нужно, наоборот, предоставить.
Рассмотрим знаки позиций типов в базовых типовых конструкторах:
\begin{center}
    \begin{tabular}[h]{|c|c|c|}
        \hline
        Тип                              & знак позиции \mintinline{haskell}{A} & знак позиции \mintinline{haskell}{B} \\
        \hline
        \mintinline{haskell}{Either A B} & $+$                                  & $+$                                  \\
        \mintinline{haskell}{(A, B)}     & $+$                                  & $+$                                  \\
        \mintinline{haskell}{A -> B}     & $-$                                  & $+$                                  \\
        \hline
    \end{tabular}
\end{center}

Действительно, из суммы и произведения можно извлечь компоненты с помощью паттерн-матчинга, а из стрелки можно получить правый тип апплицируя её к аргументу.
В то же время значение типа слева от стрелки нужно предоставить.

На плюс и минус действуют интуитивные алгебраические законы при рассмотрении более сложных типов.
Рассмотрим на примере \mintinline{haskell}{f :: ((A, B) -> C) -> (D, E)}.
\begin{itemize}
    \item Плюс на плюс даёт плюс.
    Действительно, нужно лишь применить две элиминации вместо одной, чтобы получить заветный тип.
    В нашем примере, чтобы получить \mintinline{haskell}{D}, нужно сначала апплицировать функцию, а потом разобрать пару.
    \item Плюс на минус (и наоборот) даёт минус.
    Действительно, \mintinline{haskell}{C} нам нужно предоставить: \mintinline{haskell}{f (\ab -> provideC)}.
    \item Минус на минус даёт плюс.
    Пару \mintinline{haskell}{(A, B)} нам предоставляют: \mintinline{haskell}{f (\ab -> ...)}.
\end{itemize}

\begin{task}
    Убедитесь что плюс на минус даёт минус.
\end{task}

Возвращаясь к функторам, если типовой параметр входит в декларацию только в положительных позициях, типовой конструктор можно естественным образом объявить ковариантным функтором относительно этого параметра.
Если в только в отрицательных~--- контравариантным функтором\footnote{Если параметр вообще не встречается в полях, он фантомный. В этом случае можно определить оба отображения, игнорируя переданную функцию.}.
Такой параметр называют \vocab{ковариантным} и \vocab{контравариантным} соответственно.
Иначе говоря, ковариантный функтор позволяет постобработать значение вычисления, а контравариантный~--- предобработать аргумент вычисления.

Если параметр встречается в позициях обоих знаков, его называют \vocab{инвариантным}: в общем случае одного преобразования \mintinline{haskell}|a -> b| уже недостаточно.
Например, чтобы превратить функцию \mintinline{haskell}|a -> a| в функцию \mintinline{haskell}|b -> b|, нужны преобразования в обе стороны:
\begin{minted}{haskell}
    adapt :: (a -> b) -> (b -> a) -> (a -> a) -> (b -> b)
    adapt forward backward f = forward . f . backward
\end{minted}
Преобразование \mintinline{haskell}|backward| обслуживает отрицательное вхождение параметра, а \mintinline{haskell}|forward| --- положительное.

\subsubsection{Ещё функторы}

Одновременное ковариантное отображение по двум параметрам описывает класс \vocab{бифункторов}:
\begin{minted}{haskell}
    class Bifunctor f where
      bimap :: (a -> c) -> (b -> d) -> f a b -> f c d
\end{minted}
Например, у \mintinline{haskell}|Either| оба параметра положительны: \mintinline{haskell}|bimap| применяет первую функцию к содержимому \mintinline{haskell}|Left|, а вторую --- к содержимому \mintinline{haskell}|Right|.

Отображение, контравариантное по первому параметру и ковариантное по второму, описывает класс \vocab{профункторов}:
\begin{minted}{haskell}
    class Profunctor p where
      dimap :: (c -> a) -> (b -> d) -> p a b -> p c d
\end{minted}

Функциональная стрелка --- основной пример профунктора: сначала пред-обрабатываем вход, затем вызываем функцию и пост-обрабатываем выход.
\begin{minted}{haskell}
    instance Profunctor (->) where
      dimap pre post f = post . f . pre
\end{minted}
По той же схеме можно устроить тип SQL-запроса \mintinline{haskell}|Sql input output|: \mintinline{haskell}|dimap| добавляет преобразования входных данных и результата.
Пусть заданы преобразования и исходный запрос:
\begin{minted}{haskell}
    serialize   :: Age -> Text
    deserialize :: Text -> [User]
    query       :: Sql Text Text
\end{minted}
Тогда получаем запрос с новым интерфейсом:
\begin{minted}{haskell}
    dimap serialize deserialize query :: Sql Age [User]
\end{minted}

Также понятие вариантности встречается в объектно-ориентированных языках и вообще в теории подтипизации: здесь речь идёт о переносе отношения подтипизации на параметризованные типы.

Действительно, \vocab{отношение подтипизации} \texttt{B <: A} говорит о том, что значение типа \texttt{B} безопасно использовать в позиции, где ожидается значение типа \texttt{A}.
Такое использование можно представить как специальное преобразование \texttt{upcast :: B -> A}.
При ковариантности из \texttt{B <: A} (\texttt{upcast :: B -> A}.) следует \texttt{F B <: F A} (наличие \texttt{upcast' :: F B -> F A}.), при контравариантности --- \texttt{F A <: F B}.

\subsection{Изоморфизм} \label{subsec:isomorphism}э

Один и тот же смысл можно представить разными типами.
При проектировании функции или модели данных полезно понимать, какие типы несут одинаковое ``количество информации''.
Для этого введём понятие изоморфизма, а затем воспользуемся алгеброй типов, чтобы навигироваться в пространстве решений.

В этом разделе рассматриваем полностью определённые значения и тотальные функции, то есть функции, определённые на всех входах\footnote{Это упрощённая модель, а не полная семантика Haskell: мы не учитываем незавершающиеся вычисления и частично определённые значения. Например, у типа \mintinline{haskell}|Maybe ()| есть значение \mintinline{haskell}|Just undefined|. Для приведённых ниже функций преобразование туда и обратно теряет даже его внешний конструктор: \mintinline{haskell}|to (from (Just undefined))| даёт неопределённое вычисление целиком. Поэтому законы изоморфизма здесь утверждаются в выбранной модели.}.

Два типа \texttt{A} и \texttt{B} называются \vocab{изоморфными} (обозначают \texttt{A $\iso$ B}) тогда и только тогда, когда существует такая пара функций \texttt{to :: A -> B} и \texttt{from :: B -> A}, что\footnote{Под равенством термов можно понимать разное, например, $\alpha\beta\eta$-эквивалентность. Мы будем пользоваться \vocab{экстенсиональным равенством} для функций~--- две функции равны, когда равны их результаты на всех входах. \url{https://ncatlab.org/nlab/show/function+extensionality}}
\begin{minted}{c}
    to . from = id
    from . to = id
\end{minted}

Иначе говоря, между обитателями таких типов можно установить взаимно-однозначное соответствие.
Функции перехода позволяют сменить представление данных, а затем восстановить исходное значение без потерь.
В этом смысле два изоморфных типа заключают в себе одинаковое ``количество информации''.
Например, типы \mintinline{haskell}|Bool| и \mintinline{haskell}|Maybe ()| в этом смысле совершенно взаимозаменимы.
Покажем это, предъявив пару взаимообратных функций:
\par\noindent\begin{minipage}{\linewidth}
\begin{minted}{haskell}
    to :: Bool -> Maybe ()
    to b = if b then Just () else Nothing

    from :: Maybe () -> Bool
    from m = case m of Nothing -> False; Just () -> True
\end{minted}
\end{minipage}\par
Здесь \mintinline{haskell}|False| соответствует \mintinline{haskell}|Nothing|, а \mintinline{haskell}|True| --- \mintinline{haskell}|Just ()|.
Перебрав эти случаи, проверяем, что обе композиции возвращают исходное значение.

Несмотря на смысловую взаимозаменимость, для кодирования информации о том, передал ли пользователь программе определённый флаг, мы, скорее всего, воспользуемся типом \mintinline{haskell}|Bool| ввиду нефункциональных соображений о читабельности кода.
Аналогично можно рассматривать соображения эффективности.

С категорным взглядом на происходящее можно ознакомиться в~\cite{hinze2010reason}.
Мы же придерживаемся теоретико-множественной интерпретации типов.

\subsubsection{Кардинальность: суммы, произведения, экспоненты} \label{subsubsec:cardinality}

Типы можно воспринимать как синтаксис для записи множеств, а населяющие их термы~--- как синтаксические записи элементов этих множеств.
Так терм \mintinline{haskell}|(True, False)|~--- запись элемента множества пар, записываемого в синтаксисе типов как \mintinline{haskell}|(Bool, Bool)| (вместо математического $\mathbb{B}\times\mathbb{B}$).
Или же терм \mintinline{haskell}|\x -> x + 1| является записью функции прибавляющей единицу из множества функций над целыми числами, записываемого как \mintinline{haskell}|Integer -> Integer| (вместо математического $\mathbb{Z}\to\mathbb{Z}$).

В теоретико-множественной модели изоморфизм --- это биекция, поэтому он существует тогда и только тогда, когда множества равномощны.
Между двумя конечными множествами из $n$ элементов существует $n!$ биекций\footnote{Для конечных типов, значения которых можно перечислить, функции перехода можно задать таблицей соответствий.
Для бесконечных типов равномощность сама по себе ещё не даёт алгоритма преобразования: математическая биекция не обязательно реализуема программой (вычислима).}.
Научимся определять количество таких элементов.
С помощью $|\cdot|$ будем записывать \vocab{кардинальность} типа~--- количество элементов в соответствующем множестве.

\begin{center}
    \begin{tabular}{|l|c|}
        \hline
        Тип и его декларация                                                                                                                                                                            & кардинальность \\
        \hline
        \mintinline{haskell}{data Void}                                                                                                                                                                 & $0$            \\
        \mintinline{haskell}{data Unit = Unit}\footnote{\mintinline{haskell}|Unit| записывается в Haskell с помощью специального синтаксиса \mintinline{haskell}|()|, означающем как бы пустой кортеж.} & $1$ \\
        \mintinline{haskell}{data Bool = False | True}                                                                                                                                                  & $2$            \\
        \hline
    \end{tabular}
\end{center}

Идея алгебраических типов данных в том, что сложные типы можно строить из простых с помощью операции $+$ (``или'') и операции $\times$ (``и'')\footnote{\url{https://stanford-cs242.github.io/f18/lectures/02-2-algebraic-data-types.html}}:
\begin{center}
    \begin{tabular}{|l|c|}
        \hline
        Тип                                                      & кардинальность   \\
        \hline
        \mintinline{haskell}{data Either a b = Left a | Right b} & $|a| + |b|$      \\
        \mintinline{haskell}{data Pair a b = Pair a b}           & $|a| \times |b|$ \\
        \hline
    \end{tabular}
\end{center}

Посчитаем количество значений различных типов (вы можете убедиться в справедливости заключения, перечислив все значения вручную):
\begin{itemize}
    \item \mintinline{haskell}{|Either Unit (Either Bool Bool)| = |Unit| + (|Bool| + |Bool|) = 5}.
    \item \mintinline{haskell}{|Pair (Either Bool Unit) (Pair Unit Void)| = 0} ~--- тип \mintinline{haskell}|Void| не населён, как и кортеж, его включающий.
    \item Если \mintinline{haskell}{data Example = FirstAlternative Bool | AnotherOne Unit Bool Bool}, то \\\mintinline{haskell}{|Example| = |Bool| + |Unit| * |Bool| * |Bool| = 2 + 1 * 2 * 2 = 6}.
\end{itemize}

Рассмотрим теперь функции.
У типа \mintinline{haskell}|Bool -> Bool| есть четыре различных тотальных функции:
\begin{center}
    \begin{tabular}{|l|c|c|}
        \hline
        Функция & результат на \texttt{False} & результат на \texttt{True} \\
        \hline
        \texttt{const False} & \texttt{False} & \texttt{False} \\
        \texttt{id}          & \texttt{False} & \texttt{True} \\
        \texttt{not}         & \texttt{True}  & \texttt{False} \\
        \texttt{const True}  & \texttt{True}  & \texttt{True} \\
        \hline
    \end{tabular}
\end{center}
Для каждого из двух аргументов независимо выбирается один из двух результатов, поэтому получаем $2^2 = 4$ функции.
Мы считаем функции по их поведению, а не записи программ: например, \mintinline{haskell}|id| и \mintinline{haskell}|\x -> x| здесь один и тот же элемент множества.
Аналогично для каждого элемента конечного множества $A$ есть $|B|$ вариантов результата.
Поэтому функциональную стрелку называют экспоненциальным типом:
\[
    |A \to B| = |B|^{|A|}.
\]
В теоретико-множественной интерпретации эта формула описывает множество всех тотальных функций; для бесконечных множеств среди них могут быть невычислимые функции.

Вернёмся к проектированию типов.
Пусть пользователь может задать два логических флага, причём они должны появляться только вместе.
Сравним два представления:
\begin{minted}{haskell}
    type Together = Maybe (Bool, Bool)
    type Independently = (Maybe Bool, Maybe Bool)
\end{minted}
У первого типа $1 + 2\cdot 2 = 5$ значений: оба флага отсутствуют либо оба заданы одной из четырёх пар.
У второго типа $(1 + 2)\cdot(1 + 2) = 9$ значений: каждый флаг может отсутствовать независимо от другого.
Четыре дополнительных состояния имеют вид \mintinline{haskell}|(Just b, Nothing)| или \mintinline{haskell}|(Nothing, Just b)|, где \mintinline{haskell}|b| --- \mintinline{haskell}|False| или \mintinline{haskell}|True|.
Эти типы неизоморфны; для сформулированного требования подходит первый, поскольку в нём нельзя представить состояние с одним флагом.
Если же независимое отсутствие флагов допустимо, нужен второй.

Подсчёт значений помогает проверить, соответствует ли тип предметной области.
При проектировании полезно руководствоваться следующими соображениями:
\begin{itemize}
    \item В типе должно быть не меньше элементов, чем в предметной области, чтобы все необходимые объекты были представимы.
    \item В типе должно быть как можно меньше элементов, которых нет в предметной области, чтобы пространство ошибок было минимальным.
    \item Далее среди изоморфных типов выбирается оптимальный исходя из нефункциональных требований.
\end{itemize}

Прежде чем работать с некоторым объектом предметной области, информацию о нём, в соответствии со вторым правилом, следует привести в максимально структурное представление, дающее наибольшее количество гарантий\footnote{\url{https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/}}.

\subsubsection{Алгебраическое представление типа} \label{subsubsec:type-algebra}

Как мы увидели выше, чтобы показать наличие изоморфизма между двумя типами можно либо предъявить пару взаимообратных функций, либо показать, что кардинальности этих двух типов совпадают.
В этом разделе мы научимся сопоставлять типу некоторую алгебраическую запись, отражающую его структуру и кардинальность.
Так, мы сможем синтаксическими преобразованиями формул получать эквивалентные записи, из которых будем восстанавливать типы, заведомо изоморфные данному\footnote{\url{https://codewords.recurse.com/issues/three/algebra-and-calculus-of-algebraic-data-types}}.

В основу алгебраического представления положим вычисление кардинальности типов.
Имена конструкторов при этом несущественны: мы рассматриваем типы с точностью до изоморфизма, сохраняя информацию об их структуре.
\begin{center}
    \begin{tabular}{|p{0.5\textwidth}|c|}
        \hline
        Тип                                                      & алгебраическая формула      \\
        \hline
        \mintinline{haskell}{data Void}                          & $0$                         \\
        \mintinline{haskell}{data Unit = Unit}                   & $1$                         \\
        \mintinline{haskell}{data Bool = False | True}           & $1 + 1$ (обозначим как $2$) \\
        \mintinline{haskell}{data Maybe a = Nothing | Just a}    & $1 + a$                     \\
        \mintinline{haskell}{data Either a b = Left a | Right b} & $a + b$                     \\
        \mintinline{haskell}{data Pair a b = Pair a b}           & $a \times b$                \\
        \mintinline{haskell}{a -> b}                             & $b^a$                       \\
        \hline
    \end{tabular}
\end{center}

\begin{task}
    Запишите в алгебраическом виде следующий тип:
    \begin{minted}{haskell}
        data T a b = Undefined | Defined a (a -> b)
    \end{minted}
\end{task}

В качестве отношения эквивалентности будем использовать изоморфизм соответствующих типов.
Для сумм, произведений и экспонент получаются знакомые алгебраические законы (рис.~\ref{fig:school-alg}).
Разберём дистрибутивность:
\[
    a\times(b+c) \iso (a\times b)+(a\times c).
\]
Слева у нас пара, второй компонент которой выбирается из двух вариантов.
Справа выбор варианта сделан снаружи, а общий компонент хранится внутри выбранной пары.
Функции перехода повторяют эту структуру:
\begin{minted}{haskell}
    distribute :: (a, Either b c) -> Either (a, b) (a, c)
    distribute (x, Left y)  = Left (x, y)
    distribute (x, Right z) = Right (x, z)

    factor :: Either (a, b) (a, c) -> (a, Either b c)
    factor (Left (x, y))  = (x, Left y)
    factor (Right (x, z)) = (x, Right z)
\end{minted}
Проверим обе композиции.
Для левых вариантов получаем:
\begin{minted}{text}
    factor (distribute (x, Left y))
      = factor (Left (x, y))
      = (x, Left y)

    distribute (factor (Left (x, y)))
      = distribute (x, Left y)
      = Left (x, y)
\end{minted}
Для правых вариантов рассуждение аналогично.
Мы восстановили исходные значения в обоих направлениях, поэтому предъявили изоморфизм, а не только равенство кардинальностей.

Закону $(c^b)^a \iso c^{a\times b}$ соответствуют знакомые операции каррирования и раскаррирования:
\begin{minted}{haskell}
    -- ?$(c^b)^a \iso c^{a\times b}$?
    to :: (a -> b -> c) -> (a, b) -> c
    to = uncurry
    from :: ((a, b) -> c) -> a -> b -> c
    from = curry
\end{minted}

    \includegraphics[width=0.4\textwidth]{figs/school-alg}
    \caption{Законы школьной алгебры ностальгии ради~\cite{hinze2010reason}.}
    \label{fig:school-alg}
\end{figure}

Интересным наблюдением может быть то, что функции можно использовать как структуры данных, в соответствие с изоморфизмом $c^{a + b} \iso c^a\times c^b$.
Действительно, в таком случае аргумент функции выступает индексом (его кардинальность должна совпадать с размером коллекции).
\begin{minted}{haskell}
    -- ?$a \times a \iso a^2$?
    get :: (a, a) -> (Bool -> a)
    get (x, y) idx = if idx then x else y
    tabulate :: (Bool -> a) -> (a, a)
    tabulate f = (f True, f False)
\end{minted}

\vocab{Каноническим представлением алгебраического типа (canonical representation)} называют сумму произведений типов:
\[
    \sum_{i}\prod_{j} t_{ij}
\]
Сумма соответствует выбору конструктора данных, а каждое произведение --- набору его полей.
Именно так устроены обычные \mintinline{haskell}{data} декларации в Haskell\footnote{Алгебраическая аналогия распространяется и на производные: для полиномиальных типов производная описывает контексты с одним пропущенным элементом. Такие контексты используются при построении зипперов --- структур для навигации и локального изменения данных~\cite{huet1997zipper, mcbride2001derivative, abbott2003derivatives}.}.
У рекурсивного типа такое описание задаёт один слой структуры, в полях которого могут находиться подструктуры того же типа.
В следующем разделе мы отделим эту форму слоя от рекурсии, не пытаясь развернуть всю структуру в конечный полином.

\subsection{Рекурсивные типы} \label{subsec:recursive-types}

Рекурсивные типы, подобно рекурсивным термам, могут упоминать себя в своих определениях.
Например, тип натурального числа встречается в типе поля конструктора следующего числа:
\begin{minted}{haskell}
    fac n = if n <= 1 then 1 else n * ?\framebox{fac}? (n - 1)
    data Nat = Zero | Suc ?\framebox{Nat}?
\end{minted}

Мы в основном посмотрим на рекурсивные типы с практической точки зрения.
Наша цель --- отделить форму одного слоя структуры от рекурсивных ссылок на её подструктуры.
Тогда обработку слоя можно будет задавать отдельно, а саму схему рекурсии переиспользовать для списков, деревьев и других типов.
Однако, их формальное теоретико-типовое описание, теоретико-категорная и теоретико-множественная интерпретации представляют отдельный интерес~\cite[часть 4]{pierce2002types}.

\subsubsection{Просто список}

Рассмотрим конечные списки.
Такой список содержит либо ноль элементов, либо один, либо два\ldots
Алгебраически это запишется следующим образом:
\[
    L = 1 + a + a^2 + a^3 + \ldots
\]
Каждое слагаемое описывает списки одной длины: $1$ --- пустой список, $a$ --- одноэлементные, $a^2$ --- двухэлементные и так далее.
Все списки конечны, но для перечисления всех возможных длин потребовалась бесконечная запись.
Поработаем с ним как с формальным рядом.
Вынесем $a$ за скобки:
\[
    L = 1 + a \times (1 + a + a^2 + \ldots)
\]
Выражение в скобках снова описывает список, поэтому получаем рекурсивное уравнение:
\[
    L = 1 + a \times L
\]
Легко видеть, что это на самом деле знакомое нам определение списка из Haskell:
\begin{minted}{haskell}
    data List a = Nil | Cons a (List a)
\end{minted}

Мы получили конечную запись определения, но рекурсия в ней осталась.
Теперь выделим нерекурсивную форму одного слоя, заменив в ней хвост на параметр.
Сам тип списка должен быть изоморфен этой форме, в которую снова подставлен список\footnote{Само уравнение ещё не выбирает конечные списки. В модели множеств конечные списки образуют наименьшую неподвижную точку соответствующего конструктора типов. Ленивый Haskell допускает также бесконечные и частично определённые значения; здесь вывод по длинам относится к конечным, полностью определённым спискам.}:
\[
    L \iso 1 + a \times L
\]
Расширим язык типов абстракцией (полиморфизмом) и решим полученное рекурсивное уравнение в стиле $\lambda$-исчисления, с помощью некоторого комбинатора неподвижной точки:
\[
    L = FIX\ap\lambda r\ldotp 1 + a \times r
\]

Закодируем это на Haskell.
Сначала зафиксируем форму списка, а рекурсию замкнём в отдельном типе \mintinline{haskell}{FixList a}:
\begin{minted}{haskell}
    type Shape a r = Either () (a, r) -- ?$\lambda a r\ldotp 1 + a\times r$?
    data FixList a = In (Shape a (FixList a))
    -- FixList a ?$\iso$? Shape a (FixList a) ?$\iso$? Shape a (Shape a (FixList a)) ?$\iso$? ...

    example :: FixList Int -- [1, 2, 3]
    example = In (Right (1,
                In (Right (2,
                In (Right (3, In (Left ())))))))
\end{minted}

У параметров \mintinline{haskell}{Shape a r} разные роли: \texttt{a} --- тип элемента, а \texttt{r} --- место для хвоста.
Сам \texttt{Shape} не рекурсивен; в \texttt{FixList} на место \texttt{r} подставлен снова \texttt{FixList a}.
Таким образом, мы разделили определение списка на две части: одна отвечает за форму слоя, другая --- за рекурсию\footnote{Техника абстрагирования по ``рекурсивной ссылке на себя'' называется \vocab{открытой рекурсией}. Так, мы предоставляем пользователю больше контроля. Например, на уровне термов комбинатор рекурсии может подсчитывать количество рекурсивных вызовов и оборвать вычисление при превышении какого-то лимита.}.
Форму можно переиспользовать в определении свёртки: теперь на место хвоста подставляется результат его обработки.
\begin{minted}{haskell}
    foldFixList :: (Either () (a, r) -> r) -> FixList a -> r
    foldFixList phi (In shape) = case shape of
      Left () -> phi (Left ())
      Right (x, xs) -> phi (Right (x, foldFixList phi xs))
    -- сравните с классическим определением
    foldr :: (a -> r -> r) -> r -> [a] -> r
    foldr f ini list = case list of
      [] -> ini
      x:xs -> f x (foldr f ini xs)
\end{minted}

Действительно, свёртка в общем смысле позволяет заменить каждый конструктор данных в дереве на некоторую функцию.
В результате получается вычисление, имеющее доступ ко всему содержимому структуры данных, и возвращающее результат агрегации:
\begin{center}
    \includegraphics[width=0.5\textwidth]{figs/foldr}
\end{center}

То есть количество и типы аргументов свёртки зависят от ``формы'' сворачиваемого типа.
В случае списка требуется значение вместо \mintinline{haskell}{Nil} и бинарная функция вместо \mintinline{haskell}{Cons}.
Мы же объединяем оба случая в одну функцию с помощью типа-формы.
Сравните:
\begin{minted}{haskell}
    foldr       (\e r -> e + r) 0
    foldFixList (\case Left () -> 0; Right (e, r) -> e + r)
\end{minted}

\subsubsection{Неподвижная точка функтора} \label{subsubsec:functor-fixpoint}

Абстрагируем \mintinline{haskell}{FixList} по типу-форме:
\begin{minted}{haskell}
    import Data.Kind (Type)

    type Fix :: (Type -> Type) -> Type
    newtype Fix f = In { out :: f (Fix f) }

    data ListF a r = Nil | Cons a r
    type List a = Fix (ListF a)
\end{minted}

\end{task}

Можно показать, что \mintinline{haskell}{[a] ?$\iso$? List a}:
\begin{minted}{haskell}
    to :: [a] -> List a
    to = \case
      [] -> In Nil
      x:xs -> In $ Cons x (to xs)

    from :: List a -> [a]
    from (In shape) = case shape of
      Nil -> []
      Cons x xs -> x : from xs
\end{minted}

Сравним два применения одной и той же формы:
\begin{center}
    \begin{tabular}{ll}
        \texttt{ListF a (List a)} & один слой с хвостом-списком; \\
        \texttt{ListF a Int} & один слой с числом вместо хвоста.
    \end{tabular}
\end{center}
Например, числом может быть результат свёртки хвоста.
Чтобы получить такой слой, сделаем тип формы функтором по последнему параметру.
Его \mintinline{haskell}{fmap} преобразует только рекурсивную позицию \texttt{r}, сохраняя элемент типа \texttt{a}:
\begin{minted}{haskell}
    instance Functor (ListF a) where
      fmap :: (rec -> other) -> ListF a rec -> ListF a other
      fmap f = \case
        Nil -> Nil
        Cons x xs -> Cons x (f xs)
\end{minted}

\subsubsection{Схемы рекурсии} \label{subsubsec:recursion-schemas}

Подобно тому, как структурное императивное программирование, в сравнении с беспорядочным использованием \texttt{goto}, помогает рассуждать о программах, так \vocab{схемы рекурсии} позволяют алгебраически описывать свойства рекурсивных функций, в отличие от ``неструктурной'' рекурсии\footnote{\url{https://reasonablypolymorphic.com/blog/recursion-schemes/index.html}}~\cite{meijer1991functional, meijer1995bananas}.

Практическая идея проста: схема фиксирует способ рекурсивного обхода, а пользователь задаёт обработку одного слоя.
Это позволяет переиспользовать обход и рассуждать об общих законах преобразования программ~\cite{maguire-algebra}.

Универсальная свёртка называется \vocab{катаморфизмом}.
Пусть \texttt{f} --- функтор формы, \texttt{r} --- тип результата, а \mintinline{haskell}{phi :: f r -> r} обрабатывает один слой с результатами вместо поддеревьев.
Выведем устройство катаморфизма по типам:
\[
    \texttt{Fix f}
    \xrightarrow{\texttt{out}} \texttt{f (Fix f)}
    \xrightarrow{\texttt{fmap (cata phi)}} \texttt{f r}
    \xrightarrow{\texttt{phi}} \texttt{r}
\]
Функция \texttt{out} открывает один слой.
Затем \mintinline{haskell}{fmap (cata phi)} помещает результаты рекурсивной свёртки на места поддеревьев, а \texttt{phi} получает результат для всего слоя.
Композиция этих трёх операций и есть искомая свёртка:
\begin{minted}{haskell}
    cata :: Functor f => (f r -> r) -> Fix f -> r
    cata phi = phi . fmap (cata phi) . out
\end{minted}

Иначе говоря, \mintinline{haskell}{cata} заменяет все конструкторы \mintinline{haskell}{In} на функцию \texttt{phi}, которая содержит информацию о том, как реагировать на разные варианты конструкторов в дереве:
\begin{minted}{text}
    example           = In  (Cons 1 (In  (Cons 2 (In  (Cons 3  (In  Nil))))))
    cata phi example ?$\rightsquigarrow$? phi (Cons 1 (phi (Cons 2 (phi (Cons 3 (phi Nil))))))
\end{minted}

Например, сумма списка будет выглядеть следующим образом (рис.~\ref{fig:cata-step}):
\begin{minted}{haskell}
    sum :: List Int -> Int
    sum = cata sumAlg

    sumAlg :: ListF Int Int -> Int
    sumAlg = \case
      Nil -> 0
      Cons x result -> x + result
\end{minted}
Для списка \texttt{[1, 2, 3]} хвост \texttt{[2, 3]} сворачивается в \texttt{5}.
Поэтому алгебра внешнего слоя получает \mintinline{haskell}{Cons 1 5 :: ListF Int Int}: элемент \texttt{1} сохранился, а на месте хвоста находится его сумма.
Последний шаг --- \mintinline{haskell}{sumAlg (Cons 1 5)}, то есть \texttt{1 + 5 = 6}.

\begin{figure}
    \centering
    \includegraphics[width=0.8\textwidth]{figs/cataStep.excalidraw}
    \caption{В новом слое результаты свёртки занимают позиции рекурсивных подструктур. Исходная структура при этом не изменяется.}
    \label{fig:cata-step}
\end{figure}

Функцию \texttt{f a -> a} называют \vocab{f-алгеброй}.
Действительно, если в качестве функтора \texttt{f} взять сигнатуру алгебры, а в качестве \texttt{a} носитель, то f-алгебра будет задавать некоторую интерпретацию сигнатуры:
\begin{minted}{haskell}
    data MonoidSig carrier = Mempty | Mappend carrier carrier

    interpretSig :: MonoidSig Int -> Int
    interpretSig = \case Mempty -> 0; Mappend l r -> l + r
\end{minted}

В противоположность универсальной свёртке, можно построить \vocab{анаморфизм}~--- универсальную развёртку (аналогично \texttt{unfold} для списка).
Здесь \vocab{f-коалгебра} \mintinline{haskell}{psi :: s -> f s} показывает, как из значения-зерна получить один слой структуры данных с новыми зёрнами в рекурсивных позициях.
Снова проследим типы:
\[
    \texttt{s}
    \xrightarrow{\texttt{psi}} \texttt{f s}
    \xrightarrow{\texttt{fmap (ana psi)}} \texttt{f (Fix f)}
    \xrightarrow{\texttt{In}} \texttt{Fix f}
\]
Коалгебра создаёт слой, рекурсивные вызовы разворачивают новые зёрна в поддеревья, а \texttt{In} упаковывает слой в рекурсивный тип:
\begin{minted}{haskell}
    ana :: Functor f => (s -> f s) -> s -> Fix f
    ana psi = In . fmap (ana psi) . psi
    -- сравните с классическим определением развёртки списка
    unfoldr :: (s -> Maybe (a, s)) -> s -> [a]
\end{minted}

Например, зададим обратный отсчёт от положительного числа:
\begin{minted}{haskell}
    countDown :: Integer -> ListF Integer Integer
    countDown n = if n > 0 then Cons n (n - 1) else Nil
\end{minted}
В результате \mintinline{haskell}{countDown 3} получаем \mintinline{haskell}{Cons 3 2}: здесь \texttt{3} --- элемент, а \texttt{2} --- зерно для хвоста.
Коалгебра описала только один слой; рекурсию обеспечивает \texttt{ana}, применяя её к новым зёрнам:
\begin{minted}{text}
    countDown 3 ?$\rightsquigarrow$? Cons 3 2
    countDown 2 ?$\rightsquigarrow$? Cons 2 1
    countDown 1 ?$\rightsquigarrow$? Cons 1 0
    countDown 0 ?$\rightsquigarrow$? Nil
\end{minted}
Таким образом, \mintinline{haskell}{ana countDown 3 :: List Integer} представляет список \texttt{[3, 2, 1]}.

\begin{task}
    Реализуйте анаморфизм, строящий список от $0$ до заданного $n$.
\end{task}

Также вводят \vocab{гиломорфизм (hylomorphism)}, который объединяет построение структуры и её свёртку.
Гиломорфизм задаётся как композиция анаморфизма и катаморфизма.
Промежуточная структура описывает дерево рекурсивных вызовов: коалгебра задаёт подзадачи, а алгебра собирает их результаты.
\begin{minted}{haskell}
    hylo :: Functor f => (a -> f a) -> (f b -> b) -> a -> b
    hylo psi phi = cata phi . ana psi
\end{minted}

Например, для вычисления факториала неотрицательного числа используем уже знакомый обратный отсчёт и алгебру произведения:
\begin{minted}{haskell}
    productAlg :: ListF Integer Integer -> Integer
    productAlg = \case
      Nil -> 1
      Cons n acc -> n * acc

    fac :: Integer -> Integer
    fac = hylo countDown productAlg
    -- fac 0 == 1; fac 5 == 120
\end{minted}
При \texttt{n = 3} развёртка описывает список \texttt{[3, 2, 1]}, а свёртка заменяет пустой хвост на \texttt{1} и каждый шаг \texttt{Cons} на умножение:
\begin{minted}{text}
      fac 3
    ?$\rightsquigarrow$? cata productAlg (ana countDown 3)
    ?$\rightsquigarrow$? productAlg (Cons 3 (productAlg (Cons 2
        (productAlg (Cons 1 (productAlg Nil))))))
    ?$\rightsquigarrow$? 3 * (2 * (1 * 1))
    ?$\rightsquigarrow$? 6
\end{minted}

Можно ввести ещё много различных рекурсивных схем\footnote{\url{https://wiki.haskell.org/Zygohistomorphic_prepromorphisms}} и описать их свойства.
Однако, мы пока остановимся.

Катаморфизм связан со структурной индукцией: результат для составного значения определяется через результаты для его подструктур.
Анаморфизм связан с коиндуктивным построением: очередной наблюдаемый слой задаётся вместе с состояниями для продолжения~\cite[глава 21]{pierce2002types}.

\subsection{Всё через свёртки} \label{subsec:all-folds}

Вместо хранения рекурсивной структуры можно описать, как свернуть её с любой выбранной алгеброй.
Потребитель передаёт обработчики конструкторов, а представление структуры связывает их вызовы в нужном порядке.
Так с помощью катаморфизма получаем изоморфизм между данными и их представлением через свёртку\footnote{Здесь рассматриваем индуктивные структуры с обычными функторами формы, построенными из сумм и произведений, и параметрические функции. Изоморфизм понимается экстенсионально; частичные значения и операции Haskell вроде \texttt{seq} требуют дополнительных оговорок.}:
\[
    \texttt{Fix f} \iso \texttt{forall r . (f r -> r) -> r}.
\]
Квантор \texttt{forall r} существенен: функцию типа \mintinline{haskell}{(f Int -> Int) -> Int} можно применять только к алгебрам с результатом \texttt{Int}, а полиморфное представление допускает любой тип результата.
В частности, выбрав \mintinline{haskell}{r = Fix f} и алгебру \texttt{In}, можно восстановить структуру:
\begin{minted}{haskell}
    to :: Functor f => Fix f -> (forall a . (f a -> a) -> a)
    to x alg = cata alg x

    from :: (forall a . (f a -> a) -> a) -> Fix f
    from g = g In
\end{minted}

Проверим обратимость преобразований.
После кодирования и восстановления получаем \mintinline{haskell}{cata In x}: каждый слой собирается исходным конструктором, поэтому результат снова равен \texttt{x}.
В другую сторону \mintinline{haskell}{to (from g) alg} даёт \mintinline{haskell}{cata alg (g In)}.
Параметричность \texttt{g} позволяет заменить конструирование с помощью \texttt{In} и последующую свёртку непосредственным применением \texttt{g alg}.
Получившаяся функция ведёт себя так же, как исходная \texttt{g}.

Например, следующие два списка эквивалентны (все конструкторы \mintinline{haskell}{In} заменяем на данную алгебру):
\begin{minted}{haskell}
    data ListF elem rec = Nil | Cons elem rec

    xs1 :: Fix (ListF Int)
    xs1 = In (Cons 1 (In (Cons 2 (In (Cons 3 (In Nil))))))

    xs2 :: (ListF Int a -> a) -> a
    xs2 = \alg -> alg (Cons 1 (alg (Cons 2 (alg (Cons 3 (alg Nil))))))

    ghci> xs2 @Int \case Nil -> 0; Cons x acc -> x + acc
    6
\end{minted}

Теперь разберём, что значит передать алгебру списка.
Чтобы обработать \mintinline{haskell}{ListF elem r}, достаточно задать значение для \texttt{Nil} и функцию для \texttt{Cons}:
\[
    \texttt{ListF elem r -> r}
    \iso \texttt{(r, elem -> r -> r)}.
\]
Вместо этой пары можно передать её компоненты отдельными аргументами.
Выберем порядок, принятый у \texttt{foldr}: сначала шаг для \texttt{Cons}, затем значение для \texttt{Nil}.
Получается \vocab{список Чёрча}\footnote{Типизированное обобщение этого представления для индуктивных типов называют кодированием Бёма--Берардуччи: \url{https://okmij.org/ftp/tagless-final/course/Boehm-Berarducci.html}.}:
\begin{minted}{haskell}
    xs3 :: forall r . (Int -> r -> r) -> r -> r
    xs3 = \f ini -> f 1 (f 2 (f 3 ini))
\end{minted}
Одно и то же значение допускает разные интерпретации:
\begin{minted}{haskell}
    ghci> xs3 (+) 0
    6
    ghci> xs3 (:) []
    [1,2,3]
\end{minted}

Этот переход можно провести для любой рассматриваемой алгебраической формы.
Запишем её как сумму произведений (см.~\ref{subsubsec:type-algebra}):
\[
    f\ap a \iso \sum_{i}\prod_{j} (t_{ij}\ap a)
\]
Тогда алгебра может быть записана следующим образом:
\[
    f\ap a\to a\iso a^{\sum_{i}\prod_{j} (t_{ij}\ap a)} \iso \prod_{i}a^{\prod_{j} (t_{ij}\ap a)}
\]
Каждый компонент получившегося произведения --- обработчик одного конструктора.
Каррирование превращает поля конструктора и набор обработчиков в отдельные аргументы функций.
Внешний квантор по типу результата при этом сохраняется.

\begin{task}
    Какая знакомая вам стандартная функция работы со списками по \mintinline{haskell}{data} списку возвращает список Чёрча?
\end{task}

Попробуем интуитивно понять, что это всё значит.
Заметим, что список Чёрча принимает функции, соответствующие веткам паттерн-матчинга или аргументам сворачивающей функции.
Вместо конструкторов же сразу вызываются соответствующие функции.
То есть, вместо того, чтобы создать структуру данных и доставить её к месту деконструирования (паттерн-матчингу), мы \point{доставляем место деконструирования к месту конструирования}.
Например, \mintinline{haskell}{xs3 (+) 0} сразу связывает сложения, а \mintinline{haskell}{xs3 (:) []} связывает вызовы конструкторов списка.
Само функциональное представление может хранить данные в замыканиях; при совмещении построения с потреблением промежуточное представление иногда удаётся устранить полностью.

Мы уже работали с обратным процессом, дефункционализацией, когда функции первого класса превращались в вызовы конструкторов, а их тела --- в ветки паттерн-матчинга~\ref{subsubsec:defunctionalization}.
Можно заметить, что тут мы имеем дело с обратным процессом, \vocab{рефункционализацией}, когда вместо вызовов конструкторов сразу вызывается соответствующий интерпретирующий код~\cite{DANVY2009534}.

В таком преобразовании выбор ветки паттерн-матчинга заменяется вызовом соответствующего обработчика, который может быть замыканием или методом интерфейса.
Результат вычисления сохраняется, но стоимость вызовов и размещение данных зависят от реализации и оптимизаций.

Стоит также отметить, что изоморфизм \mintinline{haskell}|Fix f ?$\simeq$? forall d . (f d -> d) -> d| является обобщением изоморфизма \mintinline{haskell}{a ?$\simeq$? forall r . (a -> r) -> r} (при \mintinline{haskell}{f = Const a}), который лежит в основе CPS-трансформации, рассматриваемой нами далее в главе~\ref{sec:continuations}.

\subsubsection{Deforestation \& list fusion} \label{subsubsec:deforestation-fusion}

В функциональном программировании мы строим новые функции путём композирования имеющихся, более простых, функций.
Этот подход позволяет переиспользовать реализованную функциональность, снижая сложность кода и вероятность ошибок.
Однако, он может приводить к излишним накладным расходам на аллокацию и деконструирование промежуточных структур данных.

Например, сравните следующие две реализации.
Первая переиспользует готовые функции, но без fusion создаёт промежуточный список по мере потребления:
\begin{minted}{haskell}
    allComposed p xs = and (map p xs)
    -- или fused версия
    allFused p = \case
      [] -> True
      x:xs -> p x && allFused p xs
\end{minted}

Очевидно, это задача оптимизирующего компилятора превращать хороший код с абстракциями в быстрый код.
Оптимизация, избавляющая программы от (промежуточных) структур данных (деревьев) называется \vocab{дефорестацией (deforestation)}.
В результате две функции, как говорят, ``сплавляются'' --- fuse.

Термин и алгоритм дефорестации предложил Philip Wadler~\cite{wadler1988deforestation}.
Раскрытие определений и переписывание выражений позволяют получить ситуацию \mintinline{haskell}{case K args of ...}, в которой построение и разбор конструктора устраняются вместе (рис.~\ref{fig:deforestation-examples}).
Бесконтрольное раскрытие рекурсивных определений может не завершаться и увеличивать код; для алгоритма Уодлера завершение доказывается на ограниченном классе программ в форме \texttt{treeless}\footnote{Дефорестация связана с более общими методами преобразования программ, в частности суперкомпиляцией~\cite{supercomp}.}.

    \caption{Примеры работы дефорестирующего алгоритма~\cite{wadler1988deforestation}.}
    \label{fig:deforestation-examples}
\end{figure}

Сфокусируемся на списках и рассмотрим более практичные решения\footnote{\url{https://markkarpov.com/tutorial/ghc-optimization-and-fusion.html}}.
Первым очевидным решением было бы для каждой пары функций, работающих со списками, добавить специальное правило переписывания (см.~\ref{subsubsec:rules}), дефорестирующее с помощью алгебраических свойств списочных трансформаций.
Для $n$ функций имеется до $n^2$ упорядоченных пар; отдельные правила для сочетаний плохо масштабируются и требуют сопровождения.
\begin{minted}{haskell}
    {-# RULES
    "map/map" forall f g xs. map f (map g xs) = map (f . g) xs
      #-}
\end{minted}

Техника foldr/build list fusion~\cite{gill1993short} определяет общий способ конструирования и деконструирования списка, позволяющий применять одно правило ко многим сочетаниям функций.
Деконструировать список будем с помощью \mintinline{haskell}|foldr|.
Конструировать будем с помощью функции \mintinline{haskell}|build|:
\begin{minted}{haskell}
    build :: (forall b . (a -> b -> b) -> b -> b) -> [a]
    build g = g (:) []
\end{minted}
Например, список \mintinline{haskell}{[1, 2, 3]} и функция \mintinline{haskell}{map} теперь запишутся следующим образом\footnote{В стандартной библиотеке Haskell функции работы со списками написаны нормально, но рядом написаны правила \texttt{RULES} (см.~\ref{subsubsec:rules}), которые подменяют их реализацию на fold/build.}:
\begin{minted}{haskell}
    list123 :: [Int]
    list123 = build \s z -> s 1 (s 2 (s 3 z))

    map :: (a -> b) -> [a] -> [b]
    map f xs = build \s z -> foldr (\x acc -> s (f x) acc) z xs
\end{minted}
На вход \texttt{build} передаётся список Чёрча.
Квантор \texttt{forall b} гарантирует, что производитель параметричен по типу результата: он связывает переданные шаг и базу, поэтому вместо построения списка с последующей свёрткой можно сразу передать нужные обработчики\footnote{Это следствие параметричности, а не только раскрытия определений. Для Haskell правило требует корректного производителя: использование \texttt{seq} для исследования строгости переданных обработчиков может нарушить закон.}~\cite{gill1993short}:
\begin{minted}{text}
    foldr f ini (build g) ?$\equiv$? g f ini
\end{minted}

Вернёмся к примеру \mintinline{haskell}{and (map p xs)}.
Раскроем \texttt{and} через \texttt{foldr}, а \texttt{map} --- через \texttt{build}, затем применим правило:
\begin{minted}{text}
      and (map p xs)
    = foldr (&&) True
        (build (\c z -> foldr (\x r -> c (p x) r) z xs))
    = (\c z -> foldr (\x r -> c (p x) r) z xs) (&&) True
    = foldr (\x r -> p x && r) True xs
\end{minted}
Последняя строка при раскрытии \texttt{foldr} даёт \texttt{allFused} из начала раздела.
В обходе больше нет конструкторов промежуточного списка булевых значений: результат \texttt{p x} сразу передаётся в \texttt{(\&\&)}.
Ленивость второго аргумента \texttt{(\&\&)} сохраняет остановку при первом \texttt{False}.

Дефорестацию также можно производить вручную (см.~\ref{fig:cpp-deforestation}).

Пусть каждое сообщение содержит одно целочисленное поле, которое парсер передаёт в \texttt{processMsg1} или \texttt{processMsg2}.
Тогда вместо создания \texttt{variant} можно сразу вычислить результат:
\begin{minted}{cpp}
    struct SignedValue {
        static int processMsg1(int value) { return value; }
        static int processMsg2(int value) { return -value; }

    // bs -- входные байты; оба обработчика возвращают int

\end{minted}
Парсер выбирает обработчик по виду сообщения; параметр шаблона задаёт эти обработчики при компиляции.

\subsubsection{Visitor pattern} \label{subsubsec:visitor}

Рассмотрим некоторое дерево и его свёртку:
\begin{minted}{haskell}
    data Tree a = Leaf | Node a [Tree a]
    foldTree :: Tree a -> r -> (a -> [r] -> r) -> r
    foldTree tree z f = case tree of
      Leaf -> z
      Node x ts -> f x (map (\t -> foldTree t z f) ts)
\end{minted}

Перепишем и переименуем:
\begin{minted}{haskell}
    data Visitor a r = Visitor { onLeaf :: r, onNode :: a -> [r] -> r }
    visitTree :: Tree a -> Visitor a r -> r
    visitTree t (Visitor z f) = foldTree t z f
\end{minted}

\par\noindent\begin{minipage}{\linewidth}
Теперь представим само дерево через свёртку: интерфейс содержит функцию \texttt{visit}, а конструкторы задаются её реализациями:
\begin{minted}{haskell}
    data Tree a = Tree { visit :: forall r . Visitor a r -> r }

    leaf :: Tree a
    leaf = Tree { visit = \Visitor{onLeaf} -> onLeaf }

    node :: a -> [Tree a] -> Tree a
    node x ts = Tree
      { visit = \v@Visitor{onNode} -> onNode x (map (\t -> visit t v) ts) }
\end{minted}
\end{minipage}\par

Определим два visitor'а для одного дерева:
\begin{minted}{haskell}
    sumVisitor :: Visitor Int Int
    sumVisitor = Visitor 0 (\x rs -> x + sum rs)

    heightVisitor :: Visitor a Int
    heightVisitor = Visitor 0 (\_ rs -> 1 + maximum (0 : rs))

    exampleTree :: Tree Int
    exampleTree = node 1 [leaf, node 2 [], node 3 [leaf]]
    -- visit exampleTree sumVisitor    == 6
    -- visit exampleTree heightVisitor == 2
\end{minted}
В \texttt{onNode} приходят результаты для детей: суммы в первом случае и высоты во втором.
Так одна структура допускает разные интерпретации без изменения её представления.

Для наглядности, покажем этот код ещё и на Kotlin:
\begin{minted}{kotlin}
    interface Visitor<a, r> {
        fun onLeaf(): r
        fun onNode(x: a, subtrees: List<r>): r
    }

    interface Tree<a> {
        fun <r> visit(visitor: Visitor<a, r>): r
    }
    class Leaf<a> : Tree<a> {
        override fun <r> visit(visitor: Visitor<a, r>): r = visitor.onLeaf()
    }
    class Node<a>(val value: a, val subtrees: List<Tree<a>>) : Tree<a> {
        override fun <r> visit(visitor: Visitor<a, r>): r =
            visitor.onNode(value, subtrees.map { it -> it.visit(visitor) })
    }
\end{minted}
Применение visitor'а выглядит так:
\begin{minted}{kotlin}
    val tree: Tree<Int> = Node(1, listOf(Leaf<Int>(), Node(2, listOf())))
    val total = tree.visit(object : Visitor<Int, Int> {
        override fun onLeaf(): Int = 0
        override fun onNode(x: Int, subtrees: List<Int>): Int =
            x + subtrees.sum()
    }) // total == 3
\end{minted}
Здесь показан вариант Visitor, реализующий свёртку.
Другие варианты передают visitor'у сам узел, позволяя ему управлять обходом; наш \texttt{onNode} получает уже результаты обработки поддеревьев.
В частности, в Kotlin вызов \texttt{subtrees.map} вычисляет все результаты для детей до вызова \texttt{onNode}, поэтому этот интерфейс не позволяет visitor'у пропустить их обход.
Само дерево при этом может по-прежнему храниться в объектах \texttt{Leaf} и \texttt{Node}; представление через Visitor ещё не гарантирует устранение этих объектов.

\subsection{Всё через развёртку} \label{subsec:all-unfolds}

Вспомним, что существует универсальная развёртка --- анаморфизм, которая по генерирующей процедуре позволяет получить целую структуру данных (см.~\ref{subsubsec:recursion-schemas}).
\begin{minted}{haskell}
    ana :: Functor f => forall s . (s -> f s) -> s -> Fix f
    ana psi = In . fmap (ana psi) . psi
\end{minted}

Чтобы описать развёртку, достаточно начального состояния и функции одного шага.
Тип состояния нужен этой функции, но пользователю получившейся структуры знать его необязательно.
Упакуем состояние вместе с коалгеброй, скрыв их общий тип \texttt{s}.
Функция \texttt{ana} умеет работать с любым типом состояния, а конкретная упаковка содержит некоторый выбранный тип.
Формально это соответствует каррированию в обратную сторону и переносу квантора через стрелку; математическая запись получившегося типа такова (\texttt{exists} здесь не синтаксис Haskell):
\begin{minted}{text}
    ana :: Functor f => (exists s . (s, s -> f s)) -> Fix f
\end{minted}
Закодируем квантор существования с помощью нового типа (см.~\ref{subsubsec:existentials}):
\begin{minted}{haskell}
    data Box f where
      --     exists s. (s,    s -> f s)
      Box :: forall f s . s -> (s -> f s) -> Box f
\end{minted}
Главная операция такого представления --- наблюдение одного слоя:
\begin{minted}{haskell}
    step :: Functor f => Box f -> f (Box f)
    step (Box s psi) = fmap (\s' -> Box s' psi) (psi s)

    ana' :: Functor f => Box f -> Fix f
    ana' = In . fmap ana' . step
\end{minted}
Функция \texttt{step} открывает упаковку, применяет коалгебру к состоянию и упаковывает каждое новое состояние с той же коалгеброй.
Внешний код получает слой с новыми \texttt{Box f} в рекурсивных позициях, а тип состояния остаётся скрыт.
Повторяя эту операцию, \texttt{ana'} строит обычную рекурсивную структуру.

В обратную сторону любую готовую структуру можно упаковать, взяв её саму в качестве состояния, а \texttt{out} --- в качестве коалгебры:
\begin{minted}{haskell}
    to :: Fix f -> Box f
    to x = Box x out

    from :: Functor f => Box f -> Fix f
    from = ana'
\end{minted}
Композиция \mintinline{haskell}{from (to x)} разворачивает \texttt{x} с помощью \texttt{out} и восстанавливает ту же структуру.
Композиция \mintinline{haskell}{to (from b)} может изменить внутреннее представление: вместо исходного состояния, например числа, теперь хранится рекурсивная структура.
Однако последовательные наблюдения с помощью \texttt{step} дают те же слои.
В этом смысле имеем изоморфизм \mintinline{haskell}|Fix f ?$\simeq$? Box f|: равенство упаковок понимается как равенство наблюдаемого поведения\footnote{Для потенциально бесконечных структур математическая модель использует наибольшую неподвижную точку функтора. Ленивый Haskell позволяет представлять их через \texttt{Fix}; для частичных значений и операций вроде \texttt{seq} законы требуют оговорок. Сравнение абстрактных представлений через их наблюдения обсуждается в~\cite{gibbons2008unfolding}.}.
Иногда такое представление называют \vocab{co-Church encoding}~\cite{gibbons2008unfolding}.

Например, бесконечный ленивый список натуральных чисел может быть задан следующим образом.
Для хранения описания и запроса отдельного слоя мы \point{не полагаемся на ленивость Haskell}, поэтому эта техника применима и в энергичных языках.
\begin{minted}{haskell}
    nats :: Box (ListF Integer)
    nats = Box 0 \curr -> Cons curr (curr + 1)
\end{minted}
Первое наблюдение даёт элемент \texttt{0} и упаковку состояния \texttt{1}, следующее --- элемент \texttt{1} и упаковку состояния \texttt{2}:
\begin{minted}{text}
    step nats ?$\rightsquigarrow$? Cons 0 <Box с состоянием 1>
    step <Box с состоянием 1> ?$\rightsquigarrow$? Cons 1 <Box с состоянием 2>
\end{minted}
Каждый вызов строит только один слой.
А вот преобразование \mintinline{haskell}{from nats} в бесконечный \texttt{Fix} уже использует ленивость Haskell: в энергичном языке потребовалась бы явная задержка рекурсивного построения.

\begin{task}
    Реализуйте функцию \mintinline{haskell}{take :: Int -> Box (ListF a) -> Box (ListF a)}, которая описывает первые $n$ элементов, не разворачивая их заранее.
    Подсказка: к скрытому состоянию можно добавить счётчик оставшихся элементов; при $n\leq 0$ исходный поток запрашивать не нужно.
\end{task}

Иначе говоря, бесконечные структуры данных представимы как процедуры, лениво генерирующие слой рекурсивной структуры за слоем по запросу.

\subsubsection{Абстрактные типы данных} \label{subsubsec:abstract-data-types}

Рассмотрим случай, когда функтор формы представляет собой произведение:
\[
    \text{\texttt{s -> f s}} \iso \left( \prod_{i}(t_i\ap s) \right)^{\displaystyle s} \iso \prod_i(s\to t_i\ap s)
\]
То есть коалгебра эквивалентна кортежу функций.
Вместе со скрытым состоянием получаем представление \point{абстрактного типа данных (abstract data type, ADT)}: пользователь работает с состоянием через заданные операции~\cite{gibbons2008unfolding}.
Здесь ADT означает абстрактный тип данных; выше то же сокращение использовалось для алгебраических типов данных (algebraic data types).
Например, у счётчика есть операция наблюдения текущего числа и операция перехода к следующему состоянию:
\begin{minted}{haskell}
    data CounterF s = CounterF Integer s
    instance Functor CounterF where
      fmap f (CounterF value s) = CounterF value (f s)

    type Counter = Box CounterF

    counter :: Counter
    counter = Box (0 :: Integer) (\n -> CounterF n (n + 1))

    counterFromInterval :: Counter
    counterFromInterval = Box (100 :: Integer, 100 :: Integer)
      (\(lo, hi) -> CounterF (hi - lo) (lo, hi + 2))
\end{minted}
Первая реализация хранит число, вторая --- границы интервала и показывает их разность.
При переходе к следующему состоянию первая увеличивает число на один, а вторая расширяет интервал на два.
Коалгебра типа \mintinline{haskell}{s -> CounterF s} объединяет две операции над скрытым состоянием: \mintinline{haskell}{s -> Integer} и \mintinline{haskell}{s -> s}.
Чтобы ими мог пользоваться клиент, определим операции над самим \texttt{Counter}:
\begin{minted}{haskell}
    value :: Counter -> Integer
    value c = current
      where CounterF current _ = step c

    increment :: Counter -> Counter
    increment c = next
      where CounterF _ next = step c
\end{minted}
Вызов \texttt{step c} имеет тип \mintinline{haskell}{CounterF Counter}: новое состояние уже упаковано вместе с коалгеброй, поэтому \texttt{increment} возвращает готовый счётчик, не раскрывая тип \texttt{s}.
Операция \texttt{value} наблюдает текущее число, а \texttt{increment} возвращает новый счётчик; исходный счётчик при этом не меняется.
Теперь можно написать клиентский код, используя только эти операции:
\begin{minted}{haskell}
    sample :: Counter -> [Integer]
    sample c0 =
      let c1 = increment c0
          c2 = increment c1
      in [value c0, value c1, value c2]

    -- sample counter             == [0, 1, 2]
    -- sample counterFromInterval == [0, 2, 4]
    -- value counter              == 0
\end{minted}
Один и тот же клиентский код работает с обеими реализациями и получает разные результаты: поведение операций задаёт упакованная коалгебра.
При этом клиенту не нужно знать, хранится ли внутри число или пара границ.
В модуле счётчика достаточно экспортировать тип \texttt{Counter}, начальные значения и функции \texttt{value} и \texttt{increment}; вспомогательные \texttt{Box}, \texttt{CounterF} и \texttt{step} клиенту не нужны.
На самом деле мы уже встречали такую конструкцию ранее, когда говорили про экзистенциальные типы~\ref{subsubsec:existentials} (там мы использовали инстансы классов типов в качестве кортежей функций).

ООП объекты тоже можно рассматривать через коалгебры.
Подробнее про соотношение объектов и абстрактных типов данных можно почитать в~\cite{cook2009understanding}.

\subsubsection{Stream fusion} \label{subsubsec:stream-fusion}

Ранее мы рассматривали foldr/build list fusion оптимизацию, элиминирующую промежуточные списки (см.~\ref{subsubsec:deforestation-fusion}).
Для некоторых сочетаний функций эффективно объединить вычисления таким способом сложнее: например, \texttt{zip} должен согласовать продвижение двух источников.
Явное состояние развёртки позволяет хранить состояния обоих источников вместе и управлять их шагами\footnote{Досрочная остановка сама по себе не мешает foldr/build: например, для \texttt{take} в GHC есть соответствующие правила переписывания. Ленивый \texttt{foldr} не обязан вычислять результат для всего хвоста.}.

Позднее была предложена техника использования ко-структуры списка --- развёртки или \mintinline{haskell}{Stream}\footnote{\url{https://markkarpov.com/tutorial/ghc-optimization-and-fusion.html}}~\cite{coutts2007stream}:
\begin{minted}{haskell}
    data ListF a r = Nil | Cons a r
    type MyStream a = Box (ListF a) -- ?$\exists$?s . (s -> ListF a s, s)
    -- ?$\iso$?
    data Step a s = Done | Yield a s
    data Stream a where
      Stream :: forall a s . (s -> Step a s) -> s -> Stream a

    stream :: [a] -> Stream a
    stream xs = Stream (\case [] -> Done; x:xs -> Yield x xs) xs
\end{minted}

\par\noindent\begin{minipage}{\linewidth}
\begin{minted}{haskell}
    unstream :: Stream a -> [a]
    unstream (Stream next s) = case next s of
      Done -> []
      Yield a s' -> a : unstream (Stream next s')
\end{minted}
\end{minipage}\par

Идея в том, что \point{преобразования потоков можно описывать нерекурсивными функциями одного шага}.
Вместо рекурсивного вызова шаг возвращает состояние следующей итерации.
Повторение шагов выполняет потребитель, например \texttt{unstream}; его определение по-прежнему рекурсивно.
Так тела преобразований становятся доступны обычному инлайнингу и устранению конструктора непосредственно перед его разбором.
\begin{minted}{haskell}
    mapS :: (a -> b) -> Stream a -> Stream b
    mapS f (Stream next s) = Stream next' s
      where
        next' s = case next s of
          Done -> Done
          Yield x s' -> Yield (f x) s'
\end{minted}

Общий пайплайн выглядит следующим образом:
\begin{enumerate}
    \item Мы пишем все функции работы со списками через стримы:
    \begin{minted}{haskell}
        map :: (a -> b) -> [a] -> [b]
        map f = unstream . mapS f . stream
    \end{minted}
    \item С помощью RULES (см.~\ref{subsubsec:rules}) устраняем соседние преобразования \texttt{stream . unstream}. Полученный поток представляет ту же последовательность элементов, хотя его скрытое состояние может отличаться\footnote{Как и для \texttt{Box}, сравниваем поведение корректных упаковок, а не их внутреннее представление. В частности, на произвольном \texttt{undefined :: Stream a} буквальное равенство с \texttt{id} не выполняется.}.
    \item Далее помогают обычные компиляторные оптимизации.\footnote{Можно гарантировать полную дефорестацию с помощью staging (см. далее~\ref{sec:datatype-generic})~\cite{kiselyov2017stream}.}
\end{enumerate}

Попробуем описать шаг фильтрации.
Если исходный шаг вернул элемент, не удовлетворяющий предикату, ни \texttt{Done}, ни \texttt{Yield} не подходят: поток ещё не закончился, но элемента для потребителя пока нет.
Без дополнительного варианта пришлось бы рекурсивно искать следующий подходящий элемент прямо внутри функции шага.
Поэтому добавим \texttt{Skip}: состояние изменилось, но элемент не появился.
\begin{minted}{haskell}
    data Step a s = Done | Skip s | Yield a s

    filterS :: (a -> Bool) -> Stream a -> Stream a
    filterS p (Stream next s) = Stream next' s
      where
        next' s = case next s of
          Done -> Done
          Skip s' -> Skip s'
          Yield a s' -> if p a then Yield a s' else Skip s'
\end{minted}

Например, последовательные шаги \mintinline{haskell}{filterS even (stream [1,2,3,4])} таковы:
\begin{center}
    \begin{tabular}{lll}
        Состояние до шага & Результат & Новое состояние \\
        \texttt{[1,2,3,4]} & \texttt{Skip} & \texttt{[2,3,4]} \\
        \texttt{[2,3,4]} & \texttt{Yield 2} & \texttt{[3,4]} \\
        \texttt{[3,4]} & \texttt{Skip} & \texttt{[4]} \\
        \texttt{[4]} & \texttt{Yield 4} & \texttt{[]} \\
        \texttt{[]} & \texttt{Done} & ---
    \end{tabular}
\end{center}
Для пользователя это по-прежнему список \texttt{[2,4]}.

\par\noindent\begin{minipage}{\linewidth}
При добавлении \mintinline{haskell}|Skip| нужно также дополнить разбор шагов в \mintinline{haskell}|unstream| и \mintinline{haskell}|mapS|:
\begin{minted}{haskell}
    unstream (Stream next s) = case next s of
      Done -> []
      Skip s' -> unstream (Stream next s')
      Yield a s' -> a : unstream (Stream next s')

    mapS f (Stream next s) = Stream next' s
      where
        next' s = case next s of
          Done -> Done
          Skip s' -> Skip s'
          Yield x s' -> Yield (f x) s'
\end{minted}

\end{minipage}\par
Теперь правило устранения \texttt{stream . unstream} понимается с точностью до внутренних \texttt{Skip}: преобразование в список стирает их.
Число пропусков не входит в наблюдаемый результат списочного интерфейса; код, который сам считает шаги \texttt{Skip}, уже может различить эти представления~\cite{gibbons2008unfolding}.

Доведём до результата пример \mintinline{haskell}{sum (map (+1) (filter even xs))} для конечного списка целых чисел.
Потребителю суммы нужен цикл с аккумулятором:
\begin{minted}{haskell}
    foldlS :: (b -> a -> b) -> b -> Stream a -> b
    foldlS f initial (Stream next s0) = go initial s0
      where
        go acc s = case next s of
          Done -> acc
          Skip s' -> go acc s'
          Yield x s' -> (go $! f acc x) s'
\end{minted}
Это строгая левая свёртка: перед следующим шагом вычисляется новый аккумулятор.
Если записать \texttt{filter}, \texttt{map} и суммирование через потоки, получим цепочку преобразований:
\begin{minted}{text}
      foldlS (+) 0 (stream
        (unstream (mapS (+1) (stream
          (unstream (filterS even (stream xs)))))))
    = foldlS (+) 0 (mapS (+1) (filterS even (stream xs)))
\end{minted}
В первой строке дважды встречается \texttt{stream (unstream ...)}; после устранения этих пар промежуточные списки исчезают.
Инлайнинг \texttt{mapS}, \texttt{filterS} и \texttt{stream} объединяет их функции шага:
\begin{minted}{haskell}
    nextCombined :: [Int] -> Step Int [Int]
    nextCombined = \case
      [] -> Done
      x:xs -> if even x then Yield (x + 1) xs else Skip xs
\end{minted}
Осталось подставить этот шаг в цикл потребителя.
Каждый \texttt{Done}, \texttt{Skip} или \texttt{Yield} сразу разбирается в \texttt{go}, поэтому конструирование и разбор можно сократить:
\begin{minted}{haskell}
    sumFused :: [Int] -> Int
    sumFused = go 0
      where
        go acc = \case
          [] -> acc
          x:xs -> if even x
            then (go $! acc + (x + 1)) xs
            else go acc xs
\end{minted}
Например, для \texttt{[1,2,3,4]} остаются слагаемые \texttt{3} и \texttt{5}, результат --- \texttt{8}.
Рекурсивный обход сохранился в одном цикле; промежуточные списки и значения \texttt{Step} в нём больше не создаются.
Это результат показанных преобразований; срабатывание всех оптимизаций в конкретной программе зависит от инлайнинга и правил компилятора.

В стандартной библиотеке Haskell всё-таки используется foldr/build fusion, однако существует множество промышленных библиотек стримов~\cite[глава 14]{bragilevsky-haskell}.

Больше про стримы можно почитать у Олега Киселёва\footnote{\url{https://okmij.org/ftp/Streams.html}}.

\subsection{Вездесущий дуализм} \label{subsec:data-duality}

Мы рассмотрели три формы рекурсивных данных:
\begin{itemize}
    \item \mintinline{haskell}{Fix f} --- обычные рекурсивные типы данных, конечные в энергичных языках;
    \item \mintinline{haskell}{?$\forall$?a . (f a -> a) -> a} --- Church encoding, конечные структуры заданные свёртками;
    \item \mintinline{haskell}{?$\exists$?s . (s -> f s, s)} --- co-Church encoding, потенциально бесконечные структуры данных, абстракции по данным (работаем через интерфейс над сокрытым представлением).
\end{itemize}

В этом разделе мы рассмотрим некоторые практические примеры, в которых пространство решений задано дуальными представлениями коллекций.

\subsubsection{Push vs pull streaming} \label{subsubsec:push-pull}

Рассмотрим различные представления списков или, как их иногда называют, потоков событий.
Подробнее сравнение можно посмотреть тут~\cite[параграф 3]{kiselyov2017stream}.

Church encoding для списков даёт \vocab{push stream}, или \vocab{internal iteration}, или \vocab{Observer pattern}\footnote{\url{https://learn.microsoft.com/en-us/dotnet/api/system.iobserver-1?view=net-9.0}} (в некотором смысле частный случай Visitor pattern~\ref{subsubsec:visitor}), когда мы регистрируем обработчика событий, а коллекция вызывает (push) на нём методы.
Примерами push потоков являются Java Stream API\footnote{\url{https://docs.oracle.com/javase/8/docs/api/java/util/stream/Stream.html}}, Closure Transducers\footnote{\url{https://clojure.org/reference/transducers}}.
\begin{minted}{kotlin}
    events.observe(object : Observer<Event> {
        override fun onComplete() { .. }
        override fun onNext(elem: Event) { .. }
    })
\end{minted}

co-Church encoding для списков даёт \vocab{pull stream}, или \vocab{external iteration}, или \vocab{Iterator pattern}.
Чтобы получить следующий элемент, его нужно явно запросить (pull) потребляющему коду.
Это представление часто гораздо удобнее с точки зрения использования (см.~\ref{subsubsec:stream-fusion})\footnote{\url{https://github.com/pulldown-cmark/pulldown-cmark/?tab=readme-ov-file\#why-a-pull-parser}}, однако сложнее на стороне имплементации, потому что нужно выделить и поддерживать экзистенциальное состояние в коалгебре.
Генераторы призваны автоматизировать выделение этого состояния, так как можно заметить, что это continuation вычисления (см. далее~\ref{subsubsec:generators-coroutines}).

\subsubsection{Data vs codata} \label{subsubsec:data-codata}

Вспомним функтор-формы для списка:
\begin{minted}{haskell}
    data ListF a r = Nil | Cons a r
\end{minted}

С помощью ключевого слова \mintinline{haskell}{data} мы определяем новый алгебраический тип данных через способы его сконструировать.
Далее, с помощью pattern-matching мы можем деконструировать значения алгебраического типа данных и воспользоваться хранящейся в нём информацией.
\begin{minted}{haskell}
    data List a where
      List :: ListF a (List a) -> List a

    fold :: (ListF a r -> r) -> List a -> r
    fold alg xs = case xs of
      List Nil -> alg Nil
      List (Cons y ys) -> alg (Cons y (fold alg ys))
\end{minted}

Однако, также можно определять тип данных через способы его деконструировать с помощью ключевого слова \mintinline{haskell}{codata} (в воображаемом языке).
Так, у ко-списка можно потребовать показать следующий слой структуры.
Сконструировать такой тип данных можно с помощью co-pattern-matching'а, описав как деконструирующая функция должна вести себя на конструирующем терме (\texttt{unfold coalg s})\footnote{\href{https://youtu.be/ZCdYIEwcna0?si=XEQSBFhnehQFZPxy}{(youtube) CS410 2017 Lecture 15 Coinduction and Coalgebras}}.
\begin{minted}{haskell}
    codata CoList a where
      force :: CoList a -> ListF a (CoList a)

    unfold :: (s -> ListF a s) -> s -> CoList a
    force (unfold coalg s) = case coalg s of
      Nil -> Nil
      Cons x s' -> Cons x (unfold coalg s')
\end{minted}

По сути, \mintinline{haskell}{codata} представляет собой словарь функций, которые захватывают некоторое состояние, необходимое для генерации следующих слоёв структуры.
Так, \mintinline{haskell}{codata} можно сравнить с ООП интерфейсами, а co-pattern-matching с анонимной реализацией интерфейса.
Предыдущие два примера можно записать, например, в Kotlin следующим образом (форма списка кодируется как \mintinline[escapeinside=**]{kotlin}|Pair<a, r>?|, убедитесь самостоятельно, что этот тип изоморфен \mintinline{haskell}{ListF}).
\begin{minted}[escapeinside=**]{kotlin}
    class List<a>(val layer: Pair<a, List<a>>?)

    fun <a, r> fold(alg: (Pair<a, r>?) -> r, xs: List<a>): r =
        if (xs.layer == null) alg(null)
        else alg(Pair(xs.layer.first, fold(alg, xs.layer.second)))

    interface CoList<a> { fun force(): Pair<a, CoList<a>>? }

    fun <a, s> unfold(coalg: (s) -> Pair<a, s>?, ini: s): CoList<a> =
        object : CoList<a> {
            override fun force(): Pair<a, CoList<a>>? {
                val layer = coalg(ini)
                return if (layer == null) null else
                    Pair(layer.first, unfold(coalg, layer.second))
            }
        }
\end{minted}

Функциональный стиль программирование в основном оперирует напрямую наблюдаемыми данными \mintinline{haskell}{data}, а ООП --- скрывает данные за интерфейсами \mintinline{haskell}{codata}.
Однако, обе конструкции имеют свои понятные области применения и ими не стоит пренебрегать вне зависимости от предпочитаемого стиля~\cite{downen2019codata}\footnote{\url{https://reasonablypolymorphic.com/blog/review-codata/}}.

В языках с проверкой тотальности функций разделяют индуктивные и коиндуктивные определения.
Для них используются паттерн-матчинг и ко-паттерн-матчинг, принцип индукции (катаморфизм) и принцип коиндукции (анаморфизм).
Индуктивные определения задают конечные структуры данных, проверка тотальности проверяет, что рекурсивные вызовы делаются на структурно меньших подтермах.
Коиндуктивные определения задают потенициально бесконечные структуры данных, для них проверяется продуктивность --- порождающая функция всегда после рекурсивного вызова породит новый конструктор~\footnote{\url{https://rocq-prover.org/doc/V8.18.0/refman/language/core/coinductive.html}}.

\subsection{Приложение: категория алгебр} \label{subsec:cats}

Это факультативный раздел, не являющийся необходимым для понимания курса в дальнейшем.
Однако, полезен для понимания часто употребимой терминологии.

\vocab{Категория} --- это коллекция объектов и коллекция стрелок.
Для каждого объекта $X$ существует тождественная стрелка, а для каждой пары стрелок существует способ получить их композицию: $f : Y \to Z, g : X \to Y \Rightarrow f \circ g : X \to Z$.

Определяют категорию, соответствующую Haskell --- $Hask$.
На самом деле это плохая категория с точки зрения теории, но для наших нестрогих рассуждений подойдёт\footnote{\url{https://math.andrej.com/2016/08/06/hask-is-not-a-category/}}.
Объектами в Hask являются типы языка Haskell, а морфизмами --- термы, задающие функции между соответствующими типами.
Тождественный морфизм --- \mintinline{haskell}|id|, композиция задаётся как \mintinline{haskell}|f . g = \x -> f (g x)|.

\begin{task}
    Как в такой категории представить константы?
\end{task}

\vocab{Функтором} называется отображение между категориями, которое объектам одной категории сопоставляет объекты другой, а стрелкам одной --- стрелки другой.
В Haskell типовые конструкторы задают отображение между объектами, а \mintinline{haskell}|fmap| --- между стрелками.
Функтор должен сохранять тождественный морфизм и композицию.
\begin{figure}[ht]
    \centering
    \includegraphics[width=0.25\textwidth]{figs/functor}
\end{figure}

\vocab{Алгеброй} в категории $C$ называется пара из объекта категории $X \in Obj(C)$ и морфизма $\phi : F\ap X \to X$, где $F$ --- функтор.
Сам морфизм $F\ap X \to X$ называют \vocab{f-алгеброй}.
Алгебрами в смысле категорий можно описывать алгебры.
Так, в качестве объекта $X$ берём носитель алгебры.
В качестве функтора $F$ --- сигнатуру алгебры в виде типа-формы.
Тогда морфизмом будет интерпретацией сигнатуры.

\vocab{Морфизмом алгебр} называется такой морфизм между носителями $h : X \to Y$, что следующая диаграмма коммутирует.
Говорят, что \vocab{диаграмма коммутирует}, если все возможные пути по стрелкам в ней равны.
\begin{figure}[ht]
    \centering
    \includegraphics[width=0.3\textwidth]{figs/alg-homomorphism}
\end{figure}

В морфизме алгебр можно обнаружить знакомые черты гомоморфизмов, то есть операций между носителями, которые ``уважают'' операции сигнатуры алгебраической теории.

Алгебры над категорией $C$ образуют \vocab{категорию алгебр}, в которой объектами являются алгебры, а морфизмами --- морфизмы алгебр.

\vocab{Начальным (инициальным) объектом} категории называется объект, из которого в каждый другой объект существует уникальная стрелка.
\vocab{Терминальным (финальным) объектом} категории называется объект, в который из каждого другого объекта категории существует уникальная стрелка.

Инициальный и терминальный объекты категории не обязательно присутствуют в единственном экземпляре.
Но все инициальные объекты изоморфны друг другу, как и все терминальные.

\begin{task}
    Приведите начальный и терминальный объекты категории $Hask$.
\end{task}

Рекурсивный тип --- это тип, значит ему соответствует объект в категории Hask.
$X$ является рекурсивным типом с формой $F$, если имеет место следующий изоморфизм:
\[X \simeq F\ap X\]

Можно заметить, что свидетель изоморфизма справа налево напоминает f-алгебру, а слева направо --- f-коалгебру (всё то же самое, только все стрелки в обратную сторону).
И действительно, подходящий объект $X$ должен быть либо начальным объектом категории алгебр, либо терминальным объектом категории коалгебр (с соответствующими морфизмами).
Первый вариант соответствует конечным структурам данных, второй --- потенциально бесконечным.

Начальным объектом категории алгебр над $Hask$ для функтора $f$ является следующая алгебра: \mintinline{haskell}|(Fix f, In)|\footnote{\url{https://bartoszmilewski.com/2017/02/28/f-algebras/}}\footnote{\url{https://ncatlab.org/nlab/show/catamorphism}}. % todo проверить инициальность свёрток
