In this section we will recall the main concepts of functional programming and the Haskell language.

\subsection{Terms and Reduction} \label{subsec:terms-reduction}

In FP, programs are expressions.
Program execution is the reduction of those expressions to simpler ones.
Expressions can be represented either as a linear sequence of symbols or as a tree, which makes them easier to understand without requiring knowledge of auxiliary associativity rules and so on.

The simplest functional language is the lambda calculus.
Expressions in it are called lambda terms, which consist of nodes of three kinds ($V$ is the set of valid identifiers, $\Lambda$ is the set of lambda terms):
\begin{description}
    \item[Variables] $x \in \Lambda$, if $x \in V$ \hspace{2em}
    \begin{tikzpicture}
        \node [expr] (x) {x};
    \end{tikzpicture}
    \item[Abstraction] $(\lambda x\ldotp M) \in \Lambda$, if $x \in V, M \in \Lambda$ \hspace{2em}
    \begin{tikzpicture}
        \node [expr] (lam) {$\lambda$};
        \node [decl] (x) [below right = of lam] {$x$};
        \node [subtree] (m) [below = of lam] {$M$};
        \draw[->] (m.north) -- (lam);
        \draw[->] (x) -- (lam);
    \end{tikzpicture}
    \item[Application] $(M~N) \in \Lambda$, if $M \in \Lambda, N \in \Lambda$ \hspace{2em}
    \begin{tikzpicture}
        \node [expr] (dog) {$@$};
        \node [subtree] (m) [below left= of lam] {$M$};
        \node [subtree] (n) [below right= of lam] {$N$};
        \draw[->] (m.north) -- (lam);
        \draw[->] (n.north) -- (lam);
    \end{tikzpicture}
\end{description}

In an arbitrary expression, some subterm can be replaced with a formal parameter that must be declared higher in the tree by a special lambda node.
Instead of the formal parameter, we can later substitute various concrete arguments using the application node $@$ and reuse the expression for different purposes (for example, see Fig. \ref{fig:lam}).
Reduction is defined by the following rewriting rule: an application of a lambda function to an argument is found, and the argument is substituted for all free occurrences of the variable bound by the lambda in the function body (Fig. \ref{fig:reduction}).

\subsection{Types}

Software is hard.
Therefore, bugs constantly and inevitably appear in programs.
They can be found, among other ways, statically, that is, without running the program.
One form of static analysis is type checking.

The idea of type analysis is that we attempt to assign a syntactic label to every node of the program tree according to certain rules.
If every node can be labeled that way, then we say the program type-checks and is “good”.
For example, Fig. \ref{fig:to-be-typed} shows an expression, and Fig. \ref{fig:typed} shows the same tree with labels assigned consistently with a type system.

\vocab{A type system} defines the syntax of type labels and the rules by which they can be assigned.
Syntax is usually described in a classical BNF-like notation, and rules are expressed as typing judgments.
For example, the rules for simply-typed lambda calculus look like this:
\[
    %! suppress = EscapeAmpersand
    \begin{array}{l c r}
        \infer[ctx]{\Gamma \vdash x: \sigma}{(x: \sigma) \in \Gamma}
        &
        \infer[elim\to]{\Gamma \vdash M\;N : \tau}{\Gamma \vdash M : \sigma \to \tau & \Gamma \vdash N : \sigma}
        &
        \infer[intro\to]{\Gamma \vdash \lambda x^{\color{red} \sigma}\ldotp M : \sigma \to \tau}{\{x : \sigma\} \cup \Gamma \vdash M : \tau}
    \end{array}
\]

Type labels are purely syntactic, but they can be interpreted.
The most popular interpretation is to treat a type label as a set.
Thus, the label $int \to int$ can correspond to the set of functions between the sets of integers $\mathbb{Z} \to \mathbb{Z}$.

\subsection{Functions in Haskell}

At its core, Haskell is an extended typed lambda calculus enriched with primitive types, the ability to declare new names, data structures, and type classes.

Examples of lambda abstractions in the GHCi REPL:

\begin{minted}{haskell}
    ghci> (\x -> x + 1) 4
    5
\end{minted}

You can learn the type of a function in the interpreter (in reality numbers are polymorphic, but we will discuss that later):
\begin{minted}{haskell}
    ghci> :t \x -> x + 1
    \x -> x + 1 :: Int -> Int
\end{minted}

Functions can be given names.
Names can be annotated with types, and it is recommended to do so explicitly for top-level declarations in source files:
\begin{minted}{haskell}
    f :: Int -> Int
    f x = x + 1
\end{minted}

If a type name begins with a lowercase letter, it is not a concrete type but a type variable that can take different values depending on the call site.
This capability is called \vocab{parametric polymorphism}.
Thus, a function that simply returns its argument does not constrain the argument type.
At the same time, the result type must match the argument type:
\begin{minted}{haskell}
    id :: a -> a
    id x = x

    ghci> :t id 5
    id 5 :: Int
\end{minted}

Functions can take other functions as arguments (such functions are called \vocab{higher-order functions}).
A function name can consist of special symbols, in which case it is treated as an operator and can be used in infix form:
\begin{minted}{haskell}
    ($) :: (a -> b) -> a -> b
    f $ x = f x
\end{minted}

Example of a recursive function using guards to distinguish the base case:
\begin{minted}{haskell}
    factorial :: Int -> Int
    factorial n
      | n < 1 = 1
      | otherwise = n * factorial (n - 1)
\end{minted}

\subsection{Data in Haskell}

Haskell has built-in support for declaring new data types from other types and constructing values of those types.

Define a data type describing animals:
\begin{minted}{haskell}
    data Animal
      = Cat String Int
      | Dog String
\end{minted}

We defined the data type \texttt{Animal} and two ways to create values of this type: one for cats and one for dogs.
\texttt{Cat} and \texttt{Dog} are \vocab{data constructors}.
They are functions whose implementation is provided by the language.
They allocate memory for instances of the type and place components positionally.
Cats are described by a name and the remaining number of lives, while dogs are described only by a name.
\begin{minted}{haskell}
    Cat :: String -> Int -> Animal
    Dog :: String -> Animal
\end{minted}

To use the information stored in a data structure, it must be deconstructed using pattern matching.
We match the value against a pattern.
If the pattern resembles the way the value was constructed, it is selected among other alternatives and the variables declared in it bind to the corresponding positional contents of the data structure:
\begin{minted}{haskell}
    show :: Animal -> String
    show animal = case animal of
      Cat name nLives -> "This is cat " ++ name ++ " " ++ show nLives
      Dog name -> "This is dog " ++ name
\end{minted}

Haskell offers special syntax for declaring record fields with named labels.
\begin{minted}{haskell}
    data Penguin = Penguin { getName :: String, getAge :: Int }
    penguin = Penguin { getName = "Andrey", getAge = 500 }
\end{minted}
Haskell generates accessor functions for field access:
\begin{minted}{haskell}
    ghci> :t getName :: Penguin -> String
\end{minted}

Often functions in programming are partial — for some argument values they return a result, and for others they do not.
Let us model this with a dedicated data type.
If there is a real result, we return it.
If there is none, we return a specially reserved constant value of that type.
\begin{minted}{haskell}
    data MaybeD = NothingD | JustD Double
    sqrt :: Double -> MaybeD
    sqrt x = if x < 0 then NothingD else JustD (calcSqrt x)
\end{minted}

One can notice that this would require defining a separate type \texttt{MaybeT} for each type \texttt{T}.
Therefore Haskell allows type-level abstraction, just as we can abstract over values in terms.
\begin{minted}{haskell}
    data Maybe a = Nothing | Just a
    sqrt :: Double -> Maybe Double
    sqrt x = if x < 0 then Nothing else Just (calcSqrt x)
\end{minted}

Note that \texttt{Maybe} is not a concrete type itself; it requires a type parameter to produce a concrete type.
\texttt{Maybe} is called a \vocab{type constructor}.

With abstraction at the type level also comes application of types to types.
What if a type constructor is given fewer parameters than expected?
What if it is given more?
Correctness of type applications is enforced by the \vocab{kind system}\footnote{In Russian literature, kinds are sometimes called “genera of types”, but we will not use that terminology.}.
Kinds are the simplest “types for types”, syntactic labels that control whether the types written by the programmer are valid.
Ordinary types have kind \texttt{*}.
Type constructors have arrow kinds.
For example, \texttt{Maybe :: * -> *}.
Applying a type constructor to a type of the appropriate kind consumes one arrow:
\begin{minted}{haskell}
    ghci> :k Int
    Int :: *
    ghci> :k Maybe
    Maybe :: * -> *
    ghci> :k Maybe Int
    Maybe Int :: *
\end{minted}

In addition to brand-new data types, Haskell allows type synonyms.
These are names that can be used instead of other types when the original type expression is too long to write everywhere:
\begin{minted}{haskell}
    type T a = VeryLongType Int (a -> AnotherLongType a)
\end{minted}

If a data type has only one constructor and only one field, there is no need to allocate runtime memory containing a constructor tag and field references.
In that case, the value of the new type can be represented by the wrapped value itself, leaving the new type present only at compile time and reducing runtime overhead.
To declare such wrapper types, use \texttt{newtype} instead of \texttt{data}:
\begin{minted}{haskell}
    newtype CourseId = CourseId Int64
    newtype ModuleId = ModuleId Int64
\end{minted}

\subsection{Type Classes in Haskell}

Parametric polymorphism allows the same code to work for different input types.
Type classes allow one identifier to refer to different implementations for different data types (which is analogous to overloading in other languages).
Type classes are, as they say, the mechanism of \vocab{ad-hoc polymorphism}.
For example, we can declare the symbol \texttt{==}, whose implementation depends on the chosen type \texttt{a}:
\begin{minted}{haskell}
    class Eq a where
      (==) :: a -> a -> Bool
\end{minted}

For each type, one can declare its own implementation of \texttt{Eq}:
\begin{minted}{haskell}
    instance Eq CourseId where
      CourseId x == CourseId y = x == y

    instance Eq a => Eq [a] where
      [] == [] = True
      x:xs == y:ys = x == y && xs == ys
\end{minted}

Now, depending on the concrete type \texttt{a} at the call site, the appropriate implementation for that type will be selected:
\begin{minted}{haskell}
    ghci> CourseId 1 == CourseId 2
    False
    ghci> [CourseId 1, CourseId 2] == [CourseId 1, CourseId 2]
    True
\end{minted}

Earlier, parametrically polymorphic functions could only do one of two things with their arguments: return them or pass them to other polymorphic functions.
To do anything else, additional information about the type is needed, because otherwise there is no guarantee that the required operations are defined for a value of that type.
For example, the function \texttt{suc n = n + 1} will not work for strings, because addition is not defined for them.
Therefore it would be incorrect to assign it the polymorphic type \texttt{suc :: a -> a}.

Type classes, in addition to overloading, are also a mechanism for restricting polymorphism.
We can explicitly specify that a function requires not any type as input, but any type for which the operations we need are defined.
Thus, for the type of \texttt{suc} it is enough to constrain it with the presence of addition (the operation denoted by \texttt{+} is declared in the \mintinline{haskell}|Num| type class):
\begin{minted}{haskell}
    suc :: Num a => a -> a
\end{minted}

\subsection{Monads in Haskell}

The type class \texttt{Functor} is declared for type constructors and allows replacing every element of one type in a container with elements of another type while preserving the container structure.

\begin{minted}{haskell}
    class Functor (f :: * -> *) where
      fmap :: (a -> b) -> f a -> f b

    instance Functor [] where
      fmap :: (a -> b) -> [a] -> [b]
      fmap _ [] = []
      fmap f (x:xs) = f x : fmap f xs
\end{minted}

In Haskell, every function simply produces a result of some type.
However, in programming we often need functions that not only produce a result but also do something else.
For example, modify some state or write to the console.
In other words, they perform side effects.
In any case, in Haskell we can only return a result from a function, so such side effects are encoded as additional structure wrapping the pure result.
Thus, where a pure function would return a value of type \texttt{a}, after introducing effects it instead returns a \point{computation} of type \texttt{f a}.

\begin{itemize}
    \item If a function can fail, then \texttt{f = Maybe}.
    \item If a function reads a global environment of type \texttt{e}, then \texttt{f = e -> \_}.
    \item If a function reads and updates state \texttt{s}, then \texttt{f = s -> (s, \_)}.
\end{itemize}

The Haskell standard library provides several type classes for working with values of the form \texttt{f a}.
They allow you to abstract away from the structure \texttt{f} and work with values of type \texttt{a} inside as if there were no additional structure.

The first such type class allows writing expressions over computations \texttt{f a}.
\begin{minted}{haskell}
    class Functor f => Applicative (f :: * -> *) where
      pure :: a -> f a
      liftA2 :: (a -> b -> c) -> f a -> f b -> f c

    instance Applicative Maybe where
      pure :: a -> Maybe a
      pure = Just

      liftA2 :: (a -> b -> c) -> Maybe a -> Maybe b -> Maybe c
      liftA2 _ Nothing _ = Nothing
      liftA2 _ _ Nothing = Nothing
      liftA2 f (Just x) (Just y) = Just (f x y)
\end{minted}

The second type class allows sequential composition of computations in an imperative style:
\begin{minted}{haskell}
    class Applicative m => Monad (m :: * -> *) where
      (>>=) :: m a -> (a -> m b) -> m b

    newtype State s a = State { runState :: s -> (s, a) }

    instance Monad (State s) where
      (>>=) :: State s a -> (a -> State s b) -> State s b
      m >>= k = State \s ->
        let (s', x) = runState m s in
        runState (k x) s'
\end{minted}

Now, if we define the basic state operations, we can write code in an imperative style with effects.
\begin{minted}{haskell}
    get :: State s s
    get = State \s -> (s, s)

    put :: s -> State s ()
    put newS = State \oldS -> (newS, ())

    example :: State Int Int
    example =
      get >>= \x ->
      put 42 >>= \() ->
      get >>= \y ->
      pure (x + y)

    ghci> runState example 1
    43
\end{minted}

For such monadic chains there is special syntactic sugar:
\begin{minted}{haskell}
    example :: State Int Int
    example = do
      x <- get
      put 42
      y <- get
      pure (x + y)
\end{minted}
