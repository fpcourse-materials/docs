Once, Joe Fasel in a conversation with Philip Wadler expressed the idea that function overloading should be reflected in types.
Wadler misunderstood him~\cite{hudak2007history}.
But what he understood turned out to be type classes~\cite{wadler1989make}.

Christopher Strachey introduced a classification of polymorphism into two categories~\cite{strachey2000fundamental}.
Parametric --- the same code works with data of different types.
\vocab{Ad-hoc polymorphism} --- code is selected depending on the type.
For example, the same multiplication symbol acts differently on integers and on floating-point numbers.

Overloading in languages refers to the ability to give the same name to several functions with different sets of input parameters.
At the call site, the compiler statically determines by the argument types which one should actually be called.
\begin{minted}{cpp}
    string toString(x: int) { ... }
    string toString(fmt: String, d: double) { ... }
\end{minted}

Type classes require first declaring a named entity (the type class itself) that includes a set of function declarations that can be overloaded for different types.
\begin{minted}{haskell}
    class Show a where
      show :: a -> String

    instance Show Int where
      show :: Int -> String
      show = ...
\end{minted}

It is important to note that a type class declaration contains a formal type parameter, and by its occurrences in the function type, the overloading is selected.
There can be many such parameters (\href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/multi_param_type_classes.html}{MultiParamTypeClasses}), and they can have arrow kinds.
For example, in the case of the type class \mintinline{haskell}|Applicative|, the choice of implementation for the operation \mintinline{haskell}|pure| happens based on the type constructor of the result, i.e. not even on a full type.
\begin{minted}{haskell}
    class Functor f => Applicative (f :: Type -> Type) where
      pure :: a -> f a
      ...

    instance Applicative Maybe where
      pure :: a -> Maybe a
      ...
\end{minted}

Also, unlike overloading, type classes are compatible with parametric polymorphism.
In the type of a polymorphic function, one cannot specify that a certain overloading must exist for a type.
Type classes, however, allow constraining the set of possible type arguments to those for which an instance of the required type class is implemented:
\begin{minted}{haskell}
    showPrefixed :: Show a => a -> String -> String
\end{minted}

Comparing type classes with overriding in OOP languages, the resolution of a virtual function call uses a table stored in the object of the first parameter (the call receiver).
Type classes, on the other hand, rely exclusively on the type, so, for example, it is possible to define constants in type classes\footnote{Modern OOP languages, however, strive to support static functions in interfaces, which makes them closer to type classes and allows doing similar things. For example, Swift.}: % todo reference
\begin{minted}{haskell}
    class Enum a => Bounded a where
      minBound :: a
      maxBound :: a
\end{minted}

At the same time, type classes are not types, but rather predicates on types.
A type satisfies such a predicate, or property, if there is a corresponding instance for it.
Therefore, in particular, the familiar OOP way of creating a heterogeneous collection of elements with a common interface does not work directly with type classes.
For example, this type would not be valid: \mintinline{haskell}|[Show]|.
We will return to this problem in~\ref{subsubsec:existentials}.

\subsection{Type classes in the language}

Despite its remarkable power, the idea of implementing type classes is extremely simple.
It was already fully presented in the original paper~\cite{wadler1989make}.
Subsequent work refined the type inference mechanism by reducing it to the classical Hindley-Milner type system~\cite{hall1996type}.
Other work mostly proposes a huge variety of extensions and applications~\cite{jones1997type}.

\subsubsection{Dictionaries} \label{subsubsec:tc-dict}

Let us consider the idea of implementing type classes using the example of polymorphic sorting.
Writing a sort for a list of elements of a specific type is trivial:
\begin{minted}{haskell}
    sort :: [Int] -> [Int]
    sort = \case [] -> []; x:xs -> insert x (sort xs)
      where
        insert x xs = let (l, r) = List.partition (?\framebox{<}? x) xs in l ++ x : r)
\end{minted}

In the implementation, the only type-specific information we use is the ordering on its inhabitants.
Thus, when moving to polymorphic sorting, we need to accept a dictionary with predicates defining the required ordering for the given type.
\begin{minted}{haskell}
    data OrdDict a = OrdDict { less :: a -> a -> Bool }

    sort :: OrdDict a -> [a] -> [a]
    sort d@OrdDict{ less } = \case [] -> []; x:xs -> insert x (sort d xs)
      where
        insert x xs = let (l, r) = List.partition (?\framebox{`less`}? x) xs in l ++ x : r
\end{minted}

Now, to use sorting on a list of numbers, we need to construct the appropriate record and call the function with it on a list of specific types:
\begin{minted}{haskell}
    intOrd :: OrdDict Int
    intOrd = OrdDict { less = (<) }

    ghci> sort intOrd [3, 2, 1]
\end{minted}

There can be a situation where an instance for one type depends on an instance for another.
For example, ordering on lists can be derived automatically, knowing the ordering on elements.
In the case of dictionaries, we model this as a function between dictionaries:
\begin{minted}{haskell}
    listDict :: OrdDict a -> OrdDict [a]
    listDict d = OrdDict { less = ... ?\framebox{less d}? ... }
\end{minted}

Now we can sort a list of lists by constructing the appropriate dictionary:
\begin{minted}{haskell}
    ghci> sort (listDict intDict) [[3, 2], [2, 1], [0]]
\end{minted}

A comparison of explicit dictionary passing and type classes can be seen in the following table:

\begin{tabular}{p{8cm}p{8cm}}
    \begin{enumerate}
        \item Definition of a dictionary of functions
        \begin{minted}{haskell}
            data MyOrd a = MyOrd
              { less :: a -> a -> Bool }
        \end{minted}
        \item Dictionary instance for a specific type
        \begin{itemize}
            \item Named value
        \end{itemize}
        \begin{minted}{haskell}
            intMyOrd :: MyOrd Int
            intMyOrd = MyOrd { less = (<) }
        \end{minted}
        \item Explicit function parameter
        \begin{minted}{haskell}
            sort :: MyOrd a -> [a] -> [a]
        \end{minted}
        \item Passed by the user
        \begin{minted}{haskell}
            test = sort ?\framebox{intMyOrd}? [3, 2, 1]
        \end{minted}
    \end{enumerate}
    &
    \begin{enumerate}
        \item Definition of a type class
        \begin{minted}{haskell}
             class MyOrd a where
               less :: a -> a -> Bool
        \end{minted}
        \item Declaring a type as a member of a type class
        \begin{itemize}
            \item Has no name
        \end{itemize}
        \begin{minted}{haskell}
            instance MyOrd Int where
              less = (<)
        \end{minted}
        \item Implicit function parameter
        \begin{minted}{haskell}
            sort :: MyOrd a => [a] -> [a]
        \end{minted}
        \item Passed by the compiler
        \begin{minted}{haskell}
            test = sort [3, 2, 1]
        \end{minted}
    \end{enumerate}
\end{tabular}

Thus, a dictionary is a \vocab{witness} or proof that the type satisfies the constraint.

\subsubsection{Implicit arguments} \label{subsubsec:ad-hoc-implicits}

One can think of it as follows: to the left of \mintinline{haskell}|=>|, implicit function arguments are passed, inferred by the compiler from the context.
That is, for example, one should not be surprised by occurrences of \mintinline{haskell}{=>} in the type of an argument --- it is simply a function with an implicit argument.
Thus, the following code will not compile because at the use site of variable \texttt{y} there is no value of type \mintinline{haskell}|Show b|:
\begin{minted}{haskell}
    f :: (Show b => b) -> b
    f x = ?\framebox{x}? -- error
\end{minted}
We can accept this value in function \texttt{f}, and then it will automatically propagate to \texttt{x}:
\begin{minted}{haskell}
    f :: Show b => (Show b => b) -> b
    f x = ?\framebox{x}?
\end{minted}

The extension \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/implicit_parameters.html}{ImplicitParams} provides the ability to make some function arguments implicit.
In fact, this is an implementation of dynamic binding in a static language~\cite{lewis2000implicit} (see~\ref{subsubsec:name-bindings}).
Implicit arguments are taken from the scope by name and substituted automatically:
%! suppress = EscapeHashOutsideCommand
\begin{minted}[escapeinside=##]{haskell}
    sortBy :: (a -> a -> Bool) -> [a] -> [a]

    sort :: (?cmp :: a -> a -> Bool) => [a] -> [a]
    sort = sortBy ?cmp
\end{minted}

Haskell also provides the ability to store dictionaries in data structures:
\begin{minted}{haskell}
    data ShowDict a where
      ShowDict :: Show a => ShowDict a

    f :: ShowDict b -> (Show b => b) -> b
    f d x = case d of ShowDict -> ?\framebox{x}? -- the Show b instance is available in scope
\end{minted}

\subsubsection{Instance inference} \label{subsubsec:instance-inference}

To call a constrained-polymorphic function, GHC performs instance inference, or in other words, automatically constructs witnesses.
Instance inference is tightly integrated with Haskell's overall type inference system~\cite{spj-type-inference}.

In reality, instance inference is nothing other than \point{the type inhabitation problem}.
Indeed, after translation to Core (the intermediate representation in GHC), type classes are represented as dictionaries of functions.
We have in context specific dictionaries and functions that allow deriving new dictionaries from existing ones.
We need to find a term that constructs a dictionary of the required type.

Suppose, for example, that inside function \mintinline{haskell}|f :: Show a => ..| there is a call to a constrained-polymorphic function
\mintinline{haskell}|g :: Show [a] -> ..|.
That is, we have a dictionary \mintinline{haskell}|d1 :: ShowDict a|, as well as a function \mintinline{haskell}|d2 :: ShowDict a -> ShowDict [a]|, coming from imports\footnote{Instances can be imported with an empty import: \mintinline{haskell}|import Module ()|.}.
We need to construct a term of type \mintinline{haskell}|ShowDict [a]|.
Obviously, it is simply the application of one to the other: \texttt{d2 d1}.

Instance inference proceeds recursively.
To infer \mintinline{haskell}|ShowDict [a]|, the premise \mintinline{haskell}|ShowDict a| is first inferred.
That is, we get recursion on the structure of the type.
In other words, instance inference can be exploited as a type-level computational primitive.
For example, we can lower information from types into terms (analogous to \href{https://hackage.haskell.org/package/base-4.20.0.1/docs/GHC-TypeLits.html}{GHC.TypeLits}):
\begin{minted}{haskell}
    type data Nat = Zero | Suc Nat

    class KnownNat (n :: Nat) where
      natVal :: Int

    instance KnownNat Zero where
      natVal = 0

    instance KnownNat n => KnownNat (Suc n) where
      natVal = 1 + natVal @n

    ghci> natVal @(Suc (Suc Zero))
    -- will be inferred as natVal {knownSuc (knownSuc knownZero)}
\end{minted}

In the general case, the type inhabitation process, as one might expect by computational analogy, is undecidable.
Therefore GHC imposes many restrictions on the form of instances that guarantee totality of inference.
These restrictions are described in detail in~\cite{sulzmann2007understanding}.
GHC also provides various extensions that relax these restrictions, shifting part of the responsibility to the programmer\footnote{\url{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/instances.html}}.
For example, with \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/instances.html\#extension-UndecidableInstances}{UndecidableInstances} one can easily write type-level list reversal at compile time, as well as any other function:
\begin{minted}{haskell}
    class Reverse (acc :: [Type]) (tys :: [Type]) where
      showReverse :: String

    instance ShowT acc => Reverse acc '[] where
      showReverse = showTypes @acc

    instance Reverse (ty : acc) tys => Reverse acc (ty : tys) where
      showReverse = showReverse @(ty : acc) @tys

    ghci> showReverse @'[] @'[Char, Int, Double]
\end{minted}

One can notice that the process of type class inference is very similar to the evaluation of logic programs, for example in Prolog, only without backtracking (trying different solution variants in search of a suitable one).
As, indeed, type inference in Haskell~\cite{spj-type-inference} in general: the equivalences collected across the program can be viewed as a logic program, and solving this system of type equations as executing that program.

There is an interesting synergy between type classes and type inference (Fig.~\ref{fig:class-sinergy})\footnote{\href{https://youtu.be/5QQdI3P7MdY?si=VAgqyD7iycALTrz_}{(youtube) Hackett: a metaprogrammable Haskell}.}.
Based on terms, types are inferred.
Then, based on types, type class instances are inferred.
That is, we write some interesting intellectual code, and in parallel the compiler writes out the uninteresting code.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.4\textwidth]{figs/class-sinergy}
    \caption{Type classes + instance inference = code generation.}
    \label{fig:class-sinergy}
\end{figure}

Instance inference relies only on the form of the ``head'' of the declaration --- to the right of \mintinline{haskell}|=>|, while constraints on the left are applied after the fact.
This can be used to write more general instances.
For example, this is how the \vocab{constraint trick}\footnote{\url{https://chrisdone.com/posts/haskell-constraint-trick/}} works, allowing one to resolve ad-hoc polymorphic functions in a parametrically-polymorphic context.

\subsubsection{Constructing a type from a value} \label{subsubsec:reify}

After we have learned to lower values from types, it is natural to learn the reverse --- lifting values into types.
We use the technique described in~\cite{kiselyov2004functional}.
There is a corresponding library \href{https://hackage.haskell.org/package/reflection-2.1.6/docs/Data-Reflection.html}{Data.Reflection} (see~\ref{subsubsec:data-reflection}).

In reality, we of course cannot honestly obtain a syntactically correct type of the needed size, simply because types exist strictly before the execution stage.
However, as we know, type class dictionaries have a runtime representation (the case of polymorphic recursion is precisely an example where this cannot be entirely avoided).
Therefore, we use continuation passing style, which will be examined in detail later in chapter~\ref{sec:continuations}: instead of returning a result, we accept a continuation that can work with any type with \mintinline{haskell}|KnownNat| (we use type abstractions and applications, see\ \ref{subsec:lang-parametric-polumorphism})\footnote{In not the most recent versions of GHC, you will need to use the \mintinline{haskell}{Proxy} technique from \ref{subsubsec:proxy}.}:
\begin{minted}{haskell}
    reify :: Int -> (forall n. KnownNat n => a) -> a
    reify n k
      | n <= 0 = k @Zero
      | otherwise = reify (n - 1) \@n' -> k @(Suc n')
\end{minted}

The continuation passed to the recursive call captures the dictionary for type \texttt{n} and constructs a dictionary for \mintinline{haskell}|Suc n|.

Finally, we can write the following surprising identity function that first lifts a value into a type and then lowers the type back into terms:
\begin{minted}{haskell}
    wonderId :: Int -> Int
    wonderId n = reify n (\@t -> natVal @t)
\end{minted}

\subsubsection{Implicits and coherence}

Type classes need not be a special language mechanism; instead, one can provide at the language level implicit parameters and inhabitation sufficient to implement type classes.

Thus, in Scala there is the mechanism of implicits~\cite{kvrikava2019scala}\footnote{The design of implicit parameters in Scala 3 has changed \href{https://youtu.be/dr0PUXQhg3M?si=pCydSikA_gnnCMrq}{(youtube) Scala Implicits Revisited, Martin Odersky}.}.
Function parameters can be marked with the keyword \mintinline{scala}|implicit|, and Scala will try to infer them automatically using the \mintinline{scala}|implicit| declarations available in scope.
Declarations of variables, functions, and object constructors can also be marked \mintinline{scala}|implicit|, and they will be used during inhabitation.
Now we can model a dictionary of functions, for example using interfaces (which in Scala are called \mintinline{scala}|trait|) and OOP singletons, to obtain type classes~\cite{oliveira2010type}:
\begin{minted}{scala}
    // A bundle of functions.
    trait Show[T] {
        def show(x: T): String
    }

    // Wrapper for convenient calling.
    def show[T](x: T)(implicit ev: Show[T]): String = ev.show(x)

    // Singleton object, a value for the bundle of functions.
    implicit object intShow extends Show[Int] {
        def show(x: Int): String = x.toString
    }

    def showAll[T](xs: List[T])(implicit ev: Show[T]): String =
        xs.map(show(_)).join(", ")
\end{minted}

As we discussed earlier (\ref{subsec:lang-parametric-polumorphism}), working with type parameters is similar to working with ordinary ones.
Also, type inference can be viewed as the process of recovering omitted type applications.
Note that the implicit inference mechanism does approximately the same thing.
Therefore, when trying to make functions with implicits first-class functions, difficulties similar to those of first-class polymorphism arise (\ref{subsubsec:first-class-polymorphism}).

In dependently typed languages, implicit parameters\footnote{\url{https://agda.readthedocs.io/en/v2.7.0.1/language/implicit-arguments.html}} are especially needed because, for example, types are exactly the same parameters of a function as all others.
Therefore, type inference is essentially the inference of implicit function arguments.
Moreover, dependent functions, along with arguments, often accept proofs of some properties of those arguments, which one also wants to infer from context automatically where possible.
Such an inference mechanism can be reused for emulating type classes\footnote{\url{https://agda.readthedocs.io/en/v2.7.0.1/language/instance-arguments.html}}~\cite{devriese2011bright}.
It also works in the reverse direction --- one can emulate dependent typing mechanisms using type classes~\cite{mcbride2002faking}.

\begin{figure}
    \centering
    \includegraphics[width=0.8\linewidth]{figs/coherence}
    \caption{Instance coherence --- the diagram commutes.}
    \label{fig:coherence}
\end{figure}

As we will see later, implicit parameters on their own are also needed as a static approximation of dynamic free variables for implementing effect systems (see~\ref{sec:effect-systems}).
However, having type classes as a separate language feature is still useful, despite them seemingly being the same implicit parameters (albeit with a recursive inhabitation mechanism).
One can support an important property when all restrictions are respected, i.e. in the absence of \vocab{orphan instances}\footnote{\url{https://stackoverflow.com/questions/3079537/orphaned-instances-in-haskell}}.
\vocab{Instance coherence} --- for a given type, all instances of a given type class obtained by different means are indistinguishable (Fig.~\ref{fig:coherence}).
Accordingly, the origin of any particular instance does not matter.
In other words, one need not think about this, which removes a significant amount of cognitive load and simplifies refactoring\footnote{\href{https://youtu.be/hIZxTQP1ifo?si=aG2Lk2eb-5E5SOLb}{Edward Kmett - Type Classes vs. the World.}}.
In contrast, other approaches require careful attention to the calling context, because an unexpected implementation may come from it.

\subsubsection{Rules and specialization} \label{subsubsec:rules}

GHC allows specifying optimizing rewrite rules for the compiler directly in code using a special pragma\footnote{\url{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/rewrite_rules.html}}~\cite{jones2001playing}.
For example:
\begin{minted}{haskell}
    {-# RULES
      "map/map"    forall f g xs.  map f (map g xs) = map (f . g) xs
      "map/append" forall f xs ys. map f (xs ++ ys) = map f xs ++ map f ys
     #-}
\end{minted}

The first law is nothing other than the functor law.
Ideally, we formulate laws at the design stage~\cite{maguire-algebra}, verify their correctness using property-based testing\footnote{\href{https://youtu.be/G0NUOst-53U?si=vdcKVUi9vSPBY0Jz}{(youtube) John Hughes - Keynote: How to specify it!}}, and then use them for optimizations.

One can rewrite a polymorphic version of a function to a specialized one when the types match.
For this, one needs to implement the specialized version (semantic equivalence is entirely the programmer's responsibility) and set up the corresponding rewrite rule:
\begin{minted}{haskell}
    genericLookup :: Ord a => Table a b   -> a   -> b
    intLookup     ::          Table Int b -> Int -> b

    {-# RULES "genericLookup/Int" genericLookup = intLookup #-}
\end{minted}

The main effect of this optimization is the guaranteed conversion of dynamic type class function calls into static ones (because the type is known, and therefore so is the corresponding dictionary).

\subsubsection{Digression: defunctionalization} \label{subsubsec:defunctionalization}

\vocab{Defunctionalization} --- a technique for eliminating higher-order functions from a program\footnote{\url{https://en.wikipedia.org/wiki/Defunctionalization}}~\cite{defunctionalization-slides}.
It was first proposed in~\cite{reynolds1972definitional, reynolds1998definitional}.

The idea is to replace every creation of a lambda function with a call to a constructor of some algebraic data type.
And every call site of a function is replaced with a call to a special first-order function \texttt{apply} that interprets this algebraic type.

Consider the example with the higher-order function \texttt{map} and two call sites that create lambda functions:
\begin{minted}{haskell}
    map :: (Int -> Int) -> [Int] -> [Int]
    map f = \case [] -> []; x:xs -> f x : map f xs

    example1 xs = map (\x -> x + 1) xs
    example2 y xs = map (\x -> x * y) xs
\end{minted}
For each lambda literal we create a constructor that stores the closure.
Application is replaced with a call to \texttt{apply}.
Thus we obtained a first-order version of \texttt{map}.
\begin{minted}{haskell}
    data Fun = F1 | F2 Int
    apply :: Fun -> Int -> Int
    apply df x = case df of F1 -> x + 1; F2 y -> x * y

    map :: Fun -> [Int] -> [Int]
    map df = \case [] -> []; x:xs -> apply df x : map df xs

    example1 xs = map F1 xs
    example2 y xs = map (F2 y) xs
\end{minted}

\subsubsection{Emulating higher-kinded polymorphism} \label{subsubsec:simulating-hkt}

Not all languages have higher-rank polymorphism, but sometimes it is useful.
Its most common application is emulating type classes of arrow kinds like \mintinline{haskell}{Monad}.

Note that a type constructor of kind \mintinline{haskell}|Type -> Type| is a function on types that takes one type and returns another.
Let us apply defunctionalization to avoid the need to parameterize one type constructor by another~\cite{defunctionalization-slides, yallop2014lightweight}.

We associate to the type constructor \mintinline{haskell}{List} a type ``symbol'' \mintinline{haskell}{ListSym} (for illustration we use Kotlin):
\begin{minted}{kotlin}
    class ListSym
\end{minted}
We create a type corresponding to the application of a symbol to a type, storing the original value with erased type:
\begin{minted}{kotlin}
    class Apply<Sym, T>(val value: Any)
\end{minted}
We establish an isomorphism between the original type obtained by type application of the constructor and the new symbol application:\footnote{To the left of the dot in the declaration, an additional function argument is specified with call syntax matching a method call on an object. From the body of the function, it can be referenced using \mintinline{kotlin}{this}.}
\begin{minted}{kotlin}
    fun <T> List<T>.to(): Apply<ListSym, T> = Apply(this)
    fun <T> Apply<ListSym, T>.from(): List<T> = this.value as List<T>
\end{minted}

Now we can declare a monad interface and provide an implementation for lists using a singleton object:
\begin{minted}{kotlin}
    interface Monad<M> {
        fun <T> pure(x: T): Apply<M, T>
        infix fun <T, R> Apply<M, T>.bind(k: (T) -> Apply<M, R>): Apply<M, R>
    }

    object ListMonad : Monad<ListSym> {
        override fun <T> pure(x: T): Apply<ListSym, T> = listOf(x).to()
        override fun <T, R> Apply<ListSym, T>.
                bind(k: (T) -> Apply<ListSym, R>): Apply<ListSym, R> =
            this.from().flatMap { k(it).from() }.to()
    }
\end{minted}
And finally we can write functions over arbitrary monads:\footnote{Arguments to the left of the dot can automatically jump into subsequent calls. In fact, they are implicit parameters.}
\begin{minted}{kotlin}
    fun <M> Monad<M>.go(x: Apply<M, Int>): Apply<M, Int> =
        x bind { it -> pure(it + 1) } bind { it -> pure(it + 2) }

    fun test(xs: List<Int>): List<Int> = ListMonad.go(xs.to()).from()
\end{minted}

It is worth noting that the resulting code is rather unwieldy.
Most likely, using this technique does not pay for itself and one should choose a different programming style.

\subsection{Families} \label{subsec:families}

The idea of ad-hoc polymorphism is to obtain different code depending on the type.
Families started as an extension of this idea into the domain of data and types.
Thus, associated type synonyms provide different types for different indices (type parameters)~\cite{chakravarty2005associated-syn}.
Associated \mintinline{haskell}|data| provide different representations for different indices~\cite{chakravarty2005associated}.
Eventually these ideas were generalized to open families~\cite{schrijvers2008type}, and then closed families were introduced~\cite{eisenberg2014closed}.

One can think of families\footnote{\url{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/type_families.html}}\footnote{\url{https://serokell.io/blog/type-families-haskell}} as type constructors that define a set of types.
A specific type from the set can be selected by passing a type parameter called an \vocab{index}.
Compare this with ordinary polymorphic type constructors, which behave the same regardless of type parameters.

A large number of interesting usage examples can be found, for example, in~\cite{kiselyov2010fun}.

\subsubsection{Data families}

Data families allow choosing an algebraic type declaration depending on the type index.
For example, for a more efficient implementation of data structures.
This resembles template specialization in C++.

\begin{minted}{haskell}
    data family XList elem
    data instance XList () = IntList Int
    data instance XList Bool = BoolList ByteArray
\end{minted}

The only way to work with a data family is to place the implementation in a type class so that it accompanies the value from the point when the type index is concrete.

\begin{minted}{haskell}
    class XListOp elem where
      xelem :: elem -> XList elem -> Bool

    instance XListOp () where
      xelem () (IntList size) = size > 0

    instance XList Bool where
      xelem key (ByteArray bs) = ...

    xelemAll :: XListOp elem => XList elem -> [elem] -> Bool
    xelemAll xs = all (`xelem` xs)
\end{minted}

Unfortunately, unlike template specialization, one cannot provide a default definition like \mintinline{haskell}{data instance XList a = AList [a]}.

\subsubsection{Synonym families}

Synonym families (type families) are effectively functions on types.
They can be open, closed, and associated.
Open families are open in the sense that instances can be written separately from the declaration, similar to type classes.
Closed families, on the contrary, are fully described in one place, cases are ordered top to bottom, which somewhat relaxes restrictions on patterns.

\begin{minted}{haskell}
    type family Plus (n :: Nat) (m :: Nat) :: Nat where
      Plus Zero m = m
      Plus (Suc n) m = Suc (Plus n m)
\end{minted}

To see what something at the type level evaluates to, one can use the following command in ghci:
\begin{minted}{haskell}
    ghci> :k! Plus (Suc Zero) (Suc (Suc Zero))
    Plus (Suc Zero) (Suc (Suc Zero)) :: Nat
    = Suc (Suc (Suc Zero))
\end{minted}

Associated families work similarly, only they are declared within a certain type class, serving as a functional alternative to \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/functional_dependencies.html}{FunctionalDependencies}\ \cite{jones2000type} (which look more relational).
In other words, they allow associating another type with the type for which an instance is written.
For example, collections and their element type:

\begin{minted}{haskell}
    class Container c where
      type Elem c
      elements :: c -> [Elem c]

    instance Container [a] where
      type Elem [a] = a
      elements = id

    instance Container ByteString where
      type Elem ByteString = Word8
      elements = ByteString.unpack
\end{minted}

In modern languages, associated families often appear as associated types\footnote{Associated types are essentially existential types; they are connected to associated families by the logical process of Skolemization.}.
Swift relies heavily on associated types, not supporting generics in protocols (interfaces) at all\footnote{\href{https://youtu.be/ctS8FzqcRug?si=y_ZYnuUOulA33d_X}{(youtube) 2017 LLVM Developers' Meeting: ``Implementing Swift Generics''}}.
Meanwhile, Scala attempts to track, in the presence of existential types (interfaces), which specific value a given associated type came from, using path-dependent types~\cite{amin2014foundations}.

\subsubsection{Injective families}

Type families differ from type constructors roughly in the same way that functions differ from data constructors.
Constructors are passive and do not reduce (\mintinline{haskell}|Maybe Int|), while functions compute to some result (e.g. \mintinline{haskell}|F Int ?$\sim$? Bool|).
In particular, like functions, families are not necessarily injective.

For type constructors, knowing that the types they construct are equivalent, one can infer that the type arguments are equivalent too.
For example:
\begin{minted}{haskell}
    Maybe a ?$\sim$? Maybe b ?$\Rightarrow$? a ?$\sim$? b
\end{minted}

Obviously, for type families this property does not hold by default:
\begin{minted}{haskell}
    type family NonInjective a where
      NonInjective Int = Double
      NonInjective Char = Double
\end{minted}

Haskell provides explicit syntax for declaring injective type families, resembling functional dependencies in type classes (\href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/type_families.html#extension-TypeFamilyDependencies}{TypeFamilyDependencies})~\cite{stolarek2015injective}.
Of course, the compiler will verify that the implementation is injective.
The syntax requires binding the result to a name via equality and specifying, analogous to \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/functional_dependencies.html}{FunctionalDependencies}, that the result determines some of the type indices of the family:
\begin{minted}{haskell}
    type family InjectiveB a b = r | r -> b
      ...
\end{minted}

\subsubsection{First-class families}

Besides injectivity, type families also do not necessarily possess the property of \vocab{generativity}, which is critically important for type inference --- the same result is not necessarily obtained from the same family:
\begin{minted}{haskell}
    f a ?$\sim$? g a ?$\Rightarrow$? f ?$\sim$? g
\end{minted}

Together, injectivity and generativity constitute \vocab{matchability}.
When Haskell works with a type of arrow kind, it assumes that the type is matchable.
Accordingly, families cannot be passed as parameters, and all their occurrences must be fully applied to all arguments (fully saturated).
Or one needs to explicitly indicate that the family returns a constructor (in this specific case the semantics depend on moving arguments to the right of \mintinline{haskell}{::}):
\begin{minted}{haskell}
    type family ToCtor (s :: Symbol) :: Type -> Type where
      ToCtor "maybe" = Maybe
      ToCtor "identity" = Identity
\end{minted}

One way to work around this restriction is defunctionalization of families~\cite{defunctionalization-slides, eisenberg2014promoting}.
As we discussed earlier~\ref{subsubsec:defunctionalization}, instead of a first-class function, a symbol designating it is introduced, along with an interpretation function that can perform the action corresponding to that symbol.
In this case, the interpretation function will be an open family \mintinline{haskell}|Apply|~\cite[chapter 10]{maguire-types}.

There is ongoing work in Haskell\footnote{\href{https://ghc-proposals.readthedocs.io/en/latest/proposals/0242-unsaturated-type-families.html}{GHC proposal: Unsaturated Type Families}.} to remove the saturation restriction~\cite{kiss2019higher}.
For this, one needs to distinguish matchable and unmatchable type functions.
This is proposed to be done by additional indexing of arrow kinds: $\to \equiv
\to^M$ and $\twoheadrightarrow \equiv \to^U$.
And, of course, these indices can be polymorphic.

    hMap

\end{minted}

\subsection{The \texttt{Constraint} kind}

There had long been proposals to add support for constraint synonyms, constraint families, etc. to GHC~\cite{orchard2010haskell}.
Eventually, a mechanism for unifying types and constraints was proposed\footnote{\url{https://gitlab.haskell.org/ghc/ghc/-/wikis/kind-fact}} and implemented\footnote{\url{http://blog.omega-prime.co.uk/2011/09/10/constraint-kinds-for-ghc/}}.
Thus, everything that worked for types now also works for constraints.

In GHC with \href{https://downloads.haskell.org/ghc/9.2-latest/docs/html/users_guide/exts/constraint_kind.html}{ConstraintKinds}, a special kind \mintinline{haskell}|Constraint| was added:
\begin{itemize}
    \item A type class constructs a constraint: \mintinline{haskell}|Monad :: (Type -> Type) -> Constraint|;
    \item Equality is a constraint: \mintinline{haskell}|(a ?$\sim$? b) :: Constraint|;
    \item An empty constraint tuple is a constraint: \mintinline{haskell}|() :: Constraint|;
    \item A constraint tuple is a constraint: \mintinline{haskell}|(Eq a, a ?$\sim$? b) :: Constraint|.
\end{itemize}

Now, for example, we can reify a dictionary as a language-level object:\footnote{\url{https://hackage.haskell.org/package/constraints-0.14.2/docs/src/Data.Constraint.html\#Dict}}
\begin{minted}{haskell}
    data Dict (c :: Constraint) where
      Dict :: c => Dict c
\end{minted}

Recall the heterogeneous list considered earlier~\ref{subsubsec:promotion}:
\begin{minted}{haskell}
    data HList (tys :: [Type]) where
      HNil :: HList '[]
      HCons :: ty -> HList tys -> HList (ty : tys)
\end{minted}
This data structure is the first-class analogue of variadic generics in C++ or Swift\footnote{\url{https://github.com/swiftlang/swift-evolution/blob/main/proposals/0398-variadic-types.md}} (the whole point of variadics is to avoid working with \mintinline{haskell}|HList|-like structures directly).
For example, we can write \texttt{map} for such a structure if all types satisfy a certain constraint.
For this, we first implement a family that generates a constraint tuple for each type in the list:
\begin{minted}{haskell}
    type family All (c :: k -> Constraint) (tys :: [k]) :: Constraint where
      All c '[] = ()
      All c (ty : tys) = (c ty, All c tys)

    -- All Show [Int, Double] ?$\sim$? (Show Int, (Show Double, ())
\end{minted}

Now we can implement \texttt{map}:
\begin{minted}{haskell}
    hmap :: forall c res tys . All c tys
         => (forall ty . c ty => ty -> res) -> HList tys -> [res]
    hmap f = \case
      HNil -> []
      HCons x xs -> f x : hmap @c f xs

    ghci> hmap @Show show (HCons (1 :: Int) $ HCons 'a' HNil)
\end{minted}

More exercises of this kind with heterogeneous constructions can be found in~\cite{de2014true}.

Constraints can also be parametrically polymorphic\footnote{\url{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/quantified_constraints.html}}~\cite{bottu2017quantified}:
\begin{minted}{haskell}
    data Rose f x = Rose x (f (Rose f x))

    instance (Eq a, forall b. Eq b => Eq (f b)) => Eq (Rose f a) where
      Rose x1 rs1 == Rose x2 rs2 = x1 == x2 && rs1 == rs2
\end{minted}

\subsection{Uses of ad-hoc polymorphism}

Often languages that have something resembling type classes try to express as many other language features and useful techniques through them as possible.
It turns out that this is a surprisingly powerful mechanism.
In this section we will consider some selected examples.

\subsubsection{Serialization}

A classic example of using type classes is serialization.
The problem is that deserialization is performed when the object does not yet exist (we do not consider the deficient Java approach of filling an object with default values followed by mutation).
Therefore, it is not possible to write an OOP interface Serializable.

The standard serialization library in Kotlin\footnote{\url{https://github.com/Kotlin/kotlinx.serialization}} provides the entity \mintinline{kotlin}|KSerializer|, which is an interface for a separate serializer object for our type (for efficiency, CPS in the form of encoder and decoder event streams is used here; we will return to this approach later\ \ref{subsubsec:deforestation-fusion}):
\begin{minted}{kotlin}
    interface KSerializer<T> {
        fun serialize(encoder: Encoder, value: T)
        fun deserialize(decoder: Decoder): T
    }
\end{minted}

Obviously, to construct a serializer for a polymorphic type, serializers for the type parameters are needed.
Which already clearly resembles type classes.
\begin{minted}{kotlin}
    class PairSerializer(
        keySerializer: KSerializer<K>,
        valueSerializer: KSerializer<V>,
    ): KSerializer<Pair<K, V>> { ... }
\end{minted}

However, Kotlin does not have type classes, so serializers must be created manually.
A set of technologies helps with this: \mintinline{kotlin}|inline fun|, \mintinline{kotlin}|reified| generics, reflection, and a compiler plugin from the library, which however is not type-safe.

\subsubsection{Existential types} \label{subsubsec:existentials}

The existential quantifier in types is an encapsulation mechanism~\cite[chapter 24]{pierce2002types}.
We can replace occurrences of a subtype $\sigma$ in a type $\tau$ with a variable $\alpha$ and obtain $\exists \alpha\ldotp \tau'$, where $\subst{\tau'}{\alpha}{\sigma}\equiv\tau$.
Thus, we have hidden part of the type from the user.

For example, one can use existential types to bring different types to a common form and put their values in a single list.
In Haskell, an existential type is expressed through a \mintinline{haskell}{data} declaration in which the data constructor is polymorphic but the type is monomorphic\footnote{Similar to the type erasure idiom in C++.}.
Thus, the trivial existential type $\exists \alpha\ldotp \alpha$ can be obtained in Haskell as the type \mintinline{haskell}{Any}, defined as follows:
\begin{minted}{haskell}
    data Any where
      Any :: forall a . a -> Any  -- logically equivalent to (exists a . a) -> Any

    list :: [Any]
    list = [Any 42, Any "Hello", Any (Just Nothing)]
\end{minted}

At the deconstruction site of \mintinline{haskell}|Any|, a value of some unknown type will be available.
Obviously, nothing can be done with such a value.
However, in addition to the value, one can place in the constructor a witness that this unknown type satisfies some type class\footnote{Similar to Rust fat pointers (a pair of a pointer to data and a pointer to a virtual function table) and OOP objects.}.
\begin{minted}{haskell}
    data Has (c :: Type -> Constraint) where
      Has :: c a => a -> Has c
\end{minted}

A value of type \mintinline{haskell}|Has| witnesses that there exists some inhabited type \texttt{a} that belongs to a certain type class.
For example, consider \mintinline{haskell}|Show|:
\begin{minted}{haskell}
    showAll :: [Has Show] -> String
    showAll = List.intercalate "," . map \(Has x) -> show x
\end{minted}

In general, to eliminate such a data type, higher-rank types are needed~\cite[chapter 24.3]{pierce2002types}:
\begin{minted}{haskell}
    foldHas :: Has c -> (forall a . c a => a -> b) -> b
    foldHas (Has x) k = k x
\end{minted}

More details can be found in~\cite[chapter 7]{maguire-types} and~\cite[chapter 24]{pierce2002types}.

\subsubsection{Name resolution} \label{subsubsec:resolve}

The process of name resolution in programming languages determines which program entity a given use of a name is bound to.
Name resolution considers imports, the hierarchy of namespaces and scopes, expression types\ldots
As a rule, this is a complex process, inseparable from type inference.

However, in GHC the name resolution stage is rather simple and runs before type inference.
Its trivial nature is hinted at by its name --- Renamer --- it simply rewrites names in the program to fully-qualified names, relying on imports.

On one hand, simplicity is good.
On the other, strict separation from type inference imposes an unpleasant restriction: types cannot participate in name resolution.
This problem is most acute with record field labels.
One has to name all fields in a module differently to avoid clashes.

To make name resolution depend on types, Haskell once again resorts to type classes.
Namely, a type class \mintinline{haskell}{IsLabel} is defined that depends on a symbol and the expected type:
\begin{minted}{haskell}
    class IsLabel (s :: Symbol) a where
      fromLabel :: a
\end{minted}
There is syntactic sugar for calling \texttt{fromLabel} (\href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/overloaded_labels.html}{OverloadedLabels}):
\begin{minted}{haskell}
    #name ?$\equiv$? fromLabel @"name"
\end{minted}
Now resolution of the name \texttt{name} will take the type into account\footnote{To get rid of the redefinition error, you need to enable \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/field_selectors.html\#extension-FieldSelectors}{NoFieldSelectors}.}:
\begin{minted}{haskell}
    data Pet = Pet { name :: String }
    instance IsLabel "name" (Pet -> String) where
      fromLabel Pet{ name } = name

    data Person = Person { name :: String, pets :: [Pet] }
    instance IsLabel "name" (Person -> String) where
      fromLabel Person{ name } = name

    ghci> #name pet
\end{minted}

\subsubsection{Non-syntactic type equalities, System FC} \label{subsubsec:system-fc}

Modern Haskell is a syntactically rich language that, despite its diversity of constructs, is translated into a small typed internal language.
This is the language $System~F_C$~\cite{sulzmann2007system}, which extends $System~F$ (\ref{subsec:lang-parametric-polumorphism}) with non-syntactic type equalities.
It turns out that this is sufficient to support such Haskell features as generalized algebraic data types, associated type families, functional dependencies, and so on.

Specifically, a built-in constraint $\sim$ is introduced, witnessing the equivalence of two types\footnote{\url{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/equality_constraints.html}}.
For example, the type of function \texttt{id} can be written in this unusual way:
\begin{minted}{haskell}
    f :: forall a b . a ?$\sim$? b => a -> b
    f = id
\end{minted}
In fact, this is a function of four parameters: two type parameters, a coercion, and an argument.
A coercion is a zero-sized value, automatically inferred by the compiler, that serves as a witness that the two corresponding types are equivalent.

For example, the GADT from~\ref{subsubsec:gadts} is desugared as follows:
\begin{minted}{haskell}
    data Expr ty where
      Const :: Int -> Expr Int
      IsZero :: Expr Int -> Expr Bool
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty
    -- translates to
    data Expr ty where
      Const :: forall ty . ty ?$\sim$? Int => Expr ty
      IsZero :: forall ty . ty ?$\sim$? Bool => Expr Int -> Expr ty
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty
\end{minted}
And after pattern matching on the constructors, the equality constraint enters the branch and allows the type inference system to perform the necessary rewrites.

More on type inference in the presence of local assumptions can be found in the classical paper $OutsideIn(X)$~\cite{vytiniotis2011outsidein}.

Obviously, Haskell can inhabit an equality constraint following reflexivity, symmetry, and transitivity.
Also, the compiler can generate new axioms (the user cannot directly write their own axioms).
For example, for a type family the compiler generates equality axioms between the applied family constructor and the resulting types:
\begin{minted}{haskell}
    type family Plus (n :: Nat) (m :: Nat) :: Nat where
      Plus Zero m = m
      Plus (Suc n) m = Suc (Plus n m)
    -- expands to
    axiom Plus Zero m ?$\sim$? m
    axiom Plus (Suc n) m ?$\sim$? Suc (Plus n m)
\end{minted}

\subsubsection{Coercions and roles} \label{subsubsec:coercions}

Haskell supports \vocab{generative type abstractions} in the form of \mintinline{haskell}|newtype| declarations.
This technique allows defining domain-specific types that are indistinguishable from the wrapped types at runtime but allow distinguishing them at compile time.
For instance, we can introduce wrappers for numbers that in the problem domain represent identifiers of different entities.
Now the type system will prevent confusing them.
\begin{minted}{haskell}
    newtype ModuleId = ModuleId Int64
    newtype CourceId = CourceId Int64
\end{minted}

There is an extremely underappreciated programming practice\footnote{\url{https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/}} where our program has a clear boundary at which data from the external world is parsed.
Beyond it, raw unstructured data is enriched with structure and takes on meaning within the problem domain.
Or we reject this data as incorrect.
In the remaining part of the program, we work with typed data whose properties have already been established and guaranteed.
For example, we can be sure that the number \mintinline{haskell}|ModuleId| is strictly greater than zero.

However, if we have a collection of wrapped data and we want to work with it as a collection of raw data, we would have to transform the collection, even though this transformation does nothing.
The Haskell optimizer cannot eliminate it because it works with a typed intermediate representation and cannot remove a conversion that changes the type.
\begin{minted}{haskell}
    newtype Csv = Csv { unCsv :: String }

    concatC :: [Csv] -> Csv
    concatC = Csv . concat . ?\framebox{map}? unCsv
\end{minted}

Therefore, Haskell has a mechanism of safe coercions between types with the same runtime representation.
This is implemented using the magical type class \mintinline{haskell}|Coercible|.
The compiler implements it automatically (see\ Fig.~\ref{fig:coersions}).
\begin{minted}{haskell}
    class Coercible from to where
      coerce :: from -> to
\end{minted}

\begin{figure}[h]
    \centering
    \includegraphics[width=\linewidth]{figs/coersions}
    \caption{Principles of constructing \mintinline{haskell}|Coercible| instances~\cite{breitner2014safe}.}
    \label{fig:coersions}
\end{figure}

Now we can eliminate the unnecessary list transformation:
\begin{minted}{haskell}
    concatC :: [Csv] -> Csv
    concatC = coerce concat
\end{minted}

The safety of coercions is ensured by the \vocab{role system}.
Each type parameter has a special property --- a role.

The phantom role is assigned to phantom type parameters.
They can be freely coerced (there are no prerequisites for \mintinline{haskell}|Coercible| instances):
\begin{minted}{haskell}
    data Phantom h = Phantom
    data NestedPhantom b = MkNP [Phantom b] | SomethingElse

    instance Coercible (Phantom a) (Phantom b)
    instance Coercible (NestedPhantom a) (NestedPhantom b)
\end{minted}

A type parameter has the representational role if the type constructor can be coerced only when the arguments can be coerced:
\begin{minted}{haskell}
    data Maybe a = Nothing | Just a
    instance Coerce a b => Coerce (Maybe a) (Maybe b)
\end{minted}

A type parameter has the nominal role if the type constructor can be coerced only when the arguments are equal.
This is required when the type argument indexes a family or a constraint.
\begin{minted}{haskell}
    type family F a
    data Applied a = Applied (F a)
    instance (a ?$\sim$? b) => Coercible (Applied a) (Applied b)

    data ShowDict a where
      ShowDict :: Show a => a -> ShowDict a
    instance (a ?$\sim$? b) => Coercible (ShowDict a) (ShowDict b)
\end{minted}

Sometimes the compiler infers the wrong role for a type parameter.
For example, if the invariants of a structure depend on a specific implementation of some type class for the type argument, which is not visible in the type declaration itself.
In such cases, roles can be specified explicitly:
\begin{minted}{haskell}
    type role Map nominal representational
    data Map k v = ...
\end{minted}

More details can be found in~\cite{breitner2014safe} and~\cite[chapter 8]{maguire-types}.

\subsubsection{Type reflection} \label{subsubsec:type-reflection}

Reflection is a language mechanism for obtaining information about types at runtime (at the term level).
This sounds familiar, and indeed Haskell implements this mechanism through type classes~\cite{peyton2016reflection}.

The library provides the magical type class \href{https://hackage.haskell.org/package/base-4.20.0.1/docs/Type-Reflection.html}{\mintinline{haskell}|Typeable|}, which is implemented by the compiler for each concrete type via \mintinline{haskell}{deriving}.
To obtain information about a type, a \mintinline{haskell}|Typeable| instance for that type must be in scope.
The type structure is represented by the sum type \href{https://hackage.haskell.org/package/ghc-internal-9.1001.0/docs/src/GHC.Internal.Data.Typeable.Internal.html#TypeRep}{\mintinline{haskell}|TypeRep|}, which provides the ability for additional type checking using generalized algebraic data types and type tags.
\begin{minted}{haskell}
    class Typeable a where
      typeRep# :: TypeRep a
\end{minted}

For example, one can obtain the name of a type constructor as follows:
\begin{minted}{haskell}
    typeName :: forall a. Typeable a => String
    typeName = tyConName $ typeRepTyCon $ typeRep $ Proxy @a

    ghci> typeName @Int
\end{minted}

\begin{task}
    Declare a type class that allows printing a list of types.
\end{task}

Using the type representation structure and existential types, one can emulate dynamic typing in Haskell.
Namely: any type can be converted to \href{}{\mintinline{haskell}|Dynamic|}, and then safely converted back.
\begin{minted}{haskell}
    data Dynamic where
      Dynamic :: Typeable a => a -> Dynamic

    fromDynamic :: Typeable a => Dynamic -> Maybe a
\end{minted}

This can be useful, for example, for defining a heterogeneous key-value store:
\begin{minted}{haskell}
    data Store = Map Key Dynamic
    data Ref ty = Ref Key
    get :: Typeable ty => Store -> Ref ty -> Maybe ty
\end{minted}

\subsubsection{Data reflection} \label{subsubsec:data-reflection}

As we discussed earlier, the coherence property guarantees that each type in Haskell corresponds to exactly one instance of a given type class.
And the only way to declare an instance in Haskell is with a top-level declaration, meaning it cannot depend on any local data.
However, Haskell has the library \href{https://hackage.haskell.org/package/reflection-2.1.6/docs/Data-Reflection.html}{Data.Reflection}\footnote{\url{https://www.tweag.io/blog/2017-12-21-reflection-tutorial/}}, which allows creating local instances for fresh, magically generated\footnote{\url{https://www.schoolofhaskell.com/user/thoughtpolice/using-reflection}} types.

It uses the idea of ``lifting values into types'' that we discussed earlier (see~\ref{subsubsec:reify}), but in a somewhat more general form.
Instead of defining type classes of the form \mintinline{haskell}|Known_|, a single type class is introduced, indexed by the type of terms \texttt{terms} that are lowered from types:
\begin{minted}{haskell}
    class Reifies ty terms | ty -> terms where
      reflect :: Proxy ty -> terms
\end{minted}

Also, using the following function, the library allows generating a fresh type and a \mintinline{haskell}|Reifies| instance that, given this fresh type, returns the given value of type \texttt{a} (passed as the first argument).
Since it is passed into a higher-rank function, the fresh type cannot escape the scope~\ref{subsubsec:first-class-polymorphism}:
\begin{minted}{haskell}
    reify :: a -> (forall fresh . Reifies fresh a => Proxy fresh -> res) -> res
\end{minted}

To use a non-standard instance of a type class for some type \texttt{a}, one needs to declare a new type (for example, using \mintinline{haskell}|newtype|), containing the given one, and write the needed instance for it (see, for example, \href{https://hackage.haskell.org/package/base-4.20.0.1/docs/Data-Ord.html#t:Down}{Down}).
We do not want to declare a new declaration for each case, so we create a wrapper similar to \href{https://hackage.haskell.org/package/tagged-0.8.8/docs/Data-Tagged.html}{Data.Tagged}, which allows adding a phantom type tag to the value type.
By varying the tag, we can obtain as many types wrapping the given one as we need.
\begin{minted}{haskell}
    newtype Wrapped tag a = Wrapped { unwrap :: a }
\end{minted}

We declare the wrapper type \mintinline{haskell}|Wrapped tag a| as a member of the needed type class.
The implementation code is obtained via \texttt{reflect} by the tag type in the form of an actual dictionary.
\begin{minted}{haskell}
    data ReifiedOrd a = ReifiedOrd { compare :: a -> a -> Ordering }

    instance Reifies tag (ReifiedOrd a) => Ord (Wrapped tag a) where
      compare = coerce $ compare $ reflect $ Proxy @tag
\end{minted}

Finally, we can call the sort function, locally replacing the ordering with the reverse one:
\begin{minted}{haskell}
    sort :: Ord a => [a] -> [a]

    sortReverse :: forall a . Ord a => [a] -> [a]
    sortReverse xs =
      let dict = ReifiedOrd { compare = flip compare } in
      reify dict \(Proxy :: Proxy fresh) ->
        coerce $ sort @(Wrapped fresh a) $ coerce xs
\end{minted}

\subsubsection{Open structures} \label{subsubsec:open-structs}

In dynamic languages, one can create objects on the fly, sequentially adding content to them without introducing a declaration beforehand.
In Haskell, this is also possible using pairs for products and \mintinline{haskell}|Either| for sums.
For example, one can add a new field by creating a new pair: \mintinline{haskell}{(oldObj, newField)}.

However, this implementation is suboptimal both in terms of efficiency (more efficient implementations can be found in~\cite[chapter 11]{maguire-types}) and in terms of usability.
Namely, the order of fields matters and there is no subtyping relation on types in Haskell (for example, one cannot pass a value with fewer fields or variants).
But one can notice that constraints lack these drawbacks.
Therefore, the type of a data structure can be organized, for example, as follows:
\begin{minted}{haskell}
    (Int, Double) ?replaced by? (Member Int d, Member Double d) => Prod d
\end{minted}

\subsubsection{Exceptions and the open hierarchy}

An important aspect of error handling is that many errors are handled uniformly.
Thus, errors should form a hierarchy similar to the one obtained in OOP languages through inheritance, so that one can react to a group of errors with a single handler.
This gives rise to the task of modeling such a hierarchy in Haskell.

Moreover, statically typed errors are an active area of research; we will discuss this in the context of effect systems (see~\ref{sec:effect-systems}).
Classical exceptions, however, are dynamically typed.
This variant is especially well-suited for programmer errors, which ideally should not be handled in the program except for resource cleanup. % todo citations

Exception support is present in the Haskell runtime system as a simple and familiar way to handle exceptional situations: programmer errors, incomplete pattern match execution, asynchronous system signals~\cite{marlow2001asynchronous}\ldots
Exceptions are dynamically typed and form a hierarchy~\cite{marlow2006extensible}.
While pure code can throw an exception, since $\bot$ by Haskell's semantics inhabits every type, catching an exception is only possible\footnote{\href{https://stackoverflow.com/questions/3642793/why-can-haskell-exceptions-only-be-caught-inside-the-io-monad}{(stackoverflow) Why can Haskell exceptions only be caught inside the IO monad?}} in \mintinline{haskell}|IO|~\cite{jones2001tackling}, using special language primitives.

To make a type an exception, one needs to declare an \mintinline{haskell}|Exception| instance for it:
\begin{minted}{haskell}
    class (Typeable a, Show a) => Exception a where
      toException :: a -> SomeException
      toException = SomeException

      fromException :: SomeException -> Maybe a
      fromException (SomeExcetion e) = cast e
\end{minted}
Where \mintinline{haskell}|SomeException| is an existential wrapper similar to \mintinline{haskell}|Dynamic| (see\ \ref{subsubsec:type-reflection}), into which the concrete exception type is wrapped.
By catching \mintinline{haskell}|SomeException|, one can catch any exception (\texttt{cast} will always succeed).
\begin{minted}{haskell}
    data SomeException where
      SomeException :: Exception a => a -> SomeException

    instance Exception SomeException
\end{minted}

The Haskell runtime system provides intrinsics for throwing and catching exceptions; we wrap them to support any \mintinline{haskell}|Exception| type:
\begin{minted}{haskell}
    throw :: Exception e => e -> a
    throw = primThrow (toException e)

    catch :: Exception e => IO a -> (e -> IO a) -> IO a
    catch io handler = io `primCatch` \e -> case fromException e of
      Nothing -> throw e
      Just e' -> handler e'

    ghci> throw "error" `catch` (e :: String) -> putStrLn e
\end{minted}

In the simplest case, a custom exception type can be implemented in two lines.
To catch it, one must either catch this type itself or \mintinline{haskell}|SomeException|, because for both of them \mintinline{haskell}|fromException| on an object of the form \mintinline{haskell}|SomeException MyError| will return \mintinline{haskell}|Just|\footnote{\mintinline{haskell}{instance Exception SomeException where fromException = Just}}.
\begin{minted}{haskell}
    data MyError = MyError deriving (Show, Typeable)
    instance Exception MyError
\end{minted}

Let us add the exception \mintinline{haskell}|ArithException| and one more, more general exception type between it and \mintinline{haskell}|SomeException| --- \mintinline{haskell}|SomeArithException| (thus, there will be three ways to catch \mintinline{haskell}|ArithException|).
For this, we make \mintinline{haskell}|SomeArithException| an existential wrapper, and automatically wrap each exception of type \mintinline{haskell}|ArithException| in it.
In \mintinline{haskell}|fromException|, at each level of nesting, we try to obtain the wrapping constructor by a recursive call.

\begin{minted}{haskell}
    data SomeArithException where
      SomeArithException :: Exception a => a -> SomeArithException

    -- SomeException - base (default implementation)
    instance Exception ArithException

    data DivisionByZero = DivisionByZero deriving Show
    instance Exception DivisionByZero where
      toException = toException . SomeArithException
      fromException e = do
        SomeArithException e' <- fromException e
        cast e'
\end{minted}

Thus, when throwing \mintinline{haskell}|DivisionByZero|, an object of the following form will be constructed:
\begin{minted}{haskell}
    SomeException (SomeArithException DivisionByZero)
\end{minted}
The implementation of \mintinline{haskell}|fromException| for a concrete type can verify the presence of the corresponding constructor in the resulting exception object.

\subsubsection{Lightweight partial stack traces}

An amusing exploitation of type classes in Haskell is lightweight partial stack traces\footnote{\url{https://downloads.haskell.org/ghc/latest/docs/users_guide/exts/callstack.html}}.
In general, collecting traces requires runtime support, which in Haskell's case is further complicated by the fact that the computation model, graph reduction, does not contain real traces and they have to be emulated.
Here we obtain traces without runtime support.

The standard library defines the constraint \mintinline{haskell}|GHC.Stack.HasCallStack|, allowing one to obtain information about the call site of a function.
This information is effectively placed by the compiler during instance inference.
If information from the level above is available at the call site, the compiler propagates it further.
Thus, information is available only to a certain depth of the call stack.
\begin{minted}{haskell}
    myHead :: HasCallStack => [a] -> a
    myHead []     = error "empty"
    myHead (x:xs) = x

    bad :: Int
    bad = myHead []

    ghci> bad
    *** Exception: empty
    CallStack (from HasCallStack):
      error, called at Bad.hs:8:15 in main:Bad
      myHead, called at Bad.hs:12:7 in main:Bad
      -- no information about bad call site here
\end{minted}

\mintinline{haskell}{HasCallStack} is simply an implicit (see~\ref{subsubsec:ad-hoc-implicits}) that the compiler knows about:
\begin{minted}[escapeinside=##]{haskell}
    type HasCallStack = (?callStack :: CallStack)
\end{minted}

\subsubsection{Customizable type errors} \label{subsubsec:custom-type-errors}

When developing libraries that are complex from the type perspective, it is desirable to provide users with more informative type errors than the defaults.
For this, GHC has a mechanism in \href{https://hackage.haskell.org/package/base-4.20.0.1/docs/GHC-TypeLits.html}{GHC.TypeLits} that allows constructing a special type whose information will appear in the error message.
For example, this type can be returned from a synonym family with an incorrect set of arguments.
Or one can use the constraint trick (see\ \ref{subsubsec:instance-inference}) and place such a type as a premise in an instance.
If the instance matched and the compiler started processing the constraints on the left, something went wrong~\cite[chapter 12]{maguire-types}.

\begin{minted}{haskell}
    instance (TypeError
      ( Text "Attempting to show a function of type "
        :<>: Text "'" :<>: ShowType (a -> b) :<>: Text "'"
        :$$: Text "Did you forget to apply an argument?"
      )) => Show (a -> b) where
      show = undefined -- the implementation does not matter, execution will not reach here
\end{minted}
