In functional programming it is common to work with data persistently.
In this chapter we consider when and why this is important.
As well as functional optics --- a set of abstractions for convenient work with data.

\subsection{Persistent data structures}

Data structures are divided into \vocab{mutable} and \vocab{immutable}.
This is a classification solely by internal implementation --- whether mutable memory cells are used or not.

By usage, one distinguishes \vocab{ephemeral} and \vocab{persistent} data structures. % todo verify
Changes to an ephemeral data structure can be observed through the same reference:
\begin{minted}{Swift}
    let xs = MutableList<Int>.empty()
    xs.add(42)
    print(xs)
\end{minted}
Whereas modifying a persistent one produces new references each time, while the previous versions of the structure remain accessible through the old ones:
\begin{minted}{haskell}
    let xs = []
    let xs' = 42 : xs
    print xs
\end{minted}

It might seem that ephemeral structures are mutable and persistent ones are immutable.
In reality these are more or less orthogonal classifications.
For instance, one can provide a persistent interface to a mutable data structure via copying, and an ephemeral interface to an immutable one (using the \mintinline{haskell}|State| monad).

In practice, when people talk about persistent data structures, they often mean data structures with a persistent interface that are specially optimized for it (not requiring a full copy on every operation).
Such data structures can be surprisingly optimal and diverse~\cite{okasaki1999purely}.

For example, one can implement an efficient persistent array with logarithmic complexity for all operations.
In Haskell, such a data structure is \mintinline{haskell}|Seq|\footnote{\url{https://hackage.haskell.org/package/containers-0.7/docs/Data-Sequence.html}}\footnote{\url{http://www.staff.city.ac.uk/~ross/papers/FingerTree.html}}.
If small arrays are stored in the nodes, which modern processor architectures can efficiently copy, one can substantially reduce the tree height and the algorithmic complexity of operations (e.g.\ \mintinline{scala}|scala.immutable.Vector|).

When should one use ephemeral, and when persistent data structures?
Comparing the two, one can find that ephemeral structures can be implemented more efficiently in many cases: processor caches work better with local data, fewer allocations and indirections.
At the same time, persistent structures are bound to be trees, in order to reallocate not the entire structure but only the path to the root.

Persistent structures, on the other hand, allow writing more modular and thread-safe code that need not account for the possibility of the structure being modified through a reference.
Whereas working with an ephemeral structure is not pure code but involves producing observable side effects.
Also, combining persistent results of different calls can be cheaper; for example, concatenation of persistent arrays is cheaper than concatenation of ephemeral ones (logarithmic complexity versus linear).

Thus, within a limited, easily surveyable scope it is better to use ephemeral structures due to their efficiency (for example, to initially populate a collection with elements).
However, across abstraction boundaries it is better to pass only persistent structures (or rely on an effect system, see~\ref{sec:effect-systems}).
That is, each data structure should support two phases of its life.
For example, this is how it is done in Scala, where many persistent collections have a \mintinline{scala}|Builder| version.

\subsection{The idea of optics}

\vocab{Functional optics} allows building functional references that focus on certain properties of data structures.
Subsequently, using eliminating functions, one can read a property or persistently update it given a functional reference and an object.
For example, we can focus on the first component of a pair using the reference \texttt{\_1} and read the first component:
\begin{minted}{haskell}
    ghci> view _1 (42, 43)
    42
\end{minted}
Or we can focus on the property of membership of a certain element in a set \texttt{member}, set the property to \mintinline{haskell}{True}, and obtain a new set with the desired element:
\begin{minted}{haskell}
    ghci> set (member 42) (Set.fromList [1, 2]) True
    Set.fromList [1, 2, 42]
\end{minted}

Functional references compose (here, using \texttt{\%}).
So, if the set is in the first component of a pair, we can still add an element to it:
\begin{minted}{haskell}
    ghci> set (_1 % member 42) (Set.fromList [1, 2], 3) True
    (Set.fromList [1, 2, 42], 3)
\end{minted}

It is important to note that functional references, unlike ordinary pointers, are on the one hand more abstract and do not necessarily simply refer to a memory region, and on the other hand are detached from a particular object, thus more closely resembling pointers to methods in C++.

Thus, optics helps bring the convenience of programming with persistent data structures closer to that of programming with mutable ones.
This is important because good programming practices should be at least as accessible as less optimal ones.

Functional references can provide various usage interfaces, which are called \vocab{optical devices}.
Devices form a hierarchy (Fig.~\ref{fig:optics-hierarchy}): when composing two devices, the result is the nearest common ancestor with functionality equal to the intersection of the functionalities of the originals.

\begin{figure}
    \centering
    \includegraphics[width=\textwidth]{figs/optics-hierarchy}
    \caption{Hierarchy of optical devices of the \texttt{optics} library.}
    \label{fig:optics-hierarchy}
\end{figure}

Both references above are the optical device \vocab{lens}, which historically appeared first.
Initially, lenses were proposed as a solution to the view-update problem in databases~\cite{bohannon2006relational, foster2008quotient}.
Namely --- how should the actual database be changed when the view is changed.
Or how to reconstruct the whole after extracting and modifying a part.
Lenses here serve as a means of bidirectional programming --- they allow simultaneously describing both the view and the way to update.
In parallel\footnote{\url{https://github.com/ekmett/lens/wiki/History-of-Lenses}}, lenses are mentioned in a series of blog posts describing an attempt to work more conveniently with mutable state when writing games\footnote{\href{https://web.archive.org/web/20140402193032/https://lukepalmer.wordpress.com/2007/07/26/making-haskell-nicer-for-game-programming/}{(post) Making Haskell nicer for game programming}}\footnote{\href{https://web.archive.org/web/20120303223802/https://lukepalmer.wordpress.com/2007/08/05/haskell-state-accessors-second-attempt-composability/}{(post) Haskell State Accessors (second attempt: Composability)}} (lenses in games continue to delight\footnote{\url{http://www.timphilipwilliams.com/posts/2019-07-25-minecraft.html}}).

Numerous optics libraries exist for both Haskell\footnote{\url{https://hackage.haskell.org/package/optics-0.1/docs/Optics.html}}\footnote{\url{http://lens.github.io/}}\footnote{\url{https://github.com/marcosh/existential-optics/tree/main}} and other languages: Kotlin\footnote{\url{https://arrow-kt.io/}}, Scala\footnote{\url{https://github.com/optics-dev/Monocle}}, Swift\footnote{\url{https://github.com/swiftlang/swift-evolution/blob/main/proposals/0161-key-paths.md}} (language support).

\subsection{Data optics}

\subsubsection{Lenses}

The simplest lens is formed by a pair of functions --- viewing and setting a property:
\begin{minted}{haskell}
    data SimpleLens' s a = SimpleLens'
      { view' :: s -> a
      , set' :: s -> a -> s
      }
\end{minted}

Natural laws are imposed on these functions:
\begin{minted}{haskell}
    view l (set l s x) ?$\equiv$? x
    set l s (view l s) ?$\equiv$? s
    set l (view l s x) y ?$\equiv$? set l s y
\end{minted}

For example, one can easily modify a user's age:
\begin{minted}{haskell}
    newtype Age = Age { _getAge :: Int }
    data User = User { _userName :: String, _userAge :: Age }

    userAge :: SimpleLens' User Age
    userAge = SimpleLens' { view' = _userAge, set' = \s x -> s { _userAge = x } }

    getAge :: SimpleLens' Age Int
    getAge = SimpleLens' { view' = _getAge, set' = \s x -> s { _getAge = x } }

    ghci> set (userAge % getAge) user 1
\end{minted}

One can generalize lenses to polymorphic lenses, which allow recreating the structure with new type parameters:
\begin{minted}{haskell}
    data SimpleLens s t a b = SimpleLens
      { view :: s -> a
      , set :: s -> b -> t
      }

    _1 :: SimpleLens (a, c) (b, c) a b
    _1 = SimpleLens { view = \(x, _) -> x, set = \(x, c) y -> (y, c) }
\end{minted}

One can notice that a lens in this representation is a costate comonad coalgebra\footnote{\href{https://youtu.be/9_iYlp8smc8?si=NLka0vnnhYDdTfgm}{(youtube) Category Theory II 9.1: Lenses.}}.
Indeed, the pair of functions can be replaced with a function returning a pair:
\begin{minted}{haskell}
    data Store a s = Store (a, a -> s)
    data DataLens s a = DataLens (s -> Store a s)
\end{minted}

If we define a comonad instance for \mintinline{haskell}|Store a s| and write out the laws of compatibility with the coalgebra, we obtain exactly the lens laws.

\subsubsection{Prisms}

Prisms allow obtaining a property that may be absent, and setting it when present.
Thus, a specific field of a sum type may fail to be extracted if an unexpected constructor is passed.

Simple prisms can be defined analogously to lenses, accounting for possible absence of the property:

\begin{minted}{haskell}
    data SimplePrism' s a = SimplePrism'
      { preview' :: s -> Maybe a
      , review' :: a -> s
      }
\end{minted}

A polymorphic prism must provide the structure with an updated type in case the preview fails:
\begin{minted}{haskell}
    data SimplePrism s t a b = SimplePrism
      { preview :: s -> Either t a
      , review :: b -> t
      }
\end{minted}

One can define a prism for working with the contents of the \mintinline{haskell}|Left| constructor:
\begin{minted}{haskell}
    _Left :: SimplePrism (Either a c) (Either b c) a b
    _Left = SimplePrism
      { preview = \case Left a -> Right a; Right c -> Left (Right c)
      , review = Left
      }
\end{minted}

Composition of prisms is defined in a natural way.

\subsubsection{Composition of lenses and prisms}

Let us introduce a type class with which we will learn to compose various combinations of lenses and prisms.
The resulting device is uniquely determined by the operands of the composition.

\begin{minted}{haskell}
    class Composable o1 o2 o3 | o1 o2 -> o3 where
      compose :: o1 s t a b -> o2 a b c d -> o3 s t c d
\end{minted}

Now we can naturally define composition for various devices.
One can notice that this approach requires a quadratic number of instances in the number of optical devices.

\begin{minted}{haskell}
    instance Composable SimpleLens SimpleLens SimpleLens where
      compose :: SimpleLens s t a b -> SimpleLens a b c d -> SimpleLens s t c d
      compose l2 l1 = SimpleLens
        { view = view l1 . view l2
        , set = \s x -> set l2 s (set l1 (view l2 s) x)
        }
\end{minted}

Composition of lenses and prisms forms a different device --- affine traversals, which are something in between.
The presence of a prism in the composition does not allow guaranteed viewing of the property, while a lens does not allow creating a new value without the original.
\begin{minted}{haskell}
    data AffineTraversal s t a b = AffineTraversal
      { apreview :: s -> Either t a
      , aset :: s -> b -> t
      }

    instance Composable SimplePrism SimpleLens SimplePrism where
      compose :: SimplePrism s t a b -> SimpleLens a b c d -> SimplePrism s t c d
      compose p l = SimplePrism
        { preview = fmap (view l) . preview p
        , pset = \s d -> case preview p s of
            Left t -> t
            Right a -> pset p s (set l a d)
        }
\end{minted}
