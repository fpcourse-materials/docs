The art of programming largely consists of the ability to manage complexity, and within this course we will consider building languages and interpreters as the primary tool for this.

\subsection{Interpreters as the foundation} \label{subsec:interpreters-rules}

We begin with an overview of the role of interpreters in programming.

\subsubsection{The tower of interpreters} \label{subsubsec:interpreters-tower}

The most basic interpreter is the processor, physically embodied in hardware.
It receives a program in some language, such as x86, reads instructions, and turns them into actions on memory.
However, it is difficult for a human to program in this language; a new language is needed that encapsulates part of the complexity and hides unnecessary details.

To obtain a new language, we build a software interpreter.
A \vocab{software interpreter} $U_M^N$ is a program in language $M$\footnote{By a language we mean the set of programs in that language, in other words, the set of trees of a certain form.} that takes as input a program in language $N$ and its input --- data from $D$, and returns the result of executing that program on that data: \[U_M^N : N\times D\to D\]

We will call the implementation language of the interpreter $M$ the \vocab{meta-language}, and $N$ the \vocab{object language}.
One can intuitively think of an interpreter as follows: it is an explanation, understandable to the meta-language, of what the constructs of the object language mean.
In other words, which meta-language instructions need to be executed to obtain the desired semantics of the object language instructions.

For example, given a program $p_N$ and its input data $d_{in}$, the result of executing this program $d_{out}$ can be obtained as \[d_{out} = U_M^N\left( \underbrace{\langle p_N, d_{in} \rangle}_{\in N\times D} \right)\]

But an interpreter is also a program.
How do we run it?
Take our basic interpreter $U^{x86}$; it has no implementation language since it is implemented in hardware, not software.
Take an assembly language interpreter implemented in x86 codes, $U_{x86}^{Asm}$, an assembly program $p_{Asm}$, and its input $d_{in}$.
Recall that a program is also data, just in a special format.
Then we obtain the result of applying $p_{Asm}$ to the data as follows:
\[
    d_{out} = U^{x86}\left(\left<\underbrace{U_{x86}^{Asm}}_{\in x86}, \underbrace{\overbrace{\langle p_{Asm}}^{\in Asm}, \overbrace{d_{in} \rangle}^{\in D}}_{\in D} \right>\right)
\]

But assembly language is also not very pleasant for programming.
However, in it one can already write an interpreter for a more complex language.
And so on.
We obtain a \point{tower of interpreters}, at the top of which is the language in which we want to solve our actual problem:
\[
    d_{out} =
    U^{x86}\left(\left<
                     U_{x86}^{Asm}, \left<
                                        U^C_{Asm}, \left<
                                                       U^{Has}_C, \left< p_{Has}, d_{in}
                \right>\right>\right>\right>\right)
\]

In practice, a language is often defined via translation (compilation) into another.
However, we will focus on embedded languages going forward, and the notion of an interpreter will be more useful to us.
Moreover, there exist universal theoretical methods for deriving a compiler from an interpreter\footnote{\url{https://en.wikipedia.org/wiki/Partial_evaluation}} (see~\ref{sec:datatype-generic}), so for us they are similar.

\subsubsection{Interpreters everywhere} \label{subsubsec:interpreters-everywhere}

Very well, we have arrived at the language of our heart (Haskell); why do we continue talking about interpreters?
Because for solving concrete business problems, general-purpose languages are still too ceremonious --- the programmer has to think about a large number of things irrelevant to their domain and the problem at hand.
Complexity is the programmer's main enemy, because the human brain's resources are no match for the complexity of the reality our programs must describe.
Thus, in practice one constantly has to describe new languages most suited for solving specific applied problems.
And new languages are defined using interpreters.

What does a classical recursive interpreter look like?
It receives a program in the form of some tree and recursively traverses it, computing the results of subtrees.
When it visits a tree node, it determines its type and understands what actions need to be performed.
That is, the node type dispatches, navigates, the interpreter's execution to the appropriate code.
Thus, an interpreter for a simple expression language looks as follows:
\begin{minted}{haskell}
    eval :: Expr -> Int
    eval prog = case prog of
      Const x -> x
      Plus l r -> eval l + eval r
\end{minted}

One can see that this resembles, for example, a command-line utility --- we parse arguments, determine what needs to be done and how, and do it.
Surprisingly, the Unix philosophy, in particular, consists of building small languages (utilities with a text API) that solve one problem well~\cite{bentley1986little}.
It also resembles handling a request by a web server --- determining the route the request arrived at and performing the corresponding action.
That is, we write interpreters in real life more often than we think.
We simply do not see that what we write is actually an interpreter for some language.
In general, folding a data structure can already be considered as interpretation~\cite{gibbons2014folding}.

Moreover, as we will see later~\ref{subsec:tagless-final}, writing any function is already defining a new language.
There was a language in which one could not add a user to an application.
We wrote a function \texttt{registerUser} --- a new command appeared in the language --- add a user.
Below we will formally show that this approach is equivalent to adding a new node to the language's syntax tree (\ref{subsubsec:shallow-embedding}).
Using functions is an example of language embedding, when instead of creating a new separate language, we implement it as a library for an already existing language~\cite{gibbons2013functional}.

As we will see throughout the course, many problems can be viewed as inventing a language and implementing an interpreter.
This means that if we learn to write interpreters well, we will learn to do a lot of things at once!
And our main efforts will be directed at studying the tools for building interpreters of embedded languages.

During the exposition we frequently use the Hutton's Razor technique, which involves considering a ridiculously small language for studying complex concepts.
It is argued that for studying most questions one can construct such a language that makes everything important maximally clear.

\subsubsection{Interpreters and programming language semantics} \label{subsubsec:semantics}

Programming language semantics\footnote{\url{https://en.wikipedia.org/wiki/Semantics_(computer_science)}\label{note:sema-wiki}} is a discipline studying the properties of languages and the meaning of programs, its properties, and methods of description.
An excellent introduction is the Software Foundations book series\footnote{\url{https://coq.vercel.app/ext/sf/}}~\cite{pierce2010software}.
There are many different styles of describing program semantics; the most important for us will be denotational semantics.

\vocab{Denotational semantics}\footnote{\url{https://en.wikipedia.org/wiki/Denotational_semantics}}\footnote{\url{https://en.wikibooks.org/wiki/Haskell/Denotational_semantics}}\footnote{\href{https://youtu.be/pQyH0p-XJzE?si=TUEzrpHhJZfO7dTF}{(youtube) The Lost Art of Denotational Semantics --- Eric Meyer.}\label{foot:the-lost-art-of-denotations}} describes the meaning of programs by associating them with objects of some set, the \vocab{semantic domain}.
In other words, the denotational semantics of a language $L$ is a total function from a program in that language to an element of the domain $D$:
\[
    \sembr{\bullet} : L \mapsto D
\]

The domain is chosen based on the language and the information one wants to extract from programs.
For example, to find out the size of a program (here, expressions with addition), one can take natural numbers as the domain:
\[
    \begin{array}{lcl}
        \sembr{n}     & = & 1                                \\
        \sembr{l + r} & = & 1 + \max{(\sembr{l}, \sembr{r})}
    \end{array}
\]
If we are interested in the final result, we can compute it:
\[
    \begin{array}{lcl}
        \sembr{n}     & = & n                     \\
        \sembr{l + r} & = & \sembr{l} + \sembr{r}
    \end{array}
\]
If the program has input, the domain will be a function $\mathbb{N}\to\mathbb{N}$:
\[
    \begin{array}{lcl}
        \sembr{n}(m)     & = & n                           \\
        \sembr{l + r}(m) & = & \sembr{l}(m) + \sembr{r}(m) \\
        \sembr{input}(m) & = & m
    \end{array}
\]

Thus, \point{a program is merely a syntactic notation for some element of the semantic domain}.
There are many possible domains; they can even be games\footnote{\url{https://en.wikipedia.org/wiki/Game_semantics}}. % todo domain theory

It is easy to see that the denotational semantics of a language is simply an interpreter, only written in the language of mathematics.
Such interpreters are placed at the base of the tower of interpreters when the goal is to study properties of languages and programs rather than to execute them.

Also, we can implement an interpreter in some real language, and it too will define the semantics of the object language.
However, the formality of such a definition will depend on the formality of the meta-language's semantics description.
Such interpreters are called \vocab{definitional}; they define the semantics of a language, typically sacrificing efficiency for clarity.
The relationships between the object language and the meta-language are studied in the classical papers~\cite{reynolds1972definitional,reynolds1998definitional}\footnote{The notion of continuation, actively used by the author, will be considered later in this course (section \ref{sec:continuations}).}.

We will use definitional interpreters to define the semantics of new languages, using Haskell as the meta-language.
And as domains we will take Haskell types.
And we will interpret programs not into the set of functions between natural numbers, but, say, into the type \mintinline{haskell}|Nat -> Nat| in Haskell\footnote{\url{https://okmij.org/ftp/Denotational.html}}.
Thus, the denotational semantics of the language of sums with input will be written as follows:
\begin{minted}{haskell}
    eval :: Prog -> (Nat -> Nat)
    eval = \case
      Val n -> \_ -> n
      Plus l r -> \m -> eval l m + eval r m
      Input -> \m -> m
\end{minted}

A semantics is called \vocab{compositional} if the meaning of constructs depends only on the meaning of subconstructs.
In other words, if the denotational semantics is a fold over the program (Fig.\ \ref{fig:eval-prog}) and can be written in terms of a catamorphism~\ref{subsubsec:recursion-schemas}.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{figs/eval-prog}
    \caption{Denotational semantics defines the meaning of syntactic constructs through operations on the domain~\cite{hutton1998fold}.}
    \label{fig:eval-prog}
\end{figure}

Another popular style of describing semantics is \vocab{operational semantics}, which represents the meaning of a program as a sequence of computation steps.
This can be either sequential rewriting of the expression itself, or rewriting the state of some abstract machine.
Operational semantics, in turn, is defined as an unfold (or anamorphism~\ref{subsubsec:recursion-schemas}) of the sequence of computation steps from the program.
Here one can clearly see a certain duality between denotational and operational semantics~\cite{hutton1998fold}.

\subsubsection{Embedded domain-specific languages (eDSL)} \label{subsubsec:edsl}

By \vocab{domain-specific languages (DSL)}\footnote{\url{https://en.wikipedia.org/wiki/Domain-specific_language}} one often means specialized languages for specific domains, such as database queries or document formatting.
As a rule, such languages are not Turing-complete.

In this course, however, we will consider any domain-specific specialization of a general-purpose language to be a domain-specific language\footnote{\url{https://en.wikipedia.org/wiki/Language-oriented_programming}.}.
This follows from the consideration that code should read like well-written prose with appropriate word usage, providing the reader with only the necessary amount of detail, hiding the inessential behind conventions and terminology.

\vocab{Standalone domain-specific languages} are languages that have their own concrete syntax as well as programming tools (IDE, runtime\ldots).
Examples: SQL, AWK, Antlr\ldots\footnote{There is an excellent practical book~\cite{nystrom2021crafting} that covers building interpreters and simple virtual machines.
At the same time it covers the creation of a full-fledged language in all its aspects, from parsing to memory management.}

\vocab{Embedded domain-specific languages (eDSL)} are languages that leverage the infrastructure of other languages.
They are usually implemented as libraries for programs in an already existing general-purpose language.
They do not have a fully independent concrete syntax.
Examples: ORM, string processing functions, parser combinator libraries\ldots

\vocab{Deep eDSL} --- terms in such a language build an abstract syntax tree for further interpretation:
\begin{minted}{haskell}
    f :: Int -> Int
    f = eval $ Const 1 `Plus` Input
\end{minted}

Interpreters that take trees as input and interpret them into a semantic domain are called \vocab{initial}\footnote{The syntax type defined using \mintinline{haskell}{data} is the initial object of the category of interpretations.}; we will also call them ``classical.''
We will start with them.
Classical interpreters are useful, for example, for implementing the ``last language'' --- the program's interface to the outside world, and as a foundation for our further constructions.

%Now we can write imperatively in Haskell without a single monad!
%\begin{minted}{haskell}

%\end{minted}

However, one can notice that the intermediate tree that is produced typically does not interest us.
We only care about obtaining the domain element, which we already know how to use directly.
\vocab{Shallow eDSL} skip the tree construction stage and directly build the value in the semantic domain.
We will call such interpreters \vocab{final}. % todo verify
\begin{minted}{haskell}
    cnst :: Int -> (Int -> Int)
    cnst x _ = x

    input :: Int -> Int
    input env = env

    plus :: (Int -> Int) -> (Int -> Int) -> (Int -> Int)
    plus l r env = l env + r env

    f :: Int -> Int
    f = cnst 1 `plus` input
\end{minted}

Interpreters are often called \vocab{observers}, which analyze terms and give them some meaning~\cite{gibbons2013functional}.
One can notice that for deep eDSL one can write arbitrarily many different observers.
However, in the case of shallow embedding, observers are always \texttt{id}.
We will discuss possible solutions to this problem later in section~\ref{subsubsec:shallow-embedding}.

A discussion of terminology and comparison of approaches to DSL construction can be found in~\cite{gibbons2013functional}.
A brief description of terms is in the Language Engineering course notes~\cite{languageEngineering}.

Let us introduce one more important concept.
A \vocab{meta-circular interpreter}\footnote{\url{https://en.wikipedia.org/wiki/Meta-circular_evaluator}} is an interpreter that defines constructs of the object language through constructs of the meta-language~\cite{reynolds1972definitional}.
For example:
\begin{minted}{haskell}
    interpret term = case term of
      App f t -> (interpret f) (interpret t)
      If c t e -> if interpret c then interpret t else interpret e
      ...
\end{minted}

The properties of the meta-language in this case largely determine the properties of the object language~\cite{reynolds1972definitional,reynolds1998definitional}.
In this course we will strive to reuse the capabilities of the meta-language as much as possible.

\subsubsection{Example: the Accelerate library}

An interesting example of an embedded language that lies somewhere between deep and shallow is the Accelerate library\footnote{\url{https://hackage.haskell.org/package/accelerate}}~\cite[chapter 6]{marlow2011parallel}.
It allows describing computations in Haskell that will be executed on a GPU\footnote{Another approach: \href{https://youtu.be/6c0DB2kwF_Q?si=-nB7AkCsDWB_Q-hy}{Java code reflection}, to extract a model of the code at runtime. However, such an approach does not provide static guarantees to the programmer and requires deep integration into the meta-language.}.

To execute something on a GPU, one needs to generate and compile Cuda code.
Thus, the Accelerate language must be a deep embedding in order to have the computation tree for translation into Cuda in the most efficient manner.

At the same time, describing numerical computations as a tree is extremely inconvenient.
It would be nice to have familiar operators and higher-order functions for working with arrays on the GPU\@.
Therefore, Accelerate actually provides a shallow interface for building trees.
Thus, for expression trees, implementations of numeric type classes are defined, e.g. \mintinline{haskell}|Num|, where operations simply extend the tree:
\begin{minted}{haskell}
    example :: Acc (Vector Int) -> Acc (Vector Int) -> Acc (Vector Int)
    example xs ys = A.zipWith (+) xs ys
\end{minted}

\subsection{Value types}

Let us consider the possible ways to implement languages whose values can have different types.

\subsubsection{Untyped tagless interpreters}

First, let us consider a trivial untyped language.
By untyped we mean the absence of type checking both before and during program execution.
We define the abstract syntax of this language as follows:
\begin{minted}{haskell}
    data Expr = Const Int | IsZero Expr | If Expr Expr Expr
\end{minted}

Values arising during the execution of programs in this language will be represented by values of types \mintinline{haskell}|Bool| and \mintinline{haskell}|Int| of the Haskell language.
Accordingly, the semantic domain of a program in this language is either \mintinline{haskell}|Bool| or \mintinline{haskell}|Int|, depending on the program itself.
\begin{minted}{haskell}
    evalUnsafe :: Expr -> forall res . res
    evalUnsafe = \case
      Const val -> unsafeCoerce val
      IsZero cond -> unsafeCoerce $ evalUnsafe @Int cond == 0
      If c t e -> if evalUnsafe c then evalUnsafe t else evalUnsafe e
\end{minted}

Here \texttt{unsafeCoerce} is used to circumvent Haskell's static type system and simply execute programs in our untyped language.
We are entitled to do this because \mintinline{haskell}{Int} and \mintinline{haskell}{Bool} in Haskell have the same size.
Writing an incorrect program in this language or choosing the wrong interpretation domain leads to a crash.

\subsubsection{Typed tagged interpreters}

To achieve some safety during execution, we will attach tags to values that will be available at runtime.
We introduce the following algebraic type:
\begin{minted}{haskell}
    data RtValue = RtBool Bool | RtInt Int
\end{minted}

Now the semantic domain will be the type \mintinline{haskell}|RtValue|, and the interpreter can check types at runtime:
\begin{minted}{haskell}
    evalRt :: Expr -> RtValue
    evalRt (IsZero expr) = case evalRt expr of
      RtBool value -> error "Type error"
      RtInt value -> RtBool (value == 0)
    -- ...
\end{minted}

The safety situation has definitely improved, but type checking at runtime is already too late: it requires additional performance overhead and makes testing more expensive.

This approach is often called \vocab{dynamic typing}, when we attribute values with some type information for use at runtime (see also\ \ref{subsubsec:type-reflection}).

\subsubsection{Typed tagless interpreters} \label{subsubsec:typed-tagless-initial}

Let us describe the type system of our small language.
%! suppress = EscapeAmpersand
\begin{equation*}{}
    \infer[Const]{Const~n : int}{n : Int}
    \quad
    \infer[IsZero]{IsZero~n : bool}{n : int}
    \quad
    \infer[If]{If~c~t~e : \tau}{c : bool & t : \tau & e : \tau}
\end{equation*}
We can reuse Haskell types as type tags: \[int \rightsquigarrow Int, bool \rightsquigarrow Bool\]

Notice that with the help of a generalized algebraic data type \mintinline{haskell}|Expr ty| (\ref{subsubsec:gadts}), we have precisely encoded these typing rules.
In other words, we have obtained a statically typed programming language by reusing Haskell's type system.
\begin{minted}{haskell}
    data Expr ty where
      Const :: Int -> Expr Int
      IsZero :: Expr Int -> Expr Bool
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty

    eval :: Expr ty -> ty
    eval = \case
      Const n -> n
      IsZero e -> eval e == 0
      If c t e -> if eval c then eval t else eval e
\end{minted}

Thanks to static typing, we can dispense with tagging values during interpretation without losing safety.

\subsection{Bindings and first-class functions} \label{subsec:first-class-functions}

In this section we consider techniques and concepts related to implementing first-class functions and bindings in general.
Since this functionality is typically already implemented in the meta-language, we will strive to reuse it as much as possible.

\mintinline{haskell}|let|-bindings can be represented through first-class functions as follows:
\[
    \term{let} \ap x \termdef N \ap \term{in} \ap M \equiv (\lambda x\ldotp M) \ap N
\]

Recall that first-class functions can be eliminated using defunctionalization, considered earlier~\ref{subsubsec:defunctionalization}.

\subsubsection{Name semantics} \label{subsubsec:name-bindings}

There are several ways to assign semantics to identifiers.

\vocab{Dynamic scoping} --- the values of free variables of a function depend on the scope at the call site.
That is, name resolution happens at the moment the variable is accessed.
For example, the following code prints \texttt{42}:
\begin{minted}{scala}
    val x = 4
    val f = () => x + 1
    val x = 41
    println(f())
\end{minted}

This approach is simpler to implement and was used in early versions of Lisps, for example.
However, in this case functions are not a reliable abstraction barrier; ideally all free variables should be part of the signature (we will return to this in the chapter on effect systems~\ref{sec:effect-systems}).

\vocab{Lexical/static scoping} --- variables are bound to values at the point of function declaration; at the point of invocation the result depends only on the parameters (modulo mutable state\footnote{For example, in Kotlin, mutable variables can be captured in lambdas. Changes outside are observable inside the lambda, and vice versa. This can sometimes be very convenient, but often leads to very non-obvious behavior.}).
The word ``lexical'' is often used in languages when we can determine something from the source code without running the program.
Thus, the code from the example above would print 5.

In the rest of this section we will discuss various ways of implementing first-class functions with static variable scoping, of which there are, in fact, a great many\footnote{\url{https://jesper.cx/posts/1001-syntax-representations.html}}.

\subsubsection{Substitutions} \label{subsubsec:substitutions}

As one can notice, in classical lambda calculus, substitutions from beta-reduction (recalled in section~\ref{subsec:terms-reduction}) provide static scoping.
Indeed, the argument is immediately substituted into all occurrences of the variable, so it does not remain free but simply disappears.
\[
    (\lambda x\ldotp (\lambda x\ldotp \lambda y\ldotp x + y) \ap 4) \ap 41 \rightsquigarrow (\lambda x\ldotp (\lambda y\ldotp 4 + y)) \ap 41
\]

This approach is not the most efficient, because each application requires rewriting the entire function body (!).
At the same time, it is fairly simple to implement for certain representations of lambda terms.
Let us consider an example of such a representation --- \vocab{locally nameless}~\cite{chargueraud2012locally}.

\begin{minted}{haskell}
    data Term var
      = Var var
      | App (Term var) (Term var)
      | Lam (Term (Maybe var))
\end{minted}

In this representation one can choose any type for naming free variables:
\begin{minted}{haskell}
    example :: Term String
    example = Var "x" `App` Var "y" -- x y
\end{minted}
Adding each bound variable adds a new inhabitant \mintinline{haskell}|Nothing| to the variable type for referring to the nearest bound variable:
\begin{minted}{haskell}
    -- ?$\lambda x\ldotp x \ap y$?
    example1 = Lam $ Var Nothing `App` Var (Just "y")
    -- ?$\lambda x \ap y\ldotp x \ap y \ap z$?
    example2 = Lam $ Lam $ Var (Just Nothing) `App` Var Nothing `App` Var (Just (Just "z"))
\end{minted}

Monadic bind is the implementation of substitution for such terms:
\begin{minted}{haskell}
    instance Monad Term where
      (>>=) :: Term var -> (var -> Term var') -> Term var'
      Var var >>= subst = subst var
      App l r >>= subst = App (l >>= subst) (r >>= subst)
      Lam t >>= subst = Lam $ t >>= \case
        Nothing  -> Var Nothing
        Just var -> Just <$> subst var
\end{minted}

\begin{task}
    Think about why \texttt{fmap Just} is needed in the last line.
\end{task}

Accordingly, a call-by-name interpreter for this lambda calculus will look as follows:\footnote{Since we are considering classical $\lambda$-calculus, the resulting value is also a term, but in normal form.}

\begin{minted}{haskell}
    eval :: Term var -> Term var
    eval = \case
      Var var -> Var var
      App f arg -> case eval f of
        Lam body -> eval $ body >>= maybe arg Var
        t -> App t (eval arg)
      Lam t -> Lam (eval t)
\end{minted}

\subsubsection{Environment}

One can perform substitution of variable values lazily, propagating an environment that maps free variables to terms.
Things have not yet improved much overall, but we have obtained compositional semantics from non-compositional semantics by making context dependencies explicit (more on this later~\ref{subsubsec:recover-compositionality}).

\begin{minted}{haskell}
    data Term1 = Var1 String | App1 Term1 Term1 | Lam1 String Term1
    type Env = Map String Term1

    eval1 :: Term1 -> Env -> Term1
    eval1 term env = case term of
      Var1 name -> Map.findWithDefault (Var1 name) name env
      App1 f arg -> case eval1 f env of
        Lam1 name body -> eval1 body (Map.insert name arg env)
        t -> App1 t (eval1 arg env)
      Lam1 name body ->
        let env' = Map.delete name env in
        Lam1 name (eval1 body env')
\end{minted}

\begin{task}
    Explain why the environment is modified on line~10?
\end{task}

If the \mintinline{haskell}|Lam1| branch does not recursively traverse the subterm and substitute variable values, the information about free variable values in it will be lost and we will get dynamic scoping instead of static scoping.
To restore static scoping, the \mintinline{haskell}|Lam1| branch of the interpreter must construct a closure that includes the current environment (see~\ref{subsubsec:closures}).

\subsubsection{Closures} \label{subsubsec:closures}

To avoid eagerly performing substitution into function bodies while preserving static scoping, we add one more construct, a \vocab{closure}\footnote{\url{https://en.wikipedia.org/wiki/Closure_(computer_programming)}}\footnote{The term closure was proposed by Peter Landin, along with a bunch of other things.}~\cite[chapter 11]{nystrom2021crafting}.
It will store the context in which the corresponding term should be executed.

\begin{minted}{haskell}
    data Term1 = Var1 String | App1 Term1 Term1 | Lam1 String Term1
               | Closure Env String Term1 -- only for computations
    type Env = Map String Term1

    eval1 :: Term1 -> Env -> Term1
    eval1 term env = case term of
      Var1 name -> Map.findWithDefault (Var1 name) name env
      App1 f arg -> case eval1 f env of
        Closure env' name body ->
            let arg' = eval1 arg env in
            eval1 body (Map.insert name arg' env')
        t -> App1 t (eval1 arg env)
      Lam1 name body -> Closure env name body
\end{minted}

Closures are typically used in industrial languages as the runtime representation of higher-order functions.
During compilation, \vocab{closure conversion} is performed first --- higher-order functions are represented as a pair of an environment and a pointer to a function that takes the environment as an extra argument.
Now that the function contains no free variables, \vocab{lambda lifting}\footnote{\url{https://en.wikipedia.org/wiki/Lambda_lifting}} is done --- it is lifted to the top level.
Detailed examples can be found in the Harvard slides~\cite{closures-slides}.

\subsubsection{Typed context} \label{subsubsec:typed-env}

Let us consider the encoding described, for example, in~\cite{kiselyov2012typed}.

First, let us learn to use Haskell's type system to check the validity of environment lookups.
We represent the environment as a list of types encoded using nested pairs:
\begin{minted}{haskell}
    (4, (4.0, "hello")) :: (Int, (Double, String))
\end{minted}

Environment lookups will be encoded as numbers in unary notation.
The type of the number (a typed reference into the context) specifies the set of environments \texttt{env} from which a value of type \texttt{ty} can be extracted at the given position.
\begin{minted}{haskell}
    data Ref env ty where
      Here :: Ref (ty, env) ty
      There :: Ref env ty -> Ref (ty', env) ty
\end{minted}
For example, the type of the number 1 asserts that it can be used to extract a value of type \texttt{ty} from a context where a value of the corresponding type is at position one (zero-indexed):
\begin{minted}{haskell}
    There Here :: Ref (ty', (ty, env)) ty
\end{minted}

Now we can encode a typed safe lookup into the context:
\begin{minted}{haskell}
    envLookup :: env -> Ref env ty -> ty
    envLookup env ref = case (ref, env) of
      (Here, (x, _)) -> x
      (There ref', (_, env')) -> envLookup env' ref'
\end{minted}

\subsubsection{Meta-circular interpretation} \label{subsubsec:meta-circular-initial}

It would be extremely undesirable to implement bindings and first-class functions for an eDSL by ourselves.
Let us build a meta-circular interpreter (see~\ref{subsubsec:edsl}) that will reuse the meta-language's first-class functions to implement them in the object language.

Terms will now be annotated not only with resulting types but also with the types of environments needed for interpretation, considered earlier~\ref{subsubsec:typed-env}.
An abstracted term has access to a larger environment.

\begin{minted}{haskell}
    data Term2 env ty where
      Var2 :: Ref env ty -> Term2 env ty
      App2 :: Term2 env (arg -> res) -> Term2 env arg -> Term2 env res
      Lam2 :: Term2 (arg, env) res -> Term2 env (arg -> res)
\end{minted}

Now we can interpret abstraction as a Haskell function and application as application:
\begin{minted}{haskell}
    eval2 :: Term2 env ty -> env -> ty
    eval2 term env = case term of
      Var2 ref -> env `envLookup` ref
      App2 f arg -> (eval2 f env) (eval2 arg env)
      Lam2 t -> \arg -> eval2 t (arg, env)
\end{minted}

\subsubsection{Higher-order abstract syntax} \label{subsubsec:h-syntax}

Another thing we are still doing manually is defining binders (and in unary notation, no less).
We want to reuse them from the meta-language.
For this, we will store meta-language functions directly in the syntax tree --- use \vocab{higher-order abstract syntax (HOAS)}\footnote{\url{https://en.wikipedia.org/wiki/Higher-order_abstract_syntax}}\footnote{\href{https://cstheory.stackexchange.com/questions/20071/what-is-higher-order-in-higher-order-abstract-syntax}{What is higher-order in higher-order abstract syntax?}}~\cite{pfenning1988higher}:
\begin{minted}{haskell}
    data Term3 ty where
      Val3 :: ty -> Term3 ty
      Plus :: Term3 Int -> Term3 Int -> Term3 Int
      App3 :: Term3 (arg -> res) -> Term3 arg -> Term3 res
      Lam3 :: (Term3 arg -> Term3 res) -> Term3 (arg -> res)

    example3 :: Term3 Int
    example3 = (Lam3 \x -> x `Plus` Val3 41) `App3` Val3 1
\end{minted}

The interpretation is very simple and completely meta-circular:
\begin{minted}{haskell}
    eval3 :: Term3 ty -> ty
    eval3 term = case term of
      Val3 x -> x
      Plus l r -> eval3 l + eval3 r
      App3 f arg -> (eval3 f) (eval3 arg)
      Lam3 f -> \arg -> eval3 (f (Val3 arg))
\end{minted}

\subsubsection{Serialization of functions}

In this section we discussed possible implementations of first-class functions, i.e. functions that can be used as flexibly as data.
A natural question arises: can we serialize a first-class function and send it for execution on another machine?

A function consists of code and captured free variables in the case of static scoping.
Accordingly, if the code is in a serializable form (e.g. position-independent bytecode), it can in principle be sent over the network and executed on another virtual machine instance.
This is what Erlang does, for example.
However, this approach is inefficient, since the bytecode needs to be interpreted or pre-compiled.
Thus, Erlang sacrifices execution speed for horizontal scalability.

If we guarantee that the same code runs on different cluster nodes, as is usually the case in practice, a more efficient implementation can be achieved.
For example, using defunctionalization~(see~\ref{subsubsec:defunctionalization}), we can serialize only the algebraic type objects encoding functions.
Since the same code runs on the other cluster node, we can deserialize the object there and execute it using \texttt{apply}.
However, this approach does not support modularity well (it is hard to split one algebraic type into many), and \texttt{apply} performs decoding before executing the code each time (which, admittedly, can be neglected given network overhead).

The approach implemented in Haskell\footnote{\url{https://blog.ocharles.org.uk/blog/guest-posts/2014-12-23-static-pointers.html}}\footnote{\url{https://hackage.haskell.org/package/distributed-closure}} allows assigning each function without free variables a statically known address, the same for all application instances.
Then one can construct a serializable closure through a sequence of partial applications:
\begin{minted}{haskell}
    data Closure a where
      StaticPtr :: StaticPtr b -> Closure b
      Encoded :: ByteString -> Closure ByteString
      Ap :: Closure (b -> c) -> Closure b -> Closure c

    main = send "some-node" $
      closure (static factorial) `closureAp` closurePure 10
\end{minted}

More details can be found in the foundational paper on Cloud Haskell~\cite{epstein2011towards}.
From a practical perspective --- in the book~\cite[chapter 16]{marlow2011parallel}.

\subsection{Tagless final interpreters} \label{subsec:tagless-final}

As we established earlier (\ref{subsubsec:interpreters-everywhere}), programming consists of writing interpreters on top of each other.
Interpreters define the semantics of new languages (\ref{subsubsec:semantics}).
In the classical form, a language is defined as a set of trees, and an interpreter maps trees to meta-language objects.
If the language is embedded, this approach is called deep embedding (see~\ref{subsubsec:edsl}), and the corresponding interpreter is initial.
\[
    \sembr{\bullet} : L \to D
\]

One can notice that ultimately we only use the domain element to which the interpreter maps the program.
The program itself is merely a convenient syntactic notation for a domain element and is an intermediate step, not an end in itself.
At the same time, the domain for embedded languages defined by interpreters consists of meta-language objects.
Can we bypass the stage of interpreting our own syntax and directly build the domain object in the meta-language syntax?
Yes, such an embedding is called shallow embedding (\ref{subsubsec:edsl}); this chapter is about it.

\subsubsection{Different interpretations for shallow embedding} \label{subsubsec:shallow-embedding}

As we learned earlier (\ref{subsec:all-folds}), any data structure can be represented as a fold.
And, moreover, in the end one can do without a single data constructor (as in Church lists, for example): the algebra is represented by a set of functions, each responsible for folding a particular constructor.
\begin{minted}{haskell}
    Fix f ?$\iso$? forall a . (f a -> a) -> a
    List e ?$\iso$? forall a . (e -> a -> a) -> a -> a
\end{minted}

Thus, instead of constructing a language tree and then interpreting (folding) it, we can directly construct a term of type \mintinline{haskell}{?$\forall$?a . (f a -> a) -> a}.
By providing it with a domain type \texttt{a} and an algebra \texttt{f a -> a} (or as a bundle of functions), we immediately obtain an element of the desired domain.
To specify a different interpretation, one needs to pass a different domain type and algebra:
\begin{minted}{haskell}
    example :: (Int -> a) -> (a -> a -> a) -> a
    example cnst plus = cnst 1 `plus` cnst 41

    ghci> example show (\l r -> l ++ " + " ++ r)
    "1 + 41"
\end{minted}

If we fix the interpretation, the argument functions can be implemented statically and simply referenced in the term.
Thus, declaring functions can be thought of as extending some embedded domain-specific language.
General discussions about shallow embeddings, folds, and libraries can be found in~\cite{gibbons2013functional, gibbons2014folding}.
Compare:
\begin{figure}[h]
    \centering
    \begin{tabular}{|p{0.45\linewidth}|p{0.45\linewidth}|}
        \hline
        Deep                                                                                                                                 & Shallow                                                                              \\
        \hline
        The language syntax is defined by the set of valid tree nodes                                                                        & A function declaration defines a new tree node: a call to that function               \\
        \hline
        The interpreter, upon encountering each node, executes the corresponding meta-language code (a pattern-match branch) after computing subtrees & The interpreter, upon encountering a call, executes the function body code after computing arguments \\
        \hline
    \end{tabular}
\end{figure}

\subsubsection{Going all the way}

Let us return to the uncurried version of folds: this is now a type accepting a tuple of functions.
And a tuple of functions can be replaced by a type class.
Then the class declaration will define the syntax of the embedded language, and instances for domains --- the implementation.
This approach is called \vocab{tagless final encoding}\footnote{\url{https://okmij.org/ftp/tagless-final/}} and is effectively Church encoding of data with type classes and a set of tricks~\cite{carette2007finally, kiselyov2012typed}.

Let us again consider the language with addition:
\begin{minted}{haskell}
    data Expr = Const Int | Plus Expr Expr

    eval :: Expr -> Int
    eval = \case Const x -> x; Plus l r -> eval l + eval r
\end{minted}
Or via catamorphism:
\begin{minted}{haskell}
    data ExprF rec = Const Int | Plus rec rec

    eval :: Fix ExprF -> Int
    eval = cata \case Const x -> x; Plus l r -> l + r
\end{minted}
The corresponding tagless final encoding will look as follows:
\begin{minted}{haskell}
    class Expr domain where
      cnst :: Int -> domain
      plus :: domain -> domain -> domain

    instance Expr Int where
      cnst x = x
      plus l r = l + r
\end{minted}

Now we can construct an ordinary Haskell term, specify the domain, and the type class machinery will supply the appropriate algebra automatically:
\begin{minted}{haskell}
    example :: forall domain . Expr domain => domain
    example = cnst 1 `plus` cnst 41

    ghci> example :: Int
    42
\end{minted}

To add another interpretation, we implement an instance for a different domain:
\begin{minted}{haskell}
    instance Expr String where
      cnst x = show x
      plus l r = l <> " + " <> r

    ghci> example :: String
    "1 + 41"
\end{minted}

\subsubsection{Recovering compositionality of semantics} \label{subsubsec:recover-compositionality}

A \vocab{semantics} is called \vocab{compositional} if the semantics of constructs depends only on the semantics of subconstructs (see~\ref{subsubsec:semantics}).
In other words, it can be defined by a catamorphism and, accordingly, by a type class instance in tagless final.
That is, to be able to build a tagless final implementation for any semantics, one needs to be able to universally turn non-compositional semantics into compositional ones.

Various code transformations are typically not compositional.
As an example, consider pushing through unary negations:
\begin{minted}{haskell}
    data Expr1 = Lit Int | Add Expr1 Expr1 | Neg Expr1

    transform1 :: Expr1 -> Expr1
    transform1 = \case
      Lit x -> Lit x
      Add l r -> Add (transform1 l) (transform1 r)
      Neg (Lit x) -> Lit (-x)                                        -- problem
      Neg (Neg e) -> transform1 e                                    -- problem
      Neg (Add l r) -> Add (transform1 (Neg l)) (transform1 (Neg r)) -- problem
\end{minted}
To recover compositional semantics, one needs to make context dependencies explicit using an arrow domain~\cite{kiselyov2012typed}:
\begin{minted}{haskell}
    data Ctx = CtxPos | CtxNeg
    flipCtx = \case CtxPos -> CtxNeg; CtxNeg -> CtxPos

    transform1' :: Expr1 -> (Ctx -> Expr1)
    transform1' expr = case expr of
      Lit x -> \case CtxNeg -> Lit (-x); CtxPos -> Lit x
      Neg e -> \ctx -> transform1' e (flipCtx ctx)
      Add l r -> \ctx -> Add (transform1' l ctx) (transform1' r ctx)
\end{minted}
From here one can obtain the tagless final version:
\begin{minted}{haskell}
    class Expr2 d where
      lit :: Int -> d
      add :: d -> d -> d
      neg :: d -> d

    instance Expr2 d => Expr2 (Ctx -> d) where
      lit x = \case CtxNeg -> lit (-x); CtxPos -> lit x
      neg e = \ctx -> neg e (flipCtx ctx)
      add l r ctx = add (l ctx) (r ctx)
\end{minted}

\subsubsection{Typed tagless final interpreter}

Let us consider our example of tagless initial encoding~\ref{subsubsec:typed-tagless-initial}:
\begin{minted}{haskell}
    data Expr ty where
      Const :: Int -> Expr Int
      IsZero :: Expr Int -> Expr Bool
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty

    eval :: Expr ty -> ty
    eval = \case
      Const x  -> x
      IsZero t -> eval t == 0
      If c t e -> if eval c then eval t else eval e
\end{minted}
To obtain a final encoding, we parameterize the domain by the resulting type of the expression:
\begin{minted}{haskell}
    class Expr (domain :: Type -> Type) where
      cnst :: Int -> domain Int
      isZero :: domain Int -> domain Bool
      if' :: forall ty . domain Bool -> domain ty -> domain ty -> domain ty

    instance Expr Identity where
      cnst x = Identity x
      isZero (Identity x) = Identity (x == 0)
      if' (Identity c) t e = if c then t else e
\end{minted}

\begin{tabular}{p{8cm}p{8cm}}
    \begin{minted}[numberblanklines=true]{haskell}
        eval :: Expr s ty -> s -> (s, ty)
        eval = \case


          Val x -> \s -> (s, x)
          App fs xs -> \s1 ->
            let (s2, f) = eval fs s1 in
            let (s3, x) = eval xs s2 in
            (s3, f x)


          LetIn comp k -> \s ->
            let (s', x) = eval comp s in
            eval (k x) s'


          Get -> \s -> (s, s)
          Put s -> \_ -> (s, ())
    \end{minted}
    &

        newtype State s a = State
          { runState :: s -> (s, a) }

        instance Applicative (State s) where
          pure x = State \s -> (s, x)
          fs <*> xs = State \s1 ->
            let (s2, f) = runState fs s1 in
            let (s3, x) = runState xs s2 in
            (s3, f x)

        instance Monad (State s) where
          comp >>= k = State \s ->
            let (s', x) = runState comp s in
            runState (k x) s'

        instance MonadState s (State s) where
          get = State \s -> (s, s)
          put s' = State \s -> (s', ())
    \end{minted}
\end{tabular}

Thus, \point{applicative functors are a meta-circular language with application}, and \point{monadic bind is essentially let-in in higher-order syntax}.

If we recall that $\text{let } x = M \text{ in } N \equiv (\lambda x\ldotp N)\ap M \equiv \subst{N}{x}{M}$, then we understand that monadic bind is the substitution \texttt{a -> m b} of the computation \texttt{m b} in place of results of type \texttt{a} in the computation \texttt{m a}.
Or, if we take an expression tree as \texttt{m}, then bind is the substitution of subtrees in place of variables:
\begin{minted}{haskell}
    data Expr var = Var var | Empty | Append (Expr var) (Expr var)
    instance Monad Expr where
      (>>=) :: Expr var -> (var -> Expr var') -> Expr var'
      Var name >>= subst = subst name
      Empty >>= _ = Empty
      Append l r >>= subst = Append (l >>= subst) (r >>= subst)
\end{minted}

The idea to use the category-theoretic notion of a monad\footnote{\url{https://ncatlab.org/nlab/show/monad+(in+computer+science)}} in $\lambda$-calculus was originally proposed in~\cite{moggi1988computational} for more conveniently writing denotational semantics\footnote{The notion of effect, often accompanying monads, will be considered later~\ref{sec:effects}.}.
This turned out to be so convenient at the time that monads began to be used ubiquitously in functional programming to extend simple functional languages with various powerful capabilities without changing the languages themselves~\cite{wadler1990comprehending, wadler1992essence}.
Moggi's principle was formulated:
\begin{center}
    ``Computations of type $\alpha$ correspond to values of type $f\ap\alpha$.''
\end{center}

The use of applicative functors was proposed significantly later, to avoid naming intermediate computation steps when this is unnecessary~\cite{mcbride2008applicative}.
Thus, applicatives provide an embedded language of expressions, while monads provide a language of statements.

\subsection{Expression problem} \label{subsec:expression-problem}

The \vocab{expression problem}\footnote{\url{https://en.wikipedia.org/wiki/Expression_problem}} is a criterion for the expressiveness of a programming language, formulated by Wadler in 1998\footnote{\url{https://homepages.inf.ed.ac.uk/wadler/papers/expression/expression.txt}}.
The question is: how easy is it to extend the syntax of an embedded language and add new interpretations?
In other words, how easy is it to add new kinds of data and processing methods.

By ``easy'' we mean locality: does one need to modify various pieces of code for this?
For example, if the language syntax is defined by an ordinary algebraic data type, then adding a new interpretation is ``easy'' --- just add a new recursive function, but adding a new syntactic construct is ``hard'' --- all interpreters must be changed:
\begin{minted}{haskell}
    data Expr
      = Const Int
      | Plus Expr Expr -- adding

    eval :: Expr -> Int
    eval = \case Const x -> x; Plus l r -> eval l + eval r

    show :: Expr -> String
    show = \case Const x -> show x; Plus l r -> show l ++ " + " ++ show r
\end{minted}

If the language is defined, for example, using inheritance, then conversely, extending the syntax is easy --- add a new class, but adding an interpretation is hard --- add a method implementation in each class:
\begin{minted}{kotlin}
    interface Lang {
        fun eval(): Int
        fun show(): String
    }
    class Const(val x: Int) : Lang {
        override fun eval() = x
        override fun show() = x.toString()
    }
    class Plus(val l: Lang, val r: Lang) : Lang {
        override fun eval() = l.eval() + r.eval()
        override fun show() = "$l + $r"
    }
\end{minted}

It turns out there exist approaches that achieve ``ease'' along both dimensions.
We will devote much attention to them in this course.

Indeed, as we discussed earlier~\ref{subsubsec:interpreters-tower}, programs are a series of interpreters.
For the same fight against complexity, it is important to be able to describe these interpreters modularly --- defining parts of languages independently of each other and assembling the needed languages on the spot from ready-made blocks.
This helps compose programs from simple reusable components, each with a clear area of responsibility.

The expression problem has arisen and been solved many times: expression problem, stable denotations, extensible (modular) interpreters.
It took a long time before the understanding emerged that all of these are about the same thing\footnote{\url{https://okmij.org/ftp/Computation/having-effect.html}}.

\subsubsection{Coproduct of functors} \label{subsubsec:functor-coprod}

Let us use the representation of data as a fixed point of a functor (see~\ref{subsubsec:functor-fixpoint}).
As a model language we take the expression language with addition:
\begin{minted}{haskell}
    data Basic rec = Const Int | Plus rec rec

    algBasic :: Basic Int -> Int
    algBasic = \case Const x -> x; Plus l r -> l + r

    evalBasic :: Fix Basic -> Int
    evalBasic = cata algBasic
\end{minted}

Note that the sum (coproduct) of shape functors gives a shape functor whose algebra is obtained from the algebras of the components\footnote{We use the \href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/type_operators.html}{TypeOperators} extension.}:
\begin{minted}{haskell}
    data (l :+: r) rec = L (l rec) | R (r rec)

    (\/) :: (l a -> a) -> (r a -> a) -> ((l :+: r) a -> a)
    phi \/ psi = \case L l -> phi l; R r -> psi r
\end{minted}

Let us extend our language with reading a number from the environment.
Following the denotational semantics considered earlier~\ref{subsubsec:semantics}, we choose the function \mintinline{haskell}{Int -> Int} as the domain:
\begin{minted}{haskell}
    data Basic rec = Const Int | Plus rec rec
    data Input rec = Input

    algBasic' :: Basic (Int -> Int) -> Int -> Int
    algBasic' = \case Const x -> \_env -> x; Plus l r -> \env -> l env + r env

    algInput :: Input (Int -> Int) -> Int -> Int
    algInput = \case Input -> \env -> env
\end{minted}

Thus, we have achieved the ability to separately define parts of the syntax and semantics of a language and assemble the needed language on the spot.
Let us write a program in our language with implicit immutable state:
\begin{minted}{haskell}
    f :: Int -> Int
    f = cata (algBasic' \/ algInput) $
      In (L (Plus (In (L (Const 1))) (In (R Input)))) -- 1 + input
\end{minted}

However, note that we have not yet fully solved the problem, since interpreting the new construct \mintinline{haskell}{Input} required a more complex domain and we had to rewrite the interpretation of the old one: from \mintinline{haskell}{algBasic} to \mintinline{haskell}{algBasic'}.
Now we understand why stable denotations is another name for the expression problem~\ref{subsec:expression-problem}.
We will complete this solution later~\ref{sec:effects}.

\subsubsection{Product of algebras} \label{subsubsec:prod-algebras}

Let us build a tagless final representation for the interpreter from the previous section.
Now the syntax is defined by type classes:
\begin{minted}{haskell}
    class Basic domain where
      cnst :: Int -> domain
      plus :: domain -> domain -> domain

    class Input domain where
      input :: domain
\end{minted}

As before, we take functions \mintinline{haskell}{Int -> Int} as the domain and implement the interpretation:
\begin{minted}{haskell}
    instance Basic (Int -> Int) where
      cnst value = \_ -> value
      plus l r = \env -> l env + r env

    instance Input (Int -> Int) where
      input = \env -> env
\end{minted}

Now, to assemble the language on the spot, one can simply take advantage of the composability of type class contexts; all the rest of the work:
\begin{minted}{haskell}
    example :: forall domain . (Basic domain, Input domain) => domain
    example = cnst 1 `plus` input

    ghci> (example :: Int -> Int) 41
    42
\end{minted}
