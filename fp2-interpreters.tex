Искусство программирования во многом состоит в умении управлять сложностью, и в рамках данного курса основным инструментом для этого мы будем рассматривать построение языков и интерпретаторов.

\subsection{Интерпретаторы как основа основ} \label{subsec:interpreters-rules}

Мы начнём с обзора роли интерпретаторов в программировании.

\subsubsection{Башня интерпретаторов} \label{subsubsec:interpreters-tower}

Самым базовым интерпретатором является процессор, он воплощён физически в железе.
Ему на вход подаётся программа на некотором языке, например, x86, он зачитывает команды и превращает их в действия над памятью.
Однако, человеку сложно программировать на этом языке, нужен новый язык, инкапсулирующий часть сложности и скрывающий лишние детали.

Чтобы получить новый язык, мы строим программный интерпретатор.
\vocab{Программный интерпретатор} $U_M^N$ --- это программа на языке $M$\footnote{Под языком мы тут понимаем множество программ на этом языке, иначе говоря, множество деревьев определённого вида.}, получающая на вход программу на языке $N$ и вход для неё --- данные из $D$, и возвращающая результат выполнения этой программы на этих данных: \[U_M^N : N\times D\to D\]

Язык реализации интерпретатора $M$ мы будем называть \vocab{мета-языком}, а $N$ --- \vocab{определяемым}.
Про интерпретатор можно интуитивно думать следующим образом: это понятное мета-языку объяснение того, что значат конструкции определяемого языка.
Иными словами, какие инструкции мета-языка нужно исполнить, чтобы получить нужную семантику инструкций определяемого языка.

Например, у нас есть программа $p_N$ и данные для неё $d_{in}$, результат исполнения этой программы $d_{out}$ можно получить как \[d_{out} = U_M^N\left( \underbrace{\langle p_N, d_{in} \rangle}_{\in N\times D} \right)\]

Но интерпретатор это тоже программа.
Как её запустить?
Возьмём наш базовый интерпретатор $U^{x86}$, у него нет языка реализации, так как он реализован в железе, а не программно.
Возьмём интерпретатор языка ассемблера, реализованный в кодах x86, $U_{x86}^{Asm}$, программу на ассемблере $p_{Asm}$ и вход для неё $d_{in}$.
Вспомним, что программа --- это тоже данные, просто в некотором специальном формате.
Тогда результат применения $p_{Asm}$ на данных мы получим следующим образом:
\[
    d_{out} = U^{x86}\left(\left<\underbrace{U_{x86}^{Asm}}_{\in x86}, \underbrace{\overbrace{\langle p_{Asm}}^{\in Asm}, \overbrace{d_{in} \rangle}^{\in D}}_{\in D} \right>\right)
\]

Но язык ассемблера тоже не очень приятен для программирования.
Однако, на нем можно уже написать интерпретатор языка посложнее.
И так далее.
Получаем \point{башню интерпретаторов}, на вершине находится язык, на котором мы хотим уже решать непосредственно нашу задачу:
\[
    d_{out} =
    U^{x86}\left(\left<
                     U_{x86}^{Asm}, \left<
                                        U^C_{Asm}, \left<
                                                       U^{Has}_C, \left< p_{Has}, d_{in}
                \right>\right>\right>\right>\right)
\]

На практике часто язык задают через трансляцию (компиляцию) в другой.
Однако, далее мы будем фокусироваться на встроенных языках и понятие интерпретатора будет нам полезнее.
Кроме того, существуют универсальные теоретические способы построения компилятора по интерпретатору\footnote{\url{https://en.wikipedia.org/wiki/Partial_evaluation}} (см.\ далее\ \ref{sec:datatype-generic}), так что для нас они схожи.

\subsubsection{Интерпретаторы повсюду} \label{subsubsec:interpreters-everywhere}

Хорошо, мы пришли к языку нашего сердца (Хаскеллу), почему же мы продолжаем говорить об интерпретаторах?
Потому что для решения конкретных бизнес-задач прикладные языки всё ещё слишком церемониальны~--- программисту приходится думать о большом количестве вещей, нерелевантных его предметной области и решаемой задаче.
Сложность~--- главный враг программиста, потому что ресурсы человеческого мозга несопоставимы со сложностью реальности, которую приходится описывать в программах.
Таким образом, в работе постоянно приходится описывать новые языки, наиболее подходящие для решения конкретных прикладных задач.
А новые языки мы задаём с помощью интерпретаторов.

Как выглядит классический рекурсивный интерпретатор?
Он получает программу в виде некоторого дерева и рекурсивно обходит его, считая результаты поддеревьев.
Когда он посещает вершину дерева, он определяет её тип и понимает, какие действия нужно исполнить.
То есть тип вершины диспатчит, навигирует, исполнение интерпретатора на нужный код.
Так, интерпретатор простой языка выражений имеет следующий вид:
\begin{minted}{haskell}
    data Expr = Const Int | Plus Expr Expr

    eval :: Expr -> Int
    eval = \case
      Const x -> x
      Plus l r -> eval l + eval r
\end{minted}

Видно, что это похоже, например, на работу утилиты командной строки~--- разбираем аргументы, определяем, что и как нужно сделать, делаем.
Как ни странно, философия Unix, в частности, заключается в построении маленьких языков (утилит с текстовым API), решающих хорошо одну задачу~\cite{bentley1986little}.
Ещё это похоже на обработку запроса web-сервером~--- определяем маршрут, на который пришёл запрос, выполняем соответствующее действие.
То есть не так редко мы в реальной жизни пишем интерпретаторы.
Мы просто не видим, что то, что мы пишем --- это на самом деле интерпретатор некоторого языка.
В общем случае, свёртку структуры данных уже можно рассматривать как интерпретацию~\cite{gibbons2014folding}.

Более того, интерфейс библиотеки можно рассматривать как набор конструкций встроенного языка (раздел~\ref{subsec:tagless-final}).
Вот был язык, в котором нельзя было добавить пользователя в приложение.
Написали функцию \texttt{registerUser}~--- появилась новая команда в языке~--- добавить пользователя.
Вызовы функций задают программы на таком языке, а реализации функций --- их смысл.
Далее мы покажем, как связать такое представление с явным синтаксическим деревом (раздел~\ref{subsubsec:shallow-embedding}).
Использование функций является примером встраивания языка, когда мы вместо того, чтобы делать новый отдельный язык, его реализуем как библиотеку для уже существующего языка~\cite{gibbons2013functional}.

Как мы убедимся в течение курса, многие задачи можно рассматривать как придумывание языка и реализацию интерпретатора.
Значит, если мы научимся хорошо писать интерпретаторы, мы научимся делать сразу кучу всего!
И основные наши усилия будут направлены на изучение средств построения интерпретаторов встроенных языков.

Во время повествования мы часто пользуемся приёмом Hutton's Razor, который подразумевает рассмотрение до смешного маленького языка для изучения сложных концепций.
Утверждается, что для изучения большинства вопросов можно сконструировать такой язык, делающий всё важное максимально наглядным.

\subsubsection{Интерпретаторы и семантика языков программирования} \label{subsubsec:semantics}

Семантика языков программирования\footnote{\url{https://en.wikipedia.org/wiki/Semantics_(computer_science)}\label{note:sema-wiki}}~--- это наука, изучающая свойства языков и смысл программ, его свойства и способы описания.
Отличным введением может послужить серия книг Software Foundations\footnote{\url{https://coq.vercel.app/ext/sf/}}~\cite{pierce2010software}.
Существует много различных стилей описания семантики программ, для нас важнейшим будет денотационная семантика.

\vocab{Денотационная семантика}\footnote{\url{https://en.wikipedia.org/wiki/Denotational_semantics}}\footnote{\url{https://en.wikibooks.org/wiki/Haskell/Denotational_semantics}}\footnote{\href{https://youtu.be/pQyH0p-XJzE?si=TUEzrpHhJZfO7dTF}{(youtube) The Lost Art of Denotational Semantics --- Eric Meyer.}\label{foot:the-lost-art-of-denotations}} описывает смысл программ путём сопоставления им объектов некоторого множества, \vocab{семантического домена}.
Иначе говоря, денотационная семантика языка $L$ --- это тотальная функция из программы на этом языке в элемент домена $D$:
\[
    \sembr{\bullet} : L \to D
\]

Домен выбирается исходя из языка и информации, которую хочется извлекать из программ.
Например, чтобы узнать высоту синтаксического дерева выражения со сложением, в качестве домена можно взять натуральные числа:
\[
    \begin{array}{lcl}
        \sembr{n}     & = & 1                                \\
        \sembr{l + r} & = & 1 + \max{(\sembr{l}, \sembr{r})}
    \end{array}
\]
Если нас интересует результат вычисления, возьмём домен $\mathbb{Z}$ и посчитаем значение выражения:
\[
    \begin{array}{lcl}
        \sembr{n}     & = & n                     \\
        \sembr{l + r} & = & \sembr{l} + \sembr{r}
    \end{array}
\]
Добавим в язык конструкцию $input$, обозначающую входное целое число.
Теперь доменом будет множество функций $\mathbb{Z}\to\mathbb{Z}$: смысл каждого выражения --- функция от входа к результату.
\[
    \begin{array}{lcl}
        \sembr{n}(m)     & = & n                           \\
        \sembr{l + r}(m) & = & \sembr{l}(m) + \sembr{r}(m) \\
        \sembr{input}(m) & = & m
    \end{array}
\]

Таким образом, \point{программа является лишь синтаксической записью для некоторого элемента семантического домена}.
Вариантов доменов много, это могут быть даже игры\footnote{\url{https://en.wikipedia.org/wiki/Game_semantics}}. % todo domain theory

\begin{task}
    В какой домен разумно проинтерпретировать программы на языке с целочисленными мутабельными переменными?
    А на недетерминированном языке?
\end{task}

Легко заметить, что денотационная семантика языка --- это просто интерпретатор, только написанный на языке математики.
Такие интерпретаторы ставят в основу башни интерпретаторов, когда цель исследовать свойства языков и программ, а не исполнять их.

Также, можем реализовывать интерпретатор на каком-нибудь реальном языке и он тоже будет задавать семантику определяемого языка.
Однако формальность такого определения будет зависеть от формальности описания семантики мета-языка.
Такие интерпретаторы называют \vocab{определяющими}, они задают семантику языка, как правило, жертвуя эффективностью ради наглядности.
Взаимоотношения определяемого языка и мета-языка изучаются в классических статьях~\cite{reynolds1972definitional,reynolds1998definitional}\footnote{Активно используемое автором понятие продолжения будет рассмотрено далее в этом курсе (раздел \ref{sec:continuations}).}.

Мы будем использовать определяющие интерпретаторы для задания семантики новых языков и в качестве мета-языка будем использовать Haskell.
А в качестве доменов будем брать типы Haskell.
Например, функции между целыми числами представим значениями типа \mintinline{haskell}|Int -> Int|\footnote{\url{https://okmij.org/ftp/Denotational.html}}.
Расширим прежний тип \mintinline{haskell}|Expr| конструктором \mintinline{haskell}|Input| и запишем интерпретатор:
\begin{minted}{haskell}
    data Expr = Const Int | Plus Expr Expr | Input

    eval :: Expr -> (Int -> Int)
    eval = \case
      Const n -> \_ -> n
      Plus l r -> \m -> eval l m + eval r m
      Input -> \m -> m
\end{minted}

Семантика называется \vocab{композиционной (compositional)}, если смысл составной конструкции определяется самой конструкцией и смыслами её непосредственных подконструкций.
Например, для \mintinline{haskell}|Plus l r| нужны операция сложения и значения \mintinline{haskell}|eval l| и \mintinline{haskell}|eval r|; заново разбирать синтаксис \mintinline{haskell}|l| и \mintinline{haskell}|r| не требуется.
Для нашего языка такое определение представляет собой свёртку синтаксического дерева (рис.\ \ref{fig:eval-prog}) и может быть записано в терминах катаморфизма~\ref{subsubsec:recursion-schemas}.

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.6\textwidth]{figs/eval-prog}
    \caption{Денотационная семантика определяет смысл синтаксических конструкций через операции над доменом~\cite{hutton1998fold}.}
    \label{fig:eval-prog}
\end{figure}

Другим популярным стилем описания семантики является \vocab{операционная семантика}, которая представляет смысл программы в виде последовательности шагов вычислений.
Это может быть как последовательное переписывание самого выражения, так и переписывание состояния некоторой абстрактной машины.
Операционная семантика, в свою очередь, задаётся как развёртка (или анаморфизм~\ref{subsubsec:recursion-schemas}) последовательности шагов вычисления из программы.
Тут отчётливо видна некоторая двойственность между денотационной и операционной семантиками~\cite{hutton1998fold}.

\subsubsection{Встроенные доменно-специфичные языки (eDSL)} \label{subsubsec:edsl}

Под \vocab{доменно-специфичными языками (domain specific languages, DSL)}\footnote{\url{https://en.wikipedia.org/wiki/Domain-specific_language}} часто понимают специализированные языки для конкретных предметных областей, например, запросов к БД или форматирования документов.

В этом курсе, однако, мы будем считать доменно-специфичным языком любую доменно-специфичную специализацию языка общего назначения\footnote{\url{https://en.wikipedia.org/wiki/Language-oriented_programming}, на русскоязычную страницу тоже следует заглянуть.}.
Это следует из того соображения, что код должен читаться как грамотная проза с уместным словоупотреблением, предоставляющая читателю только необходимое количество подробностей, скрывая несущественное за умолчаниями и терминологией.

\vocab{Самостоятельные доменно-специфичные языки (standalone domain specific languages)} --- языки, имеющие свой собственный конкретный синтаксис, а также инструменты программирования (IDE, исполняющую среду\ldots).
Примеры: SQL, AWK, Antlr\ldots\footnote{Есть отличная прикладная книга~\cite{nystrom2021crafting}, рассказывающая о построении интерпретаторов и простых виртуальных машин.
В то же время она покрывает создание полноценного языка во всех его аспектах, от синтаксического анализа до управления памятью.}

\vocab{Встроенные доменно-специфичные языки (embedded domain specific languages, eDSL)} --- языки, пользующиеся поддержкой инфраструктуры других языков.
Обычно реализуются как библиотеки для программ на уже существующем языке общего назначения.
Не имеют полностью собственного конкретного синтаксиса.
Примеры: ORM, функции обработки строк, библиотека парсер-комбинаторов\ldots

\vocab{Deep eDSL} --- термы на таком языке строят дерево абстрактного синтаксиса для дальнейшей интерпретации:
\begin{minted}{haskell}
    f :: Int -> Int
    f = eval $ Const 1 `Plus` Input
\end{minted}

Представление синтаксиса конструкторами алгебраического типа данных называют \vocab{инициальным (initial encoding)}\footnote{Для нашего языка конечные синтаксические деревья образуют инициальную алгебру функтора синтаксиса. Её свёртки задают интерпретации, как в разделе~\ref{subsec:all-folds}.}.
Рекурсивные интерпретаторы таких деревьев мы также будем называть ``классическими''; с них и начнём.
Явное дерево удобно, когда программу нужно анализировать, преобразовывать или интерпретировать несколькими способами.

%Например, можно построить встроенный язык для работы с изменяемым состоянием.
%Теперь можем писать императивно в Haskell без единой монады!
%\begin{minted}{haskell}
%    fac :: Int -> Int
%    fac = eval $
%
%\end{minted}

Однако, можно заметить, что промежуточное дерево, которое получается, нас, как правило, не интересует.
Нам важно только получить элемент домена, которым мы уже умеем пользоваться непосредственно.
\vocab{Shallow eDSL} минуют стадию построения дерева и сразу строят значение в семантическом домене.
Для нашего языка константы, вход и сложение можно представить непосредственно операциями над функциями:
\begin{minted}{haskell}
    cnst :: Int -> (Int -> Int)
    cnst x _ = x

    input :: Int -> Int
    input env = env

    plus :: (Int -> Int) -> (Int -> Int) -> (Int -> Int)
    plus l r env = l env + r env

    f :: Int -> Int
    f = cnst 1 `plus` input
\end{minted}

Интерпретаторы часто называют \vocab{наблюдателями (observers)}, которые анализируют термы и дают им некоторый смысл~\cite{gibbons2013functional}.
Можно заметить, что для deep eDSL можно написать сколь угодно много различных наблюдателей.
В shallow embedding значение уже принадлежит выбранному домену: например, \mintinline{haskell}|f| можно применить к входу и получить результат.
Однако исходный синтаксис при этом не сохраняется: по полученной функции нельзя восстановить, сколько сложений было записано в программе.
Например, \mintinline{haskell}|cnst 1 `plus` input| и \mintinline{haskell}|cnst 0 `plus` (cnst 1 `plus` input)| задают одну и ту же функцию, но содержат разное число сложений.

Чтобы выбирать интерпретацию, можно абстрагировать программу по операциям \mintinline{haskell}|cnst|, \mintinline{haskell}|input| и \mintinline{haskell}|plus| и по типу их результатов.
Так мы придём к \vocab{финальному представлению (final encoding)}, которое подробно рассмотрим в разделе~\ref{subsec:tagless-final}.
Различия deep/shallow и initial/final связаны, но не совпадают: первое говорит о сохранении синтаксиса для дальнейшей интерпретации, второе --- о представлении программы конструкторами данных или через абстрактный интерфейс операций.
В частности, финальную программу можно интерпретировать как в численную функцию, так и в синтаксическое дерево.

Обсуждение терминологии и сравнение подходов к построению DSL можно найти в~\cite{gibbons2013functional}.
Краткое описание терминов --- в конспекте курса Language Engineering~\cite{languageEngineering}.

Введём ещё одно важное понятие.
\vocab{Meta-circular интерпретатор}\footnote{\url{https://en.wikipedia.org/wiki/Meta-circular_evaluator}}~--- это интерпретатор, определяющий конструкции определяемого языка через конструкции мета-языка~\cite{reynolds1972definitional}.
Например:
\begin{minted}{haskell}
    interpret term = case term of
      App f t -> (interpret f) (interpret t)
      If c t e -> if interpret c then interpret t else interpret e
      ...
\end{minted}

Свойства мета-языка в таком случае во многом определяют свойства объектного~\cite{reynolds1972definitional,reynolds1998definitional}.
Мы будем в этом курсе стремиться как можно более переиспользовать возможности мета-языка.

\end{task}

\subsubsection{Пример: библиотека Accelerate}

Библиотека Accelerate\footnote{\href{https://www.acceleratehs.org/documentation/users-guide/language.html}{Документация языка Accelerate.}}~\cite[глава 6]{marlow2011parallel} демонстрирует deep embedding с привычным функциональным синтаксисом.
Она позволяет на Haskell описать параллельные вычисления над массивами, а затем оптимизировать и скомпилировать их для CPU или GPU в зависимости от выбранного backend'а.
Для этого Accelerate сохраняет представление вычислений; генерировать именно исходный код CUDA при этом не требуется.

Программисту, однако, не нужно вручную собирать дерево конструкторами: библиотека предоставляет операции над массивами и перегруженные численные операторы.
Например, поэлементное сложение векторов записывается так:
\begin{minted}{haskell}
    import Data.Array.Accelerate (Acc, Vector)
    import qualified Data.Array.Accelerate as A

    example :: Acc (Vector Int) -> Acc (Vector Int) -> Acc (Vector Int)
    example xs ys = A.zipWith (+) xs ys
\end{minted}

Здесь \mintinline{haskell}|Acc (Vector Int)| представляет вычисление над массивом.
При построении этой программы складываются скалярные выражения типа \mintinline{haskell}|Exp Int|.
Инстанс \mintinline{haskell}|Num| для таких выражений строит представление сложения; само сложение элементов произойдёт при исполнении программы выбранным backend'ом.
Таким образом, удобный синтаксис функций и операторов сам по себе не делает встраивание shallow: существенно то, какие значения строятся этими операциями.

\subsection{Типы значений}

Рассмотрим, какие есть способы реализации языков, значения в которых могут иметь различные типы.

\subsubsection{Untyped tagless interpreters}

Для начала реализуем интерпретатор без проверки типов.
В нашем языке есть целочисленные константы, проверка на ноль и условное выражение.
Зададим его абстрактный синтаксис:
\begin{minted}{haskell}
    data Expr = Const Int | IsZero Expr | If Expr Expr Expr
\end{minted}

Результат корректного выражения будем представлять значением типа \mintinline{haskell}|Bool| или \mintinline{haskell}|Int| языка Haskell.
Однако тип \mintinline{haskell}|Expr| не сообщает, какой результат имеет выражение, и позволяет строить некорректные программы.
Чтобы всё же написать интерпретатор, обойдём проверку типов Haskell с помощью \mintinline{haskell}|unsafeCoerce|:
\begin{minted}{haskell}
    import Unsafe.Coerce (unsafeCoerce)

    evalUnsafe :: forall res . Expr -> res
    evalUnsafe = \case
      Const val -> unsafeCoerce val
      IsZero cond -> unsafeCoerce $ evalUnsafe cond == 0
      If c t e -> if evalUnsafe c then evalUnsafe t else evalUnsafe e
\end{minted}

Эта сигнатура позволяет вызывающему выбрать произвольный тип результата, но не даёт гарантии, что выражение действительно имеет этот тип.
На программисте лежат два обязательства: выражение должно быть правильно типизировано, а запрошенный тип результата должен совпадать с его типом.
Интерпретатор не проверяет ни то, ни другое.
При нарушении этих обязательств поведение не определено\footnote{\href{https://hackage.haskell.org/package/base/docs/Unsafe-Coerce.html}{Документация \texttt{Unsafe.Coerce}.}}.

Сравним два выражения:
\begin{minted}{haskell}
    good, bad :: Expr
    good = If (IsZero (Const 0)) (Const 10) (Const 20)
    bad = IsZero (IsZero (Const 0))
\end{minted}
Вызов \mintinline{haskell}|evalUnsafe @Int good| удовлетворяет соглашению и даёт \mintinline{haskell}|10|.
В выражении \mintinline{haskell}|bad| внешняя проверка на ноль получает булево значение вместо целого.
Построить такое дерево можно, но исполнять его этим интерпретатором нельзя.

\subsubsection{Typed tagged interpreters}

Чтобы добиться некоторой безопасности исполнения, будем приписывать значениям теги, которые будут доступны во время исполнения.
Заведём следующий алгебраический тип:
\begin{minted}{haskell}
    data RtValue = RtBool Bool | RtInt Int
\end{minted}

Теперь семантическим доменом будет тип \mintinline{haskell}|RtValue|, а интерпретатор сможет проверять типы во время исполнения:
\begin{minted}{haskell}
    evalRt :: Expr -> RtValue
    evalRt = \case
      Const n -> RtInt n
      IsZero expr -> case evalRt expr of
        RtInt n -> RtBool (n == 0)
        RtBool _ -> error "IsZero expects Int"
      If c t e -> case evalRt c of
        RtBool b -> if b then evalRt t else evalRt e
        RtInt _ -> error "If expects Bool"
\end{minted}

Теперь \mintinline{haskell}|evalRt good| возвращает \mintinline{haskell}|RtInt 10|, а \mintinline{haskell}|evalRt bad| сообщает об ошибке: внешняя проверка \mintinline{haskell}|IsZero| обнаруживает \mintinline{haskell}|RtBool| там, где требуется \mintinline{haskell}|RtInt|.
Вместо некорректного приведения мы получаем явную диагностику.

Этот подход называют \vocab{динамической типизацией}: значения сопровождаются информацией об их типах, которую операции проверяют во время исполнения (см.\ также\ \ref{subsubsec:type-reflection}).
Ошибка обнаруживается только при выполнении соответствующей операции.
Например, следующий вызов возвращает \mintinline{haskell}|RtInt 10|, поскольку ошибочная ветка не выбирается:
\begin{minted}{haskell}
    evalRt (If (IsZero (Const 0)) (Const 10) bad)
\end{minted}
Поэтому успешное выполнение выбранной ветки не гарантирует отсутствия ошибок типов в остальных ветках программы.

\subsubsection{Typed tagless interpreters} \label{subsubsec:typed-tagless-initial}

Опишем систему типов нашего маленького языка.
%! suppress = EscapeAmpersand
\begin{equation*}{}
    \infer[Const]{Const~n : int}{n : Int}
    \quad
    \infer[IsZero]{IsZero~n : bool}{n : int}
    \quad
    \infer[If]{If~c~t~e : \tau}{c : bool & t : \tau & e : \tau}
\end{equation*}
Можем в качестве типовых тегов переиспользовать типы Haskell: \[int \rightsquigarrow Int, bool \rightsquigarrow Bool\]

Закодируем эти правила вывода с помощью обобщённого алгебраического типа данных \mintinline{haskell}|Expr ty| (\ref{subsubsec:gadts}).
Параметр \mintinline{haskell}|ty| будет указывать тип результата выражения:
\begin{minted}{haskell}
    data Expr ty where
      Const :: Int -> Expr Int
      IsZero :: Expr Int -> Expr Bool
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty

    eval :: Expr ty -> ty
    eval = \case
      Const n -> n
      IsZero e -> eval e == 0
      If c t e -> if eval c then eval t else eval e
\end{minted}

Значение \mintinline{haskell}|Expr ty| теперь представляет синтаксическое дерево вместе со свидетельством того, что выражение имеет тип \mintinline{haskell}|ty|.
В ветке \mintinline{haskell}|Const| компилятор узнаёт, что \mintinline{haskell}|ty| --- это \mintinline{haskell}|Int|; в ветке \mintinline{haskell}|IsZero| --- что это \mintinline{haskell}|Bool|.
Конструктор \mintinline{haskell}|If| требует булево условие и две ветки с одним типом результата.
Поэтому в каждом случае \mintinline{haskell}|eval| может вернуть значение нужного типа без \mintinline{haskell}|unsafeCoerce| и обёрток \mintinline{haskell}|RtValue|.

Корректный пример записывается так же, но теперь его тип точнее:
\begin{minted}{haskell}
    good :: Expr Int
    good = If (IsZero (Const 0)) (Const 10) (Const 20)
\end{minted}
А выражение \mintinline{haskell}|IsZero (IsZero (Const 0))| уже не проходит проверку типов Haskell: внутреннее выражение имеет тип \mintinline{haskell}|Expr Bool|, тогда как внешнему \mintinline{haskell}|IsZero| требуется \mintinline{haskell}|Expr Int|.
Поместить его в невыбранную ветку \mintinline{haskell}|If| тоже не получится: статически проверяются обе ветки.

Так мы получили статически типизированный язык, переиспользовав систему типов Haskell.
Проверка перенесена с исполнения программы на её построение в Haskell, и дополнительные теги типов результатов интерпретатору больше не нужны.

\subsection{Связывания и функции первого класса} \label{subsec:first-class-functions}

В этом разделе мы рассмотрим две связанные задачи: как представить связывания переменных в синтаксисе и как представить функции во время исполнения.
Сначала будем явно выполнять подстановки, затем сохранять окружения в замыканиях.
После этого будем переиспользовать из Haskell сначала реализацию функций, а затем и связывание переменных с их употреблениями.

\mintinline{haskell}|let|-связывания можно представить через функции первого класса следующим образом:
\[
    \term{let} \ap x \termdef N \ap \term{in} \ap M \equiv (\lambda x\ldotp M) \ap N
\]

Напомним, что от функций первого класса можно избавиться с помощью дефункционализации, рассмотренной ранее~\ref{subsubsec:defunctionalization}.

\subsubsection{Семантика имён} \label{subsubsec:name-bindings}

Существует несколько способов задания семантики идентификаторам.

\vocab{Динамическое связывание (dynamic scoping)} --- при обращении к переменной её связывание ищется среди активных вызовов, начиная с ближайшего.
Поэтому смысл свободного имени в теле функции может зависеть от того, откуда её вызвали.
Рассмотрим псевдокод, для которого сравним два правила связывания:
\begin{minted}{text}
    val x = 4
    val f = () => x + 1
    val g = () => {
      val x = 41
      return f()
    }
    println(g())
\end{minted}
При динамическом связывании обращение к \texttt{x} внутри \texttt{f} найдёт локальное связывание в активном вызове \texttt{g}, и программа напечатает \texttt{42}.

Этот подход проще в реализации и использовался в ранних версиях Lisp'ов, например.
Однако в таком случае функции не являются надежным барьером абстракции, по-хорошему все свободные переменные должны являться частью сигнатуры (вернёмся в этому в главе про системы эффектов~\ref{sec:effect-systems}).

\vocab{Лексическое/статическое связывание (lexical/static scoping)} --- соответствие между употреблением переменной и её объявлением определяется структурой программы\footnote{Это не означает, что значение переменной неизменно. Например, лямбда в Kotlin может захватить изменяемую переменную: её значение будет меняться, но обращение останется связанным с тем же объявлением.}.
Слово ``лексический'' часто употребляется в языках, когда мы что-то можем понять из исходного кода без запуска программы.
В нашем примере имя \texttt{x} в теле \texttt{f} связано с внешним объявлением \texttt{val x = 4}; локальная переменная из \texttt{g} на него не влияет.
Поэтому при лексическом связывании программа напечатает \texttt{5}.

Далее в этом разделе мы будем говорить о различных способах реализации функций первого класса со статическим связыванием переменных, которых, на самом деле, великое множество\footnote{\url{https://jesper.cx/posts/1001-syntax-representations.html}}.

\subsubsection{Подстановки} \label{subsubsec:substitutions}

Как можно заметить, в классическом лямбда-исчислении подстановки от бета-редукции (вспоминали в разделе~\ref{subsec:terms-reduction}) обеспечивают статическое связывание.
При бета-редукции аргумент подставляется вместо свободных вхождений параметра в теле функции; подстановка должна избегать захвата свободных переменных аргумента.
В следующем примере внутренняя лямбда связывает свой \texttt{x}, независимо от внешней:
\[
    (\lambda x\ldotp (\lambda x\ldotp \lambda y\ldotp x + y) \ap 4) \ap 41 \rightsquigarrow (\lambda x\ldotp (\lambda y\ldotp 4 + y)) \ap 41
\]

Прямая реализация подстановки требует обходить тело функции и перестраивать затронутые части дерева.
Для некоторых представлений лямбда-термов такую подстановку довольно просто реализовать.
Рассмотрим пример такого представления --- \vocab{locally nameless}~\cite{chargueraud2012locally}.

\begin{minted}{haskell}
    data Term var
      = Var var
      | App (Term var) (Term var)
      | Lam (Term (Maybe var))
\end{minted}

В этом представлении можно выбирать любой тип для именования свободных переменных:
\begin{minted}{haskell}
    example :: Term String
    example = Var "x" `App` Var "y" -- x y
\end{minted}
При входе под лямбду тип переменных меняется с \mintinline{haskell}|var| на \mintinline{haskell}|Maybe var|.
\mintinline{haskell}|Nothing| обозначает её параметр, а \mintinline{haskell}|Just| сохраняет ссылку во внешнюю область.
Под двумя лямбдами \mintinline{haskell}|Nothing| обозначает ближайший параметр, \mintinline{haskell}|Just Nothing| --- следующий наружу, а свободное имя получает две обёртки \mintinline{haskell}|Just|:
\begin{minted}{haskell}
    -- ?$\lambda x\ldotp x \ap y$?
    example1 :: Term String
    example1 = Lam $ Var Nothing `App` Var (Just "y")
    -- ?$\lambda x \ap y\ldotp x \ap y \ap z$?
    example2 :: Term String
    example2 = Lam $ Lam $
      Var (Just Nothing) `App` Var Nothing `App` Var (Just (Just "z"))
\end{minted}

Монадический bind является реализацией подстановки для таких термов:
\begin{minted}{haskell}
    instance Monad Term where
      (>>=) :: Term var -> (var -> Term var') -> Term var'
      Var var >>= subst = subst var
      App l r >>= subst = App (l >>= subst) (r >>= subst)
      Lam t   >>= subst = Lam $ t >>= \case
        Nothing  -> Var Nothing
        Just var -> Just <$> subst var
\end{minted}

\begin{task}
    Подумайте, зачем нужен \texttt{fmap Just} в последней строчке.
\end{task}

С помощью подстановки можно написать нормализатор: он возвращает синтаксическое дерево в нормальной форме, если вычисление завершается.
В отличие от обычного вычисления по имени, останавливающегося на лямбде, здесь нормализуются также тела лямбд и аргументы оставшихся аппликаций:

\begin{minted}{haskell}
    eval :: Term var -> Term var
    eval = \case
      Var var -> Var var
      App f arg -> case eval f of
        Lam body -> eval $ body >>= maybe arg Var
        t -> App t (eval arg)
      Lam t -> Lam (eval t)
\end{minted}

\subsubsection{Окружение}

Вместо перестройки тела при каждом применении можно хранить \vocab{окружение}: соответствие между переменными и их значениями.
При обращении к переменной интерпретатор ищет её значение в окружении; при вызове функции добавляет связывание параметра с аргументом.

Однако одного тела функции недостаточно: нужно знать, в каком окружении искать значения её свободных переменных.
Если использовать окружение места вызова, получится динамическое связывание.
Чтобы сохранить лексическое связывание, вместе с телом нужно запомнить окружение, в котором функция была создана.
Так мы приходим к замыканиям.

\subsubsection{Замыкания} \label{subsubsec:closures}

\vocab{Замыкание (closure)}\footnote{\url{https://en.wikipedia.org/wiki/Closure_(computer_programming)}}\footnote{Термин closure предложил Peter Landin.} хранит тело функции, её параметр и окружение определения~\cite[глава 11]{nystrom2021crafting}.
В следующем интерпретаторе синтаксис снова использует строковые имена, а конструктор \mintinline{haskell}|Closure| появляется только во время вычислений.
Результатом вычисления функции будет замыкание; нормализовать её тело заранее не требуется.

\begin{minted}{haskell}
    import Data.Map (Map)
    import qualified Data.Map as Map

    data Term1 = Var1 String | App1 Term1 Term1 | Lam1 String Term1
               | Closure Env String Term1 -- только для вычислений
    type Env = Map String Term1

    eval1 :: Term1 -> Env -> Term1
    eval1 term env = case term of
      Var1 name -> Map.findWithDefault (Var1 name) name env
      App1 f arg -> case eval1 f env of
        Closure env' name body ->
            let arg' = eval1 arg env in
            eval1 body (Map.insert name arg' env')
        t -> App1 t (eval1 arg env)
      Lam1 name body -> Closure env name body
      closure@(Closure _ _ _) -> closure
\end{minted}

Здесь два разных окружения играют разные роли.
Аргумент вычисляется в \mintinline{haskell}|env| --- окружении места вызова.
Тело функции вычисляется в сохранённом \mintinline{haskell}|env'|, дополненном связыванием параметра с аргументом.
Свободное имя поэтому не начинает ссылаться на одноимённую переменную вызывающей функции.

Вернёмся к примеру с \texttt{f} и \texttt{g} из начала раздела.
При создании \texttt{f} замыкание запоминает окружение с \texttt{x = 4}.
В момент вызова \texttt{f()} внутри \texttt{g} текущее окружение содержит \texttt{x = 41}, но тело \texttt{f} исполняется в сохранённом окружении и возвращает \texttt{5}.

Замыкания обычно и используют в промышленных языках как представление времени исполнения функций высших порядков.
Преобразование \vocab{closure conversion} делает это представление явным: функция представляется парой из окружения и указателя на код, принимающий окружение дополнительным аргументом.
Такой код уже можно разместить на верхнем уровне: значения захваченных переменных он получает из переданного окружения.
Родственное преобразование \vocab{lambda lifting}\footnote{\url{https://en.wikipedia.org/wiki/Lambda_lifting}} превращает свободные переменные функций в дополнительные параметры и дополняет соответствующие вызовы аргументами, позволяя вынести функции на верхний уровень.
Это разные преобразования; обязательной последовательности из двух шагов здесь нет.
Подробные примеры можно посмотреть в гарвардских слайдах~\cite{closures-slides}.

\subsubsection{Типизированный контекст} \label{subsubsec:typed-env}

Рассмотрим кодирование, описанное, например, в~\cite{kiselyov2012typed}.

Для начала научимся с помощью системы типов Haskell проверять валидность обращения к окружению.
Представим окружение как вложенные пары, заканчивающиеся \mintinline{haskell}|()|.
Тип такого значения перечисляет типы доступных переменных:
\begin{minted}{haskell}
    (4, (4.0, ("hello", ()))) :: (Int, (Double, (String, ())))
\end{minted}

Обращение к окружению будем кодировать числом в унарной записи.
Тип числа (типизированной ссылки внутрь контекста) пусть задаёт множество окружений \texttt{env}, из которых на данной позиции можно извлечь тип \texttt{ty}.
\begin{minted}{haskell}
    data Ref env ty where
      Here :: Ref (ty, env) ty
      There :: Ref env ty -> Ref (ty', env) ty
\end{minted}
Например, тип числа 1 утверждает, что с его помощью можно извлечь значение типа \texttt{ty} из контекста, в котором значение соответствующего типа находится на первой позиции (нумерация с нуля):
\begin{minted}{haskell}
    There Here :: Ref (ty', (ty, env)) ty
\end{minted}

Теперь мы можем закодировать типизированное безопасное обращение к контексту:
\begin{minted}{haskell}
    envLookup :: env -> Ref env ty -> ty
    envLookup env ref = case (ref, env) of
      (Here, (x, _)) -> x
      (There ref', (_, env')) -> envLookup env' ref'
\end{minted}

Например, \mintinline{haskell}|There (There Here)| позволяет извлечь строку из окружения выше.
Каждый \mintinline{haskell}|There| пропускает одну пару, а \mintinline{haskell}|Here| выбирает первый компонент текущей пары.

\subsubsection{Meta-circular интерпретация} \label{subsubsec:meta-circular-initial}

Крайне не хотелось бы для eDSL самостоятельно реализовывать связывания и функции первого класса.
Построим meta-circular интерпретатор (см.~\ref{subsubsec:edsl}), который будет переиспользовать функции первого класса мета-языка для реализации их в определяемом языке.

Термы теперь будут не только аннотированы результирующими типами, но и типами необходимых для интерпретации окружений, рассмотренных ранее~\ref{subsubsec:typed-env}.
Телу лямбды доступно окружение, дополненное её параметром.

\begin{minted}{haskell}
    data Term2 env ty where
      Var2 :: Ref env ty -> Term2 env ty
      App2 :: Term2 env (arg -> res) -> Term2 env arg -> Term2 env res
      Lam2 :: Term2 (arg, env) res -> Term2 env (arg -> res)
\end{minted}

Теперь абстракцию можем проинтерпретировать в функцию Haskell, а аппликацию --- в аппликацию:
\begin{minted}{haskell}
    eval2 :: Term2 env ty -> env -> ty
    eval2 term env = case term of
      Var2 ref -> env `envLookup` ref
      App2 f arg -> (eval2 f env) (eval2 arg env)
      Lam2 t -> \arg -> eval2 t (arg, env)
\end{minted}

Замыкания здесь не исчезли: их создаёт сам Haskell.
Лямбда в последней ветке захватывает \mintinline{haskell}|t| и \mintinline{haskell}|env|; при вызове она добавляет аргумент к сохранённому окружению.
Ссылки на переменные в синтаксисе пока остаются явными: их кодирует \mintinline{haskell}|Ref|.

\subsubsection{Синтаксис высшего порядка} \label{subsubsec:h-syntax}

Мы уже передали Haskell исполнение функций, но всё ещё вручную указываем, к какому связывателю относится каждое употребление переменной.
Передадим мета-языку и эту работу.
Для этого будем прямо в дереве синтаксиса хранить функции мета-языка~--- использовать \vocab{синтаксис высшего порядка (higher order abstract syntax)}\footnote{\url{https://en.wikipedia.org/wiki/Higher-order_abstract_syntax}}\footnote{\href{https://cstheory.stackexchange.com/questions/20071/what-is-higher-order-in-higher-order-abstract-syntax}{What is higher-order in higher-order abstract syntax?}}~\cite{pfenning1988higher}:
\begin{minted}{haskell}
    data Term3 ty where
      Val3 :: ty -> Term3 ty
      Plus :: Term3 Int -> Term3 Int -> Term3 Int
      App3 :: Term3 (arg -> res) -> Term3 arg -> Term3 res
      Lam3 :: (Term3 arg -> Term3 res) -> Term3 (arg -> res)

    example3 :: Term3 Int
    example3 = Lam3 (\x -> x `Plus` Val3 41) `App3` Val3 1
\end{minted}

В \mintinline{haskell}|example3| связь между параметром \mintinline{haskell}|x| и его употреблением задаёт лямбда Haskell.
Конструктор \mintinline{haskell}|Lam3| хранит функцию, строящую тело по представлению аргумента; при интерпретации мы передаём ей \mintinline{haskell}|Val3 arg|.

Интерпретация очень простая и абсолютно meta-circular:
\begin{minted}{haskell}
    eval3 :: Term3 ty -> ty
    eval3 term = case term of
      Val3 x -> x
      Plus l r -> eval3 l + eval3 r
      App3 f arg -> (eval3 f) (eval3 arg)
      Lam3 f -> \arg -> eval3 (f (Val3 arg))
\end{minted}
Результат \mintinline{haskell}|eval3 example3| равен \mintinline{haskell}|42|.

\subsubsection{Сериализация функций}

Хранение функций Haskell в синтаксисе удобно для исполнения, но затрудняет другие операции.
Функцию внутри \mintinline{haskell}|Lam3| нельзя разобрать паттерн-матчингом как обычное дерево; поэтому обход синтаксиса, сравнение и сериализация требуют дополнительных решений.

В этом разделе мы говорили о возможных реализациях функций первого класса, то есть функций, которые можно использовать так же гибко, как и данные.
Возникает закономерный вопрос: можем ли мы сериализовать функцию первого класса и послать исполняться на другую машину?

Замыкание состоит из кода и захваченного окружения.
Можно передать код в переносимом формате вместе с окружением, если принимающая сторона умеет его исполнять.
Но если нужный код уже есть на другом узле, достаточно передать его идентификатор и значения захваченных переменных.
Так устроена сериализация функций в Erlang: представление содержит сведения о модуле и функции, а также захваченные значения\footnote{\href{https://www.erlang.org/doc/apps/erts/erl_ext_dist.html\#new_fun_ext}{Формат сериализации функций Erlang.}}.

Например, используя дефункционализацию~(см.~\ref{subsubsec:defunctionalization}), мы можем сериализовать только объекты алгебраического типа, кодирующие функции.
Поскольку на другом узле кластера исполняется такой же код, мы там можем десериализовать объект и исполнить его с помощью \texttt{apply}.
Однако этот подход не очень поддерживает модульность (сложно один алгебраический тип разбить на много), а также \texttt{apply} каждый раз производит декодирование перед исполнением кода (чем, впрочем, можно пренебречь, учитывая работу с сетью).

В Haskell механизм \mintinline{haskell}|StaticPointers| позволяет получить переносимую ссылку на замкнутое выражение\footnote{\href{https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/static_pointers.html}{Документация GHC: Static pointers.}}.
Такая ссылка имеет ключ, по которому каждый процесс находит значение в своей статической таблице; адреса памяти у процессов могут различаться.
Согласованность ключей гарантируется для процессов, запущенных из одного бинарника.
На этом механизме построена библиотека \texttt{distributed-closure}\footnote{\url{https://hackage.haskell.org/package/distributed-closure}}.

Рассмотрим упрощённую учебную модель её идеи.
Замыкание представим деревом из статических ссылок, сериализованных данных и аппликаций:
\begin{minted}{haskell}
    import Data.Binary (encode, decode)
    import Data.ByteString.Lazy (ByteString)
    import GHC.StaticPtr (StaticPtr, deRefStaticPtr)

    data Closure a where
      Static :: StaticPtr a -> Closure a
      Encoded :: ByteString -> Closure ByteString
      Ap :: Closure (b -> c) -> Closure b -> Closure c

    unclosure :: Closure a -> a
    unclosure = \case
      Static ptr -> deRefStaticPtr ptr
      Encoded bytes -> bytes
      Ap f x -> unclosure f (unclosure x)
\end{minted}

Чтобы передать целое число, сохраним его байты и статическую ссылку на функцию декодирования:
\begin{minted}{haskell}
    decodeInt :: ByteString -> Int
    decodeInt = decode

    closureInt :: Int -> Closure Int
    closureInt n = Ap (Static (static decodeInt)) (Encoded (encode n))

    -- factorial :: Int -> Int определён на верхнем уровне
    remote :: Closure Int
    remote = Ap (Static (static factorial)) (closureInt 10)
\end{minted}
В сериализованном виде для \mintinline{haskell}|remote| нужны ключи статических ссылок на \mintinline{haskell}|factorial| и \mintinline{haskell}|decodeInt|, байты числа \mintinline{haskell}|10| и структура аппликаций.
На принимающем узле ссылки восстанавливаются через статическую таблицу, после чего \mintinline{haskell}|unclosure| исполняет построенное вычисление.
Так мы снова получаем явное представление кода и окружения, пригодное для передачи между процессами.

Подробнее можно прочитать в основополагающей статье про облачный Haskell~\cite{epstein2011towards}.
С практической точки зрения --- в книжке~\cite[глава 16]{marlow2011parallel}.

\subsection{Tagless final интерпретаторы} \label{subsec:tagless-final}

В разделе~\ref{subsubsec:edsl} мы сравнили явное синтаксическое дерево и непосредственное построение значения в выбранном домене.
Дерево позволяет выбирать интерпретацию позже, а функции, сразу вычисляющие результат, фиксируют её при написании программы.
Как писать программу через функции, сохраняя возможность выбирать её интерпретацию?

Для этого будем абстрагировать программу по операциям языка и типу их результатов.
Одни реализации операций будут вычислять значение, другие --- печатать программу или строить её синтаксическое дерево.
Так мы придём к финальному представлению: программа описывается через интерфейс операций, а конкретная интерпретация выбирается при использовании.

\subsubsection{Программа, абстрагированная по интерпретации} \label{subsubsec:shallow-embedding}

Как мы узнали ранее (\ref{subsec:all-folds}), индуктивную структуру данных можно представить через её свёртки.
И, более того, в итоге можно обойтись без единого конструктора данных (как в списке Чёрча, например): алгебра представляется набором функций, каждая из которых отвечает за сворачивание определённого конструктора.
\begin{minted}{haskell}
    Fix f ?$\iso$? forall a . (f a -> a) -> a
    List e ?$\iso$? forall a . (e -> a -> a) -> a -> a
\end{minted}

Таким образом, вместо того, чтобы конструировать дерево языка, а затем его интерпретировать (сворачивать), мы можем сразу сконструировать терм типа \mintinline{haskell}{?$\forall$?a . (f a -> a) -> a}.
Предоставив ему тип домена \texttt{a} и алгебру \texttt{f a -> a} (либо в виде пачки функций), мы немедленно получим элемент нужного домена.
Чтобы задать другую интерпретацию, нужно передать другой тип домена и алгебру:
\begin{minted}{haskell}
    example :: (Int -> a) -> (a -> a -> a) -> a
    example cnst plus = cnst 1 `plus` cnst 41

    ghci> example show (\l r -> l ++ " + " ++ r)
    "1 + 41"
\end{minted}

Если зафиксировать интерпретацию, то функции-аргументы можно реализовать статически и просто ссылаться на них в терме.
Таким образом, про объявление функций можно думать как про расширение некоторого встроенного предметного языка.
Общие рассуждения про shallow embeddings, свёртки и библиотеки можно почитать в~\cite{gibbons2013functional, gibbons2014folding}.
Сравните:

        Deep & Shallow \\

        Интерпретацию можно выбрать при обработке сохранённого синтаксиса & Интерпретация определяется реализацией используемых операций \\

\subsubsection{От явной алгебры к классу типов}

Соберём функции-аргументы в словарь, как в разделе~\ref{subsubsec:tc-dict}:
\begin{minted}{haskell}
    data ExprDict a = ExprDict
      { cnstD :: Int -> a
      , plusD :: a -> a -> a
      }

    exampleD :: ExprDict a -> a
    exampleD d = plusD d (cnstD d 1) (cnstD d 41)
\end{minted}
Класс типов позволит передавать такой словарь неявно.
Его методы зададут операции языка, а инстанс предоставит алгебру для выбранного домена.
Полиморфный терм будет описывать программу независимо от этой алгебры.
Подход называется \vocab{tagless final encoding}\footnote{\url{https://okmij.org/ftp/tagless-final/}}~\cite{carette2007finally, kiselyov2012typed}.
Для нашего языка он непосредственно продолжает кодирование через свёртки: вместо явных аргументов алгебры используется словарь класса типов.

Снова рассмотрим язык со сложением:
\begin{minted}{haskell}
    data Syntax = Const Int | Plus Syntax Syntax

    eval :: Syntax -> Int
    eval = \case
      Const x -> x
      Plus l r -> eval l + eval r
\end{minted}
Или через катаморфизм:
\begin{minted}{haskell}
    data ExprF rec = ConstF Int | PlusF rec rec deriving Functor

    eval :: Fix ExprF -> Int
    eval = cata \case
      ConstF x -> x
      PlusF l r -> l + r
\end{minted}
Соответствующее tagless final кодирование будет выглядеть следующим образом:
\begin{minted}{haskell}
    class Expr domain where
      cnst :: Int -> domain
      plus :: domain -> domain -> domain

    instance Expr Int where
      cnst x = x
      plus l r = l + r
\end{minted}

Теперь мы можем сконструировать обычный терм Haskell, задать домен, и машинерия классов типов подставит нужную алгебру самостоятельно:
\begin{minted}{haskell}
    example :: forall domain . Expr domain => domain
    example = cnst 1 `plus` cnst 41

    ghci> example @Int
    42
\end{minted}

Чтобы добавить ещё интерпретацию, реализуем инстанс для другого домена:
\begin{minted}{haskell}
    instance Expr String where
      cnst x = show x
      plus l r = l <> " + " <> r

    ghci> example :: String
    "1 + 41"
\end{minted}

Можно выбрать доменом и само синтаксическое дерево:
\begin{minted}{haskell}
    instance Expr Syntax where
      cnst = Const
      plus = Plus

    ghci> example :: Syntax
    Plus (Const 1) (Const 41)
\end{minted}
Поэтому final encoding не фиксирует shallow embedding: один и тот же терм можно непосредственно вычислить или интерпретировать в синтаксис для дальнейшей обработки.

\subsubsection{Typed tagless final interpreter}

Рассмотрим наш пример tagless initial encoding~\ref{subsubsec:typed-tagless-initial}:
\begin{minted}{haskell}
    data Expr ty where
      Const :: Int -> Expr Int
      IsZero :: Expr Int -> Expr Bool
      If :: forall ty . Expr Bool -> Expr ty -> Expr ty -> Expr ty

    eval :: Expr ty -> ty
    eval = \case
      Const x  -> x
      IsZero t -> eval t == 0
      If c t e -> if eval c then eval t else eval e
\end{minted}
Чтобы получить final encoding, параметризуем домен результирующим типом выражения:
\begin{minted}{haskell}
    class Expr (domain :: Type -> Type) where
      cnst :: Int -> domain Int
      isZero :: domain Int -> domain Bool
      if' :: forall ty . domain Bool -> domain ty -> domain ty -> domain ty

    instance Expr Identity where
      cnst x = Identity x
      isZero (Identity x) = Identity (x == 0)
      if' (Identity c) t e = if c then t else e
\end{minted}

Здесь два уровня выбора: \mintinline{haskell}|domain| задаёт интерпретацию, а аргумент \mintinline{haskell}|Int| или \mintinline{haskell}|Bool| --- тип выражения внутри языка.
Например, \mintinline{haskell}|Identity Int| представляет результат вычисления целочисленного выражения.
Программа остаётся полиморфной по интерпретации:
\begin{minted}{haskell}
    exampleTyped :: Expr domain => domain Int
    exampleTyped = if' (isZero (cnst 0)) (cnst 10) (cnst 20)

    ghci> runIdentity exampleTyped
    10
\end{minted}

\subsubsection{Восстановление композиционности семантики} \label{subsubsec:recover-compositionality}

Как преобразовывать программу, если вместо дерева с доступными для паттерн-матчинга конструкторами у нас есть полиморфный терм?
\vocab{Семантика} называется \vocab{композиционной}, если смысл составной конструкции определяется самой конструкцией и смыслами её непосредственных подконструкций (см.~\ref{subsubsec:semantics}).
Методы final-интерпретации получают именно такие результаты интерпретации подконструкций.

Некоторые определения преобразований используют больше информации: они заглядывают внутрь исходного синтаксиса аргумента.
Рассмотрим протаскивание отрицаний к литералам:
\begin{minted}{haskell}
    data Expr1 = Lit Int | Add Expr1 Expr1 | Neg Expr1

    transform1 :: Expr1 -> Expr1
    transform1 = \case
      Lit x -> Lit x
      Add l r -> Add (transform1 l) (transform1 r)
      Neg e -> case e of
        Lit x -> Lit (-x)
        Neg inner -> transform1 inner
        Add l r -> Add (transform1 (Neg l)) (transform1 (Neg r))
\end{minted}
Обработчик \mintinline{haskell}|Neg| разбирает конструктор своего аргумента.

Чтобы выразить преобразование через результаты обработки непосредственных подтермов, расширим домен: вместо одного дерева будем строить функцию от контекста знака к дереву~\cite{kiselyov2012typed}.
\mintinline{haskell}|CtxPos| означает, что результат нужен без дополнительного отрицания, а \mintinline{haskell}|CtxNeg| --- что его нужно отрицать.
\begin{minted}{haskell}
    data Ctx = CtxPos | CtxNeg
    flipCtx :: Ctx -> Ctx
    flipCtx = \case
      CtxPos -> CtxNeg
      CtxNeg -> CtxPos

    transform1' :: Expr1 -> (Ctx -> Expr1)
    transform1' expr = case expr of
      Lit x -> \case
        CtxNeg -> Lit (-x)
        CtxPos -> Lit x
      Neg e -> \ctx -> transform1' e (flipCtx ctx)
      Add l r -> \ctx -> Add (transform1' l ctx) (transform1' r ctx)
\end{minted}
Теперь обработчик \mintinline{haskell}|Neg| только меняет контекст, а обработчик \mintinline{haskell}|Add| передаёт его обеим подпрограммам.
Разбирать их синтаксис больше не нужно.

Для запуска выбираем положительный контекст:
\begin{minted}{haskell}
    original :: Expr1
    original = Neg (Add (Lit 1) (Neg (Lit 2)))

    ghci> transform1' original CtxPos
    Add (Lit (-1)) (Lit 2)
\end{minted}
Так выражение \texttt{-(1 + (-2))} превращается в \texttt{(-1) + 2}.
Это пример выбора более информативного домена для конкретного преобразования.

В final-версии можно абстрагироваться и от того, во что строится результат:
\begin{minted}{haskell}
    class Expr2 d where
      lit :: Int -> d
      add :: d -> d -> d
      neg :: d -> d

    instance Expr2 d => Expr2 (Ctx -> d) where
      lit x = \case
        CtxNeg -> lit (-x)
        CtxPos -> lit x
      neg e ctx = e (flipCtx ctx)
      add l r ctx = add (l ctx) (r ctx)
\end{minted}

Зададим две конечные интерпретации --- построение дерева и вычисление:
\begin{minted}{haskell}
    instance Expr2 Expr1 where
      lit = Lit
      add = Add
      neg = Neg

    instance Expr2 Int where
      lit = id
      add = (+)
      neg = negate

    program :: Expr2 d => d
    program = neg (add (lit 1) (neg (lit 2)))

    ghci> program :: Expr1
    Neg (Add (Lit 1) (Neg (Lit 2)))
    ghci> (program :: Ctx -> Expr1) CtxPos
    Add (Lit (-1)) (Lit 2)
    ghci> (program :: Ctx -> Int) CtxPos
    1
\end{minted}
Инстанс для \mintinline{haskell}|Ctx -> d| выполняет преобразование, а инстанс для \mintinline{haskell}|d| определяет, что делать с результатом.
Чтобы печатать преобразованное выражение, можно аналогично выбрать доменом \mintinline{haskell}|d| строковое представление.

\subsubsection{Встречаем старых друзей: \mintinline{haskell}{Applicative}, \mintinline{haskell}{Monad}}

Рассмотрим следующий язык в initial encoding с higher order abstract syntax (см.~\ref{subsubsec:meta-circular-initial}, ~\ref{subsubsec:h-syntax}).
Справа перепишем в tagless final, выбирая подходящие имена для кусков синтаксиса.

\begin{tabular}{p{8cm}p{8cm}}
    \begin{minted}[numberblanklines=true]{haskell}
        data Expr s ty where
          Val   :: ty -> Expr s ty
          App   :: Expr s (arg -> res)
                -> Expr s arg
                -> Expr s res


          LetIn :: Expr s ty
                -> (ty -> Expr s ty')
                -> Expr s ty'


          Get   :: Expr s s
          Put   :: s -> Expr s ()
    \end{minted}
    &
    \begin{minted}[numberblanklines=true]{haskell}
        class Applicative domain where
          pure  :: ty -> domain ty
          (<*>) :: domain (arg -> res)
                -> domain arg
                -> domain res

        class Monad domain where
          (>>=) :: domain ty
                -> (ty -> domain ty')
                -> domain ty'

        class MonadState s domain where
          get :: domain s
          put :: s -> domain ()
    \end{minted}
\end{tabular}
\vspace{1em}

Реализуем программу, которая изменяет состояние и возвращает его прежнее значение.
Назовём её \mintinline{haskell}|modifyOld|: стандартная \mintinline{haskell}|modify| возвращает \mintinline{haskell}|()|.
Справа программа полиморфна по интерпретации:

\begin{tabular}{p{8cm}p{8cm}}
    \begin{minted}[numberblanklines=true]{haskell}
        modifyOld
                  :: (s -> s) -> Expr s s
        modifyOld f =
          Get `LetIn` \x ->
          Put (f x) `LetIn` \() ->
          Val x
    \end{minted}
    &
    \begin{minted}[numberblanklines=true]{haskell}
        modifyOld :: MonadState s m
                  => (s -> s) -> m s
        modifyOld f =
          get >>= \x ->
          put (f x) >>= \() ->
          pure x
    \end{minted}
\end{tabular}
\vspace{1em}

И до боли знакомую интерпретацию:

\begin{tabular}{p{8cm}p{8cm}}
    \begin{minted}[numberblanklines=true]{haskell}
        eval
            :: Expr s a -> s -> (s, a)

        eval = \case

          Val x -> \s -> (s, x)
          App fs xs -> \s1 ->
            let (s2, f) = eval fs s1 in
            let (s3, x) = eval xs s2 in
            (s3, f x)


          LetIn comp k -> \s ->
            let (s', x) = eval comp s in
            eval (k x) s'


          Get -> \s -> (s, s)
          Put s -> \_ -> (s, ())
    \end{minted}
    &
    \begin{minted}[numberblanklines=true]{haskell}
        newtype State s a = State
          { runState :: s -> (s, a) }


        instance Applicative (State s) where
          pure x = State \s -> (s, x)
          fs <*> xs = State \s1 ->
            let (s2, f) = runState fs s1 in
            let (s3, x) = runState xs s2 in
            (s3, f x)

        instance Monad (State s) where
          comp >>= k = State \s ->
            let (s', x) = runState comp s in
            runState (k x) s'

        instance MonadState s (State s) where
          get = State \s -> (s, s)
          put s' = State \_ -> (s', ())
    \end{minted}
\end{tabular}
\vspace{1em}

Запустим обе версии программы с начальным состоянием \mintinline{haskell}|10|:
\begin{minted}{haskell}
    -- initial:
    ghci> eval (modifyOld (+1)) 10
    (11,10)
    -- final:
    ghci> runState (modifyOld (+1)) 10
    (11,10)
\end{minted}
Состояние стало \mintinline{haskell}|11|, а результат программы --- прежнее значение \mintinline{haskell}|10|.

Таким образом, \point{аппликативные функторы --- meta-circular язык с аппликацией}, а \point{монадический bind --- это фактически let-in в higher-order синтаксисе}.

Есть другая полезная интерпретация: если \mintinline{haskell}|m a| --- синтаксическое дерево со свободными переменными типа \mintinline{haskell}|a|, bind подставляет деревья вместо этих переменных, как в разделе~\ref{subsubsec:substitutions}.
Рассмотрим простой пример:
\begin{minted}{haskell}
    data Expr var = Var var | Empty | Append (Expr var) (Expr var)

    instance Applicative Expr where
      pure = Var
      (<*>) = Control.Monad.ap

    instance Monad Expr where
      (>>=) :: Expr var -> (var -> Expr var') -> Expr var'
      Var name   >>= subst = subst name
      Empty      >>= _     = Empty
      Append l r >>= subst = Append (l >>= subst) (r >>= subst)
\end{minted}

Здесь \mintinline{haskell}|pure| создаёт переменную, а bind заменяет каждое её вхождение результатом функции подстановки:
\begin{minted}{haskell}
    ghci> Append (Var "a") Empty >>= \x -> Append (Var x) (Var x)
    Append (Append (Var "a") (Var "a")) Empty
\end{minted}
В интерпретации с состоянием bind организует выполнение и передачу состояния, а в интерпретации синтаксиса --- подстановку.
Их объединяют интерфейс и законы монады.

Изначально использовать теоретико-категорное понятие монады\footnote{\url{https://ncatlab.org/nlab/show/monad+(in+computer+science)}} в $\lambda$-исчислении было предложено в~\cite{moggi1988computational}, чтобы удобнее записывать денотационную семантику\footnote{Часто сопутствующее монадам понятие эффекта мы рассмотрим далее~\ref{sec:effects}.}.
Это оказалось настолько удобно, что монады стали использовать повсеместно в функциональном программировании, чтобы расширять простые функциональные языки различными выразительными возможностями без изменения самих языков~\cite{wadler1990comprehending, wadler1992essence}.
Был сформулирован Moggi's principle:
\begin{center}
    <<Computations of type $\alpha$ correspond to values of type $f\ap\alpha$>>
\end{center}

Использовать аппликативные функторы предложили существенно позже, чтобы избежать именования промежуточных шагов вычислений, когда в этом нет необходимости~\cite{mcbride2008applicative}.
Таким образом, аппликативы дают встроенный язык выражений, а монады~--- язык стейтментов.

\subsection{Expression problem} \label{subsec:expression-problem}

\vocab{Expression problem} или \vocab{проблема выразительности} --- это задача расширения данных и операций над ними, получившая это название у Wadler'а в 1998 году\footnote{\url{https://homepages.inf.ed.ac.uk/wadler/papers/expression/expression.txt}}.
В применении к встроенным языкам хочется добавлять как новые синтаксические конструкции, так и новые интерпретации, сохраняя существующие определения и статическую типобезопасность.
Иначе говоря, расширения должны состоять из нового кода, а не требовать правок во всех ранее написанных компонентах.

Например, если синтаксис языка задан обычным алгебраическим типом данных, то добавить новую интерпретацию легко --- достаточно написать новую рекурсивную функцию.
Но добавление новой синтаксической конструкции требует расширить тип и дополнить все интерпретаторы обработкой нового случая:
\begin{minted}{haskell}
    data Expr
      = Const Int
      | Plus Expr Expr -- добавляем

    eval :: Expr -> Int
    eval = \case
      Const x -> x
      Plus l r -> eval l + eval r

    pretty :: Expr -> String
    pretty = \case
      Const x -> show x
      Plus l r -> pretty l ++ " + " ++ pretty r
\end{minted}

Если представить конструкции языка классами, реализующими общий интерфейс, получаем обратную ситуацию.
Добавить конструкцию можно новым классом, а новая интерпретация требует добавить метод в интерфейс и реализовать его в каждом классе:
\begin{minted}{kotlin}
    interface Lang {
        fun eval(): Int
        fun show(): String
    }
    class Const(val x: Int) : Lang {
        override fun eval() = x
        override fun show() = x.toString()
    }
    class Plus(val l: Lang, val r: Lang) : Lang {
        override fun eval() = l.eval() + r.eval()
        override fun show() = "${l.show()} + ${r.show()}"
    }
\end{minted}

Это представление через скрытое состояние и коалгебру, рассмотренное в главе «Всё через развёртку» (раздел~\ref{subsubsec:abstract-data-types}):
\begin{minted}{haskell}
    data LangF s = LangF Int String deriving Functor
    type Lang = Box LangF

    eval :: Lang -> Int
    eval lang = result
      where LangF result _ = step lang

    pretty :: Lang -> String
    pretty lang = text
      where LangF _ text = step lang

    cnst :: Int -> Lang
    cnst n = Box n \x -> LangF x (show x)

    plus :: Lang -> Lang -> Lang
    plus l r = Box (l, r) \(x, y) ->
      LangF (eval x + eval y)
            (pretty x ++ " + " ++ pretty y)

    program :: Lang
    program = plusLang (constLang 1) (constLang 41)
\end{minted}

Оказывается, можно организовать код так, чтобы расширять язык по обоим измерениям.
Как мы обсуждали ранее~(\ref{subsubsec:interpreters-tower}), программы часто представляют собой серию интерпретаторов.
Для борьбы со сложностью важно уметь описывать эти интерпретаторы модульно: задавать части языков независимо и собирать нужные языки по месту из готовых блоков.

С этим связана и задача \vocab{устойчивости денотаций (stable denotations)}: хотелось бы, чтобы добавление возможностей языка не заставляло переписывать смысл уже существующих конструкций\footnote{Связь expression problem, устойчивости денотаций и расширяемых интерпретаторов подробно обсуждается в \url{https://okmij.org/ftp/Computation/having-effect.html}.}.

\subsubsection{Копроизведение функторов} \label{subsubsec:functor-coprod}

Воспользуемся представлением данных как неподвижной точки функтора (см.~\ref{subsubsec:functor-fixpoint}).
В качестве модельного языка возьмём язык выражений со сложением\footnote{Для автоматического вывода \texttt{Functor} используем расширение \texttt{DeriveFunctor}.}:
\begin{minted}{haskell}
    data Basic rec = Const Int | Plus rec rec deriving Functor

    algBasic :: Basic Int -> Int
    algBasic = \case
      Const x -> x
      Plus l r -> l + r

    evalBasic :: Fix Basic -> Int
    evalBasic = cata algBasic
\end{minted}

Сумма (копроизведение) функторов формы даёт функтор формы, алгебру для которого можно собрать из двух алгебр с общим носителем \texttt{a}:
\begin{minted}{haskell}
    data (l :+: r) rec = L (l rec) | R (r rec) deriving Functor

    (\/) :: (l a -> a) -> (r a -> a) -> ((l :+: r) a -> a)
    phi \/ psi = \case
      L l -> phi l
      R r -> psi r
\end{minted}

Оператор \mintinline{haskell}|\/| выбирает обработчик по тому, из какого фрагмента языка пришёл узел.
Он ничего не знает о конкретных конструкциях и способе их интерпретации.

Расширим наш язык чтением числа из окружения.
Следуя рассмотренной ранее денотационной семантике~(\ref{subsubsec:semantics}), выберем функцию \mintinline{haskell}{Int -> Int} в качестве домена:
\begin{minted}{haskell}
    data Input rec = Input deriving Functor

    algBasic' :: Basic (Int -> Int) -> Int -> Int
    algBasic' = \case
      Const x -> \_env -> x
      Plus l r -> \env -> l env + r env

    algInput :: Input (Int -> Int) -> Int -> Int
    algInput Input = \env -> env
\end{minted}

Теперь синтаксис программы составляется из двух фрагментов, а её интерпретатор --- из двух алгебр:
\begin{minted}{haskell}
    program :: Fix (Basic :+: Input)
    program = In (L (Plus (In (L (Const 1))) (In (R Input))))

    f :: Int -> Int
    f = cata (algBasic' \/ algInput) program

    ghci> f 41
    42
\end{minted}

Добавим другую интерпретацию --- печать программы.
Для этого определим новые алгебры тех же фрагментов синтаксиса; определения функторов, программы и вычисляющих алгебр сохраняются:
\begin{minted}{haskell}
    prettyBasic :: Basic String -> String
    prettyBasic = \case
      Const x -> show x
      Plus l r -> l ++ " + " ++ r

    prettyInput :: Input String -> String
    prettyInput Input = "input"

    ghci> cata (prettyBasic \/ prettyInput) program
    "1 + input"
\end{minted}

Таким образом, фрагменты синтаксиса и их интерпретации можно определять отдельно и собирать по месту.
Но у композиции алгебр есть существенное условие: у них должен быть общий носитель.
Если бы мы добавляли умножение, его вычисляющая алгебра могла бы иметь носитель \texttt{Int}, и \texttt{algBasic} осталась бы прежней.
Но мы добавляем конструкцию \texttt{Input}, которая потребовала для реализации более сложной денотации \mintinline{haskell}|Int -> Int|.
Поэтому нам пришлось переписать \texttt{algBasic} в \texttt{algBasic'}.
К проблеме стабильных денотаций мы вернёмся в главе об эффектах~(\ref{sec:effects}).

\subsubsection{Произведение алгебр} \label{subsubsec:prod-algebras}

Свяжем предыдущую конструкцию с финальным представлением.
Обработать сумму можно, задав по обработчику для каждой её стороны:
\[
    \texttt{((f :+: g) a -> a)} \iso
    \texttt{(f a -> a, g a -> a)}.
\]
Таким образом, сумме фрагментов синтаксиса соответствует пара алгебр с общим носителем.
Именно в этом смысле здесь говорим о произведении алгебр: объединяем наборы операций над одним доменом.

В tagless final эти наборы операций зададим классами типов:
\begin{minted}{haskell}
    class Basic domain where
      cnst :: Int -> domain
      plus :: domain -> domain -> domain

    class Input domain where
      input :: domain
\end{minted}

Для вычисления, как и ранее, выберем домен \mintinline{haskell}{Int -> Int}\footnote{Для приведённых инстансов используем расширение \texttt{FlexibleInstances}.}:
\begin{minted}{haskell}
    instance Basic (Int -> Int) where
      cnst value = \_ -> value
      plus l r = \env -> l env + r env

    instance Input (Int -> Int) where
      input = \env -> env
\end{minted}

Программа запрашивает словари ровно тех фрагментов, которые использует.
Например, определение \texttt{one} требует только \texttt{Basic}, и его можно использовать в программе с более богатым набором конструкций:
\begin{minted}{haskell}
    one :: Basic domain => domain
    one = cnst 1

    example :: (Basic domain, Input domain) => domain
    example = one `plus` input

    ghci> example @(Int -> Int) 41
    42
\end{minted}

Контекст \mintinline{haskell}|(Basic domain, Input domain)| требует оба словаря --- пару наборов операций над общим доменом.
Это тот же принцип композиции, что и у \mintinline{haskell}|\/|: там мы явно объединяли обработчики суммы, здесь передаём программе оба словаря через ограничения классов типов.

Теперь добавим печать, выбрав отдельный тип домена:
\begin{minted}{haskell}
    instance Basic String where
      cnst value = show value
      plus l r = l ++ " + " ++ r

    instance Input String where
      input = "input"

    ghci> example @String
    "1 + input"
\end{minted}

Однако само финальное представление ещё не объясняет, как сохранять определения интерпретаций при изменении вычислительного контекста.
Домен \mintinline{haskell}|Int -> Int| уже учитывает окружение, поэтому переход от \texttt{algBasic} к \texttt{algBasic'} не возник явно.
Вопрос, как при добавлении окружения или других возможностей переиспользовать прежнюю интерпретацию арифметики, остаётся и для этого представления.
